## 3. 阅读顺序建议

1. **先读** `01` 开篇的"本文件的定位"块 → §1（背景与问题）→ §2.1~§2.6（用户与场景）；
2. **产品视角**：`01` §2.7~§2.12（画像、旅程、故事、故事地图、干系人、画布）；
3. **需求正文**：`01` §3.2 的功能需求总表（49 条，含优先级/验收标准/验证方式/现状）；
4. **看图**：先看 `01` 内嵌的 6 张（上下文、用例、旅程、时序、状态机），
   再看 [`04`](04-产品与需求图表.md)（画布、追溯、优先级、排期、风险）与
   [`05`](05-行为与数据图表.md)（时序、状态机、数据流、数据模型、部署）；
5. **关心"凭什么说能实现"**：`01` §1.4（假设依据）、§4.1（性能实测）、§5.3（当前验收结论）；
6. **关心"AI 用得规不规范"**：`02`（提示词与迭代、采纳/修改/否决）与 `03`（核实方式与未核实项）。

## 4. 关于"未完成的如实标注"

本包**不把"未实现"写成"已实现"**，也不把"设计"写成"现状"：

- 功能需求总表每条都有**现状符号**（✅ 已实现并有验证载体 / 🟡 部分实现或验证不全 / ⛔ 未开工 / ⏳ 口径未定）；
- 截至 2026-09-21，49 条功能需求中 **✅ 19 条、🟡 19 条、⛔ 11 条**（复算方式见 `01` §5.3，分布图见 `04` 的 F-4）；
- 安全部分（`SEC` 9 条）中，**只有 4 条**达到"已实现且有可执行验证载体"；
  威胁模型 13 条里**只有 1 条**达到"已缓解并验证"（分布图见 `04` 的 F-3）
  ⇒ **本包不含任何"安全已到位"的结论**。

## 5. 材料真实性约定

- `02-AI协作记录.md` 中，**【原文】**= 仓库中留存的逐字引用（开发日志中的引用段、决策记录中的批准原话）；
  **【整理】**= 依仓库记录归纳的表述，**不承诺逐字**；**【未留档】**= 当时未留下提示词原文。
  三者逐处标注；**凡无法由仓库材料支撑的"提示词原文"，一律不写**。
- `01` §2.7~§2.12 的**用户相关内容全部标注【假设·未经用户验证】**：
  本项目**未开展用户访谈、问卷或可用性测试** ⇒ 画像与旅程是**推导出的设计假设**，
  验证计划见 `01` §2.7.1。**不得**把它读作调研结论。
- `03-人工核实说明.md` 中，**核实方式与结果均给出可复核的载体**（文件路径、命令、报告）；
  无法核实的项**单列**（N-01~N-17）并说明原因，不并入"已验证"。
