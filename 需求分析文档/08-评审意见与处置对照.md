### (2.1) 🔴 云端实现的安全前提：它会碰到 `T-10`（**未缓解**）

> **这一节必须连读**：`Q-5` 裁决为"纳入本期"后，实现云端客户端**不是纯增量**——
> 它直接落在一条**未缓解威胁**上。先把代价摆清楚，再动手。

**三条仓库事实（已核，可复现）**：

| # | 事实 | 位置 |
| --- | --- | --- |
| F-1 | 本地 `ModelClient` 的**硬约束 1 是"只连回环地址"**：`host` 必须是 `127.0.0.1` / `::1` / `localhost`，其余一律拒绝；用标准库 `http.client`（同时避开 `urllib` 的 scheme 注入面 `B310`） | `src/agent_sec_perf/model/client.py` 模块 docstring 第 1 条 |
| F-2 | `ExecutionContext.network_allowed` **恒为 `False`**（`harness/loop.py:613` 硬编码）；契约明写"**出站白名单与云端客户端均未实现**"，且"`NETWORK_OUTBOUND` 已授予**不等于**可以出站——把它当'已可出站'是 **fail-open**，`T-10` 保持**未缓解**" | `docs/design/interfaces/harness.md:832`；`contracts/{sandbox,tools}.py` |
| F-3 | `T-10`（网络出站默认拒绝失效）当前状态 = **未缓解**，判定理由是"`network_allowed=False` 只是**标志位**，实际拦截出站的**机制不存在**" | 威胁模型 `execution-and-isolation.md` `T-10`；`README.md` §4.1 末段的适用澄清 |

**⇒ 因此：如果只加一个云端客户端而不加出站白名单，等于把 `T-10` 从"无载体"变成"能出网但无拦截"——
按 F-2 的口径这就是 fail-open，是**风险上升**而不是持平。**

**最小可行且 fail-secure 的做法（我的建议，待你确认范围）**：

| # | 要素 | 做法 |
| --- | --- | --- |
| 1 | **默认不出站** | 云端后端**默认关闭**；必须显式启用，且端点命中白名单才连接。**白名单默认空 = 拒绝** |
| 2 | **端点白名单** | 新增配置项（如 `LLM_API_BASE_URL`），命中白名单才允许连接；未命中 ⇒ 拒绝（不静默回退本地） |
| 3 | **凭据只走环境变量** | API Key 只从环境变量读取，**不得**进日志、不得进审计（走既有 `sanitize_for_display` 脱敏管线） |
| 4 | **复用本地 client 的三条硬约束** | 超时必须真正生效（`None`/非正数拒绝）、响应体必须有上限、错误语义沿用 `ModelUnavailableError` / `ModelProtocolError` ⇒ 上层**无差别调用**的验收对象不变 |
| 5 | **依赖零新增** | `urllib3>=2.8` 已在依赖中（`ADR-0015` §5.2 的 `D3`），注释写明用途即"云端模型薄客户端" |

**两件事已裁决**（都属**公开契约 / 安全面**）：

- ① ✅ **同步实现出站白名单**（否则按 F-2 就是 fail-open）。若落地后要升 `T-10`，
  **状态升降必须由所有者或架构师裁决，不由实现者自证**。

**为什么是"目的地白名单"，以及它不解决什么（易被误解，写清）**：

- 用云端模型**必然**把 prompt（可能含本地代码 / 文件内容）交给所选 API——这是**用户显式选择**的代价，
  **白名单不解决数据出境本身**（远端要能解析，本地加密没有意义）。
- 白名单管的是"**出境到哪一个目的地**"，防两类事：
  ① **SSRF / 端点被偷换**——`base_url` 若来自不可信来源（项目级 `.lowspec.toml` 按 `01` §3.5 是**不可信输入**），
  可被改指向内网或云元数据服务（如 `169.254.169.254`，能取到 IAM 凭据）；
  ② **注入驱动的外传**——间接注入让 agent 把数据发到攻击者的服务器。
- 它**不是网关**、不做流量深度检测；也不引入 nginx 之类的额外进程。
  ⇒ **不可用 nginx 替代**：本项目是**端侧单机 CLI**（`W-6` 云端服务与账号体系为范围外），
  nginx 是进程外网络层组件，按端口/路径管、**管不到"哪个组件想出站"**，
  且引入它等于新增一个运维面与运行期依赖，与"端侧、受限资源、最小依赖"冲突。
  本项目的既有同类机制就是本地 client 的"**只连回环地址**"（`model/client.py` 硬约束 1）——
  出站白名单是把它从"只许回环"扩展到"只许白名单内的外部端点"。

**④ 的技术考量（为什么"同形"是个真问题）**：

- **审计是"证据面"**。人工确认通路（gate）会**先写审计再返回**，因此"审计写入失败"会在 **gate 内部**抛出；
  `harness/loop.py::_request_approval` 用 `except Exception` 一把抓，把它与"gate 自身故障"
  **收敛成同一条** `ERROR(INTERNAL)` + `TASK_FINISHED(FAILED)`，文案为"人工确认通路故障"。
- 这两件事**性质完全不同**：**审计失败 = 证据面损坏**（任务可能其实成功了，但我们没有留痕）；
  **审批通路故障 = 权限输入面不可用**（确实该终止）。
  报成同一条 ⇒ 运维会去查任务逻辑，**不会发现审计已经不可信**——
  与 `Q-2`（`ERROR` vs `DENY`）、`P-4`（`invalid_arguments` 混淆两类原因）**同一族**。
- **经 CLI 时已有旁路补救**：`cli/app.py` 的 `_AuditRecorder` 记住"发生过审计写入失败"，退出码归 `4`。
  ⇒ **不经 CLI 的消费者**（直接调 `Session.run()`）**没有这条旁路**，是缺口所在。

| 候选 | 做法 | 结论 |
| --- | --- | --- |
| **(A)** `AuditWriteError` + `__cause__`，`loop` 在 `except Exception` **之前** `except AuditWriteError: raise` | 异常真的冒泡出 `run()` | ✅ **推荐**：唯一同时满足"向 §2.4 收敛（必须冒泡）"与"不经 CLI 也可判定"。代价：需先把 §2.4 的"冒泡"措辞写死（是否允许包装后冒泡）；事件流从"响亮终止"变为"异常逃逸"，属**可见行为变化**，须写进契约 |
| **(B)** 不动类型，只收窄 `except` | — | ❌ **不可实现**：`sink.emit` 在 gate **内部**，从循环侧看是同一个异常对象，无类型/字段可区分 |
| **(C)** 事件上加判别位（如 `SessionErrorKind.AUDIT_WRITE_FAILED`） | 把审计失败转成一条业务事件 | ❌ **与 §2.4 直接冲突**：把"证据面故障"伪装成"任务失败"；且 `AUDIT_FAILED` 是契约 §2.1 **已被否决**的 kind |
| **(D)** 维持现状 + 只补文档注 | — | ⚠️ 成本最低，但**缺口不闭合**：不经 CLI 的消费者仍不可判定 |
