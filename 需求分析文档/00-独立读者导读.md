## 1. 这个东西叫什么、是干什么的

| 问题 | 回答 |
| --- | --- |
| **产品名** | `lowspec`（包名 `agent-sec-perf`）——一个**命令行**客户端，不是网站、不是 App |
| **一句话定位** | 在**受限设备**（无 GPU、无 KVM、内存小、甚至断网）上，让**能力受限的小模型**既能"干活"（调用工具、多步编排），又能**被管住**（权限、审批、审计、资源上限） |
| **为什么需要** | 两端是断开的：一端是"能跑模型但不能干活"的本地推理工具；另一端是"能干活但假设你有个强模型"的云端 agent。中间缺一层 |
| **两个子问题** | **P-A 能力探索**（小模型的能力边界在哪、怎么探测、怎么按边界适配）；**P-B 综合治理**（怎么用**系统手段**把模型行为收在边界内——**不是指望模型不犯错**） |
| **关键立场** | 安全目标不是"让模型不犯错"，而是 ① **不让错误造成不可逆伤害**；② **超出能力边界时主动停下** |

## 2. 必须知道的 8 个内部概念（否则读不懂引用）

| 概念 | 一句话 | 为什么它在需求里反复出现 |
| --- | --- | --- |
| **Harness** | 包裹模型的那层软件：编排循环、工具、上下文、状态、错误处理、护栏 | 项目的自研重心就在这里 |
| **能力档位** | 对**模型能力**的粗略分级（决定给多少工具、提示多复杂） | 与硬件档位是**两个独立轴**，不可互推 |
| **硬件档位 S/M/L** | 对**硬件预算**（内存/核数）的分级（2B / 4B / 8B） | 决定了"能承受哪个模型" |
| **领域包（Domain Pack）** | 可插拔的领域配置（提示、工具集、示例、策略、输出规范）；**声明式、不含代码** | 是"不同场景给不同能力"的载体 |
| **default-deny（默认拒绝）** | 未显式授予的权限一律拒绝；配置只能**收窄**权限，不能放宽 | 全部 `REQ-SEC-*` 的地基 |
| **fail-secure** | 失败时朝"拒绝"收敛——判不出、算不出、写不出 ⇒ **不放行** | `01` §3.4 的 19 条故障模式里 18 条是这个方向 |
| **可回放审计** | 每个事件都能由**落盘文件**独立还原 | `REQ-SEC-06`；也是本项目**唯一**升为"已缓解并验证"的那条所依赖的东西 |
| **变异探针** | 故意把被测机制破坏掉，确认用例**会红**——证明断言不是"恒过" | 本项目所有安全断言的入场券 |

## 3. 缩写与编号体系（看到就知道往哪找）

| 记号 | 含义 | 落点 |
| --- | --- | --- |
| `REQ-<模块>-<序号>` | 需求编号。`模块` ∈ `MODEL`/`HARNESS`/`SEC`/`PERF`/`TOOL`/`UX`/`OBS`/`PLAT`/`OPS` | `01` §3.2（49 条）；与项目 `docs/requirements/srs.md` 逐条对应 |
| `A-1`~`A-6` | **关键假设**（每条带依据、验证方式、当前状态） | `01` §1.4 |
| `F-1`~`F-19` | **故障模式**（触发条件 / 系统行为 / fail-secure 方向 / 验证载体） | `01` §3.4 |
| `T-01`~`T-13` | **威胁条目**（STRIDE + 智能体特有问题） | 项目 `docs/design/threat-model/`；本包 `06` §4 摘录其分布 |
| `ADR-NNNN` | **架构决策记录**。编号**只增不改**，一经接受正文不得修改 | 项目 `docs/adr/`（本包引用到 `ADR-0021`） |
| `P-n` / `Q-n` / `S-n` | 待裁决的**提案** / **问题** / **建议**。**"建议 ≠ 结论"** | `01` §7.2、§9；裁决权在所有者 |
| `V-n` | 两处不同的东西：`01` §5.2 是**验收判定规则**；`03` §2 是**核实结论** | 见各处标题 |
| `N-01`~ | **未核实项**（不得并入"已验证"） | `03` §3 |
| `C-01`~ | 本包**自身的核实清单** | `03` §4 |
| `W-1`~`W-11` | **本期范围外**（刻意不做） | `01` §6.2 |

> ⚠️ **一条易混淆的纪律**：**"范围外 ≠ 未实现"**。`W-*` 是刻意不做；`REQ` 里标 ⛔ 的是**计划内但尚未开工**。

## 4. 现状符号怎么读

| 符号 | 含义 |
| --- | --- |
| ✅ | 已实现**且**有可执行的验证载体（用例 / 机器检查 / 实测报告） |
| 🟡 | 已实现或部分实现，但验证不全或标准未全部满足 |
| ⛔ | 未开工（无载体）——**计划内**，不是"做不了" |
| ⏳ | 口径未定 ⇒ **无法判定**（不是"慢一点"） |
| 【待核】 | 声明写了但**尚未核实**，按规定不计入"通过" |
| 【待所有者确认】 | 属人的决策，**未经确认不作为结论** |

**一句话记住本包的诚实口径**：
**"机制已实现" ≠ "威胁已缓解"**；**"未跑"必须写"未跑"**；**"可用性问题"不是"安全缺陷"**。

## 6. 三条最重要的"别误读"

1. **别把"已发布 0.2.0"读成"做完了"**：版本号只表达**到达了哪个里程碑**，
   不由提交历史推导（`ADR-0019`）。49 条功能需求里 ✅ 只有 19 条。
2. **别把威胁模型的"1 条已缓解并验证"读成"安全已到位"**：它是**单条目、单调用面**的结论
   （会话内工具层的路径穿越）。未缓解仍有 2 条（`T-04` 提示注入、`T-10` 出站默认拒绝失效）。
3. **别把用户画像/旅程/故事读成"调研结论"**：本项目**未开展任何用户调研**，
   全部是**推导出的设计假设**，`01` §2.7 起逐处标注【假设·未经用户验证】。
