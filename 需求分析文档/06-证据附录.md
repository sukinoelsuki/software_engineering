## 0. 证据的分级（先说清楚每一条算什么）

不是所有证据强度相同。本附录对每条证据标**级别**，读者按级别决定信多少：

| 级别 | 含义 | 包外读者能做什么 |
| --- | --- | --- |
| **E-1 可一行复跑** | 给出命令，任何人拿到仓库即可复现同一输出 | 自己跑，完全独立复核 |

## 2. 假设 A-2：受限容器内的命名空间沙箱 —— **已证伪**（含失效方式）

| 项 | 内容 |
| --- | --- |
| 级别 | **E-2**（探针与原始输出在 ADR 内逐行收录） |
| 依据文件 | `docs/adr/0006-sandbox-execution-degradation.md` |
| 它改变了什么 | 直接改写 `REQ-SEC-05` 的验收标准（`01` §1.4 / §8.2） |

**原文摘录**（`docs/adr/0006-sandbox-execution-degradation.md`）：

```text
原定的沙箱路线是用户态命名空间隔离：主方案 bubblewrap，备选 firejail   （:21）
该假设不成立，且失败方式比预期更危险——其中一个方案是静默失效（fail-open）。  （:27）

| firejail 网络隔离 | `firejail --quiet --noprofile --net=none curl https://example.com`
  | `HTTP 200`（网络未被阻断） | ❌ 静默失效 |                                    （:93）
| firejail 诊断输出 | 去掉 `--quiet` 重跑
  | `Warning: an existing sandbox was detected. /bin/sh will run
     without any additional sandboxing features` | ❌ 根因确认 |                （:94）

关键教训（安全）：firejail 的失败方式是 fail-open ——                        （:105）
```

**为什么这条重要（读者最该带走的一点）**：
它不是"某个工具不好用"，而是**"以退出码判定隔离是否生效"这种判据本身会骗人**——
`firejail` 退出码 `0`、输出正常，但**网络根本没被隔离**。
⇒ `REQ-SEC-05` 因此从"用命名空间隔离"改写为"**L1/L2 分层 + 主动探针 + fail-secure 降级**"。

## 5. 门禁与安全层计数

| 项 | 内容 |
| --- | --- |
| 级别 | **E-1**（一行可复跑） |
| 复跑命令 | `make check` / `make test-security` |

**本包提交前的实测输出（复跑即得，数字带时间点）**：

```text
$ make check                                    （时间点：2026-09-28 复跑）
  ...
  990 passed, 1 skipped in 10.91s
  uv run bandit -q -r src                        （无告警）
  detect private key ......................... Passed
  No known vulnerabilities found                 （pip-audit）

$ make test-security                            （时间点：2026-09-28 复跑）
  96 passed, 905 deselected in 2.62s
```

**⚠️ 门禁计数随时间点变化（三条必须知道的口径）**：

1. **957 / 955 / 954 不是矛盾，是时间点不同**：
   `0.2.0` 落定**前**为 `955 passed`；落定**后**台账最高一级即当前版本，一致性用例进入
   **预期休眠** ⇒ `954 passed / 1 skipped`；随后 `P-3` 落地（`758bad7`）新增 **2 条**行为级用例、
   CI 合并提交豁免修复（`27f0282`）新增 **1 条** ⇒ 当时为 **`957 passed / 1 skipped`**。
   那个 skip **不是缺陷**（`docs/devlog/0020` §3.6 有逐字说明）。
   ⇒ **本包的门禁计数是一组随时间点的数字，不是固定值**；引用时**必须带时间点**。
2. **990 的来源（相对 957 的定因，可复算）**：`957` 采集时点为 **2026-09-22**（提交 `27d32a1`）；
   `990` 采集时点为 **2026-09-28**。二者相差 **33** 条，**逐笔定因如下**（复算命令与结论）：
   - 复算命令：
     ```bash
     # 在同一 venv 下分别收集两份用例清单并取差集
     VIRTUAL_ENV=/workspace/.venv /workspace/.venv/bin/python -m pytest --collect-only -q   # HEAD（990 版）
     git worktree add /tmp/wt957 27d32a1    # 957 那一版
     VIRTUAL_ENV=/workspace/.venv /workspace/.venv/bin/python -m pytest --collect-only -q   # 在 /tmp/wt957 内
     # 差集：HEAD 收集 1001 实例 / 957 版收集 968 实例 ⇒ 净差 33（= 净增 34 − 净减 1）
     ```
   - **净增 34 个用例实例**（按函数聚合）：`tests/unit/test_apply_ide_settings.py` **22 条**
     （`ec8791d` / `62eab5f`，Agent 命令闸门与设置源拆分，其中
     `test_guard_failures_detects_broken_configuration` 参数化展开 **4** 个实例）
     ＋ `tests/unit/test_bench_store.py` **3 条**（`60d6b0e`，轮次目录按轮次 id 命名）
     ＋ `tests/unit/test_cnb_config.py` **9 条**（`f65d2be` / `74233e1` / `3cf05c7` / `0b3085f` /
     `01c5ac9` / `a222baa`，流水线与发布脚本的机器检查换靶）。
   - **净减 1 个用例实例**：`tests/unit/test_cnb_config.py::test_bench_crontab_keys_are_declared`
     （停用 crontab 跑测时随之移除，`0b3085f`）。
   - ⇒ **34 − 1 = 33**，与 `990 − 957 = 33` 相符。
   - ⚠️ **口径提醒**：`make check` 报的 `990 passed` 是**选中后的执行结果**，
     而 `--collect-only` 报的 `1001` 是**收集数**（两者不相等：另有 marker 过滤/去抖，
     `-m security` 之外的部分不计入本次执行口径）；本附录只断言**差集构成 = 33** 这一可比事实。
3. **安全层零用例视为失败**：`make test-security` 的 `96` 是**门禁刻意设计**的 fail-secure 约束
   ——安全层若一条都没收集到，判失败而不是判通过。
4. **安全层的 deselected 数会随用例增长**（`869 → 871 → 905`）：它只是"本次未选中"的计数，
   **不是**通过/失败，**也不**表示用例被删。

> **独立复核**（`E-2`）：`957`/`96` 这两个数字由 2026-09-21 的**独立复核报告**在同宿主各自复跑得到
> `955 passed / 8.29s` 与 `96 passed / 1.25s`（`docs/research/2026-09-21-handbook-reproducibility-review.md:88,100,313-314`），
> **通过数一致**，墙钟差属环境噪声。
