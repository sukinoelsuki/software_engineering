## 2. 行为层

### 2.1 C-3 越权调用被拒的时序

- **用途**：说明"**拒绝发生在执行之前**"，且三类拒绝原因**可分**。
- **读者**：实现者、验证者（写对抗性用例时按此图逐分支覆盖）。
- **维护时点**：判定点或原因短码变化时。

```mermaid
sequenceDiagram
    autonumber
    participant H as 编排循环
    participant P as 策略引擎
    participant T as 工具
    participant A as 审计落点

    Note over H: 已解析出工具调用，尚未执行
    H->>H: 参数校验
    alt 参数非法
        H->>A: 记录拒绝，原因等于参数非法
    else 参数通过
        H->>P: 请求策略判定
        alt 工具名不存在或已被裁剪
            H->>A: 记录拒绝，原因等于未知工具或未暴露
            Note over A: 该分支不产生策略判定事件
        else 工具存在且已暴露
            P->>P: 求值能力与风险
            alt 未授予能力
                P-->>H: 拒绝
                H->>A: 记录拒绝，原因等于策略拒绝，并记策略判定
            else 允许但需确认
                P-->>H: 需人工确认
                alt 无确认通路
                    H->>A: 记录拒绝，原因等于审批拒绝
                else 用户批准
                    H->>T: 执行
                    T->>A: 记录执行结果
                end
            else 允许且无需确认
                H->>T: 执行
                T->>A: 记录执行结果
            end
        end
    end
    Note over T: 被拒绝的路径上，工具方法从未被调用
```

### 2.2 C-4 高危操作审批的时序

- **用途**：固定"三种选择 + 风险说明来自策略引擎（不是模型自述）"以及"无通路即拒绝"。
- **读者**：实现者、UI/提示文案作者。
- **维护时点**：审批交互或确认通路变化时。

```mermaid
sequenceDiagram
    autonumber
    actor U as 用户
    participant CLI as 命令行入口
    participant H as 编排循环
    participant P as 策略引擎
    participant T as 工具
    participant A as 审计落点

    H->>P: 请求策略判定
    P-->>H: 允许但需确认，附风险等级与理由
    alt 交互形态，存在确认通路
        H->>CLI: 请求确认，附风险说明
        CLI->>U: 展示风险与三个选项
        alt 用户选本次允许
            U-->>CLI: 本次允许
            CLI->>A: 记录审批决策
            CLI-->>H: 批准
            H->>T: 执行
            T->>A: 记录执行结果
        else 用户选总是允许
            U-->>CLI: 总是允许
            CLI->>A: 记录审批决策与范围
            CLI-->>H: 批准
            H->>T: 执行
        else 用户拒绝
            U-->>CLI: 拒绝
            CLI->>A: 记录审批决策，原因等于审批拒绝
        end
    else 非交互形态，无确认通路
        Note over H: 契约规定，无通路即拒绝，不下调默认风险
        H->>A: 记录拒绝，原因等于审批拒绝
    end
```

### 2.3 C-5 审计写入失败的路径（含**已登记的缺口**）

- **用途**：把"证据面故障"的处置画清楚，并**显式标出当前未闭合的那一处**。
- **读者**：实现者、评审者（这条是已登记待裁的契约缺口）。
- **维护时点**：该缺口的处置落定后**必须回头看这张图**。

```mermaid
sequenceDiagram
    autonumber
    participant H as 编排循环
    participant G as 确认门
    participant S as 审计写入
    participant CLI as 命令行入口

    H->>G: 请求确认
    G->>S: 写入审批事件
    alt 写入成功
        S-->>G: 返回
        G-->>H: 审批结果
    else 写入失败
        S--xG: 抛出错误
        Note over G: 契约要求写入失败必须冒泡
        G--xH: 向上抛出
        alt 当前实现，已知边界
            H->>H: 统一收敛为内部错误并终止任务
            H-->>CLI: 任务失败
            Note over H,CLI: 缺口：审计失败与确认通路自身故障<br/>在类型与文本上不可分，<br/>不经命令行的消费者会读成任务失败
        else 目标形态，待裁决
            Note over H: 让可识别的审计异常直接冒泡出会话
            H-->>CLI: 审计写入失败
            Note over CLI: 命令行侧据此给出审计失败退出码
        end
    end
```

> ⚠️ **本图刻意画出"当前实现"与"目标形态"两条**。在裁决落定前，
> **不得**按目标形态表述，也不得声称该缺口已闭合（出处见 `01` §3.4 的 F-10 与 §7.2-④）。

### 2.4 C-6 会话生命周期状态机

- **用途**：把**退出码**与**状态**一一对应，防止"失败"与"步数用尽"被混为一谈。
- **读者**：集成者、脚本作者、实现者。
- **维护时点**：退出码或终止语义变化时。

```mermaid
stateDiagram-v2
    direction LR
    [*] --> 装配中
    装配中 --> 装配失败: 配置非法或模型不可用
    装配中 --> 运行中: 装配成功
    运行中 --> 运行中: 工具调用与回喂观察
    运行中 --> 已完成: 任务达成
    运行中 --> 步数用尽: 达到步数上限
    运行中 --> 任务失败: 重试耗尽或不可恢复错误
    运行中 --> 审计失败: 审计写入失败冒泡
    装配失败 --> [*]: 退出码 3
    任务失败 --> [*]: 退出码 1
    步数用尽 --> [*]: 退出码 2
    审计失败 --> [*]: 退出码 4
    已完成 --> [*]: 退出码 0
```

> **读法**：**步数用尽（2）不是失败**——它是"按预算正常停下"；
> 把它与"任务失败（1）"合并会让自动化脚本无法区分"该加预算"与"该排查"。

### 2.5 C-7 端到端业务流程图（泳道近似）

- **用途**：一眼看清"用户 → 系统 → 策略 → 工具 → 审计"的完整链路与责任边界。
- **读者**：评审者、新接入的人。
- **维护时点**：主流程变化时。

> Mermaid 无原生泳道图，此处用**子图分道**近似表达。

```mermaid
        H1["组装消息并调用模型"]

    subgraph L4["策略引擎"]
```

### 3.2 D-2 数据流图 Level 1（配置与授权的分解）

- **用途**：把最关键的一组数据流——**"谁能收窄什么"**——拆开画清楚。
- **读者**：实现者（写配置与权限代码时）、验证者。
- **维护时点**：新增配置项或权限来源时。

```mermaid
flowchart TB
    U["用户"] -->|"命令行参数"| PAR(["参数解析"])
    CFG1["项目级配置<br/>随仓库走，视为不可信"] -->|"能力授予与审计落点"| CFG(["配置加载<br/>与校验"])
    CFG2["用户级配置"] -->|"补充设置"| CFG
    PAR --> CFG
    CFG -->|"非法即拒绝启动"| FAIL(["拒绝启动<br/>退出码 3"])
    CFG -->|"合法配置"| AUTH(["授权装配"])
    PACK["领域包声明"] -->|"工具与能力白名单"| AUTH
    AUTH -->|"默认授予为空集"| CAP[("会话能力集<br/>配置只能收窄，不能扩张")]
    CAP --> POL(["策略判定"])
    CFG -->|"审计落点"| W(["落点白名单校验"])
    W -->|"越界即拒绝"| FAIL
    W -->|"通过"| AUD[("审计落点<br/>常量根")]
    POL -->|"放行"| EXEC(["受限执行"])
    EXEC -->|"结果"| BACK(["回喂观察"])
```

> **读法（本图最关键的一条）**：`配置只能收窄，不能扩张` ——
> 项目级配置**随仓库走**，属不可信输入；因此它**只能从"已授予集合"里减**，
> 不能凭空增加权限。这条决定了"伪造一份配置文件"不构成提权路径。

### 3.3 D-3 事件与审计数据模型

- **用途**：说明会话、事件、审计记录三者的关系与关键字段。

```mermaid
    }

    }
    TOOL_CALL {
        string call_id PK
        string tool_name
        string outcome
        string audit_id
    }
    POLICY_DECISION {
        string call_id PK

        bool requires_confirmation
        string risk_level
    }
    APPROVAL {

        string choice
        string risk_reason
    }
```

> **两条契约级约束（图中看不见但必须写清）**：
> ① **`denied_reason` 是定长闭集短码**（不含不可信内容）——它保证审计可被机器分类；
> ② **`outcome` 区分"未执行"与"执行失败"**——否则"拒绝了"和"跑了但报错"在审计里同形。

## 4. 结构与部署层

### 4.1 E-1 分层与依赖方向

- **读者**：实现者（写代码前必读）。
- **维护时点**：分层变化时（**属架构变更，须先有决策记录**）。

> ⚠️ **本图是简化视图**：层名与依赖白名单的**权威源在项目架构文档与分层机器检查**，
> 本图只用于本交付包的阅读，**不得**据本图改代码或判违规。

```mermaid
flowchart TB
    subgraph V["纵向层（依赖方向自上而下）"]

        FND["基础设施层<br/>错误 路径 进程 配置 日志"]

    end

    CTR["契约层<br/>零行为：纯类型与协议"]

    H --> CAP
    CAP --> FND

    CAP -.-> SEC

```

> **一条硬约束（图上画不出，但必须记住）**：**基础设施层不得反向依赖可观测层**。
> 这条不是风格偏好，而是**会被机器检查判红**的规则——它曾拦下过一个"让最底层直接写审计"的设计。

### 4.2 E-3 部署图

- **维护时点**：部署形态变化时。
