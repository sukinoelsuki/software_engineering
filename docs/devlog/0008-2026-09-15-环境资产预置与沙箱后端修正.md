## 1. 本阶段目标

承接 0007 遗留的待办，并响应项目所有者提出的新要求：

1. **预置环境资产**：把两个端侧模型与开源 Harness 参考资料随**镜像**固化
   （⛔ **不是**在当前环境里部署——当前环境会被销毁，装在这里等于白装）；
2. 核查"开发环境本身即容器、隔离由宿主机提供"这一点此前**是否有记录**；
3. 回答：**测试环境应如何设计**、开发与测试**是否要隔离**、
   如何在使用极端测试的同时**不丢失成果**、以及如何保持工作连贯。

## 2. 关键决策与理由

### 2.1 资产预置采用「清单 + 脚本」，而不是把命令直接写进 Dockerfile

| 方案 | 取舍 |
| --- | --- |
| 直接在 Dockerfile 里写 `curl` / `git clone` | ❌ 无法在**不重建镜像**的情况下验证对错——而本环境恰好无法内省镜像构建过程 |
| **清单文件 + `fetch-assets.sh`** | ✅ 采纳：脚本可在当前环境**直接跑通**，四条路径全部实测；增删资产只改数据不改逻辑 |
| 把资产下载放在开发容器里 | ❌ 明确否决：环境销毁即丢失，达不到"随 Cache 制品复用"的目的 |

配套改动：三个新文件加入 [`.cnb.yml`](../../.cnb.yml) 的 `build.by`
（CNB 硬性要求，漏了直接构建失败——这个坑 0006 已经踩过一次）。

### 2.2 资产一律放在 `/workspace` 之外

| 资产 | 镜像内位置 | 理由 |
| --- | --- | --- |
| 两个端侧模型（约 5.2 GB） | `/opt/models` | GB 级二进制不得进版本管理；工作区可能被重克隆，模型不应随之丢失 |
| 8 个开源 Harness 仓库（447 MB） | `/opt/references/harness` | 只读参考资料，不参与构建与运行 |

### 2.3 沙箱可用性结论必须**按机制类别**修正（→ ADR-0007）

0007 判定"L2 命名空间档不可用"，**该判定不完整**：实测发现开发环境内
**docker 完全可用**（CNB 的 `services: [docker]`），并提供真实的文件系统与网络隔离。
因此把隔离能力从"按工具"重新划分为**按机制类别**（详见 ADR-0007）：

| 机制类别 | 有效性 | 承担者 |
| --- | --- | --- |
| 命名空间 / mount 类 | ✅ 有效（经 daemon 创建，daemon 不受本容器 seccomp 限制） | `ContainerBackend`（L2-C） |
| cgroup 类（`--memory` / `--pids-limit`） | ❌ **静默失效** | 弃用，改由 setrlimit 承担 |
| setrlimit 类（`RLIMIT_AS` / `FSIZE` / `nproc`） | ✅ 有效 | L1 与 L2-C 的资源维度 |

### 2.4 测试环境：隔离**执行场所**，不隔离**代码**（→ ADR-0008）

回答项目所有者的三个顾虑：

| 顾虑 | 结论 |
| --- | --- |
| 极端测试会不会毁掉开发环境、丢掉成果？ | **用内核解决，不用纪律解决**：T2 载体把工作区**只读**挂载，`rm -rf /work/README.md` 被拒（已实测）。破坏性测试**物理上改不了源码** |
| 另拉容器会不会导致反馈困难、两容器隔开？ | **不会**——容器与开发环境**共享同一份工作区**（bind mount），结果直接落回同一仓库 |
| 是否要"一边开发一边测试"？ | 是。分层按**影响范围**而非测试类型划分：日常 T0/T1 就在开发容器内，只有 T2/T3 才离开 |

并确立三条成果保护硬规则：**P-1 破坏性测试前工作树必须干净**、
**P-2 原始数据必须落进仓库才算完成**、**P-3 会话结束前写入 devlog**。

## 4. 数据与证据

### 4.1 隔离能力探针矩阵（2026-09-15 实测）

| 控制手段 | 结果 | 判定 |
| --- | --- | --- |
| `--read-only` + 写根目录 | `Read-only file system` | ✅ 有效 |
| `--network=none` + `wget` | `bad address 'example.com'` | ✅ 有效 |
| `--user 65534` / `--cap-drop=ALL` | uid 65534、能力被丢 | ✅ 有效 |
| `-v /workspace:/work:ro` + 写 | `Read-only file system` | ✅ 有效 |
| `-v /workspace:/work:ro` + `rm -rf /work/README.md` | 被拒 | ✅ **源码受内核保护** |
| `--memory=64m --shm-size=1g` + 写 300 MB | **写满成功** | ❌ 静默失效 |
| `--memory=64m` + Python 分配 200 MB | **分配成功** | ❌ 静默失效 |
| `--pids-limit=16` + 起 50 进程 | **50 个全部起来** | ❌ 静默失效 |
| `--ulimit nproc=16:16` | `can't fork` | ✅ 有效 |
| `--ulimit fsize=1M` | `File size limit exceeded` | ✅ 有效 |
| 进程内 `setrlimit(RLIMIT_AS, 64 MiB)` | `MemoryError` | ✅ 有效 |
| 进程内 `setrlimit(RLIMIT_FSIZE, 1 MiB)` | `File size limit exceeded` | ✅ 有效 |

> 根因：容器内 `/sys/fs/cgroup` 为 tmpfs，**无 cgroup v2 委派**，`pids.max`/`memory.max`
> 均读不到 → cgroup 类限制无法生效。

**⚠️ 一次必须记录的自我纠错**：`--memory=64m` 下 `dd` 写到 64 MB 就停了，
我最初据此判定"内存限制生效"。**这是误判**——64 MB 恰好是 Docker `--shm-size` 的
**默认值**，与内存限制无关；加 `--shm-size=1g` 后同一探针写满 300 MB 才暴露真相。
**教训：探针必须能把"竞争解释"区分开，否则"验证通过"本身就是误判。**

## 6. 学到了什么

1. **退出码 0 不等于控制生效。** 本阶段又遇到两次（`--memory`、`--pids-limit`），
   加上之前的 `firejail`，**三次**都是"命令成功、隔离为零"。
   这不是偶发，而是容器化环境的常态：控制是否生效取决于宿主是否**委派了相应权限**。
2. **探针必须能区分竞争解释。** `--memory` 那次误判的根因不是不够谨慎，
   而是探针的两种解释（内存限制生效 / 默认 shm 只有 64 MB）都会产生同一现象。
   **写探针时先问：还有哪种解释能产生同样的观测？**
3. **"不生效"必须先排除"没配对"。** 我第一次跑 `--ulimit as=…` 报的其实是
   参数写法错误，不是限制失效——差点又记错一条结论。
4. **结论不完整比结论错误更危险。** ADR-0006 的判定基于真实现象，却因为
   **没检查另一条路径**（docker）而得出过窄结论，直接影响后续设计。
   **下结论前先问：还有哪条路我没试？**
5. **目标设备能力未知时，不要把它当作已知。** 容器后端很好用，
   但手机没有 docker——所以它只能进测试链路，不能进产品链路。
