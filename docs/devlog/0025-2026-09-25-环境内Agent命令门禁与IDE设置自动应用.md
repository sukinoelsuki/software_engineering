## 1. 本阶段目标

把主 Agent 的命令执行闸门从"逐类逐次弹确认"放宽为"**默认全自动、少数不可逆操作保留确认**"，
并让这套偏好在**本环境真正生效**——而非只是一份写在仓库里、运行时被平台覆盖掉的 `settings.json`。

附带两项配套：① 把 CNB"同时存在容器数上限"的核实结论记入平台事实资产（官方未公布）；
② 由架构师落盘 ADR-0032、机制文档与威胁模型 T-15，使决策、机制、残余风险三者可追。

## 2. 关键决策与理由

### 2.1 真正的难点不是"配什么"，而是"配了不生效"

第一版实现（把 `codingcopilot.*` 写进仓库设置文件）**看起来完全正确，运行时却照样弹确认**。
根因三层（详见 ADR-0032 §1.2，均已自证）：

1. **`scope = application`**：`codingcopilot.autoRun` / `safeDeleteEnabled` / `safeDeleteBulkThreshold` /
   `customBlacklistCommands` / `disabledSecurityCategories` / `autoAcceptWebSearch` 六键的 scope 均为 application
   （`autoRunMode` 未声明，见 ADR-0032 §5.3 `N-2`）⇒ **只能写在 User 级**；
2. 仓库级 `.vscode/settings.json` 与镜像 Machine 级那份对该六键**都不生效**；
3. **平台在环境启动时用自己的一份覆盖 `User/settings.json`** ⇒ 构建期 COPY 进 User 级的键**会被抹掉**。

⇒ 唯一可靠时机是**环境启动之后**、由平台事件钩子把设置**合并**进**运行中的** User 文件。
`.ide/settings.json` 单独存在不会自动生效——这正是"配置是对的、运行时不生效"的直接根因。

### 2.2 决策：默认全自动 + 红线黑名单提醒 + 启动期 stage 保证落地

- **默认全自动**：`autoRun=true`、`autoRunMode="runEverything"`；
- **红线改为黑名单提醒**：禁用 12 个内置安全类别（只留 `custom`），并设 33 条黑名单正则
  （不可逆操作 + 项目 B/D/E 类红线，按 `git-workflow.md` §4 可回退性判据取材）；
- **防删库回收站阈值收紧到 200**：`safeDeleteEnabled=true`、`safeDeleteBulkThreshold=200`；
- **启动期落地**：新增 `.cnb.yml` 的 `vscode` 事件首段 stage `agent-permissions`，
  环境启动后由 `scripts/apply_ide_settings.py` 把设置**合并**进运行中的 User 设置并**断言**生效
  （含"设置文件与启动期 stage 成对存在"不变式）。

### 2.3 并发上限：记入平台事实，但"撞上限表现"未验证

`43a57a2` 把"同时存在容器数上限"的核实结论写入平台事实资产 §9 与 V7：
官方文档与 Open API **均未公布**该上限；**实测下界 = 4**（参考实现 `compute-matrix`）；
所有者观察约 6（跨仓库、按人/组织，**未实测**）；撞上限的具体表现**未验证**，仅附探针配方。

## 5. 问题与卡点

1. **运行会话是否真正用了新偏好——已于 2026-09-25 环境重建后闭环**：原先只验到"脚本合并 + 断言通过"，
   运行中会话的扩展日志仍显示旧值（安全检查读面板会话态 `chatModeSettings`，需重载或新环境才重初始化）——
   这是本仓库反复强调的"**改了文件 ≠ 设置生效**"的又一直观实例（与 0024 §5 第 7 条同源）。
   重建后在同一会话里实测到 `Loaded 33 / Loaded 12 / isAutoExecuteTerminal: true`，**且**两次命中探针
   都走到 `waiting_user_input → user_confirmed` ⇒ 判据补齐（细节见 §3 / §4）。
2. **并发上限"撞上限表现"未验证**：§9/V7 只确认了下界 = 4、所有者观察 ≈ 6，但撞上限后
   平台是排队、拒绝还是报错均未实测，仅留探针配方（§7 第③项）。
3. **参考实现 `compute-matrix` 不可直接读取**：ADR-0032 对其 `apply-workspace-settings` 与
   `docs/platform-facts.md` 的引用，一律来自本次任务口径与本仓库 `.cnb.yml` 既有注释，
   **不声称已逐字核对原文**（ADR-0032 §10 `U1`）。
4. **文档口径与实现不一致（本批已更正机制文档）**：`agent-command-gate.md` 的 `D7` 与 `.ide/settings.json`
   第 175 行注释都写"按 `|`、`||`、`&&`、`&`、`;`、换行切分"，而扩展只切 `||`（**不含单 `|`**）。
   按错口径推演会得出反向结论（把 `base64 … | sh` 那条判成"永不命中的死条"）。
   ⚠️ `.ide/settings.json` 的同款注释**尚未改**——它触发约 20 min 全量镜像重建，留待下次镜像改动合并（§7 ②）。
5. **误报面的两种形态（新发现，处置未定）**：① 把红线文本**当数据**传递会触发
   （`git commit -m "docs: 说明 rm -rf / …"`、`grep -rn "git push --force" docs/ | head`）；
   ② `git rebase develop`、`git checkout -- .` 这类"合法但破坏工作树"的操作也会触发。
   日常命令集 27/27 零误报，但这两类落在"日常"边缘 ⇒ 属**规则取舍**，须事先确认（§7 ③）。
   ⚠️ **本批实测例证（现场发生）**：把探针命令的原文写进**提交信息**后，那条 `git commit` 命令
   自身被判 `needUserConfirm=true`，因无人应答而超时未执行，只能改用 `-F <消息文件>` 提交
   —— "文本即触发"与"是否真的会执行危险操作"无关，正是这一形态的后果。
6. **绕过面已具体化为 18 条形态**：含"未覆盖命令"（`truncate -s 0 /dev/sda`、`shred`、`git push --mirror`）、
   "未覆盖路径"（`rm -rf /var/lib/mysql` —— rm 条目只拦根级/家目录/仓库根/通配符）、
   "前缀改写"（`git -c … push --force`、`git pu""sh --force`）与"漏项"（`git checkout .`、`git stash -u`）。
   `T-15` 的"部分缓解"**不得**因本轮数据自行升级——升级须架构师判定（§7 ④）。

## 6. 学到了什么

1. **"配了不生效"比"配错"更隐蔽**：`scope=application` 的键只能落在 User 级，而平台启动时
   会覆盖 User 设置 ⇒ 把偏好写进仓库/镜像这份"看似正确"的配置**根本不生效**。判断设置类缺陷
   的第一问应是「**这份配置是从哪里被读出来的**」（与 0024 §6 第 8 条同源）。
2. **"改了文件 ≠ 设置生效"是结构性事实，不是偶然**：平台对 User 设置的覆盖、扩展对会话态
   的缓存，两层都会让"文件已改"与"运行时已用"脱节 ⇒ 验证时必须去读**运行中的会话**，而非只检查文件。
3. **黑名单优于逐次确认**：真正不可逆的操作不靠"点确认"防住（点击者常不知在点什么），
   把范围约束写成**纪律 + 黑名单提醒**，既保效率又保留不可逆操作的可视性。
4. **"文档口径"本身也是一处会漂移的实现依赖**：把 `C1`/`C2` 那种"读产物"的做法用到**切分口径**上，
   立刻发现文档写错了一处——而按错写法推演会得出"某条黑名单是死条"这种**反向结论**。
   ⇒ 凡"某条防线有效/无效"的判断，都必须落到**产物或一次实机探针**上，不能只看注释（同 §6 第 1 条家族）。
