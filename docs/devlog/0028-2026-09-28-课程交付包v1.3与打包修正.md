## 2. 关键决策与理由

### 2.1 优先级改用"本期不实现即不可交付"，并与 §2.10 的发布分层绑定

**问题**（评审原话口径）：49 条需求里 **36 条（73%）**标"高"，优先级**不再承载排期信息**。

**根因**：原判据是"**是否每次会话都会触发**"——它把"**常用**"当成了"**必要**"。
`REQ-OBS-01`（日志与回放）、`REQ-UX-04`（中文优先）确实每次会话都走到，但**缺了不影响交付**。

**处置**：判据换成一条——"**本期不实现即不可交付**"，并显式绑定发布分层：

| | 判据 | 与 §2.10 发布分层 |
| --- | --- | --- |
| **高** | 属本期最小闭环必需 / 是"交付动作本身"的前提（门禁·测试分层·可复现构建·测量纪律）/ 是安全前提 / 已裁决纳入本期的 Must | 恒落「本期（必须达成）」 |
| **中** | 在本期范围内，但**缺失不使交付不可成立**；B 类用户需求按 `Q-1` 裁决固定为中 | 「本期（部分达成）」或「下一期」 |
| **低** | 已排到下一期，或属范围外的结论型需求 | 「下一期」/ §6.2 范围外 |

**结果：36 / 11 / 2 ⇒ 20 / 26 / 3**（16 条高→中、1 条中→低，逐条理由在 `01` §7.1）。

**三个副产物（这才是这次改动的实际收益）**：

1. **"高"里不再有"本期不可能达成"的条目**（`REQ-SEC-04`/`05` 已如实下移）——
   原先把未开工项标成"高优先级"，等于宣称"必须做但没做"，是自我欺骗；
2. **筛减给出可排期结论**：**高 20 条中仍有 2 条未达成**（`REQ-MODEL-03`、`REQ-SEC-07`）⇒
   把"本期到底还差什么"压成了两个编号；
3. **发布分层与优先级重新对得上**（原来 36 条"高"时，这个对应关系不可能成立）。

⚠️ **边界（不得误读）**：**降级 ≠ 降要求**——17 条被移出"高"的需求**仍在 §6.1 本期范围内**，
**验收标准与现状符号一条未改**，变的只是"是否声称缺了它就交付不了"。

### 2.2 打包排除 `.git`：两条理由，第二条与体积无关

**核查结论（实测）**：`.git` 确实是超限的**唯一主因**——含它 `8.82 MB`，不含它 `2.37 MB`，
它在包内占 **≈6.45 MB（73%）**。

**但真正必须先处理的是第二条**：`.git/config` 里写着
`credential.helper = store --file=/workspace/.git/.git-credentials`，而该凭据文件**真实存在**。
`.gitignore` 对 `.git/` 内部文件**不起作用** ⇒ **只要打 `.git/`，它照样进包**。
⇒ 上一版分发出去的 zip **很可能把 cnb.cool 凭据一起发给了评审**（见 §5 第 2 条）。

**决策**：新包**排除 `.git/`**；不再用"打 `.git`"来承载"逐笔核对提交哈希"（见 §2.4）。

### 2.3 为什么新开一篇，而不是接着 0027 写

**主判据是"议题/阶段的完整性"**（`docs/devlog/README.md`）：本批是**交付物文档迭代**，
与 0027 的"产品带读与跑测交接"**不是同一个议题** ⇒ 各占一篇。
**行数是旁证**（0027 已 265 行、本就偏长）——⚠️ 但**不是**判据：该 README 的修订记录
（2026-09-15 行）已把"300 行"改为**软性参考**，不再是硬上限；
以"超行数"当收篇理由会把已废止的口径又抬出来一次。

⇒ 新开 `0028`，并把 0027 收篇、**未完成项逐条重新判断后抄入本篇 §7**
（先例：0014→0015、0019→0020 等；0027 §7 原文保留作历史）。

### 2.4 去掉 `.git` 之后，如何保住"逐笔核对提交哈希"

原方案把 `.git/` 打进包，理由是"供逐笔核对提交哈希"。去掉后由两处替代：

1. **包根 `提交历史.txt`**：全量 `git log --format='%h %ad %s' --date=short`（625 笔）；
2. `需求分析文档/07-原始输出附录.md` §5：**关键载体**的提交哈希 + 核对命令
   `git log -1 --format='%h %ad %s' --date=short <hash>`。

### 2.5 包内说明书必须写"没有 `.git` 时怎么跑门禁"

实测发现门禁与 git 是**耦合**的：`hooks-check` 需要钩子已安装，
而 `security-secrets` 直接调 `pre-commit run detect-private-key --all-files` —— pre-commit **需要 git 仓库**。
⇒ 说明书给出的步骤是 `git init -q` → `git add -A` → `make setup` → `make check`
（并标注 `git add -A` **只适用于解压出来的临时副本**，不要照搬进真仓库）。
详见 §5 第 1 条：**不 `git add` 的话密钥扫描会空转**。

## 5. 问题与卡点

1. **⚠️ `pre-commit --all-files` 只覆盖"已跟踪"文件 ⇒ 解压后不 `git add` 会让密钥扫描空转**
   （输出 `(no files to check) Skipped`，看起来"通过"，实际一步没查）。
   这与本项目反复记的同一条教训同族：**"跑起来了" ≠ "真的生效了"**。
   ⇒ 已写进包内说明书，并把 `git add -A` 的**适用范围**（临时副本）一并标注，避免被照搬进真仓库。

   ⇒ 需 `unzip -l 旧包 | grep credentials` 确认；**若命中即按泄露处置、轮换 CNB 令牌**（最高优先级）。
3. **`03` §4 的乙类 8 项中仍有 7 项（`C-07`/`C-12`~`C-17`）需所有者一句话确认**
   （`C-08` 已于同日获确认 ⇒ 移入丙类，见 §3.4）。本轮**不代裁**，状态统一改为
   「⏳ 已提交所有者一句话确认（2026-09-28）」；确认后需回写并**重打一次包**。
4. **`.git` 与"包内门禁"的耦合此前未被记录**：去掉 `.git` 后，评审必须多做 `git init` + `git add` 两步

## 6. 学到了什么

1. **"常用"不是"必要"**：一个判据里混进两个概念（频率 vs 必要性），
   指标就会"看着合理、实际无用"（36/49 标高）。**修法是换判据，不是调阈值。**
2. **凭据的暴露面常常不在"配置里"，而在"打包/备份/复制"这些动作里**：
   `.gitignore` 只保护**工作树**，对 `.git/` 内部文件完全无效——"我 ignore 了"是**假安全感**。
3. **交付物与"跑得起来"是同一件事的两半**：去掉 `.git` 是体积与安全的胜利，
   却顺手打掉了"包内能跑门禁"的前提 ⇒ **任何"精简"都要回头问一句"谁在依赖被删的东西"**。
4. **"通过"也可能是空转**：`(no files to check) Skipped` 这类**绿色但什么都没做**的输出，
   比红色更危险（与 `ADR-0006` 的 fail-open 教训同族）。
