## 2. 关键决策与共识

### 2.1 修正：不是多方会诊，而是"请来一位最好的专家"

| 项 | 内容 |
| --- | --- |
| 用户原始意图 | **请来一个最好的医生**，而不是举办一场医学探讨 |
| 明确排除 | 多专家并行参与/会诊。判定为"没必要，且可能带来浪费与危害" |
| 资源现实 | 手机普遍内存 12 GB，**同时驻留 2 个模型已足够**（1 个主 Agent + 1 个专家） |
| 代价判断 | 让 6 个 4B 模型挤进 12 GB 内存是错误方向 |

### 2.2 架构定型：主 Agent（调度器）+ 按需加载的单专家

```text
        用户
          │
          ▼
    ┌──────────────┐
    │   主 Agent    │  ← 常驻内存；负责路由、上下文组装、结果汇总
    │  （通用小模型）│
    └──────┬───────┘
           │ 按需加载 / 卸载（同时最多 1 个）
           ▼
    ┌──────────────┐
    │  领域专家模型  │  ← 无状态；用毕可释放
    └──────────────┘
```

**主 Agent 的职责边界**：完成**简单通用任务** + **模型选择与切换**（路由）。
它不需要专精，只需要**可靠**。

### 2.3 真正的瓶颈：上下文切换，而不是多模型共存

用户的判断（已采纳）：

> 瓶颈在 **2~3 个模型之间的上下文切换**。
> 若真的让多个模型同时存在，首先要处理**上下文污染**——这很麻烦，且不好解决。

因此本项目的核心工程问题从"多专家协同"收敛为：
**在模型之间安全地迁移上下文，并控制切换次数。**

### 2.4 与操作系统的类比（回到"原生智能系统"）

这个设计本质上就是操作系统语义：

| OS 概念 | 本项目对应 |
| --- | --- |
| 内核 / 调度器 | 主 Agent |
| 进程 / 服务 | 专家模型（无状态、按需加载） |
| 进程控制块（PCB）/ 进程状态 | 任务状态与上下文切片 |
| 进程间通信（IPC） | 结构化的 Handoff 请求 / 结果 |
| **上下文切换开销** | **模型加载 + KV Cache 失效重建** |
| **状态串扰 / 内存越界** | **上下文污染** |

> 项目所有者最初关注的方向就是"原生智能系统"。这个设计把该方向**落在了具体产品上**：
> 一个**面向本地模型的调度器与上下文管理器**。

## 3. 技术问题拆解：上下文迁移的五个具体问题

| # | 问题 | 说明 |
| --- | --- | --- |
| P-1 | **对话模板不兼容** | 不同模型的 chat template、特殊 token 不同，同一份对话历史无法直接复用 |
| P-2 | **上下文污染** | 专家输出若原样写回主历史，会把专家的术语、风格与**幻觉**带进主 Agent 的判断；且因为它看起来像"自己说过的话"，主 Agent **无法识别其可信度** |
| P-3 | **历史膨胀** | 每切换一次就多一段历史，成本线性增长 |
| P-4 | **KV Cache 失效** | 切换后缓存全部作废，必须重新 prefill —— 这是**真实的大头开销**，CPU 上尤其明显 |
| P-5 | **用户感知不一致** | 用户以为在与"一个助手"对话，实际更换了模型，语气/能力/拒答策略可能突变 |

**P-2 是本项目最有价值的技术难点**，也是"自研 Harness"存在的核心理由。

## 4. 设计草案：单一权威上下文 + 无状态专家

**核心原则：主 Agent 持有唯一权威上下文；专家模型是无状态的被调用者，不得直接写入历史。**

```text
用户 → 主 Agent
         │ ① 路由决策（查模型注册表）
         │ ② 组装**受控输入**：任务 + 相关上下文切片（不是全部历史）
         ▼
       专家模型（无状态）
         │ ③ 返回**结构化结果**：结论 + 置信度 + 依据 + 注意事项
         ▼
       主 Agent 合并
         │ ④ 只把【结论摘要 + 来源标记】写回主上下文；原始推理过程丢弃
         ▼
       用户（感知上仍是"一位专家的回答"）
```

### 四条落地规则

| 规则 | 作用 |
| --- | --- |
| **R1 单一权威上下文** | 主 Agent 是唯一历史持有者，避免多份历史分叉与不一致 |
| **R2 专家无状态** | 每次调用都是独立请求，不继承专家自身历史 → **天然隔离** |
| **R3 受控回填** | 专家输出经结构化 + 摘要化后才进入主上下文；原始推理过程丢弃 |
| **R4 粘性路由** | 同一话题保持同一专家，直到话题切换；**减少往返切换次数** |

### 受控回填的数据结构（草案）

```json
{
  "expert": "medical-4b",
  "topic": "用药注意事项",
  "conclusion": "……",
  "confidence": "medium",
  "caveats": ["未考虑与其他药物的相互作用"],
  "verified": false
}
```

主上下文中只保留压缩形式，例如：`[医疗专家 · 置信中] 建议饭后服用；未覆盖药物相互作用`

> 这与公开研究结论一致：保留**推理痕迹的摘要**而非**原始工具输出**，
> 可在保持准确率的同时显著降低 token 消耗（见 [0001 第 6 节](0001-2026-09-14-工程初始化与方向选型.md) 相关记录）。

## 5. 可测量指标

| 指标 | 定义 | 作用 |
| --- | --- | --- |
| **路由准确率** | 主 Agent 选对专家的比例 | **核心 KPI**——决定"是否一次请对了医生" |
| **单任务切换次数** | 完成一个任务期间的模型切换次数 | **主要优化杠杆**（见第 6 节） |
| **切换开销占比** | （加载 + prefill 时间）/ 任务总时间 | 体验指标 |
| **上下文污染度** | 未经验证的专家内容进入主上下文的比例 | 安全指标 |
| 端到端任务成功率 | 达到预期结果的任务比例 | 总指标 |

## 6. 一处技术修正：切换成本不是"边际成本"

用户判断："没必要考虑一个模型跑多少秒，只要不出现极低效率就行。"

**方向正确，但有一个前提需要修正**：

如果一次交互需要 **3 次切换**，每次（加载 + prefill）**8 秒**，就是 **24 秒纯等待**。
这不是边际成本，而是**每次交互的固定成本**——手机端几乎不可接受。

**但修正的杠杆不是"加快单次切换"，而是"减少切换次数"**：

| 手段 | 效果 |
| --- | --- |
| 提升路由准确率 → 一次选对 | 不需要来回换 |
| 粘性路由（R4） | 同一话题不重复切换 |
| 主 Agent 常驻 | 只有专家需要加载 |

> **结论：本项目的性能指标应当是"切换次数"，而不是"单次加载耗时"。**
> 这让性能主线变得可实现——不必与 llama.cpp 的加载速度较劲，
> 而是把自己的**调度策略**做好。这才是 Harness 的职责。

**旁证**：项目中"把 6 个 4B 模型塞进 12 GB 内存"之所以是错误方向，
不是因为加载慢，而是因为**没有内存留给系统与 KV Cache**，会导致频繁换页而整体崩塌。

## 7. 主 Agent 的选型建议（待验证）

| 项 | 建议 |
| --- | --- |
| 参数规模 | **1.5B ~ 3B** |
| 理由 | 主 Agent 的工作是**路由、格式转换、结果汇总**，不是深度推理——要的是**可靠 + 快**，不是"聪明" |
| 内存账（12 GB 手机，可用约 8 GB） | 主 Agent 3B ≈ 2.8 GB + 专家 4B ≈ 3.5 GB ≈ **6.3 GB**，可行；若主 Agent 降到 1.5B 则约 5.0 GB，更宽裕 |
| 关键约束 | 主 Agent **常驻**，其体积直接决定留给专家的内存 → 越小越好，但路由准确率不能牺牲 |

## 8. 问题与卡点

| 问题 | 状态 | 说明 |
| --- | --- | --- |
| "相关上下文切片"如何选取 | 待设计 | 送给专家的输入不应是全部历史，需要切片策略（相关性检索 + 最近若干轮） |
| 主 Agent 路由准确率的下限 | 未测 | 若 3B 主 Agent 路由准确率过低，需退化为**规则路由 + 用户确认** |
| 用户是否应知道"换了模型" | 待决策 | 产品呈现为"一个助手"还是"一位专家"？影响信任感的建立方式 |
| 切换次数与内存驻留的权衡策略 | 待设计 | 何时预加载、何时释放、是否允许 2 个专家同时驻留 |
| 上下文污染度如何度量 | 待设计 | 需要可操作的实验设计（例如污染前后主 Agent 准确率对比） |
