## 2. 关键决策与理由

### 2.1 远端授权：从"一刀切事先批准"改为"按可回退性分级"（ADR-0016 方案 B）

所有者最初的提议是**整条取消**"推送前事先批准"，改为事后报告。我在 ADR 起草前给出了
反对意见并使其写进 ADR 的论证（§5.2）——**按可回退性把操作分成 A~F 六类**：

- **A 类**（`develop` / 短期分支上的代码·文档·测试·配置）⇒ **改为事后报告**；
- **B~F 类保持原规则**：`main`（事先批准）、**凭据类入库**（保持禁止 + 事先拦截）、
  强推/改写已推送历史/删远端分支（保持禁止）、`bench/data`（只由 CI 写）、
  新增依赖/改门禁强度/改规则本身（事先确认）。

判据（§5.2 写死三条可检验条件）：一个已推送的变更属"可回退"，当且仅当
① 存在语义等价的逆操作；② 逆操作代价与一次普通提交同量级；③ 逆操作后内容**不残留于任何其它可达载体**。

逐类对照后 C 类**不满足 ③**：`git revert` 只在新提交里删掉它，**远端历史 / 平台缓存 /
他人 fork 均留存** ⇒ 不可回退 ⇒ 必须事先拦截。
并且**唯一能自动拦它的 `detect-private-key` 有已登记漏洞**——
`pre-commit run --all-files` 走 `git ls-files`，**未 `git add` 的新文件不在扫描范围内**
（`docs/devlog/0014` §5 残余 2）。**把 A 与 C 并进同一条规则，就是把不可逆风险交给一个已知有覆盖漏洞的检查。**

### 2.2 只装官方 11 个 Skill 中的 5 个

官方 `cnb/skills/cnb-skill` 的 `skills/` 下**共 11 个 Skill**（不是 1 个）。
只取 `cnb-api` / `cnb-docs` / `cnb-code-review` / `cnb-pr-analysis` / `cnb-pipeline`；
排除 `cnb-code-commit`（引导"提交并创建 PR"，与项目的 PR 模板 + Conventional Commits 门禁
**职责重叠**，会形成"同一件事两处口径"——A-3 / A-14 / A-16 同族失效模式）；
其余 5 个（NPC 搜索 / TAPD / 路径转换 / 附件上传 / 仓库知识库）本项目用不上。

理由不只是"用不上"：**Skill 的 `description` 是常驻上下文**，11 → 5 把这块开销砍掉一半。

### 2.3 项目内 Skill 改名 `repo-ci-conventions`

官方集合里**已有一个 `cnb-pipeline`**，与 ADR-0017 原定的项目内同名 Skill **重名且职责重叠**。
ADR-0017 §5.3.2 的分工判据是"**交集必须为空**；有歧义时归官方（仓库约定应能被本地文件证明，
平台用法只能来自上游）"——但该判据当时**只考虑了职责、没考虑命名空间**。
⇒ 项目内改名 `repo-ci-conventions`（"本仓库 CI 约定"），并把分工表重写。

### 2.4 镜像新增阶段刻意放在 GB 级资产**之后**

`.ide/fetch-assets.sh` 的 `COPY` 位于第 10~12 阶段（GB 级资产）**之前**，
改它会使模型层缓存失效（`.ide/Dockerfile` 注释里已记录该代价约 20~25 分钟）。
⇒ 本次**新增独立脚本** `.ide/install-cnb-skills.sh` + 清单 `.ide/assets/cnb-skills.txt`，
并把 `COPY`/`RUN` 插在第 12 阶段之后、自检之前 ⇒ **前序层输入不变、命中缓存**。
新阶段编号为**第 13 阶段**，**原自检顺延为第 14 阶段**。

### 5.3 【未裁决·待落地】`agent-teams.md` 的两条机制副作用

并发写入暴露两条**此前未记录**的机制事实，均已由成员/领导实测：

1. **`-o/--only` 只保证"提交内容"不含他人文件，不保证"钩子的文件清单"**——
   pre-commit 面向**全局暂存集合**。成员 `arch-skills` 两次被
   `trailing-whitespace` / `mixed-line-ending` 拦下，而**同一文件单独复跑该钩子是通过的**
   （其文件行尾空白与 CR 均为 0）⇒ **失败归属可能是他人文件**；
2. **pre-commit 会对共享工作树执行 `git stash` / `restore`**
   （每次提交日志里的 `Stashing unstaged files` / `Restored changes`）
   ⇒ 窗口内他人正在写的文件**存在风险**。

⇒ 合并为一条结构性风险：**"同一工作树 + 并行 agent"下，pre-commit 自身成了跨成员耦合点。**
**裁决**：并入 `agent-teams.md` §6「共享暂存区」（新增第 5、6 条）+
§8 增设第 4 类失效模式「派活未投递」。**环境中销毁时未落地**（见 §7）。
**状态更新（同日第二段）**：**已落地**，见 §3.1（`e896766`）。

## 6. 学到了什么

第一条：**"批准"与"可行"之间隔着一次核验。** ADR-0016 被批准后，核验才暴露出
**官方安装路径无法钉 commit** 与 **`skills` 要求 node ≥ 22.20 而镜像是 20**。
两条都改变实现方案。若跳过核验直接照官方文档写 Dockerfile，构建必然失败。

第二条：**"可回退"不是一句话，是一组可检验条件。** 凭据类改动与代码改动在
"能不能撤销"上**完全不同**——这条判据把一个含糊的"要不要事先批准"变成了可逐项对照的表。

第三条：**对账必须以仓库为准，且不得自造"物证"。** 我提出"空信箱 ⇒ 未投递"时，
它是从"消息丢了"这个真实痛点上**推出来的**，看起来很有说服力；
但它**当场就被证伪**，且危害方向是**打到正在工作的成员**。
`agent-teams.md` §8 早就写过"现象是证据、归因只是假设"——这次是我自己踩了。

第四条：**并行的耦合点是"共享的东西"，不只是文件。** 本轮依次撞上：
**共享 git 索引**（`-o` 解决）、**共享工作树上的 pre-commit stash**（新增）、
**pre-commit 读全局暂存集合**（新增）、**`commitizen` 偶发误报**
（成员两次遇 `Commit validation: successful!` 但 `exit≠0`，重试即过，
**都发生在他人并发提交的窗口内**）。⇒ 护栏必须一条条补，不能假定"文件域不重叠就安全"。

第五条：**"谁都看见了、但没人有权改"是一种真实的残留形态。**
两个成员都发现了 `post-build-checklist.md` 的残留、都**正确地拒改并上报**——
但如果没有"指派单一写者"这一步，它会一直留在那里。**发现 ≠ 修复，必须有人被指派。**

第六条（第二段）：**"落地一项裁决"不等于"改一处文字"。** A-1 表面上只需动五份 agent 定义，
但同一条义务在**另外四处**也有表述（权威源 / 常驻摘要 / 两份常驻结论）；而 A-3 落地前的
反向搜索又挖出**同一份证据笔记内部**一处已被证伪、却仍以"建议待办"身份躺着的判据。
⇒ **反向搜索的收益不在"确认没漏"，而在"找到自己没想到要看的地方"**；
这条规则（「规则变更的联动更新」）第一次给出了**闭环实例**，而不只是"写了但没跑"。

第七条（第二段）：**fail-secure 的检查会让"新环境"看起来像"坏环境"。**
本段首次 `make check` 直接红在 `hooks-check`——新工作区默认没有 `pre-commit` / `commit-msg`
钩子，而该检查是**故意 fail-secure** 的（宁可红，也不假装保护生效）。
正确反应是 `make setup` 恢复钩子层并复验，**不是**绕开这条红。
⇒ 这两条（"检查会红" 与 "保护真的生效"）的判据不同：**`make setup` 的输出里那句
`[local-hooks] pre-commit：OK / commit-msg：OK` 才是后者的证据。**
