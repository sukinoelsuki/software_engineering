### 4.4 V-3：主题 ID 有效（代码级证据）

`theme-defaults` 贡献的主题 id 是 `Dark Modern`（label 同为 `Dark Modern`），
与 settings 中写的 `Default Dark Modern` **字面不同**，一度怀疑是错误值。
在 workbench 产物中定位到内置主题标识的实际映射：

```js
function gst(s){switch(s){
  case "Default Dark Modern": return "Dark Modern";
  case "Default Light Modern": return "Light Modern";
  case "Default Dark+": ...
}}
```

即 `Default Dark Modern` 是 workbench 侧的**内置主题标识**，会被映射到 theme id。
settings 中的写法**正确**，V-3 通过。

### 4.5 V-4：settings.json 四条落盘路径只有一条生效

`.ide/Dockerfile` 把 settings 写入 4 个路径。实测：

| 路径 | 大小 | 结论 |
| --- | --- | --- |
| `~/.local/share/code-server/Machine/settings.json` | 6796 B | ✅ **是我们的文件**（生效） |
| `~/.local/share/code-server/User/settings.json` | 1017 B | ❌ 被 CNB 平台启动时写入的默认设置**覆盖** |
| `~/.vscode-server/data/Machine/settings.json` | 1017 B | ❌ 同上 |
| `~/.vscode-server/data/User/settings.json` | 缺失 | ❌ 平台在运行期重建该目录 |

平台写入的 1017 B 文件内容包含 `cnb-welcome.locale`、`codingcopilot.welcomeMessage`、
CNB yaml schema 等平台自有配置——可确认**不是**我们的版本被保留。
镜像内那份与仓库当前版本的差异还有一处历史遗留：
镜像里是 `"workbench.colorTheme": "Dark Modern"`、`"extensions.autoUpdate": "off"`，
仓库里已是 `"Default Dark Modern"` 与布尔值——即**当前环境运行的是更早一版 settings**，
属预期（修改 Dockerfile/settings 需销毁重建才生效）。

取舍：保留 4 条 COPY（成本为零、可能在其它客户端生效），但已在 Dockerfile 注释中
写明"真正生效的是 Machine 作用域那一份"，避免后续有人误以为改 User 路径能生效。

### 4.6 V-5：bwrap 不可用（含根因）

```text
$ bwrap --bind / / --tmpfs /tmp --proc /proc --dev /dev /bin/echo sandbox-ok
bwrap: Creating new namespace failed: Operation not permitted
exit=1
```

根因逐项排除后确认是**平台硬约束**：

| 检查 | 结果 | 说明 |
| --- | --- | --- |
| `unshare(CLONE_NEWUSER)`（Python 直接调用 libc） | `EPERM` | 不是 bwrap 的问题 |
| `unshare(CLONE_NEWNS)` | `EPERM` | 同上 |
| `CapEff` / `CapBnd` | `0x00000000a80c05fb` | **不含 `CAP_SYS_ADMIN`**，且为 bounding set，无法从容器内获取 |
| `Seccomp` | `2`（filter） | 容器 seccomp 策略在拦截 |
| `/proc/sys/user/max_user_namespaces` | `2147483647` | **不是**这个开关导致的 |
| `/usr/bin/bwrap` 权限 | `-rwxr-xr-x`（**非 setuid**） | 无回退路径 |

补充排除：内核为 `5.4.241`，**Landlock 需要 ≥ 5.13**，同样不可用。

### 4.7 firejail：最危险的失败方式——静默直通

首轮表面结果是"firejail 通过"：

```text
$ firejail --quiet --noprofile /bin/sh -c 'echo net-ok'
sandbox-ok
exit=0
```

去掉 `--quiet` 后真相暴露：

```text
Warning: an existing sandbox was detected. /bin/sh will run without any additional sandboxing features
```

对抗性验证（对比 namespace inode，宿主 vs firejail 内）：

| namespace | 宿主 | firejail 内 | 是否隔离 |
| --- | --- | --- | --- |
| user | 4026543963 | 4026543963 | ❌ |
| mnt | 4026546742 | 4026546742 | ❌ |
| pid | 4026546745 | 4026546745 | ❌ |
| net | 4026548046 | 4026548046 | ❌ |
| ipc | 4026546744 | 4026546744 | ❌ |
| uts | 4026546743 | 4026546743 | ❌ |
| cgroup | 4026531835 | 4026531835 | ❌ |

`--net=none` 下 `eth0` 依然可见、netns inode 不变。
**结论：firejail 检测到自己已在沙箱中就放弃了加固，但退出码仍为 0。**

> 这是本轮最有价值的发现：原清单第 2 步判据是"**任一可用** → 方案可行"，而 firejail 的表现恰是
> "输出 `sandbox-ok`、退出码 0"——**按表面判定会得出错误结论**，让整个安全设计建立在不存在的边界上。
> 判据已修正为"必须验证隔离**确实发生**"（见 checklist 第 2 步）。

### 4.8 可行路径：Docker 容器作为隔离边界

`docker` 29.6.2 可用（CNB 的 `services: [docker]`），且加固参数实测逐项生效：

```bash
docker run --rm --network none --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --cap-drop=ALL --security-opt=no-new-privileges \
  --pids-limit=64 --memory=256m -u 65534:65534 alpine:latest sh -c '...'
```

| 验证点 | 结果 |
| --- | --- |
| 非 root 运行 | `uid=65534` ✅ |
| 根文件系统只读 | `touch /x` → `Read-only file system` ✅ |
| 可写临时区 | `/tmp` 可写 ✅ |
| 网络隔离 | `--network none` 下外网不可达 ✅ |
| capability | `--cap-drop=ALL` ✅ |

注：容器**内部**同样无法 `unshare`（失败原因与本容器相同），
但这不影响隔离——隔离边界由容器运行时在宿主侧建立，不需要嵌套命名空间。

## 6. 学到了什么

1. **"工具没报错"和"隔离生效了"是两件事。**
   firejail 退出码 0、还打印了成功字样，但它什么都没做。
   **安全组件必须用"攻击者视角"验证结果状态，而不是验证退出码**——
   本次是靠对比 namespace inode 才看穿的。这条经验直接影响后续所有安全测试的写法。
2. **文档里的"任一可用即可"是危险的可满足性判据。**
   checklist 由我自己写、自己执行，依旧差点被自己的乐观判据骗过。
   凡是"降级/兜底"类判据，都必须写明**如何证明它真的成立**。
3. **平台约束要一次性摸清，并记录"为什么不行"。**
   本轮排除的 bwrap、firejail、nsjail（同因）与 Landlock（内核版本）根因都在同一处：
   容器禁用了嵌套命名空间。写下根因，以后就不会再有人（包括未来的我）去"再试一次 bwrap"。
4. **沉默失败在配置层面同样致命。** Pylance 装不上、构建不报错、编辑器里只是少了类型提示——
   这类问题只能靠**期望清单与实际清单的集合比对**发现；幸好"17 请求 + 2 依赖 = 18 实装"让缺口无处藏身。
