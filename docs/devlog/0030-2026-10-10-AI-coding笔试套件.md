## 1. 本阶段目标

所有者下达的诉求（原话要点）：**设计一道题** → **给 agent 补齐工具** → **补完环境里的工具链** →
**给一份面向第三方的人性化使用手册**；关键约束有三条：

1. **「我需要的是直接和端侧模型交互，而不是和你交互」** —— 使用者要面对模型，不是面对代理；
2. **新开一个分支做，后续这个 AI coding 笔试功能就专门在那个分支上**；
3. **「注意新开一次流程不要上下文污染」** —— 可重复使用。

**目标（可核对）**：`bash exam/run.sh` → 粘题面 → 与模型多轮对话 → `bash exam/verify.sh <工作区>` 得到客观分数。

## 2. 关键决策与理由

> 完整论证（候选方案 × 权衡 × 负面后果 × 验证方式）在 [ADR-0033](../adr/0033-ai-coding-exam-kit.md)。本节只留结论与**为什么**。

1. **多轮交互用"新增子命令 + 复用装配"，不另写一条通路**（ADR-0033 §3.1 选 C）。
   `run` 是一次性的（任务启动时给定），笔试要的是回合制。但**不能**在 `exam/` 里自建装配：
   那会衍生出第二条装配路径（装配顺序、能力收窄、审计包装都得复制），**必然漂移**。
   做法：`cli/app.py` 暴露 `Assembly` / `assemble_session` 两个**公开别名**（`_assemble` 的别名，
   **不改名**——`docs/engineering/` 与 `docs/research/` 里有若干处按 `_assemble` 指向实现），
   `cli/exam.py` 直接复用。
2. **工具补齐走"独立领域包"，不动示例包**（§3.2 选 G）。
   仓库两份示例包是**只读**的（ADR-0021），用它们写不出文件、编译不了；但把它们改成可写会
   破坏那条**有意的**安全边界（`tests/unit/test_example_packs.py` 会翻红——那正是护栏在起作用）。
   因此新增 `exam/pack/`：暴露 `read_file`/`list_dir`/`write_file`/`run_command` 四项 + 三项能力。
3. **⚠️ 登记一次"下调安全默认"**（§3.3 选 I）：笔试要 `write_file` / `run_command` **自动放行**，
   否则每次调用都要人工确认、一场笔试几十次 ⇒ 流程不可用。做法是把它们在该包内声明为 `low`，
   并**显式限定适用范围**（本机、自用、建议一次性容器）+ 逐条列出仍然生效的机制
   （default-deny 能力授予 / 路径白名单 / 非特权 uid + rlimit / 不经 shell / 全程审计）。
   按项目规则，这属 **F 类**，**必须先走 ADR** ⇒ 这正是 ADR-0033 的主要篇幅所在。
   受影响面已追加到威胁条目 `T-01`（**编号与计数不变**：仍 `15 / 1 / 12 / 2`）。
4. **线程数由启动脚本钉住，不改产品接口**。`llama-server` 按**物理机核数**开线程
   （本机检测到 **192**，容器只给 8 核）⇒ 严重超订。`cli` 目前不向 `LocalLlamaClient` 传
   `server_args`，因此 `exam/run.sh` 用一层**最薄的 `exec` 包装**把 `-t min(核数, 8)` 钉住。
   把它做成产品接口（或让 `LocalLlamaClient` 按 `sched_getaffinity` 自校正）是**行为变更**，
   登记为 ADR-0033 §8 的遗留项 1。
5. **`/new` = 换一个全新会话**（新 `session_id`、历史归零），代价是模型服务重启约 1~2 s。
   换来的是"会话生命周期的所有者只有一处"（`Session.close()`），不存在"客户端该由谁关"的模糊地带。
6. **`Session` 新增两个只读属性**（`session_id` / `exposed_tools`）：让界面能**如实**展示
   "模型实际能用哪些工具"。取的是 `trimming.select_tools` 的同一份结果——另算一份必然漂移。
   两者**不参与任何判定**。
7. **题面改为"只给目标与协议、不给规格"**（2026-10-10 追加，所有者下达）。
   原多段式题面把**边界条件、错误判定的优先级、具体校验规则**逐条列成表格，等于替模型做完了
   "读需求 → 找边界"这一步——而那一步正是 AI coding 要考的东西。改法：`exam/PROBLEM.md` 的
   **「题面」缩成一段话**（只含命令、结果行格式、五个错误词、`#`/空行处理、编译命令与禁用项），
   原版**逐字保留**并降级为「完整版题面（供人理解）」，与评分标准一起**只给出题者 / 评审者 / 判分依据**看。
   取舍判据（已写进文件）：**协议（跨边界要传的字节）必须给全**——不给就无法判分，那是接口定义；
   **判定规则可以扣**——它替代的正是模型该做的推理。
   已如实登记的代价：通过门槛升高，且"并列名次""取值上限"这类**多解细节**会掺入推断运气
   （见 `PROBLEM.md`「从题面里故意扣掉的部分」）。

## 4. 数据与证据

### 4.1 端侧速度实测（2026-10-10，本机 8 核 / 16 GiB / CPU-only / `llama.cpp` build 69eb250）

`llama-bench`（纯生成，无上下文负担）：

| 模型 | pp128 | tg128 | 线程 |
| --- | --- | --- | --- |
| Qwen3-4B-Q4_K_M | 64.80 t/s | **16.46 t/s** | 8 |
| Qwen3-8B-Q4_K_M | 34.74 t/s | **9.38 t/s** | 8 |

**线程扩展曲线（8B，tg128）**：4 线程 **9.85** · 8 线程 **8.85** · 16 线程 **7.60** · 32 线程 **5.67** t/s
⇒ **生成是内存带宽受限，加线程只会更慢**。"换 64 核机器"对生成速度几乎无益（本机 `Cpus_allowed_list` = 257-264，即 8 核 cpuset）。

### 4.2 与"根因"的对照

`llama-server` 的启动日志实测 `n_threads = 192`（按**物理机 384 核**开线程，无视容器 cpuset）
⇒ 这解释了产品手册里"生成速度 ≈ 2~3.4 tok/s"与裸测 9.4 t/s 之间**约 3~4 倍**的差距。
用 `-t 8` 包装后，会话内实测 **tg = 7.4 ~ 8.0 t/s**。

### 4.3 一次真实端到端实跑（8B，写/编译/运行 C 程序）

| 指标 | 实测 |
| --- | --- |
| 退出码 / 终态 | `0` / `completed` |
| 事件数 / 模型往返 | 22 / **6** |
| 生成 token | 5 542（单步 412 ~ 1 465） |
| 墙钟 | **745.3 s（12.4 min）** |
| 产物 | `student.c` 112 行，`gcc -Wall` 零警告，独立复跑输出正确 |

同一次实跑里暴露的三类"必须靠人纠正"的模型行为（**已写进领域包提示片段与手册话术**）：

1. **路径幻觉**：第一步用绝对路径 `/workdir/student.c` → 被路径白名单拒（这是安全机制**正常**工作的形态）；
2. **需求偏离**：要求"main 内置测试数据"，第一版写成 `scanf` 交互式 ⇒ 运行时卡在提示符上；
3. **⚠️ 未运行却声称有运行输出**：重写后**没有**重新编译运行，就在最终回答里"给出"了运行输出。
   独立编译复跑证明**产物是对的**，但它声称的输出与真实输出在并列名次顺序上**不一致**
   ⇒ **产物正确 ≠ 它声称的证据正确**。这条是"证据片段"提示与 `verify.sh` 存在的直接理由。

### 4.4 隔离路径的实测

`proc.run(isolation="user")` 在本容器可用：`id` → `uid=65534(nobody)`；`gcc --version` 正常；`touch` 在工作目录内可写。
**同时观察到一处缺口**（已登记 ADR-0033 §8 遗留项 2）：进程保留**补充组 `0(root)`**
（`groups=65534(nogroup),0(root)`）——`subprocess` 的 `group=` 只设主 gid，未清补充组。

## 5. 问题与卡点

1. **线程超订是产品侧的静默退化**：`cli` 不传 `server_args` ⇒ 用户**无从**在命令行纠正（只能靠包装脚本绕），
   而症状表现为"模型很慢"，极易被误判成"模型不行 / 硬件不行"。已登记为 ADR-0033 §8 遗留项 1。
2. **`T-15` 与 `T-11` 之外又出现一处"呈现面"**：`cli/exam.py` 会显示 `arguments_json` 的**摘要**，
   而 `cli/render.py` 按契约 `I8` **不显示**。两者服务不同对象（产品事件流 vs 笔试教练界面），
   但这是**新增的呈现面**，评审时应重点核对"净化是否到位、是否只供展示"。
3. **`0029` 未正式收篇**：本次按"议题分离"新开 `0030`，并把 `0029` §7 的未完成项**逐条重判后抄入本篇 §7**
   （其中"确认 zip 是否含 `.git`"是**安全项**，优先级最高，不能因换篇而丢失）。
4. **本分支是"长驻特性分支"，与分支模型默认相反**：`git-workflow.md` 规定短期分支
   **必须在同一次会话内合回 `develop`**，而所有者 2026-10-10 明确要求
   **"后面的这个 AI coding 笔试功能，就专门在那个分支上进行"** ⇒ 本分支**刻意不合回**。
   它与 `bench/nightly` / `bench/data` 属同一类例外（需要长期存在的载体），
   但**尚未写进 ADR-0013 §9 的例外清单** ⇒ 已登记为 §7 ⑭。
   现实影响：`make branch-status` 会**如实把它报成"未合入 `develop`"**——那是**设计如此**，不是遗漏。

## 6. 学到了什么

1. **"快慢"要分层次归因，不能一步跳到"硬件不行"**。同一台机器：裸测 9.4 → 服务默认 2 → 修线程 8 t/s。
   三次读数差 4 倍，而**代码一行没改**。⇒ 遇到"慢"，先把**可测的量**测出来（`llama-bench` 的 tg/pp、
   服务日志的 `n_threads`、"会话内 tg"），再谈结论。
2. **生成速度对线程数是非单调的**（4→9.85、8→8.85、16→7.60、32→5.67）。"核多=快"是 CPU 推理里
   最容易误用的一条直觉；瓶颈是**内存带宽**，不是算力。
3. **"产物对了"不等于"过程可信"**。模型自述的运行输出可以是**没跑过**的。
   ⇒ 一切"它说它验证过"的话都不可当证据；**验收必须独立复跑**（这也是 `verify.sh` 的设计理由）。
4. **安全默认一旦放宽，必须把"适用范围"与"仍然生效的机制"一起写下来**。
   只写"我们把它设成 low 了"，后人只会看到"这里松了"；写上"限定本机 + 这五条仍在拦"，
   后人才能判断"换个场景还能不能这么干"。
5. **复用装配比重写装配便宜**：`exam` 子命令全程**没有**复制一行装配逻辑（连审计失败归因都沿用
   `_Assembly.recorder`），因此 `run` 修一处 bug，`exam` 自动受益。
