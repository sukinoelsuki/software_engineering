## 1. 本阶段目标

所有者 2026-09-26 的指令（两句话，直接决定本议题的范围）：

1. **"带我理解熟悉当前做的产品 demo"**——要知道**各个流程、基本原理、核心技术**，
   且要求"**带我使用产品讲解技术的同时，把核心代码也带我读懂**"；
2. 目的写得很直白：**"这样我就算是把这个产品吃下来了，也才能更好的做后面的 Harness 调教工作"**。

⇒ 本议题的判据因此不是"产出多少代码"，而是**所有者能否独立回答"一次运行发生了什么、
拒绝与失败怎么分、七条核心判据是什么"**。落点是一份可续上的带读材料 + 一次阶段式跑测。

**顺序由所有者选定**：先**跑一遍**（"流程简单、有参照对照着学效率更高"），再讲 R2/R3。
且所有者明确 **R2 与 R3 都要学**——"即使我是在做 Harness，我也不能没有相应的配套的技术基础知识"。

## 2. 关键决策与理由

### 2.1 为什么必须把带读材料落盘（而不是留在对话里）

2026-09-26 凌晨，所有者提示**平台会在 4~6 点强制关闭超过 8 小时的容器** ⇒ 需要重启环境。
按 `ADR-0013` 与 `CODEBUDDY.md` §2 的机制性理由：云环境每次从 `develop` 拉起、
**重启即清空上下文** ⇒ **未落盘的内容下次会话等于不存在**（2026-09-16 已因此丢过一批内容）。

⇒ 落盘不是"顺手整理"，而是**本议题能否继续的前提**。处置：

- 带读内容（产品全景 / 主流程 / 七把钥匙 / 路线图 / 跑测要点）落
  `docs/engineering/product-onboarding-notes.md`；
- **不新建目录**（"新目录必须先有 ADR"）；`docs/engineering/` 已放同类的非规范文档
  （`product-handbook.md` / `product-walkthrough.md` / `post-build-checklist.md`）；
- 该文件**不重抄命令**——命令真源是 `product-handbook.md`，与 `product-walkthrough.md` §0 的分工
  同一条理由：本项目的重复失效模式是"**同一事实两处表述 ⇒ 必然漂移**"。

### 2.2 为什么新开一篇，而不是堆在 0026 里

判据只有一条（`docs/devlog/README.md` 分篇约定）：**议题/阶段的完整性**。

- `0026` 的议题 = "**收尾承接**"（0025 的观察项 + 例行回填），**不是新议题**，其 §7 ③ 已写明
  "主线任务的下一步须所有者指定，代理不得自行选定"；
- 现在所有者**下达了**一个新议题（产品带读 + 跑测），它与"收尾承接"**是两件事**
  ⇒ 按索引的既有先例（每次"新议题 ⇒ 新开一篇"）开 `0027`；
- `0026` §7 的 ②（例行：哈希回填、扩展升级后复跑 `C1`/`C2`/`C7`）**唯一仍有效**，故抄进本篇 §7 ①。

### 2.3 跑测纪律（沿用所有者自己写的 `product-walkthrough.md` §0.2）

四条写死：**一次一个阶段 · 命令由所有者亲自敲 · 输出不符就停下 · 跑测不产仓库改动**。
助手**不得替跑、不得编造输出**——理由是学习场景下"亲眼看到 + 亲自敲"不可由转述替代。

例外（本轮已说明并采用）：`阶段 1` 与 `阶段 2` **都是秒级且不起模型**，而"一次一个阶段"
针对的是 `3/4/5` 这三个长耗时段 ⇒ 两者合批**符合规则意图**，不改变其约束。
