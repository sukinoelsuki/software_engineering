# 开发日志（Devlog）

本目录记录项目的**开发过程**：每个阶段做了什么、为什么这么做、遇到什么问题、学到什么。

> 开发日志与 [ADR](../adr/) 分工不同：
> **ADR 记录"决策"**（只增不改，供追溯）；**开发日志记录"过程"**（按时间演进，供回顾）。
> 开发日志也不是 [CHANGELOG](../../CHANGELOG.md)——后者面向使用者，只写用户可见的变更。
> 与 [学习笔记](../notes/) 的分工：**日志记"过程发生了什么"，笔记记"我学到了什么、想到了什么"**。

---

## 为什么需要开发日志

| 目的 | 说明 |
| --- | --- |
| **过程证据** | 软件工程课程考察的是过程；日志是"过程真实发生"的直接证据 |
| **重拾语境** | 任何人都可能随时中断。日志是**唯一的跨会话记忆**（AI 代理的上下文不持久，环境重启即清空） |
| **活待办载体** | 最新一篇的「§7 下一步」就是当前的任务清单，无需另建 list（见下） |
| **防止重复踩坑** | 记录失败与卡点，避免几周后重犯 |
| **辅助复盘** | 与计划书配合，判断进度是否偏离、计划是否现实 |
| **自我提升** | 记录"学到了什么"，把开发过程转化为能力积累 |

## 分篇约定

**日志必须分篇，不允许全部写在同一个文件里。**

### 唯一判据：议题/阶段的完整性

一篇日志对应**一个完整的议题，或一个开发阶段**。判断标准是一句话：

> 读者能否在**一篇之内**完整看完"这里发生了什么、为什么、结论是什么"？

**议题讲完即收篇。** 既不要为了凑篇幅塞无关内容，
**更不要为了卡行数把一个连贯的议题硬切成两半**。

### 篇幅：软性参考，**不是**切分依据

| 项 | 参考值 |
| --- | --- |
| 单篇行数 | **150 ~ 300 行**较适宜；**300 上下都正常，略超无妨** |
| 单篇覆盖时间 | 约 5 个工作日（提示性，非硬性） |

- **可读性优先**：判断标准是"拿起来能不能顺畅读完、读完能不能理解"，
  而不是"有没有超多少行"。
- 篇幅明显偏长（经验上 > 400 行）**且**议题尚未讲完时，处理顺序是：
  ① 先精简表述 → ② 再按**子议题**拆分。拆出的新篇必须**自成一段可读内容**。
- 命名：`NNNN-YYYY-MM-DD-<slug>.md`，编号四位递增，不复用。

### 收篇与承接

- 议题讲完 → 补"学到了什么"与"下一步"，**新开下一篇**；
  旧篇由此成为**封闭记录**，不再修改。
- **未完成的待办**：新开一篇时，把旧篇 §7 未完成的项**抄进新篇 §7**。
  旧篇 §7 保留原文（作为历史），不做删改。

## 活待办：最新一篇的「§7 下一步」就是唯一的任务清单

**不另建 todo / backlog 文件**——它会立刻与日志脱节，且需要额外维护。

| 场景 | 动作 |
| --- | --- |
| 开工 | 读**最新一篇**的 §7，它就是"接下来该干什么" |
| 完成一项 | 在**当前（最新）篇**的 §7 中**删除**该项（"擦去"），并在 §3 变更记录里写下它已完成的内容与提交哈希 |
| 新增任务 | 直接追加到当前篇 §7 |
| 收篇 | 未完成项抄进新篇 §7（见上） |

于是：**§7 永远是待办，§3 永远是已做**，两者都无需额外维护，也不会互相矛盾。

### §3 与 §7 的写法要求（重要）

- **§3 变更记录是"内容总结"，不是完成项清单。**
  写"完成了什么、为什么、怎么验证的"，读起来应是一段连贯叙述；
  **禁止**写成 `☑ 做了 A` / `☑ 做了 B` 这种流水账式打勾表。
- **§7 是"待办"，不是"愿景"。** 每条应具体到可以立刻动手；
  跨篇继承时要重新判断是否仍然需要，不无脑搬运。

## 重拾语境（新会话 / 中断后的固定动作）

> 目标：**任何时候中断，都能在几分钟内恢复完整语境。**

1. 读本文件的**索引**，找到状态为「进行中」或编号最大的一篇；
2. 读该篇全文——重点看 **§2 关键决策**、**§5 问题与卡点**、**§7 下一步**；
3. 顺着 §7 的引用读对应 ADR / 设计文档 / 调研笔记；
4. 从 §7 的第一项开始动手。

> 这也是把"下一步"写在日志里、而不是记在脑子里的原因：
> **日志就是恢复点。**

## 更新时机

| 时机 | 动作 |
| --- | --- |
| 每次提交 | 在**当前篇**追加一条变更记录（含提交哈希、变更内容、验证方式）；**落盘归记录员 / 团队领导**（`docs/devlog/` 是记录员独占产出域，见 `CODEBUDDY.md` §10.1），**其他角色只负责报告** |
| 一项待办完成 | 从当前篇 §7 删除该项，并在 §3 记录 |
| 完成一个议题 / 阶段 | 收尾当前篇（补"学到了什么"与"下一步"），**新开下一篇** |
| 发生方向性变化 | 记入当前篇的"关键决策"，并链接到对应 ADR/提案 |
| 遇到阻塞或失败 | 立即记录，包括失败原因与当时的判断依据 |

> **原则：日志是"当时"写的，不是事后补的。**
> 禁止事后大规模补写——那样会失真，失去日志最大的价值。

**哈希引用规则（避免"追哈希"死循环）**：

- 日志只能引用**产生它的那笔提交之前**的提交哈希；
- 日志自身的提交哈希**由下一次更新回填**（收篇时一并核齐），
  这样无需为补一个哈希去改写历史（`--amend` 已推送提交是禁止的）；
- 因此篇头「提交」列表出现"最新一条缺自身哈希"是**正常现象**，不是遗漏。

## 单篇结构模板

```markdown
# NNNN. <阶段名称>

- 时间范围：YYYY-MM-DD ~ YYYY-MM-DD
- 状态：进行中 / 已完成
- 关联：Issue #N、ADR-NNNN、提案 NNNN
- 提交：<哈希列表>

## 1. 本阶段目标
## 2. 关键决策与理由
## 3. 变更记录（内容总结，含提交哈希）
## 4. 数据与证据（基准、实测、截图）
## 5. 问题与卡点
## 6. 学到了什么
## 7. 下一步（= 当前活待办清单）
```

> §6「学到了什么」是**线索**，指向 [学习笔记](../notes/)；
> 成体系的经验、方法论与思考写在笔记里，日志只留一句结论 + 链接。
