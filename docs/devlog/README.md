# 开发日志（Devlog）

本目录记录项目的**开发过程**：每个阶段做了什么、为什么这么做、遇到什么问题、学到什么。

> 开发日志与 [ADR](../adr/) 分工不同：
> **ADR 记录"决策"**（只增不改，供追溯）；**开发日志记录"过程"**（按时间演进，供回顾）。
> 开发日志也不是 [CHANGELOG](../../CHANGELOG.md)——后者面向使用者，只写用户可见的变更。

---

## 为什么需要开发日志

| 目的 | 说明 |
| --- | --- |
| **过程证据** | 软件工程课程考察的是过程；日志是"过程真实发生"的直接证据 |
| **防止重复踩坑** | 记录失败与卡点，避免几周后重犯 |
| **辅助复盘** | 与计划书配合，判断进度是否偏离、计划是否现实 |
| **降低上下文成本** | 新会话开始时，读日志即可快速回到状态（对人与 AI 都重要） |
| **自我提升** | 记录"学到了什么"，把开发过程转化为能力积累 |

## 分篇约定（重要）

**日志必须分篇，不允许全部写在同一个文件里。**

### 主判据：按议题/阶段的完整性

一篇日志对应**一个完整的议题，或一个开发阶段**。判断标准是一句话：

> 读者能否在**一篇之内**完整看完"这里发生了什么、为什么、结论是什么"？

**议题讲完即收篇。** 既不要为了凑篇幅塞无关内容，
**也不要为了卡行数把一个连贯的议题硬切成两半**。

### 硬上限（兜底，不是目标）

| 项 | 限制 |
| --- | --- |
| 单篇行数 | **≤ 300 行**（硬上限） |
| 单篇覆盖时间 | **≤ 5 个工作日** |
| 健康篇幅 | 150 ~ 300 行 |

- 命名：`NNNN-YYYY-MM-DD-<slug>.md`，编号四位递增，不复用。
- 达到任一硬上限即**新开一篇**并在索引登记；旧篇不再追加（成为封闭记录）。
- **篇幅接近上限但议题未讲完时**，处理顺序是：
  ① 先精简表述 → ② 再**按子议题拆分**。
  拆出的新篇必须**自成一段可读内容**，不能是上半句在 A 篇、下半句在 B 篇。
- **拆分依据是主题，不是行号。**
- 例外：纯追加性的"待办/下一步"可在下一篇承接，不在旧篇修改。

### 为什么是 300 行

- 这是**兜底阈值**，不是精确目标。作用是防止单文件无限膨胀到几百上千行而失去可读性。
- 300 行中文约 10 KB，可一次读完；作为 AI 上下文约占 6~8K token，成本可控。
- **行数只是代理指标**：真正决定分篇的是"议题是否讲完"。

## 更新时机

| 时机 | 动作 |
| --- | --- |
| 每次提交 | 在**当前篇**追加一条变更记录（含提交哈希、变更内容、验证方式） |
| 完成一个阶段 / 达到容量上限 | 收尾当前篇（补"学到什么"与"下一步"），**新开下一篇** |
| 发生方向性变化 | 记入当前篇的"关键决策"，并链接到对应 ADR/提案 |
| 遇到阻塞或失败 | 立即记录，包括失败原因与当时的判断依据 |

> **原则：日志是"当时"写的，不是事后补的。**
> 禁止事后大规模补写——那样会失真，失去日志最大的价值。

## 单篇结构模板

```markdown
# NNNN. <阶段名称>

- 时间范围：YYYY-MM-DD ~ YYYY-MM-DD
- 状态：进行中 / 已完成
- 关联：Issue #N、ADR-NNNN、提案 NNNN
- 提交：<哈希列表>

## 1. 本阶段目标
## 2. 关键决策与理由
## 3. 变更记录（按时间倒序，含提交哈希）
## 4. 数据与证据（基准、实测、截图）
## 5. 问题与卡点
## 6. 学到了什么
## 7. 下一步
```
