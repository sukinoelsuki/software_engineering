## 2. 关键决策与共识

### 2.1 技术栈定案：Python 单一主语言

项目所有者提出：既然对标 Ollama（**Go**）与 CodeBuddy / Cursor（**TypeScript**），
是否该用 Go 或 TypeScript？经论证后**采纳 Python 单一主语言**，详见
[ADR-0005](../adr/0005-single-primary-language.md)。

| 项 | 决定 | 关键理由 |
| --- | --- | --- |
| 主语言 | **Python ≥ 3.12** | 自研增量（上下文引擎、护栏、评估、检索）**全部落在 Python 生态**；换语言等于放弃唯一的技术优势 |
| 推理后端 | llama.cpp（C++） | 通过 HTTP 调用，**不做语言绑定** |
| Node.js / pnpm | **预装，但非主语言** | 用于 MCP 官方 server、promptfoo、将来可能的 Web UI |
| Go | **不引入** | 其"单二进制分发"优势属于**产品化阶段**问题，本期不是关键需求 |
| Rust / C++ | 本期不引入 | 真正的性能瓶颈由 llama.cpp 承担，编排层不构成瓶颈 |

> **这个决策有明确的可逆性边界**：若 Demo 成功、需真正装进老人手机，
> 届时应**新增 ADR** 评估打包方案（PyInstaller vs 运行时重写为 Go）。
> 本决策不排除该演进路径，只是不在本期支付其成本。

### 2.2 开发环境采用 `.ide/Dockerfile` 定制（单容器模式）

CNB 的平台约定（已通过官方示例源码核实）：

| 文件 | 作用 |
| --- | --- |
| `.ide/Dockerfile` | 构建开发环境镜像 |
| `.ide/settings.json` | VS Code 设置，**必须由 Dockerfile 的 COPY 指令写入镜像** |
| `.cnb.yml` 的 `vscode` 事件 | 声明 `docker.build.dockerfile` 与 **`build.by`** |

**两个硬性约束**：

1. `build.by` 必须列出构建期用到的其它文件（即 `.ide/settings.json`），
   否则构建报错——这是 CNB 的强制要求。
2. 镜像内**安装了 code-server** 才会以**单容器模式**启动；否则退化为双容器模式。

### 2.3 环境内容边界

| 类别 | 内容 | 理由 |
| --- | --- | --- |
| 基础工具 | git + git-lfs、curl/wget、jq、ripgrep、fd、tree、sqlite3、vim、tmux、zsh | 日常开发与调试 |
| 构建工具链 | build-essential、cmake、ninja、pkg-config、libcurl-dev | 编译需要本地构建的 Python 包；构建 llama.cpp |
| **沙箱组件** | **bubblewrap**（主）、**firejail**（备）、nsjail 的构建依赖 | 本项目需要**无需 KVM 的用户态隔离**执行 AI 生成的命令 |
| Python | 3.12 + `uv`（通过 `pip install` 而非 `curl \| sh`，减少远程脚本执行） | 主语言工具链 |
| Node.js | Node 20 + pnpm 9 | 备用工具链（见 2.1） |
| IDE | code-server + 16 个扩展 | 见 2.4 |
| 推理 | **llama.cpp（CPU，源码构建）** | 主推理后端，预装可让 W1 验证立即开始 |

### 2.4 容器相关扩展的选择（回答项目所有者的疑问）

| 扩展 | 是否安装 | 理由 |
| --- | --- | --- |
| `ms-azuretools.vscode-docker` | ✅ **安装** | 镜像/容器/卷管理、Dockerfile 与 compose 语法支持；配合 `.cnb.yml` 中 `services: [docker]` 使用 |
| `ms-vscode-remote.remote-containers` | ❌ **不安装** | 该扩展面向"在**本机 Docker Desktop** 中开发 devcontainer"。我们的环境是**云端 WebIDE**，其自身已运行在容器内，该扩展在此不可用。安装它只会增加噪音 |

> 若后续确实需要，加一行 `code-server --install-extension` 即可。

### 2.5 明确不安装 Android / 移动端工具链

移动端已在 [0003](0003-2026-09-15-单专家调度与上下文迁移.md) 中定为
**"架构约束 + 可行性验证"**，不做 App。且既定的验证路线是 **Termux**
（运行在手机上，不需要在开发机安装 Android SDK / NDK / Gradle）。

因此本期**不安装** Android 工具链——避免为一条尚未确定的路径付出环境成本。

## 4. 数据与证据

### 4.1 CNB 官方示例源码（已克隆核实）

来源：`https://cnb.cool/20210805/custom-vscode`（CNB 官方示例仓库，4 commits）

关键摘录（原文）：

```dockerfile
COPY .ide/settings.json /root/.vscode-server/data/Machine/settings.json
COPY .ide/settings.json /root/.local/share/code-server/Machine/settings.json
```

```yaml
$:
  vscode:
    - docker:
        build:
          dockerfile: .ide/Dockerfile
          by:
            - .ide/settings.json
      services:
        - vscode
        - docker
```

### 4.2 资源配置与免费额度核算

| 项 | 数值 |
| --- | --- |
| 云原生开发-CPU 免费额度 | **1600 核时/月**（月底清零） |
| 本次配置 | `runner.cpus: 8` → 8 核 / 16 GiB |
| 月用量估算 | 8 核 × 8 小时/天 × 22 工作日 = **1408 核时** |
| 结论 | **8 核属于可持续用量**，不会超额度 |

## 5. 问题与卡点

| 编号 | 问题 | 状态 |
| --- | --- | --- |
| V-1 | 首次构建耗时（llama.cpp 源码编译约 5~10 分钟）是否可接受 | **待验证** |
| V-2 | `.cnb.yml` 的 `vscode` 事件挂在 `"**"` 下是否可行 | **待验证**——官方示例用的是 `$`（兜底）。但根据触发规则文档，`$` 仅在**未被任何 glob 命中**时生效，而 `"**"` 命中所有分支，故挂在 `"**"` 下更可靠。若无效则改回 `$` |
| V-3 | `Default Dark Modern` 主题 ID 在所用 code-server 版本中是否存在 | **待验证**——不存在时 VS Code 会回退默认主题 |

| V-5 | 容器内 `bwrap` 能否实际创建用户命名空间（沙箱方案的前置条件） | **待验证**——CNB 容器可能限制 unprivileged user namespaces |
| V-6 | llama.cpp 跟随 master 构建，缺少版本固定 | **已知问题**——待基准测试需要复现时改为固定 release 标签 |

## 6. 学到了什么

1. **文档不一定写全，官方示例源码往往更可靠。**
   文档页里完全没提 `.ide/settings.json` 的落盘路径，示例仓库的 Dockerfile 里却写得很清楚
   （而且写的是 `Machine/` 而非直觉上的 `User/`）。**遇到平台约定，直接拉示例源码。**
2. **平台约束要主动找**：`build.by` 这条"构建期依赖必须显式声明"的硬性要求，
   藏在示例 README 里而非主文档——漏了就是构建失败。
3. **"不做"也是决策**：明确写下"不装 Android 工具链""不装 remote-containers"，
   比装一堆用不上的东西更有价值——**每个未安装的组件都省下了一次未来的困惑**。
