## 2. 关键决策与共识

### 2.1 技术栈定案：Python 单一主语言

项目所有者提出：既然对标 Ollama（**Go**）与 CodeBuddy / Cursor（**TypeScript**），
是否该用 Go 或 TypeScript？经论证后**采纳 Python 单一主语言**，详见
[ADR-0005](../adr/0005-single-primary-language.md)。

| 项 | 决定 | 关键理由 |
| --- | --- | --- |
| 主语言 | **Python ≥ 3.12** | 自研增量（上下文引擎、护栏、评估、检索）**全部落在 Python 生态**；换语言等于放弃唯一的技术优势 |
| 推理后端 | llama.cpp（C++） | 通过 HTTP 调用，**不做语言绑定** |
| Node.js / pnpm | **预装，但非主语言** | 用于 MCP 官方 server、promptfoo、将来可能的 Web UI |
| Go | **不引入** | 其"单二进制分发"优势属于**产品化阶段**问题，本期不是关键需求 |
| Rust / C++ | 本期不引入 | 真正的性能瓶颈由 llama.cpp 承担，编排层不构成瓶颈 |

> **这个决策有明确的可逆性边界**：若 Demo 成功、需真正装进老人手机，
> 届时应**新增 ADR** 评估打包方案（PyInstaller vs 运行时重写为 Go）。
> 本决策不排除该演进路径，只是不在本期支付其成本。

### 2.2 开发环境采用 `.ide/Dockerfile` 定制（单容器模式）

CNB 的平台约定（已通过官方示例源码核实）：

| 文件 | 作用 |
| --- | --- |
| `.ide/Dockerfile` | 构建开发环境镜像 |
| `.ide/settings.json` | VS Code 设置，**必须由 Dockerfile 的 COPY 指令写入镜像** |
| `.cnb.yml` 的 `vscode` 事件 | 声明 `docker.build.dockerfile` 与 **`build.by`** |

**两个硬性约束**：

1. `build.by` 必须列出构建期用到的其它文件（即 `.ide/settings.json`），
   否则构建报错——这是 CNB 的强制要求。
2. 镜像内**安装了 code-server** 才会以**单容器模式**启动；否则退化为双容器模式。

### 2.4.1 CodeBuddy 补装（环境重建后发现遗漏）

首版镜像**漏装了 CodeBuddy**——而它在本项目中承担**主要的智能开发**工作。
漏装的影响不只是"少一个插件"，而是两处独立缺失：

| 形态 | 组件 | 漏装后果 |
| --- | --- | --- |
| CLI | `@tencent-ai/codebuddy-code`（提供 `codebuddy` 命令） | CNB 云开发入口页中的 **CodeBuddy Web 入口被静默隐藏**（不报错，直接不显示） |
| VS Code 扩展 | `Tencent-Cloud.coding-copilot` | WebIDE 内没有代码补全与 AI 对话面板 |

处理：两者都装。CLI 固定版本 `2.151.0`（≥ CNB 要求的 `2.137.0`），
扩展按 ID 从 Open VSX 安装，并在**镜像自检阶段硬校验**
（`codebuddy --version` 与 `code-server --list-extensions | grep -qix Tencent-Cloud.coding-copilot`），
确保"漏装"这类问题在构建期暴露，而不是等进入环境后才发现。

### 2.4.2 GitLens 移除（决策）

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 安装/保留 GitLens | ❌ 移除 | 核心增益（作者归属、多人协作视图、Launchpad、Workspaces）在**单人单作者**仓库中几乎无价值；体积与启动开销却是真实的；新版本还会持续推送 GitKraken 账号登录 |
| 内置 SCM + Git Graph | ✅ 采用 | 暂存/提交/分支切换/diff/文件历史由 VS Code 内置 Source Control（含内置 Source Control Graph）覆盖；`mhutchie.git-graph` 提供更顺手的提交图，纯本地、无需登录 |

补充事实（避免后续重复纠结）：**不存在名为 "GitLens Inspect" 的独立扩展**——
Open VSX 与 Marketplace 均无此包，它是 GitLens 自带的 Inspect 面板，
装了 GitLens 就有、不装就一起没有，因此**不需要单独决策**。

### 2.4.3 顺带修复：工程基线的 lint 门禁一直是红的

环境重建后第一次执行 `make check`，发现**develop 上的门禁从未真正绿过**：
`make check` 在 lint 阶段失败，报 6 处 `RUF001` / `RUF002`（歧义 Unicode 字符），
来源是基线包与冒烟测试的**中文** docstring 与断言消息中的全角括号、逗号、冒号：

| 文件 | 位置 |
| --- | --- |
| `src/agent_sec_perf/__init__.py` | docstring 中的 `（Phase 0）` 与 `，见 ...` |
| `tests/unit/test_package.py` | docstring 中的 `：`；断言消息中的两处 `，` |

**排查结论：不是版本漂移。** 用 `ruff 0.6.9`（pre-commit 固定版本）与 `ruff 0.16.7`
（`uv sync` 安装版本）分别扫描，报错**完全一致**（同为 6 处），
说明该缺陷自「工具链基线」提交起就存在。
本地钩子只在被改动的文件上运行，因此一直没暴露；该提交能进仓库，
说明当时钩子未生效或被绕过（二者无法从历史判定）。
其余门禁阶段均正常：`mypy --strict`、`pytest`、`bandit`、`pip-audit` 全部通过。

当轮处理：先把这 6 处措辞改写为「句号分隔」的形式，让门禁恢复绿色（**不改动任何 lint 规则**）。

**长期方案（已确认并实施）**：项目所有者确认采纳候选 ① —— 在 `[tool.ruff.lint]` 中配置
`allowed-confusables` **字符白名单**，放行中文全角标点，而不是关闭整条规则。
实施前先用探针实测「究竟哪些字符会被报」（见 §4.3），实施后做反弹测试，
确认**西里尔字母 `а` 与全角拉丁字母 `ＡＢ` 仍被拦截**——同形字检测没有被削弱。
已改写的 6 处措辞保留（两种写法都是通顺的中文），不回改。

### 2.4.4 门禁与 JSONC 的冲突：排除 settings.json 的 `check-json` 校验

`.ide/settings.json` 是 VS Code 设置文件，按编辑器与 CNB 平台约定使用 **JSONC**（允许注释），
因此**必然**无法通过 pre-commit 的 `check-json` 钩子。
该文件在 HEAD 上即如此，说明它当初进仓库时同样绕过了钩子。

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 为 `check-json` 排除该文件 | ✅ **采纳** | 改动最小。JSONC 的合法性由 VS Code 在运行时校验，此处静态校验收益极低 |
| 改写为严格 JSON（去注释） | ❌ 未采纳 | 会丢失该文件内已有的说明性注释，与项目「留痕」的风格相悖 |
| 更换支持 JSONC 的钩子 | ❌ 未采纳 | 需引入新的第三方钩子依赖，收益不抵成本 |

> ⚠️ **风险与补偿**：排除后该文件不再受静态 JSON 校验保护。若出现语法错误，
> 表现为**设置静默不生效**（VS Code 会提示解析失败，但不会阻止环境启动）。
> 补偿措施：把它登记为**改动后必须人工确认**的检查点，写入
> [`post-build-checklist`](../engineering/post-build-checklist.md) 第 1 步。

### 2.4.5 依赖锁定：把 `uv.lock` 纳入版本管理

`uv.lock` 由 `make setup` 生成，但此前**未被版本管理**——本地与 CI 每次都重新解析依赖版本，
同一份 `pyproject.toml` 可能装出不同版本的工具链，复现性无从保证。
本次排查门禁时恰好碰到这个风险的两面：`ruff>=0.6` 解析到 **0.16.7**，
而 pre-commit 里钉的是 **0.6.9**，两个版本并存（好在实测结论一致，见 §2.4.3）。

现将其纳入版本管理。锁定的关键版本（2026-09-15）：

| 工具 | 版本 | 工具 | 版本 |
| --- | --- | --- | --- |
| ruff | 0.16.7 | pytest | 9.1.1 |
| mypy | 2.3.1 | pytest-cov | 7.1.0 |
| bandit | 1.9.4 | pytest-xdist | 3.8.0 |
| pip-audit | 2.10.1 | commitizen | 4.18.1 |
| pre-commit | 4.6.2 | | |

约定：**任何依赖变更必须同步提交 `uv.lock`**（`uv sync` 会自动更新它），
否则本地与 CI 会再次分叉。

### 2.5 明确不安装 Android / 移动端工具链

移动端已在 [0003](0003-2026-09-15-单专家调度与上下文迁移.md) 中定为
**"架构约束 + 可行性验证"**，不做 App。且既定的验证路线是 **Termux**
（运行在手机上，不需要在开发机安装 Android SDK / NDK / Gradle）。

因此本期**不安装** Android 工具链——避免为一条尚未确定的路径付出环境成本。

### 4.3 RUF 探针：哪些中文标点会被报（2026-09-15 实测）

目的：**避免凭猜测写 `allowed-confusables` 白名单**。探针构造：一行 docstring、
一个含全角逗号的字符串、一个含**西里尔字母 `а`（U+0430）** 的字符串、
一个含**全角拉丁字母 `ＡＢ`** 的字符串，以及一行含全角冒号的注释。

| 字符 | RUF 是否报错 | 处置 |
| --- | --- | --- |
| `，`（全角逗号） | ✅ 报（RUF001 / RUF002） | 列入白名单 |
| `：`（全角冒号） | ✅ 报（RUF002 / RUF003） | 列入白名单 |
| `；` `？` `！` | ✅ 报 | 列入白名单 |
| `（` `）`  | ✅ 报 | 列入白名单 |
| `‘`（左单引号） | ✅ 报（被判为反引号） | 列入白名单 |
| `。`（句号）`、`（顿号）`《》` `“”` | ❌ **不报** | 一并列入白名单，表达「中文标点整体允许」的意图 |
| **`а` 西里尔小写 a（U+0430）** | ✅ 报 | **必须保持被报**——反弹测试确认仍被拦截 |
| **`ＡＢ` 全角拉丁字母** | ✅ 报 | 同上，确认检测未被削弱 |

实施后的反弹测试：同一探针的报错数由 **11 处降到 3 处**，
剩下的 3 处恰为西里尔 `а` 与全角 `Ａ`、`Ｂ`——即"放行中文标点"与"保留同形字检测"同时成立。

复现命令（探针文件写在 `/tmp`，不进仓库）：

```bash
printf '"""%s"""\n\n_A = "%s"\n_B = "p\xd0\xb0ckage"\n_C = "\xef\xbc\xa1\xef\xbc\xa2"\n# spot%scheck\n' \
  '，。、：；？！（）《》“”‘' '版本号应为 MAJOR.MINOR.PATCH，实际为 1' '：' > /tmp/ruf_probe.py
uv run ruff check --no-cache --stdin-filename probe.py - < /tmp/ruf_probe.py
```

## 6. 学到了什么

1. **文档不一定写全，官方示例源码往往更可靠。**
   文档页里完全没提 `.ide/settings.json` 的落盘路径，示例仓库的 Dockerfile 里却写得很清楚
   （而且写的是 `Machine/` 而非直觉上的 `User/`）。**遇到平台约定，直接拉示例源码。**
2. **平台约束要主动找**：`build.by` 这条"构建期依赖必须显式声明"的硬性要求，
   藏在示例 README 里而非主文档——漏了就是构建失败。
3. **"不做"也是决策**：明确写下"不装 Android 工具链""不装 remote-containers"，
   比装一堆用不上的东西更有价值——**每个未安装的组件都省下了一次未来的困惑**。
