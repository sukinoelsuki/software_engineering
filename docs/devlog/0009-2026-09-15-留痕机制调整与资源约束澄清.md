## 2. 关键决策与理由

### 2.1 学习笔记独立成目录（→ ADR-0009）

项目已有 ADR（决策）、devlog（过程）、research（课题结论），但**没有一处承载
"学到了什么、想到了什么"**——这类内容会被过程流水淹没，且无法按主题重读。
故新建 [`docs/notes/`](../notes/)，按**主题**命名（不用日期编号，因为它的价值在于被反复重读），
配索引，并把"维护学习笔记"写入 [`CODEBUDDY.md`](../../CODEBUDDY.md) /
[`AGENTS.md`](../../AGENTS.md) 的强制义务——**只靠文档里"约定"不够，必须是每个会话都要履行的基准线**。

首批写入三条本次会话已获得的经验：
[探针方法论](../notes/probe-methodology.md)、
[隔离机制分类](../notes/isolation-mechanisms.md)、
[复现性与门禁](../notes/reproducibility-and-gates.md)。

### 2.2 活待办 = 最新一篇 devlog 的「§7 下一步」，不另建 list

比较过两种做法：

| 方案 | 问题 |
| --- | --- |
| 单独维护 todo / backlog 文件 | 会立刻与日志脱节，且需要额外维护；中断后要读两处才敢开工 |
| **最新篇 devlog 的 §7 即任务清单** | ✅ 采纳：**§7 永远是待办、§3 永远是已做**，两者零额外维护 |

配套规则（已写入 [`docs/devlog/README.md`](README.md)）：

- 开工 → 读**最新一篇**的 §7；
- 完成一项 → 从当前篇 §7 **删除**该项，并在 §3 记录内容与提交哈希（"擦去"）；
- 收篇 → 未完成项抄进新篇，旧篇 §7 保留原文作为历史；
- **§3 是内容总结，禁止写成打勾清单**。

同时新增「**重拾语境**」四步流程：索引找最新篇 → 读全文（§2/§5/§7）→ 顺引用读 ADR → 从 §7 第一项动手。

### 2.3 行数从"硬上限"降为"软性参考"

项目所有者明确：**行数是软要求，重点是内容连贯、随时拿起来能读懂**。
故修订为：150 ~ 300 行较适宜，**300 上下都正常、略超无妨**；
唯一的分篇依据仍是"议题是否讲完"。真正的兜底是"可读性"，不是某个数字。

> 这已是该数字的**第三次修订**（200 → 300 硬上限 → 软参考）。
> 每次修订的原因都记在 [`docs/devlog/README.md`](README.md) 的修订记录里——
> 数字本身没有实证依据，**实践才是判据**。

## 4. 数据与证据

### 4.1 资源约束的**精确**事实（本轮实测，修正了此前过窄的判断）

| 项 | 事实 | 判定 |
| --- | --- | --- |
| cgroup 版本（开发容器自身） | **v1**（命名控制器） | — |
| 开发容器内存上限 | `memory.limit_in_bytes = 17179869184` = **16 GiB** | ✅ **强制执行** |
| 开发容器 CPU 配额 | `cpu.cfs_quota_us = 800000` = **8 核** | ✅ **强制执行** |
| 内置 docker 模式 | **rootless**，`Cgroup Version: 1`，**`Cgroup Driver: none`** | ⚠️ 不做 cgroup 管理 |
| 子容器 cgroup 类限制 | `--memory=64m` 下逐页写满 **300 MB** 仍成功；`--pids-limit=16` 下起满 **50** 进程 | ❌ **无效** |
| 子容器命名空间类隔离 | `--read-only` 拒绝写、`--network=none` 拒绝出站 | ✅ 有效 |
| 自行创建子 cgroup | `/sys/fs/cgroup/memory` 归 `nobody:nogroup`、模式 `555`、无子组目录 | ❌ 无法委派 |

### 4.2 三个误解的澄清（回答项目所有者的提问）

| 疑问 | 结论 |
| --- | --- |
| "是否意味着没法自由使用 16 GiB 内存？" | **反了**。16 GiB 是**被强制执行的我们的上限**，可以用满。受限的只是"**无法给自己起的子容器设上限**"。实测 llama-server 常驻约 5 GiB，**我们连三分之一都没用到** |
| "导致端侧模型能力下降、能掌控的上下文受限？" | **无关**。上下文上限由**内存总量 + 模型/KV 大小**决定，与 cgroup 无关。真正的上下文约束在**目标设备（8 GiB）**，不在开发机 |
| "这与开发中的性能关系很大？" | 性能瓶颈是 **CPU 算力**（实测生成 ~16.5 tok/s、prefill ~67 tok/s），cgroup **完全不影响算力** |

**真正的"枷锁"只有两条**：① **8 核 CPU 算力**；② **开发机 16 GiB vs 目标设备 8 GiB 的不一致**。
而这两条**恰是本项目的核心命题**（"低资源环境下让弱模型能用"）——
所以在 8 核/16 GiB 上开发是**宽松**而非受限，**不应**为"更自由"而取消限制，
而应**主动测量降级曲线**。

## 6. 学到了什么

本阶段的三条经验已成体系，写在 [学习笔记](../notes/) 中（日志只留线索）：

1. **退出码 0 ≠ 控制生效**；探针必须能**区分竞争解释**，并且必须包含"必须失败"的用例
   → [probe-methodology.md](../notes/probe-methodology.md)；
2. 隔离能力应按**机制类别**（命名空间 / cgroup / setrlimit）划分，而非按工具；**资源限制一律用 setrlimit**
   → [isolation-mechanisms.md](../notes/isolation-mechanisms.md)；
3. **证据不能为通过检查而变形**（换载体，不改内容）；**构建期失败默认是静默的**，必须显式自检
   → [reproducibility-and-gates.md](../notes/reproducibility-and-gates.md)。

另有一条关于**判断**本身的教训：本阶段我先给出"沙箱完全不可用"（过窄），
又给出"内存限制生效"（误判），随后又给出"内存限制失效"（结论对、推理不牢）。
**三次都在同一个方向上出错——把单一观测当成充分证据。**
这正是把学习笔记立为基准线任务的理由。
