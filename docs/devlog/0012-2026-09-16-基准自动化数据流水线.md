## 1. 本阶段目标

之前只有两个数据点（09-15 三档基线、09-16 重建后复跑），无法回答三件事：
**环境是否漂移**、**判据是否可靠**、**改动是否真的更好**。本阶段把它变成一条可维护的流水线：

1. 脚手架随仓库走（不再放在 `/root/w1`：环境一重建就丢）；
2. 定时 + 推送 + 手动三种触发，结果自动发布到数据分支，**任意分支可 `git fetch` 取数**；
3. 数据自带**环境指纹与协议版本**，跨轮比较只在可比条件下进行；
4. 项目所有者给定的资源边界（17600 核时/月，需克制使用）转成明确预算与纪律。

## 2. 关键决策与理由

### 2.1 "并行"不是这个场景的加速手段

基准测量必须独占 CPU：同机并发会让**所有**吞吐数字失去可比性
（09-16 实测到同机同参数的 prefill 极差已有 8.4%）。因此：

- **不并行**：基准测量串行 + 独占，用一把 `lock` 保证同一时刻只有一轮；
- **可并行**：与 CPU 独占无关的部分（判定、聚合、报告）；
- CNB 上"并行"的真实代价：`docker.volumes` **不支持跨节点缓存**，每个 runner 都要
  重新拉镜像 ⇒ 并行是线性成本，不是免费加速。

### 2.2 三个轴，各用各的预算

| 轴 | 取数方式 | 回答什么 |
| --- | --- | --- |
| 同夜重复 | 每档 R 次（夜轮 10、深跑 20） | 测量噪声（极差） |
| 跨夜序列 | 同一协议冻结后逐日累积 | 环境漂移 |
| 参数维度 | 周一深跑额外跑线程 4 轮 | "核数变少时该降哪一档"（REQ-PERF-05/06） |

余量不用于无脑加重复：噪声只随 √n 下降，边际收益递减；余量投向**扩任务集**。

### 2.3 数据分支 + 死循环防护

`bench/nightly`（代码，crontab 挂载点）与 `bench/data`（机器产出，**不被任何流水线触发**）。
若数据写回代码分支，CI 会再次触发 push 流水线 → 死循环；靠 `ifModify` 过滤很脆。

### 2.4 协议版本是可比性的锚点

`PROTOCOL_VERSION`（`bench-v2`）+ 比较签名（协议、ctx、threads、max_tokens、tiers）。
任一口径变化都必须提版本，否则"改进"与"口径变了"无法区分。

### 2.5 每次重复重启服务进程（本次试跑换来的）

第一次试跑得到一条 **极差 326%** 的 prefill 序列。查日志（不猜）后发现：
同一进程内重复发送同一提示词时，服务端复用了该槽位的 KV 前缀，
日志给出的是 `prompt eval time = 34.89 ms / 1 tokens`——**那不是 prefill 测量**，
而是缓存命中的 1 个 token。9 条 prefill 行里后 6 条都是 `1 tokens`。

对策是结构性的，不是加过滤：

1. **每次重复重启服务进程**（KV 为空 ⇒ R 次重复是真正的独立测量）；
2. prefill 行必须通过 **token 数闸门**（≥ 32）才计入统计；
3. 每次重复一份日志，**行数严格匹配**（3 条），不符即拒绝该重复并告警。

附带好处：加载耗时现在有 R 个样本（可报极差），不再是一次性的数。

## 3. 变更记录

**基准子系统（d66b6af，`src/agent_sec_perf/bench/`）**：按数据流拆成
`protocol`（协议/任务集/参数校验）→ `assets`（清单摘要真源）→ `proc`（唯一进程启动点，
隔离与资源上限）→ `runner`（服务端生命周期与计时采集）→ `evaluate`（客观判定）→
`stats`（重复测量汇总）→ `store`（schema 校验与落盘）→ `report`（人读报告与可比性判定）
→ `rounds`（编排与 CLI）。夹具（4 个）以 `.txt` 入库：它们**故意**含缺陷且无类型标注，
以 `.py` 保存会被 ruff/mypy"修好"，等于篡改被测对象。

**判定口径的两处修正**（对应 `notes/evaluation-pitfalls.md`）：

1. 变异测试判据由"退出码非零"改为"**至少一个断言失败**"（退出码是复合信号，
   "测试没跑起来"也会非零）；
2. 变异点必须命中，否则**主动报错**而不是把"没变异"当成"杀不死变异体"。

**三条 make 目标 + 一个发布脚本**：`bench-round` / `bench-verify-assets` / `bench-publish`
（CI 与本地同一条命令）；`scripts/bench/publish.sh` 负责"校验 → 数据分支提交 → 推送"，
只推数据分支、禁 force、凭据经 credential helper 传入（不写入 URL/config）。

**流水线与触发**：`bench/nightly` 上挂 `push`（S/M × R=3）、
`crontab: 0 4 * * 2-6,0`（三档 × R=10）、`crontab: 0 4 * * 1`（R=20 + 线程 4 对照）、
`web_trigger_bench`（手动）；发布放在 `endStages`，因此测量失败也会落盘**部分数据**
（标记 `partial`）。

**发布链路上踩到的三个坑**（都已修，且都不是"改配置躲过去"）：

| 坑 | 症状 | 处置 |
| --- | --- | --- |
| `.gitignore` 的 `*.log` / `artifacts/` | 数据分支只收到 JSON，**日志与产物被丢**——而日志是性能数字的原件 | 末尾加 `!bench/**` 显式豁免；本地演练目录 `.bench-data/` 单独忽略 |
| 提交触发代码钩子 | `ruff` 去"格式化"模型产物，且 6 处 F841 直接让提交失败 | 数据提交用空 `hooksPath`（**不跑代码钩子**）；理由与影响登记在 ADR-0014 §2.9 |
| 平台签名助手不可用 | `gpg failed to sign the data`，提交流程中断 | 先按平台默认签名提交；失败则**显式**降级为未签名并打印原因（不静默降级） |

**数据分支的"保真"与"可审阅"（6c4c0d2）**：`bench/**` 原本整体标为
`-text -diff`，结果是连 JSON 与报告在数据分支上也变成了不可 diff 的二进制——
而数据分支同样要能被审阅。收窄为只对 `logs/` 与 `artifacts/` 做字节保真
（**证据**不得被换行归一化改写），结构化数据与报告保持文本。

**文档**：ADR-0014（决策、备选方案、安全边界、豁免登记）、运行手册
（数据怎么读、三种触发、改协议的姿势、首夜验证清单、排障表）、SRS 新增
`REQ-PERF-07/08`、CHANGELOG 同步。

**第一次真实运行就撞上"sh 不认 pipefail"（见 §4 证据）**：`bench-push` 的
`verify` 阶段第一行退出码 2——`sh: 1: set: Illegal option -o pipefail`。
阶段脚本由镜像的 `/bin/sh` 执行，而开发镜像是 **Debian 12**（dash `0.5.12-2`，
不支持 `pipefail`），门禁镜像 `python:3.12` 已经漂到 **Debian 13**
（dash `0.5.12-12`，支持）⇒ **同一份配置在两条流水线上语义不同**。
更糟的是 `endStages` 里我写的是 `set -uo pipefail`（没有 `-e`）——它同样中止整段脚本，
于是数据发布根本没执行，外部看像"什么都没发生"。

三处处置：①全部改为 `set -eu`；②把门禁镜像由浮动标签钉到 `python:3.12-bookworm`
（与开发镜像同源，消除本地/CI 分叉）；③把两条规则写成机器检查
（`tests/unit/test_cnb_config.py`）并写进 `.cnb.yml` 头部与手册排障表——
"约定只写在注释里" 就会再次被绕过。

修复提交为 `647e7db`，已推送 `develop` 与 `bench/nightly`（`f053b18..647e7db`）；
修复后的 `push` 流水线（`cnb-prv-1k2ld45ul`）随即触发。

**首轮的真实结果：测量走通了，发布没走通**。`set -eu` 修好后整条流水线跑完
（`make setup` → `make check` → S/M × R=3 即时轮，354 s、0.79 核时、`status=complete`），
但 `endStages` 的 `git push origin HEAD:bench/data` 报
`error: The destination you provided is not a full refname`。
根因已用**假远端复现**（不是猜的）：远端存在**带斜杠**的分支（`bench/nightly`）时，
短写法 `HEAD:bench/data` 会被 git 拒绝，必须写全限定名 `HEAD:refs/heads/bench/data`；
换成全限定名后输出 `* [new branch] HEAD -> bench/data`。

更要记的是**它为什么差点被漏掉**：我在 `endStages` 写了 `|| echo "[warn] …"`，
把发布失败降级成警告 ⇒ 构建显示 `success`、数据一条也没有。
"**绿着但没数据**"是最难发现的一类失败，比直接报错糟得多（我自己犯了这条）。
两处都已改：refspec 用全限定名；发布不再吞错误（失败即把构建标红）。

**跨环境可比性（同一份日志里暴露的第三个问题）**：CI runner 与开发容器的吞吐差
**25% 以上**（数据见 §4），而当时的比较签名只含协议与参数、**不含机器标识**
⇒ 两个环境的数字会被当成同一条序列。已把 CPU 型号纳入比较签名
（`env.runner.cpu_model`）并加测试钉住。

**发布链路验证通过（`73f0f23` 之后的 `cnb-d4h-1k2leskv7`）**：`bench/data` 分支已创建
（首个提交 `639260e`），内容与设计一致——`index.json`（签名含 CPU 型号、核时 0.766）、
`latest.md`、`daily/2026-09-16/` 下的三个 JSON + `report.md` + **6 份服务端日志** +
**18 份模型产物**。这同时确认了三件事：refspec 修复生效、`.gitignore` 的 `!bench/**`
豁免生效（日志与产物确实进了版本库）、数据提交没有触发代码钩子改写产物。

**首夜（2026-09-17 04:00）的完整结果：测量成功、发布失败，两个缺陷都在发布脚本里。**
定时任务正常触发（04:00:10 检出 `bench/nightly` @ `73f0f23`），`make setup` 与三档 × R=10
的测量全部跑完（2966 s、约 **6.59 核时**、`status=complete`，每档有效速率样本 10/10），
却在最后一步 `make bench-publish` 报 `Error 141`（= 128 + 13，**SIGPIPE**）：

1. **`git show --stat … | head -30`**：`set -o pipefail` 下 head 读完 30 行即退出，
   git 后续写入收到 SIGPIPE，整条管道被判为非零 ⇒ `set -e` 中止脚本。
   **它只在输出超过截断行数时出现**——09-16 只有 6 个文件（输出 7 行）故不暴露，
   09-17 有 135 个文件必现。构建日志里的输出恰好停在第 30 行，与复现一致（§4）。
2. **整体替换数据子目录**：`rm -rf "${WORKTREE}/bench"` + `cp -a .bench-data bench`，
   而 CI 的数据根目录只有本轮 ⇒ 提交 diff 里真实出现了
   `delete mode bench/daily/2026-09-16/{capability.json,perf.json,report.md}` 与全部
   `server.log`，`index.json` 同样会退化成一条。也就是说**这次若推送成功，09-16 的数据
   会被一并删掉**，数据分支永远只剩最新一轮——"跨夜序列"根本建立不起来。

修复（`63e6888`）：

1. 发布改为**合并**：只写本轮 `daily/<日期>/`（目录名加日期白名单校验，避免路径构造问题），
   索引交给新增的 `store.merge_index_files` + `rounds --merge-into` 按 `round_id` 并入，
   `latest.md` 覆盖为最新一轮；
2. 去掉"管道接 `head`"的写法：先落盘再截断；签名降级路径改用 `awk`。
   两条规则写进 `tests/unit/test_cnb_config.py`——**该检查当场又抓到第二处**
   `sed … | head -3`（在签名降级的错误路径上；CI 上签名成功，所以那条路从未走到），
   说明"把约定做成机器检查"比写进文档有效。

**手册的一处更正**：§6.1 给的"用 `/-/build/logs?sourceRef=…` 查 crontab 构建"在开发
工作区会话里**查不到别人的构建**（不带过滤 `total=1`、加过滤 `total=0`、
`swagger.json` 返回 `errcode 16`）⇒ 不能把"查不到"当作"没触发"的证据。

  能力判定：t1 三档 0/10；t2 三档 10/10；t3 S/M 10/10、**L 0/10**。
  S/M 与 09-16 的值（prefill 92.10 / 51.09）同量级 ⇒ 跨夜序列的第一步站得住。
- **SIGPIPE 的复现（本地，非推测）**：
  `bash -c 'set -euo pipefail; git --no-pager log --stat | head -5'` → **rc=141**；
  改成"先落盘再 head" → rc=0。
  另注：`seq 1 100 | head -30` **不触发**——输出一次写完即进入管道缓冲，生产者没有第二次
  写入机会。这解释了为什么小输出场景不会暴露这个坑。
- **合并修复的验证**：`bash -n scripts/bench/publish.sh` 通过；
  `merge_into_published` 端到端（已发布索引含 `2026-09-16-push`、本轮含
  `2026-09-17-nightly`）→ 合并结果为 `['2026-09-16-push', '2026-09-17-nightly']`，
  `latest.md` 被本轮覆盖；`make check` 全绿（67 项单测，本轮新增 8 项）。

## 5. 问题与卡点

- **定时任务已验证注册且会触发**（2026-09-17 04:00:10）⇒ §7 里"首夜尚未发生"的悬念关闭。
- **crontab 事件的令牌权限仍未验证**：首夜在 `git show … | head` 处就以 SIGPIPE（141）
  中止，**根本没走到 `git push`**（见 §3）。因此"crontab 令牌是否有 `repo-code:rw`"
  依旧是未知项，处置预案（改挂可信的 `push` 事件）保留。
- **发布缺陷导致首夜数据不可恢复**：提交建在临时 worktree 里，脚本的 `trap cleanup`
  已把它删除；服务端日志、模型产物、报告与三个 JSON 全都没有了，6.59 核时只换回
  构建日志里的数值（§4）。结构性教训：**"先提交、再推送"之间的窗口里，数据只存在于
  临时目录**——后续步骤一失败就全丢。改进方向见 §7。
- **平台侧可观测性不足**："夜轮缺席"在无人值守时没有告警来源：网页构建历史要靠人看，
  而 `/-/build/logs` 在开发工作区会话里只返回自己这次构建（§3 的更正）。
- **保留期清理在 CI 上不生效**：`prune_daily` 跑在只有本轮的数据根上，历史轮次不在那里。
  合并修复之后仍需把清理挪到数据分支的工作副本上（§7）。
- **数据分支结构的一处冗余**：首次创建时 worktree 取自 `bench/nightly` 的 HEAD，
  因此首个提交携带了**整棵代码树**（188 个文件）。无害但不整洁——publish 只写 `bench/`，
  代码部分是**冻结快照**、不会漂移。收紧需要把数据分支改成 orphan 分支
  （= 重写远端分支），**需所有者批准**，列入 §7。
- **定时任务的确认方式（2026-09-16 决策）**：平台**没有**查询定时任务列表的能力
  （swagger 里只有 `POST .../crontab/sync/{branch}`，且不返回列表；文档是"配置即管理"）。
  可选手段是临时加一条零副作用自检键（`*/10` + `echo`，不挂锁）让它真的触发一次；
  但**每推送一次 `bench/nightly` 都会额外触发一轮约 20 分钟的基准测试**，
  为验证一件"最迟次日必然揭晓"的事付这个成本不划算 ⇒ **决定跳过自检，以 04:00 首夜为准**。
  自检方案保留在手册 §6.1 作为诊断手段：首夜若未触发，加自检键即可区分
  "注册机制问题"与"表达式本身问题"。
- **温度 0 让能力重复没有方差**：同一任务的多次产出几乎逐字相同（438/438/438 tokens），
  因此"重复"对能力指标只提供稳定性证据，不提供方差。**能力的精度只能靠扩任务集**，
  这是下一步的主要投资方向。
- **残余安全风险**（已登记 ADR-0014 §2.8）：评测在非特权 uid + 清空环境 + rlimit 下执行
  模型产物，但**无法断网**（本平台命名空间不可用）。理论逃逸路径仍可读到宿主令牌
  （短时、限本仓库）。进一步硬化需把"执行"与"发布"拆成两条流水线。
- **本地 GPG 签名不可用**：数据提交只能降级为未签名；若平台在流水线里可用则会自动签名。

## 6. 学到了什么

一句话：**在重复测量里，最容易被忽视的干扰项是"被测系统自身的状态"**——
不是机器、不是模型，而是服务端的 KV 缓存。它让同一份提示词的第二次"测量"
根本不再是同一件事，而日志会给出一个看起来正常的数字（`1 tokens` 也是"速率"）。
完整论证见 [`notes/evaluation-pitfalls.md`](../notes/evaluation-pitfalls.md) 情形五。

第二条（工程侧）：**把约定做成机器检查，比写进文档有效得多**。本轮把
"子进程只能从封装层启动""`src/` 里不许有 `print`"变成了测试
（`tests/unit/test_bench_encapsulation.py`）；这三条约定以前只在规则文档里。
