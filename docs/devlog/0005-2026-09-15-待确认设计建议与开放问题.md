## 0. 本篇的用途

讨论中产生了不少**尚未拍板的设计建议与开放问题**。此前它们散落在各篇日志与对话中，
容易遗漏。本篇把它们集中成一份**清单**，用途有三：

1. **不丢失**——AI 代理提出的建议同样需要被记录与评审，而不是只留在对话里；
2. **可跟踪**——每条都有明确状态（待定 / 采纳 / 否决）；
3. **防止重复提出**——被否决的建议保留理由，避免反复讨论同一个点。

> 本清单后续将并入开发计划书（待建立）。
> **确认规则**：采纳 → 落成 SRS 需求或 ADR；否决 → 记录理由并保留，不得重复提出。

| **S-2** | **代码优先原则**：能用确定性代码做的，不要交给模型 | 把模型自由度收窄到"在 2~3 个候选中选 1 个"，远比要求 1.5B 模型"从 20 个专家里挑一个"可靠；这直接决定小模型是否够用 | [0004 §3 R-1](0004-2026-09-15-产品本质与能力包定位.md) | 待定 |
| **S-3** | **标签体系是产品决策界面**，并增加「**能力边界前置声明**」——专家名片中明确写出"不擅长什么" | 在用户提问**之前**设定预期，把"能力边界感知"从内部机制变成**用户可见的产品元素**；可能比任何技术护栏都更能防止高危提问 | [0004 §2.4](0004-2026-09-15-产品本质与能力包定位.md) | 待定 |
| **S-4** | **权限判定与工具执行分离** | 参考 Anthropic 在 Claude Code 中的做法：把权限执行与模型推理**彻底解耦**，安全上更可靠 | [0004 §2.3](0004-2026-09-15-产品本质与能力包定位.md) | 待定 |
| **S-5** | 主 Agent 选型 **1.5B ~ 3B**，核心 KPI 为**路由准确率** | 它的职责是路由、格式转换与汇总，不是深度推理；要"可靠 + 快"而非"聪明"。其体积直接决定留给专家的内存 | [0003 §7](0003-2026-09-15-单专家调度与上下文迁移.md) | 待定 |
| **S-6** | 性能指标采用「**单任务切换次数**」而非「单次加载耗时」 | 成本 ≈ 切换次数 × 上下文长度（每次切换都要重新 prefill）；且切换次数**由自己的调度策略决定**，加载速度取决于 llama.cpp。前者可控，后者不可控 | [0003 §6](0003-2026-09-15-单专家调度与上下文迁移.md) | 待定 |
| **S-7** | 单专家调度四条规则：**R1 单一权威上下文 / R2 专家无状态 / R3 受控回填 / R4 粘性路由** | R2+R3 解决**上下文污染**（专家幻觉不得写入主历史）；R4 解决**切换次数** | [0003 §4](0003-2026-09-15-单专家调度与上下文迁移.md) | 待定 |
| **S-8** | **demo 范围收窄**：只用 3~5 个"专家"，其中至少一个允许用云端模型替代 | 2~3 个月只能证明**机制**（路由准、切换可控、污染隔离、标签可理解），不能证明**规模** | [0004 §5](0004-2026-09-15-产品本质与能力包定位.md) | 待定 |
| **S-9** | SRS 在设计稳定后**集中修订至 v0.2.0** | 现行 SRS 成型于"本地编码代理"阶段，已与讨论结果明显不一致 | [0004 §4](0004-2026-09-15-产品本质与能力包定位.md) | 待定 |
| **S-10** | 把"**没有工具 = 高质量文档片段；有工具 = 能干活的人**"作为判据，衡量 Agent 能力是否真的落地 | 这是区分"检索能力"与"检索知识"的唯一标准——没有工具，产品就退化为会说话的文档库 | 本篇补充 | 待定 |

## 3. 确认方式

1. 项目所有者对每条标注：**采纳 / 否决 / 待定**；
2. **采纳** → 落成 SRS 需求条目，或写成 ADR（视影响面而定）；
3. **否决** → 在本篇记录理由并保留（防止重复提出同一建议）；
4. 确认结果更新到 `docs/devlog/README.md` 索引与本篇状态列。
