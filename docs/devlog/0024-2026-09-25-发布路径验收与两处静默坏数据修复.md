## 2. 关键决策与理由

### 2.1 照原计划跑会静默删掉当天的另一轮 ⇒ 先修缺陷（所有者裁定方案 A）

**证据（三条，缺一不可）**：

1. `rounds.py` 的每日目录按**日期**命名：`daily_dir = data_root / DAILY_DIRNAME / date`，
   而索引条目按 **`round_id = <日期>-<标签>`** 区分轮次；
2. `publish.sh` 对目标目录是"先 `rm -rf` 再 `cp -a`"（其注释写明判据是"**绝不删除历史轮次**"）；
3. 数据分支上**当天已有一轮**：`daily/2026-09-25/`（**124 个文件，其中 120 份是服务端日志与模型产物原件**），
   索引里对应 `2026-09-25-nightly`。

⇒ 同日第二轮会**删掉第一轮的原件**，而索引里第一轮的 `report` 仍指向该目录
⇒ **索引指向错报告、原件永久丢失**。此前从未触发，只因"每天最多一轮"这一偶然事实。

三个候选（A 目录按轮次 id / B 只加拒绝覆盖守卫 / C 接受覆盖）与推荐过程见 [ADR-0026](../adr/0026-benchmark-round-directory-keyed-by-round-id.md)；
**所有者 2026-09-25 裁定方案 A**。

### 2.2 触发的两个技术约束（都是本次实测才明确）

| # | 约束 | 后果 |
| --- | --- | --- |
| 1 | **`--sha` 不能跨分支**：git-clone 只 fetch `--branch` 指定的 ref，再 `git checkout <sha>` ⇒ `fatal: reference is not a tree`（退出码 128） | 想验证"某个提交"必须让**环境分支快进到它**（引用级操作，不新增提交） |
| 2 | **环境分支的引用不会自己前进** | `test/amd64-8` 停在 `006ff4f`（落后 develop 3 笔）⇒ 若不察觉，**测的是旧代码**，而日志里看不出来 |

⇒ 推论：**触发前必须核对"环境分支指向的提交 = 被测代码"**。这条目前**没有任何检查会报警**
（本次靠人工发现），已登记为 §7 的待办。

### 2.3 第二处缺陷：能力读数恒为 0%（流水线漏了 `make setup`）

发布验收跑通后核对数据，发现本轮 `capability.round_pass_rate = 0.0`（历史同档为 0.6667）。
**不是模型能力问题**，`capability.json` 里每条判定都写着：

```text
"mypy_rc": 1, "mypy_tail": "/workspace/.venv/bin/python: No module named mypy"
```

根因：能力判定要跑 `mypy --strict`，而 `mypy` 属于 `[project.optional-dependencies].dev`、
**只有 `make setup` 会装**；`api_trigger_bench` 的 `run` 阶段直接跑 `make bench`。
归档的 `bench/nightly` 各段**都有** `prepare: make setup` ⇒ 是重构（`423f659`）**漏掉了这一步**。

⚠️ 它的失效方式是**静默的**：四道可信闸门**全部通过**（它们管 KV / 计时行 / 暴露面 / schema，
不管评测工具链）、构建**全绿**、报告 §4 还写着"无告警"。
⇒ 这就是本仓库反复强调的"**坏数据比没有数据更难发现**"的又一实例。

### 2.4 用**同一个 label** 重跑，原地替换坏轮次

`round_id` 是幂等键：`append_index` 按 `round_id` 去重、`publish.sh` 只 `rm -rf` 本轮自己的目录
⇒ 用同一 label 重跑会**原地替换**那一条坏数据（而不是新增一条）。因此不必手改数据分支
（E 类：`bench/data` 只由跑测脚本写）。

## 5. 问题与卡点

1. **环境分支引用陈旧没有任何检查会报警**（§2.2 第 2 条）。本次靠人工核对发现；
   若未发现，会"**用旧代码测新修复**"并给出**看起来正常**的结果——这类失效最难察觉。
2. `bench/data` 的 `fetch` 输出里出现 `(forced update)`，**是浅克隆的假象**：
   发布提交的父提交正是上一轮的发布提交（§4.1）⇒ 是快进推送。
   ⚠️ 判定依据必须用**父提交关系**，不能用 fetch 的那行提示。
3. **当前有 3 个云原生开发环境在 `running`**（2 个 `develop` + 1 个 `main`），非本会话产生
   ⇒ 按 `D-C1`（环境生命周期优先）属**成本观测点**：8 核 × 存活时长是账单主要来源，待所有者确认归属。
4. **资产 `A-4`（代码与数据完整性）没有对应的 `T-*` 威胁条目**：本次的覆盖缺陷正是打在 `A-4` 上。
   是否新增条目**待所有者裁决**（ADR-0026 §6 已登记，未擅自扩威胁模型）。
5. 本次为验证发布路径而跑的规模是 **S × R=3**（不是完整一轮），因此它在索引里是一条**低价值基线**；
   它**可以被同 label 的完整一轮原地替换**（§2.4）。
6. 第 3 次触发是一次**操作失误**（推送命令被 zsh 的参数修饰符吃掉了 `refs` 的 `r`，
   且 `| tail` 掩盖了退出码）⇒ 已用 `stop-build` 止损；教训见 §6 第 5 条。

## 6. 学到了什么

1. **"先验证再花钱"有具体形态**：本次若直接照 §7 的计划跑一次（约 1.7 核时），
   损失是**不可恢复的**（120 份原件 + 索引错链）。而前置核对（读三处代码 + 读数据分支现状）
   的成本是**零**。⇒ 触发类动作前，"这次动作会**写到**哪里、那里**现在有什么**"应当成为固定一问。
2. **机器检查会把注释当证据 ⇒ 恒过。** 本次 `block.find("make setup")` 命中了注释里的同名字符串，
   检查在**删掉命令后照样通过**。变异探针是唯一能发现它的手段
   （与 0014 的"反静默过度豁免"、0023 的"检查换靶"同源：**检查必须被真的失效一次**）。
3. **迁移配置时，"搬了什么"记得住，"漏了什么"记不住。** 定位 `make setup` 缺失靠的是
   **归档的旧流水线**（`archived-ci-benchmark-pipelines.md` 里每一段都有 `prepare`）
   ⇒ 归档不只是留痕，它是**迁移时的对照物**。
4. **引用陈旧 ≠ 代码陈旧。** `test/<slug>` 零提交的代价是"它指向的提交不会自己前进"；
   而"环境必须从与 `develop` 一致的提交拉起"这一前提**不会自动成立**，必须显式快进。
5. **一行命令里的管道会掩盖退出码。** `git push … | tail` 的退出码是 `tail` 的 ⇒ 失败被吞掉、
   后续动作照常执行。要止损就得**显式回显 `$?`**；而 `$SHA:refs/...` 在 zsh 下会被当作
   参数修饰符（`$SHA:r`）解析 ⇒ 写 `HEAD:refs/...` 或用 `${SHA}:refs/...`。
6. **幂等键（`round_id`）是纠错的手段**：同一 label 重跑可以**原地替换**坏数据，
   不必去动数据分支（那属 E 类禁止项）。
