## 1. 本阶段目标

在方向冻结（低资源能力感知智能体运行时）之后，进一步厘清**产品的核心结构**与**模型策略**，
把"综合智能体"从一句话拆解成可设计、可实现的结构。

---

## 2. 关键决策与共识

### 2.1 主 Agent 的职责被明确定义为"通用 + 路由"

| 结论 | 说明 |
| --- | --- |
| 主 Agent 不追求专精 | 只需可靠完成**简单通用任务** |
| **主 Agent 的核心职责是模型选择与切换** | 即"模型路由"：根据任务选择最合适的模型（通用 / 领域专家 / 云端） |
| 模型能力信息由**人工提供标签**，不由模型自主辨别 | 见 2.2 —— 这是成本最低、最可靠的做法 |

> 这一条把"模型能力探测"从一个**高成本的研究问题**降级为一个**可管理的数据问题**：
> 不需要让模型自己搞清自己会什么，只需要在模型注册表里为每个模型写好标签。

### 2.2 模型注册表（Model Registry）成为核心数据结构

模型选择的前提是模型元数据。需要维护的字段：

| 字段 | 用途 |
| --- | --- |
| 领域标签 | 医学 / 法律 / 代码 / 数学 / 通用 … |
| 能力档位 | 用于选择 Harness 配置（见 SRS §4.1） |
| 体积与量化档 | 用于内存预算校验与加载决策 |
| 硬件要求 | CPU / GPU / 最低内存 |
| 许可证与来源 | 合规与审计 |
| 本地/云端 | 路由决策 |

### 2.3 产品价值锚点：受限环境下的"参考"，而非"代决"

项目所有者明确的价值表述（已采纳）：

> 不是代替用户做决断，而是在用户无助的时候提供一个可参考的"专家"，
> 帮助其做出更好的决策，**最终决策权始终在用户手中**。

**场景判断**：咨询、交谈、学习类场景通常是**长过程且私密**的，
因此端侧（本地推理）在**隐私、成本、可用性**三个维度上优于云端 API，
而"比 API 慢一些"的时间成本在这些场景中不构成障碍。

**推论**：产品的竞争维度不是"响应速度"，而是**在无网络/受限条件下仍能提供一个可用的专家**。

### 2.4 双轨 Harness 策略

| 场景 | Harness 策略 |
| --- | --- |
| 联网 + 强模型 | 复用主流开源 Harness 的工程形态，**对齐 Cursor / CodeBuddy 类产品的能力与体验** |
| 离线 / 受限 + 小模型 | **自研**——这是本项目的主战场（目标场景） |

> 这条策略把 SRS §4.1 的论点向前推了一步：
> 不只是"Harness 适配模型能力"，而是 **Harness 适配（模型能力 × 场景 × 网络状态）**。
> 同一套产品在两种环境下的 Harness 形态应当不同。

### 2.5 移动端策略确认

采纳"架构约束 + 可行性验证"方案（不做 App）：

- 所有核心逻辑不依赖 x86 专有指令、不依赖 GPU、不依赖 KVM；
- 接口层与交互层分离；
- 逐步做一次 Termux 可行性验证（若 CLI 可在 Termux 运行，"移动端可用"即已被证明）。

## 3. 数据与证据

### 3.1 模型体积核算（纠正一处估算偏差）

**原估算**：4B 模型 < 1 GB。
**实测核算**（Q4_K_M 量化，约 4.5 bit/权重）：

```text
文件体积 ≈ 参数量 × 4.5 bit ÷ 8 ≈ 参数量 × 0.56 字节
常驻内存 ≈ 文件体积 × 1.3 ~ 1.6（含 KV Cache 与框架开销）
```

| 参数量 | GGUF 文件体积（Q4_K_M） | 常驻内存（估算） |
| --- | --- | --- |
| 0.6B | ≈ 0.4 GB | ≈ 0.6 GB |
| 1.5B | ≈ 1.0 GB | ≈ 1.5 GB |
| **3B** | **≈ 1.9 GB** | **≈ 2.8 GB** |
| **4B** | **≈ 2.4 GB** | **≈ 3.5 GB** |
| 7B | ≈ 4.4 GB | ≈ 6.4 GB |
| 8B | ≈ 4.9 GB | ≈ 7.2 GB |

**结论**：4B 模型约为 **2.4 GB**（不是 1 GB 以下）；"< 1 GB"对应的是 **1.5B 级**模型。

**但原判断的结论仍然成立，只是瓶颈不同**：

| 维度 | 判断 |
| --- | --- |
| 存储 | 10 个专家 × 2.4 GB ≈ **24 GB**，手机（128~256 GB）与 PC 均可容纳 → **不是瓶颈** |
| **内存** | 同时只能常驻 1~2 个模型 → **这是真正的瓶颈** |
| **切换成本** | 每次切换需重新加载（数秒级），冷启动有代价 → **这是本产品独有的、可量化的性能问题** |

> 由此产生一个重要的设计方向：**快速模型切换**（mmap 复用页缓存、模型预热与钉住、
> 避免重复加载）。这把"多专家"从概念变成了一个具体的、可测量的工程命题。

### 3.2 领域专精模型现状（事实核查）

| 观察 | 证据 |
| --- | --- |
| 专精模型**确实已存在**，且已有 4B 级 | MedGemma 1.5 4B（Google，医疗多模态，基于 Gemma 3）—— 仓库 `google-health/medgemma` 已核验存在 |
| 领域专精是 2026 年公认趋势 | Gartner 将 domain-specific language models 列为 2026 趋势；法律/医疗/金融均有专门模型 |
| 小模型能力提升快 | 公开横评显示 4B~9B 级模型已能超过前代 30B+ 模型 |

**结论**：项目所有者的"多专家端侧共存"设想**有事实基础**，
但当前 1~4B 级专精模型在其垂直领域的绝对水平仍需逐领域核实，不能一概而论。

### 3.3 模型路由的既有工作

| 项目 | 说明 |
| --- | --- |
| RouteLLM | 按查询难度与成本阈值在强弱模型间路由，支持本地模型 |
| 各类 LLM Router / Gateway | 多为**云侧、按成本/质量路由**，不针对"端侧多专家 + 受限环境"场景 |

**判断**：通用模型路由已有成熟工作可借鉴，但**面向端侧多专家、受内存与切换成本约束的路由**
缺少现成方案 → 是可做差异化的点（**【待验证】**，实施前需再核对竞品）。

## 4. 问题与卡点

| 问题 | 状态 | 说明 |
| --- | --- | --- |
| **多专家结果分歧如何处理** | **待设计** | 多个专家模型对同一问题给出不同答案时，系统应如何处理？（初步倾向：**显式呈现分歧与置信度**，而不是隐藏矛盾、输出单一答案） |
| 分支成本（模型下载与存储管理） | 待设计 | 何时下载、如何淘汰、如何管理磁盘占用 |
| 切换成本的量化基线 | 未测 | 需在 W1 一并测量"加载耗时 / 内存峰值 / 冷启动 vs 热切换" |
| 专精模型的绝对能力水平 | 未核实 | 需逐领域抽样验证，不能只看宣传 |
| 主 Agent 本身的能力下限 | 未测 | 若 4B 主 Agent 连"选对模型"都做不到，则需退化为**规则路由 + 用户确认** |

## 5. 学到了什么

1. **约束的"位置"比约束的"大小"更重要**——存储不是瓶颈（24 GB 很小），
   但内存与切换成本是。识别出真正的瓶颈，才找到了可量化的性能主线。
2. **把研究问题降级为工程问题是一种重要的能力**——"让模型自知能力"很难，
   但"给模型打标签"很容易；后者同样能实现产品目标。**能简化的设计就是好设计。**
3. **产品定位必须能回答"为什么是它而不是云端 API"**——
   本次讨论给出的答案是"隐私 + 成本 + 无网可用"，且承认"比 API 慢"不是问题。
   这个诚实的定位比"又快又好又便宜"要坚实得多。
