## 1. 本阶段目标

一次普通的"重建开发环境"暴露了两组被掩盖的问题，本阶段把它们一次性了结：

1. **默认开发环境构建失败**（第 17 步，退出码 1）——先让它能构建，否则后续所有
   依赖该环境的实验都无从谈起；
2. **旧分支 `chore/env-verification` 与 develop 分叉**：该分支的工作在 develop 上被
   重做并扩展后经 PR #2 合入；本分支在远端又做了一次"合并 develop 并解决冲突"
   （`7741c75`），6 个冲突文件一律取 develop 一侧。需要查清**这样取舍是否丢了东西**，
   把仍可用的内容收回来；
3. 由此引出的第三个问题：**我们的分支协作模式是否有问题**（决策项见 §2.3、§7）；
4. **重建一次把它验证掉**：修复是否真的生效，只能由"销毁 → 重建 → 按清单逐项复核"证明
   ——只改 Dockerfile 不等于环境变好（结果见 §3、§4）。

## 2. 关键决策与理由

### 2.1 冲突取舍的判据是"内容"，不是"文件"

合并提交 `7741c75` 的说明自称"无 PR 分支独有内容丢失（develop 为超集）"，
但**这个结论没有被验证过**——它只说明了"取了 develop 一侧"，没有说明另一侧有什么。

核对方式是把旧分支的 12 个独有提交（`git log --oneline develop..e2b0594`）逐项对照
develop 现状，结论是**丢了三类内容**：

| 丢失项 | 性质 | 处理 |
| --- | --- | --- |
| llama.cpp 版本固定（V-6，commit `69eb250`） | 可复现性前提 | 回收（4c29bea） |
| 清单第 6/7 步：重启后验证清单 + DSpark 实验步骤（135 行实测命令与判据） | 旧分支独有章节 | 回收并按 develop 现状适配（8a2c631） |
| `docs/learning/0002`、`0003` 两篇笔记 | 因目录重命名被静默删除 | 迁入 `notes/` 并改写（a544a0a） |
| 旧分支 devlog 0008 §8「重启前任务交接」 | 已被 0010 §7 与 research 文档覆盖 | **不回收**（避免两处事实分叉） |

判断"是否丢失"的关键：**树相等不等于内容无损**。`git diff c849953 7741c75` 为空
（合并结果树 == develop），而这恰恰是丢失的证据——所有"合并是否成立"的检查
（能合、树一致、无冲突标记、链接校验）**都会给出绿灯**。
`git cherry -v` 同样无效：12 个提交全标 `+`，但对重命名/重写过的文档，
`+` 既可能是"丢了"也可能是"改写了"。详见
[`notes/conflict-resolution-and-branch-hygiene.md`](../notes/conflict-resolution-and-branch-hygiene.md)。

### 2.2 构建修复：改 Dockerfile，而不是给脚本加 fallback

失败信息：

```text
#21 0.594 [assets][ERROR] 找不到清单文件：/tmp/assets/assets/models.txt
#21 ERROR: process "/bin/sh -c set -eux; bash /tmp/assets/fetch-assets.sh models /opt/models" ... exit code: 1
Dockerfile:236
```

根因是**两侧对目录布局的约定不一致**：`fetch-assets.sh` 用"脚本所在目录 + `/assets`"
解析清单（`ASSETS_DIR`），而 Dockerfile 把脚本与清单一起 `COPY` 进 `/tmp/assets/`，
脚本遂去找 `/tmp/assets/assets/`。该缺陷自资产预置引入（`0bc000c`）即存在，
此前未触发重建所以没暴露——**它一直都在**。

两个候选修法：

| 方案 | 代价 |
| --- | --- |
| A. 改 Dockerfile：镜像内复刻仓库 `.ide/` 结构（脚本 `/tmp/ide/`，清单 `/tmp/ide/assets/`） | 改 3 处 COPY + 4 处调用；脚本契约保持不变，本地与镜像行为一致 |
| B. 改脚本：`assets/` 不存在时回退到脚本所在目录 | 多一个隐式分支就多一处"静默取错"的可能；与 fail-secure 原则相悖 |

选 A：脚本的布局契约保持单一、显式，且**本地跑脚本与镜像里跑脚本走同一条路径**，
这在排障时价值很大。

### 2.3 分支协作模式：病灶是"机制"，不是"记性"

项目所有者提出的两个候选：① 在 develop 拉起的环境里提醒合并（甚至自动合并）；
② 取消 develop 的保护，直接在 develop 上开发。

我的判断是**两者都要，但主次不同**：

- 单人开发、且**每次云环境都从 develop 拉起** ⇒ develop 事实上已经是工作主干；
  此时"保护 develop"带来的收益（防误提交）远小于它带来的成本
  （工作留在分支上 → 下次会话不可见 → 被重做 → 冲突）。
- 但只有提醒机制不够：**提醒依赖有人在环境里看到它**，而环境是重启即清空的。
  真正兜底的是把"未合入分支 / 开放 PR"做成**启动自检**的输出之一。

推荐方案（待项目所有者确认后落 ADR）：

1. `main` **保持保护**（发布线，SemVer 标签）；
2. `develop` **取消"禁止直推"改为工作主干**，但仍要求 Conventional Commits
   与 `make check` 全绿（这两条由 pre-commit 与 CI 保证，不依赖分支保护）；
3. 短期分支只用于**隔离实验（`exp/`）与需要评审的大改动**，且**必须当次会话内合回**；
4. 新增"分支卫生"自检（列出未合入 develop 的分支与开放 PR），挂到开发环境
   启动与 CI；未合入的分支写进最新一篇 devlog 的 §7。

## 3. 变更记录

**构建可重建（eea145e）**：把镜像内的资产目录改为复刻仓库 `.ide/` 的结构，
脚本 `/tmp/ide/`、清单 `/tmp/ide/assets/`，并同步 references、benchmarks 的 COPY
与自检中的 `verify` 调用；同时在 Dockerfile 里写明这条约束的由来，
避免以后被"顺手改回平铺"。缓存语义不变（脚本仍在模型下载层之前）。

**回收 V-6（4c29bea）**：llama.cpp 由"跟随 master"改回固定 commit
`69eb250670f471586fcec69caacd3c014aefb185`，用 `init + fetch <完整 SHA> + checkout`
并即时断言 HEAD；这是 W1 与三档（S/M/L）实测数据所绑定的构建，
可复现性是性能主线的前提。

**回收清单第 6/7 步（8a2c631）**：恢复"重启后验证清单"与"DSpark 投机解码实验"，
并按 develop 现状适配——模型位置改为镜像预置的 `/opt/models`、校验改用
`fetch-assets.sh verify`（摘要真源指向 `.ide/assets/*.txt`，不抄数值）、
性能复跑口径改为与三档基线一致的**服务端计时**（`llama-bench` 与服务端计时
不可比这一点已显式写明）、内部引用改为重命名后的路径。

**回收两篇笔记（a544a0a）**：`docs/learning/0002`、`0003` 迁入 `notes/`，
改为主题命名、补齐"来源/关联"与"对项目的约束"，修正指向重命名文档的链接，
并登记索引。其中"思考模式与 token 预算"是 `finish_reason=length` 且空内容
= 预算耗尽这一判定纪律的依据，已由清单 §6.5 引用。

**修复第 7 步构建失败（71b8fff）**：llama.cpp 段的版本断言误写成 `$$(git ...)`——
`RUN` 由 shell 执行，`$$` 展开为 shell PID、命令替换不执行，待比较的字符串变成
`"<PID>(git -C /opt/llama.cpp rev-parse HEAD)"`，断言恒定失败，`set -e` 下以退出码 1
中止构建（耗时 2m19s）。改为 `$(git ...)`，并把该写法的约束写进 Dockerfile 注释
（`$$` 只在 docker-compose.yml 这类先做变量替换的文件里才需要转义），
CHANGELOG 同步补一条记录。附带核对：`fetch-assets.sh` 里的同类克隆逻辑用的是
正确的 `$(...)`，不受影响。

**新增冲突复盘笔记（18ce9ca）**：把"取舍按文件、丢失按内容"这条教训与本次的
证据（提交哈希、文件行号）落成可复用的约束。

**分支模式改造（6031bc3、fd5a45e、51e6b86）**：落 [ADR-0013](../adr/0013-branch-model-for-solo-dev.md)——
`develop` 改为工作主干（取消直推限制，`main` 保持保护）；新增
`scripts/check-branch-hygiene.sh` 与 `make branch-status`，挂到开发环境启动
（`vscode` 事件的一个 stage）与 push 流水线，**只报告不阻断**；pre-commit 的
`no-commit-to-branch` 收窄为只保护 `main`；流程文档与 Agent 准则同步，
并新增"含哈希引用的分支一律 merge commit"这条规则（网页端默认即 merge，
与 devlog 的哈希引用相容）。脚本本身只读、不使用凭据、不输出远端 URL，
无法判定时记为"未知"而非"干净"（`--strict` 下按失败处理）。

**重建后验证（7eab785）**：环境重建完成后按
[`post-build-checklist`](../engineering/post-build-checklist.md) §6 逐项执行，
结论是**镜像侧的三处修复全部生效**：`llama-server --version` 报
`0.4.1-dev (build 1, commit 69eb250)`（V-6）、扩展列表有 `ms-pyright.pyright` 且无
`pylance`（V-7）、4 个模型与 3 个基准文件的 sha256 与 `.ide/assets/*.txt` 逐位一致（V-9）；
工程侧 `make setup && make check` 全绿、`make branch-status` 报"未合入：0 处"。
三档基准复跑（S 档额外重复 2 次）表明**环境与基线可比**：常驻内存三档逐位一致，
吞吐差异落在同会话重复测量的极差之内。唯一挂起项是 V-1（首次构建耗时）——
本轮同样没有留下"销毁时刻 ↔ 可用时刻"的配对记录，如实记为**未测得**，
并给出容器内可得的构建期下界与下次的正确测法。

同时修正两条被数据顶出来的既有结论（证据见 §4）：

1. `> 10%` 这个基准判据**不能靠单次采样执行**——S 档 prefill 三次为
   108.69 / 117.77 / 116.16 tok/s，极差 8.4%，第一次是被单个请求（95.11 tok/s）拉低的平均值；
2. `.ide/settings.json` 的**生效文件也会被平台后置改写**（`workbench.colorTheme` →
   `One Dark Modern`、`extensions.autoUpdate` → `"off"`）⇒ **"改了文件" ≠ "设置生效"**。

**测量脚手架的重建（无提交）**：上一轮的测量脚本与任务夹具只存在于 `/root/w1`
（仓库之外——为了避免 GB 级产物入库），环境重建即丢失。本次从归档附录
[`reports/2026-09-15-w1/HARNESS.md`](../research/reports/2026-09-15-w1/HARNESS.md) 与
[`reports/2026-09-15-tier-comparison/HARNESS.md`](../research/reports/2026-09-15-tier-comparison/HARNESS.md)
**逐字还原**出 5 个夹具 + 2 个脚本后才得以复跑。这验证了"逐字归档"这条恢复路径有效，
但也暴露出**每次重建都要手工还原**的重复成本（登记到 §7）。

## 4. 数据与证据

- 构建失败原文：第 17 步 `[assets][ERROR] 找不到清单文件：/tmp/assets/assets/models.txt`，
  `Dockerfile:236`，退出码 1（构建耗时 4m19s）。
- 修复验证：按新布局落地脚本与三份清单后执行 `fetch-assets.sh plan`，
  清单全部正确解析（4 个模型 / 3 个基准 / 9 个参考仓库），退出码 0；
  `grep -rn "/tmp/assets" .ide/` 仅剩说明该坑的注释行。
- 冲突证据：`git diff c849953 7741c75` 为空；`git log --oneline develop..e2b0594`
  列出 12 个独有提交；`git cherry -v develop e2b0594` 全为 `+`。
- 第二次构建失败原文：`Dockerfile:184`（llama.cpp 段，第 7 步），退出码 1，耗时 2m19s。
- 根因验证：本地 `sh -c 'test "$$(echo x)" = "x"'` 退出码 1，同式的 `$(...)` 版本退出码 0；
  按 SHA 浅取 llama.cpp（9s / 37 MB）后 `rev-parse HEAD` =
  `69eb250670f471586fcec69caacd3c014aefb185`，与固定值一致 ⇒ 失败在断言写法，不在取码方式。
- 顺带核对（避免下一次重建再炸）：9 个参考仓库的固定提交逐个经 GitHub API 确认存在（全部 200）。
  值得先查的理由是——参考资料克隆排在 GB 级模型下载**之后**，SHA 若错，代价是 20+ 分钟。
- **未验证项**：当前环境是回退镜像（无 `make`、无 `cmake`、无 `llama-server`），
  `make check` 与 llama.cpp 编译都无法在此复现；本次改动只涉及 `.ide/Dockerfile`、
  `CHANGELOG.md` 与本篇，不触及 `src/` 与 `tests/`，故不影响 ruff / mypy / pytest 结论。
  llama.cpp 能否在 CNB 构建机上编译通过，仍需重建环境时确认。
- V-6 丢失证据：develop 的 `.ide/Dockerfile` 第 177 行仍为
  `git clone --depth 1 https://github.com/ggml-org/llama.cpp /opt/llama.cpp`
  （对应旧分支 `db42ab8` 的修复）。
- 清单第 6/7 步丢失证据：合并后 `grep "重启后\|DSpark" docs/engineering/post-build-checklist.md`

  加载差 0%/−20.4%/−11.8%。

- S 档同会话重复 3 次（同参数、同提示词）：

  | 次数 | 加载 | prefill | 生成 |

- 能力复核（§6.5，MiniCPM5-2B，`-c 8192`，`max_tokens` 256）：

  ③ 同一任务不关思考 → `stop`、`content` 仍为合法 JSON、`reasoning` 106 字符（未吃光预算）。
- V-14 槽位口径：未指定 `-np` 时服务端为 `n_slots = 4, n_ctx_slot = 8192, kv_unified = 'true'`。
- V-1 未测得的替代证据（构建期下界）：镜像内文件写入时刻 02:11:13（`/root/.config`）→
  02:13:54（`llama-server`）→ 02:14:27~02:18:07（4 个模型）→ 02:19:17（基准文件），

## 6. 学到了什么

一句话：**合并冲突里，最危险的不是冲突本身，而是"合并成功"这个信号本身**——
树相等、无冲突标记、链接校验全绿，都检查不出另一侧被丢掉的内容。
完整论证与约束见
[`notes/conflict-resolution-and-branch-hygiene.md`](../notes/conflict-resolution-and-branch-hygiene.md)。

另一条（第二次构建失败）：**`$$` 是对"会做变量替换的层"的转义，不是 shell 语法**。
Dockerfile 的 `RUN` 直接交给 shell，`$(...)` 就够；写成 `$$(...)` 反而把命令替换
变成了 PID 拼接。它在 `set -e` 下表现为"退出码 1"，与编译失败无法区分——
**错误信息本身会误导排查方向**，所以定位只能靠可复现的最小验证，不能靠读报错。

第三条（本轮复跑）：**判据的可靠性取决于采样次数，而不是阈值定得严不严。**
S 档 prefill 三次为 108.69 / 117.77 / 116.16 tok/s——单次测量与"10% 阈值"同量级，
只跑一次就会得出"环境退化 8.7%"这种看似有据、实则错误的结论。
可复用的顺序是：**先问"这个指标跨会话可比吗"，再问"差了多少"**——
与存储/调度无关的指标（常驻内存）才适合跨会话比较；含 I/O 的指标（加载耗时）
只能同会话内比较；其余指标至少要重复到能报出极差。
