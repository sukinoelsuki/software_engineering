## 2. 关键决策与理由

### 2.1 远端发布动作的执行分工：**只保留「合并」为所有者动作**（所有者 2026-09-19 指令）

所有者原话：

> 「我当前仓库没看到 pr，这个也需要我自己提交吗？后面我需要自己打 tag？
> 我觉得除了我去合并的操作，其它都是可以直接交给你来做的。」

**裁决**：

| 动作 | 谁执行 | 为什么 |
| --- | --- | --- |
| **合并到 `main`** | **恒为所有者** | 唯一"把开发线变成**发布事实**"的动作；`main` 又受平台保护 |
| 开 PR（`develop` → `main`） | 代理可代办 | 可回退（关掉即可），且不改任何分支 |
| 在 `main` 上打带注释标签 | 代理可代办 | 可回退（删标签即撤销）；**必须在合并之后**（它引用发布节点） |
| 把 `main` 回合 `develop` | 代理可代办 | 快进，不改内容 |

⚠️ **边界（不得外推）**：这**不改变 `A~F` 分级本身**——`main` 的任何写入**仍属 B 类**。
放开的只是"**谁执行一个已获准的发布动作**"，**不是**"代理可以自行决定发布"：
**发布决策（何时发、发哪个版本）仍由里程碑台账（`pyproject.toml`）+ 所有者确认承担。**

**为什么必须留这一笔**：分工改变若不落盘，文档就会继续宣称"打标签是所有者动作"，
而实际由代理执行——这正是本项目反复抓的失效模式（`ADR-0013` 的三处表述、`A-16` 的
`type` 集合、`A-17` 的版本语义，同一形状）。故本次按「规则变更的联动更新」**一次改齐 5 处**：
`ADR-0019`（新增 §5.7 + 修订 §5.3/§5.6 + 修订记录）、`git-workflow.md` §5.3、
`.codebuddy/rules/git-workflow/RULE.mdc`、`CODEBUDDY.md` §3、`AGENTS.md` §3。

- **事后补正**：推送后立即在 HEAD（此时工作树已干净）复跑 `make check` ⇒ **全绿**
  ⇒ 被推上去的状态**确实是我想要的绿**，但**这是运气，不是流程保证**。
- **一般性结论（值得带走）**：**`git push` 作用于"当时的 HEAD"，不作用于"我复核的那个哈希"**。
  ⇒ 共享分支上并行开发时，**必须**在复核与推送之间做**一次冻结**或**一次哈希相等性断言**
  （`git rev-parse HEAD` 与已复核哈希相等；不等则按推送后的 HEAD 补一次复核）。
  本轮按后者补正，代价是多跑一次门禁；若当时那位成员恰好落了一笔**红**的，**远端会先红后修**。

**（f）收口后的三条更正（如实记录，含领导自身的一处转述不完整）**

1. **成员自报的 `--amend`：判定"不违规"，但它与 `push` 竞态是同一族**。
   `verifier-security` 主动报出——末笔 `1a4a7a5` 曾用 `git commit --amend` **补写 `回报：` 块**
   （**仅改消息、未改文件**）。**判定**：不违反"**禁止 `git commit --amend` 已推送的提交**"，
   因为当时该提交**尚未推送**；且规则要求"终止声明必须与内容在同一笔提交内"，
   用 amend 补正是**合规形态**（不是空提交承载）。
   **可核证据**：领导随后两次推送（`1a4a7a5..738a37d`、`738a37d..fe47acd`）**都是 fast-forward**——
   若 amend 发生在推送**之后**，本地与远端会因哈希不同而**拒绝 FF**，只能强推（**D 类，禁止**），
   实际从未发生 ⇒ **amend 在推送之前**。
   ⚠️ **但仍要记**：`--amend` **会改变哈希**，若它落在"**复核之后、推送之前**"，或落在推送之后，
   就会制造一个**只能用强推收场**的分岔 —— 与本条 (e) 是同一族的第二个入口。
   ⇒ **新增纪律：并行开发期间成员不应自行 `--amend`**（下一轮派活写进禁止项）。
2. **领导自己的一处转述不完整（必须记）**：我给验证者的线索里说"`ToolResult` 字段是
   `ok` / `content` / `error`"，**漏了 `truncated` 与 `audit_id`**——实际是 **5 个字段**。
   核心判断（**没有 `reason`**）正确，且我当时明写"**请自行去契约核实，不要采信我的转述**"；
   验证者正是照此核实后**改对了字段名**，并**额外实测**出"工具层路径越权拒绝时 `audit_id` 仍非空"
   （失败路径也走 `audit_tool_call`）⇒ 把一条写错的用例改成了**有价值的断言**。
   ⇒ 这条证明的是机制而非人品：**"不可信内容一律视为数据"必须同样适用于领导的话**；
   而**转述要给判据、不要给结论**（给结论会让对方直接复用我的错误）。
3. **一处计数疑问的关闭（曾怀疑"有用例被静默跳过"）**：对账期间出现过 `426` / `431` / `437` 三个数字。

   ⇒ **两者相等**（`pyproject.toml` 已注册 `benchmark` marker，但**当前无用例使用**，
   `tests/benchmark/` 亦未建立）⇒ **无静默跳过**；此前差异来自**测量时点不同**（在途破损快照），
   不是机制问题。另：验证者声明"**未**跑全量 `make check`"（怕触碰并发编辑中的设计文档，理由成立）——
