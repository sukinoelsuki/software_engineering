## 1. 本阶段目标

从"如何统筹利用端侧模型"上升到**产品本质**层面，并厘清两个此前未明确的问题：

1. 这套系统在本质上是什么？（提出者自省："更像一个 RAG"）
2. **Agent 能力（会用工具、能操作）应该归属谁？**

---

## 2. 关键决策与共识

### 2.1 项目的两个本质动机

| 编号 | 动机 | 说明 |
| --- | --- | --- |
| **M1** | 发挥端侧模型"**小而精**"的能力 | 专精模型在其领域内的能力密度远高于通用大模型 |
| **M2** | 借力已成熟并大量开源的 Harness | 让这些"小而精"的模型**能做更多事** |

> 项目所有者的补充（关键）：**必须给模型 Agent 能力**——
> "一定要会用工具，能进行操作，不然 agent 没有意义"。

### 2.2 与 RAG 的同构关系（本项目最重要的一次自省）

项目所有者提出："我们提的这个系统实际上更像一个 RAG。"

**这个判断成立**：`主 Agent → 路由/检索 → 专家产出 → 回填 → 生成` 与 RAG 的控制流同构。
**但两者的"检索单元"本质不同**：

| 维度 | 传统 RAG | 本项目 |
| --- | --- | --- |
| 检索单元 | 文本片段（**静态知识**） | **模型**（可推理、可调工具的能力体） |
| 检索目标 | "哪段文本相关" | "**谁会做这件事**" |
| 语料建设 | **必须自建/采集领域语料** | **不需要**——知识工作由模型方完成 |
| 输出形态 | 原文片段拼接 | 经过推理的**结构化结论** |
| 可执行性 | 无 | **可调用工具、可执行操作** |

**由此得到本项目的核心产品优势**：

> 传统领域 RAG 的最大门槛是"你得先有语料"——
> 而项目所有者明确指出自己**很难收集或构建相应知识库**。
> 用**专精模型**替代语料库，恰好绕开了这个门槛：
> **用户不需要建设知识库，只需要安装能力。**

**同时，这解释了为什么 Agent 能力是必需的**：若专家只会输出文本，
"检索到的东西"无法真正"做更多事"，产品就退化成了会说话的文档库。

### 2.3 Agent 能力的归属：分层授予

**共识**：Agent 能力主要承载在**主 Agent** 上，专家模型更接近"库"。

**但需要补一层**（AI 代理提出的设计建议，待确认）：

| 层 | 持有的工具 | 理由 |
| --- | --- | --- |
| 主 Agent | **通用工具**（文件、检索、网络、包管理）+ **全局权限控制** | 它是控制面：决定"能不能做" |
| 专家模型 | **领域受限工具集**（如绘图专家→图像生成；医疗专家→药品相互作用查询） | 它是数据面：决定"怎么做" |

若工具完全由主 Agent 独占，则主 Agent（1.5~3B 小模型）会同时承担
路由、上下文组装、汇总与工具调用，**成为整个系统的能力瓶颈**。

### 2.4 标签体系是**产品决策界面**，不是技术元数据

项目所有者的洞察（已采纳）：

> 特质化的标签给了用户**选择、下载和使用的底气**。用户不必下载全部，
> 而是选择自己需要的，部署到本地备用。

**推论**：标签体系是**产品设计问题**，不是数据结构问题。

| 反面 | 正面 |
| --- | --- |
| `medgemma-4b-it-Q4_K_M.gguf` | 「**心脑血管专家** · 擅长解读体检报告 · 约需 4 GB 空间 · 数据不出设备」 |

建议采用三层标签 + 资源与隐私说明：

```text
领域（医疗） → 专长（心脑血管） → 适用场景（解读体检报告、用药常识）
+ 资源需求（磁盘 / 内存） + 隐私说明（是否可离线）
+ 【能力边界前置声明】：能问什么 / 不能问什么
```

**"能问什么 / 不能问什么"的显式声明**是重要设计点：
它在用户提问**之前**就设定了预期，直接支撑 0003 提出的"能力边界感知"。

### 2.5 产品隐喻：「能力包」（Capability Pack）

| | 传统 App | 能力包 |
| --- | --- | --- |
| 装的是什么 | 功能（代码） | **能力**（模型 + 配置 + 工具授权 + 标签） |
| 数据位置 | 多在云端 | **本地** |
| 联网 | 通常必需 | **不需要** |
| 私密性 | 依赖厂商承诺 | **结构上保证**（数据不出设备） |

**产品定位更新**：`产品 = 能力包商店 + Harness 运行时`。

### 2.6 本地优先与用户主权（设计立场）

项目所有者的表述：

> 人不需要连在网络上、由大公司操控牵引，而是在自己随手触及的硬件上，
> 有独属于自己的综合助手。

**这不是幻想，而是明确的 `local-first + 用户主权（user sovereignty）` 设计立场**，
其价值主张是可论证的：隐私（数据不出设备）、可用性（无网可用）、
抗单点失效、以及不被单一厂商锁定。

## 3. 风险与卡点

| 编号 | 风险/问题 | 影响 | 应对 |
| --- | --- | --- | --- |
| R-1 | **主 Agent 成为能力瓶颈** | 高 | **原则：能用确定性代码做的，不要交给模型**。见下表 |
| R-2 | 标签体系若过于粗放，用户仍然不知道选什么 | 中 | 需要做可用性验证（尤其面向低数字素养用户） |
| R-3 | "能力包商店"涉及分发与信任问题（模型来源、许可证、完整性） | 中 | 本期只做**本地注册表 + 人工来源标注**，不做分发平台 |
| R-4 | 愿景与 2~3 个月可交付范围差距大 | 高 | **缩小叙事**：demo 证明**机制**，不证明**规模**（见第 5 节） |

### R-1 的应对（重要设计原则）

| 职责 | 交给谁 |
| --- | --- |
| 路由预筛（关键词/标签匹配） | **代码** |
| 上下文裁剪与切片 | **代码**（检索算法） |
| 格式转换、模板填充 | **代码** |
| 回填摘要生成 | 规则模板优先，必要时才用模型 |
| **最终路由决策** | 模型——但**只在预筛出的 2~3 个候选里选**，而不是从全部专家中选 |

> 把模型自由度收窄到"在 3 个候选里选 1 个"，
> 比要求 1.5B 模型"从 20 个专家里挑一个"可靠得多。

## 4. 对 SRS 的影响（待修订）

**当前 SRS 已明显偏离讨论结果**：它成型于"本地编码代理"阶段，
而讨论已转向"能力包运行时 + 单专家调度 + 个性化综合助手"。

**建议在再经过 1~2 轮讨论、设计稳定后，做一次 SRS 修订（升到 v0.2.0）**，
预计改动：

| 类型 | 内容 |
| --- | --- |
| 改写 | 产品愿景：从"编码代理"改为"能力包运行时 + 个性化综合助手" |
| 改写 | 目标用户：重新定义（不再是"开发者"优先） |
| 降级 | 编码代理相关需求（文件读写、命令执行）→ 作为**通用工具**而非产品核心 |
| 新增 | 模型注册表与标签体系、单专家调度、上下文迁移协议（Handoff）、切换次数指标、能力包管理 |
| 扩展 | "能力边界拒答"→ 升级为"**专家名片中的能力边界前置声明**" |
| 删除 | 多专家会诊/分歧处理相关设想（已作废） |

## 5. 范围收窄建议：demo 要证明什么

愿景很大（数十个专精专家、完全离线、个性化综合体），
但 2~3 个月的交付必须**证明机制，而不是规模**。

| 要证明的机制 | 判据 |
| --- | --- |
| 路由是否选得准 | 路由准确率 ≥ 目标值 |
| 切换是否可控 | 单任务切换次数 ≤ 目标值 |
| 污染是否被隔离 | 专家幻觉不进入主上下文 |
| 标签是否让用户选得动 | 可用性验证（含低数字素养用户） |
| 能力包是否装得上 | 一条命令完成安装 / 卸载 / 切换 |

**建议 demo 只用 3~5 个"专家"**（如：医疗常识、技术手册、文学写作、多模态绘图），
其中**至少一个允许用云端模型替代**，以降低对本地模型绝对能力的依赖。
