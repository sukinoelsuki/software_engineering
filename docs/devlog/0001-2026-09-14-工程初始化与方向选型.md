## 1. 本阶段目标

在项目内容尚未明确的情况下，先把**工程基础设施**与**方向决策**落地，使后续开发有据可依：

1. 建立可长期运行的仓库基线（许可、忽略规则、LFS、编辑器配置）；
2. 建立软件工程流程（Git 工作流、生命周期、完成定义、测试策略）；
3. 建立安全策略与 Agent 协作准则；
4. 建立 CI 门禁与协作模板；
5. 选定项目方向。

## 2. 关键决策与理由

| 决策 | 理由 | 记录位置 |
| --- | --- | --- |
| 采用 ADR 机制，一决策一文件、只增不改 | 单人长周期项目最怕"忘了当初为什么这么定"；保留被否决的方案可防止反复推翻自己 | ADR-0001 |
| 采用**简化 Git Flow**（`main` + `develop` + 短期分支） | 保留发布隔离与集成隔离两个收益，同时把分支数量控制在单人可维护范围 | ADR-0002 |
| **禁止直接推送远端**，需事先批准 | 项目所有者要求；同时把短期分支作为默认工作单元 | `docs/engineering/git-workflow.md` |
| 采用 Python + uv + ruff + mypy + pytest 工程基线 | 智能体生态以 Python 为主导；Phase 0 需要可运行的 CI 才能出口 | ADR-0004 |
| 安全规则设为**始终生效**的 Agent 规则 | 本项目主线含系统安全，安全约束优先级高于功能与进度 | `.codebuddy/rules/security-baseline/` |

### 方向选型的三次修正（重要）

选型经历了三轮修正，每轮都推翻了一部分前一轮的假设：

| 轮次 | 初始假设 | 修正原因 |
| --- | --- | --- |
| 提案 0001 | fork 前沿项目（如 AIOS）并重写其内核 | 与项目所有者实际资源不匹配；忽略"组装"这一更现实的工作方式 |
| 提案 0002 | 组装开源组件，做"低资源安全 Agent Harness" | 定位缺少产品形态，安全显得像"插件"；且需排除 GPU 依赖（CNB 的 GPU 无免费额度） |
| 提案 0003 | **低资源本地编码代理**（有完整产品形态） | 采纳后两条主线从"附加"变为"内在需求"：执行 AI 生成的代码天然构成致命三要素；低资源下上下文与工具工程决定"能不能用" |

**最终方向**：低资源受限环境下的**能力感知智能体运行时**，详见
[`docs/requirements/srs.md`](../requirements/srs.md)。

## 4. 数据与证据

### 4.1 CNB 平台核验（官方文档）

| 项 | 结论 |
| --- | --- |
| GPU 节点 | **存在**（amd64，48 GB 显存，固定 16 核，单次最长 18 小时） |
| GPU 免费额度 | **无**；构建与开发均为 0.5 元/核时 |
| 构建-CPU 免费额度 | 160 核时/月（8 核 16 GiB ≈ 20 小时/月） |
| 开发-CPU 免费额度 | 1600 核时/月（8 核 16 GiB ≈ 200 小时/月） |
| AI Credits | 500/月 |

**结论**：本项目采用**纯 CPU 方案**，不依赖 GPU，因此不产生费用。
详见 [`docs/research/2026-09-14-cnb-quota-and-hardware.md`](../research/2026-09-14-cnb-quota-and-hardware.md)。

### 4.2 开源仓库核验

对候选组件逐仓库执行 `git ls-remote` 核验存在性，**共 73 个仓库全部通过**
（分三批：23 + 31 + 19）。核验记录见提案 0002 与提案 0003。

## 6. 学到了什么

1. **"先定方向再建设施"是错的**——方向可以反复变，但工程基础设施是通用的。
   把它先做好，后面每次方向调整都只需改文档，不必重搭流程。
2. **需求分析确实是软件工程的第一步**——三轮方向修正本质上都是需求分析（用户是谁、场景是什么、
   约束是什么），而且每一轮都推翻了上一轮的隐含假设。
3. **约束识别比方案设计更重要**——"不产生费用""必须能完成"这两条约束直接砍掉了原本评分最高的
   两个候选（GPU 推理引擎、microVM 沙箱）。
4. **决策留痕的价值在第一次修正时就体现了**——提案 0001 与 0002 保留了被否决的方案，
   使修正有据可依，而不是凭感觉推翻。
