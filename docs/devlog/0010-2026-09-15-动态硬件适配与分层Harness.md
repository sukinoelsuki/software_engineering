## 1. 本阶段目标

项目所有者补充了一项技术方向与交付定位：

1. **技术追求**：在**受限环境**发挥**最好性能**得到结果；而环境**不断变化**
   → 技术重点应增加"**动态探知硬件条件 → 生成合适的动态 Harness**"，
   即基础安全调教之外的"**剩余价值利用**"；
2. **交付定位**：当前是 **beta**，场景聚焦**笔记本与个人 PC**，移动端不适配；
   要求是"**够跑、能跑出合适结果**"；
3. **直接需求**：需要一个**稍大一点的模型**，用于"稍好硬件条件"下的适配。

本阶段要做的是：**把这个愿景收敛成一个可交付、可验证、可解释的机制，并落地第一批改动。**

## 2. 关键决策与理由

### 2.1 把"动态适配"界定在三条边界内（→ ADR-0010）

不做界定的话，它会自然膨胀成无边界研究项目（正是 SRS 已识别的 `R-2` 范围膨胀）。
因此定死三条：

| 边界 | 规定 |
| --- | --- |
| **时机** | 会话**启动时探测一次**；运行中**不调整**（允许手动覆盖，覆盖也留痕） |
| **粒度** | **固定 3 档（S/M/L）**；不做连续调优、不做自动搜索 |
| **留痕** | 必须记录 **探测值（含来源）→ 决策依据 → 生效配置**；缺任一段视为未实现 |

选它而不是"运行中持续优化"的理由很直接：**持续优化不可复现、不可解释**，
而本项目最需要的恰恰是"能解释为什么这次慢"。
加权矩阵见 [ADR-0010 §4](../adr/0010-dynamic-hardware-adaptation.md)（B = 86 分，A = 27 分）。

### 2.2 档位是**两个正交的轴**，不可互相推导

| 轴 | 决定什么 |
| --- | --- |
| **硬件档位（S/M/L）** | 能跑多大、多快 → 模型规模、量化档、上下文长度、并行度 |
| **能力档位（模型）** | 该给多少自由度和约束 → 工具集大小、提示结构、验证强度、重试预算 |

同一模型换到更强硬件，**能力档位不变但配置必须变**。这条区分直接决定了
`REQ-HARNESS-03/04`（既有）与新增的 `REQ-PERF-05/06` 是**互补而非重复**。

**顺带统一了此前的"横向/纵向"表述**：纵向 = 硬件档位差异；横向 = 同档不同模型；
再加一轴对照 = 有/无适配 Harness（即本项目核心论点的验证）。

### 2.3 新增一个大一档的模型（回应第 3 点需求）

选定 **`Qwen3-8B-Q4_K_M`（5.03 GB）** 作为 M 档主力，已加入
[`.ide/assets/models.txt`](../../.ide/assets/models.txt)（sha256 `d98cdcbd…`，取自 HF 官方 API）：

| 档 | 内存预算 | 预置模型 |
| --- | --- | --- |
| S | ≤ 8 GiB | `Qwen3-4B-Q4_K_M`（2.50 GB，W1 已实测） |
| **M** | 8 ~ 16 GiB | **`Qwen3-8B-Q4_K_M`（5.03 GB）← 新增** |
| L | ≥ 24 GiB | 【待定】14B 级 Q4（16 GiB 上属紧张配置，需实测后定） |

`AgentCPM-Explore-4B` **不作为档位**，而是**横向对比对象**——同为 4B，
用于回答"同等预算下选哪个"。这样"档位"与"对比"两条线不会互相污染。

### 2.4 探测能力复用已有的 `isolation_matrix()` 模式

ADR-0007 已经建立了"**逐维度探测 + 记录来源**"的做法（隔离能力矩阵）。
硬件探测沿用同一模式与代码骨架，不另起一套——这是本节最省力的决定。

## 4. 数据与证据

### 4.1 "核数"有六个答案（探测设计的直接依据）

| 来源 | 实测值 | 可靠性 |
| --- | --- | --- |
| `os.sched_getaffinity(0)` / `nproc` | **8** | ✅ 权威（可调度集合） |
| `/sys/fs/cgroup/cpuset/cpuset.cpus` | **81-88** | ✅ 权威（绑定的宿主物理核） |
| `cpu.cfs_quota_us / period` = 800000 / 100000 | **8 核** | ✅ 权威（配额） |
| `/proc/cpuinfo`、`/proc/stat`、`online` | 8 | ⚠️ 已被平台虚拟化，此处恰好正确 |
| `/sys/devices/system/cpu/present` | **0-383** | ❌ 泄露宿主机拓扑 |
| **`lscpu` 的 `CPU(s)`** | **384** | ❌ **给出错误答案** |

宿主真实规格为 `AMD EPYC 9K65 192-Core Processor`（单路 192 核、超线程 → 384 逻辑核），
我们只被分配 **8 个特定核（81~88 号）**。

**危险点**：`lscpu` 是最顺手的命令；按它推导线程数会启动 384 个线程、
在 8 核配额里**严重超订**，而且**不报错**。

### 4.2 其余探测项

| 项 | 实测 | 备注 |
| --- | --- | --- |
| SIMD | `avx avx2 avx512f avx512_vnni f16c fma sse4_2` | 对 llama.cpp 吞吐影响最大 |
| 内存预算 | `MemTotal` 16 GiB；`memory.limit_in_bytes` 16 GiB | 两者取较小值；实测可用约 13.6 GiB |
| 加速器 | `llama-server --list-devices` → `(none)` | 纯 CPU 路径 |
| 磁盘 | `/workspace` 512 G、`/` 253 G 可用 | — |

### 4.3 清单与脚本验证

`plan` 子命令输出：3 个模型（2.50 + 5.03 + 2.72 GB）+ 8 个参考仓库全部解析正确；
`bash -n` 语法通过；桩 `git` 验证 8 条参考资料逐条解析正确。

## 6. 学到了什么

一条新经验已写入 [学习笔记](../notes/hardware-probing.md)：

> **硬件的"能力"与"预算"是两回事**，且同一个量可能有多个互相矛盾的来源。
> 探测必须**多源交叉、记录来源、以可调度集合与配额为准**。
> 这一次的教训不是"某个命令有 bug"，而是：**做适配之前，先确认适配所依据的输入是否可信。**

这正是 ADR-0007 那条原则（"隔离是否生效必须由主动探针判定"）在**硬件维度**上的同一形状——
所以本次没有发明新方法，只是把已有方法搬过来用。
