## 1. 本阶段目标

0012 把基准流水线跑通后，项目进入"要开始搭产品框架"的节点。但搭之前必须回答两个问题：

1. **我们的协作方式是什么？** 单人 + AI 角色，需要明确分工与成本纪律；
2. **地基平不平？** 60+ 份文档与实现之间有没有互相矛盾、误导决策的地方。

本篇记录这两件事的结论，以及由此暴露的"产品主体只有零散零件"的现状。

## 2. 关键决策与理由

### 2.1 协作方式：角色分工 + 文件域独占 + 实现与验证分离

落地为 `CODEBUDDY.md` / `AGENTS.md` 的 **§10**，并进一步落到**可执行配置**
（`.codebuddy/agents/*.md` 的 `model:` 字段）——"角色-模型绑定"不再靠人工切换。

六个角色的独占产出域见 §10.1。**核心不是"分活"，而是两条纪律**：
**实现与验证分离**（安全断言不得自证）、**文件域独占**（并行度不超过冲突控制能力）。

### 2.2 模型档位：按同口径分数 ÷ 倍率决定，不按档位名或价格

调研结论进了 [`notes/dev-agent-model-selection.md`](../notes/dev-agent-model-selection.md)：
同一批可用模型里，**倍率最低的档位在 Terminal-Bench 2.1 上分数最高**
（0.03x → 90.60，3/192），而一个中价档（0.25x）分数最低（66.0）。
⇒ 分配规则：机械档用 0 积分的档位，执行/规划档默认最便宜且够用的档位，卡住再按阶梯升级。

### 2.3 先修地基，再搭框架

一致性核查发现的问题里，有四条会**持续误导决策**，因此优先修：
状态矛盾（A-2）、合并策略与 ADR 冲突（A-3）、DoD 死项（A-7）、测试目标假失败（A-9）。

## 4. 数据与证据

- **只读探索代理的实际开销**：78 次工具调用、**125 秒**、**4.02 credits**（约月额度的 0.06%）。
  产出 14 条问题 + 3 张盘点表 —— 这是"用便宜档位跑机械任务"的第一个成本样本。
- **核查暴露的两个反直觉事实**：
  ① `CONTRIBUTING.md` 与 `ADR-0013` 的合并策略冲突，而冲突方之一（squash）会**破坏证据链**
  ——这类问题只有"跨文档对照"才能发现，单看任何一份文档都是自洽的；
  ② 文档**宣称已有**但实际不存在的有四项：威胁模型（0 条）、设计文档（`design/` 下只有 README）、
  测试分层（只有 unit）、基准归档目录（`reports/bench/` 不存在）。
- **`make test-security` 的实测**：修改前 `67 deselected / 0 selected` ⇒ 退出码 5；
  修改后同一命令输出提示且 `rc=0`（`make check` 仍全绿，因为它本就不引用该目标）。
- **产品骨架的真实盘点**（读代码得出）：`src/` 下唯一有实现的是 `bench/`（12 模块 + 4 夹具），
  其中**可直接复用为产品地基的只有三处**：`proc.py`（唯一子进程封装：非特权 uid + rlimit + 最小环境）、
  `paths.py`（路径白名单）、`errors.py`（fail-secure 异常层次）。
  产品六层（模型/Harness/安全/工具/UX/可观测）中，**五层只有零散零件、没有骨架**。
- **发布链路的"三重验证"（2026-09-18，修复后的真实运行）**：数据分支现有三轮数据，
  `bench/daily/` 下 **09-16（28 文件）、09-17（28 文件）、09-18（124 文件）同时存在**：

## 6. 学到了什么

一句话：**文档会漂移，而漂移的文档比没有文档更危险——它会让人基于错误前提做决策。**

`adr/0003` 的 §0/§5.1 与 §6~§8 在同一份文件里指向两个不同的项目，`CONTRIBUTING.md` 的
合并策略与 `ADR-0013` 相反，README 说 Phase 0 已完成而基准里四项待办未勾——
**每一份单独看都自洽，只有横向对照才暴露矛盾**。这正是"记录员"这个角色存在的理由，
也是"把约定做成机器检查"（A-3 那类规则本可以写成测试）的价值所在。

第二条：**"宣称已有"与"实际存在"之间要定期对账**。四项内容被反复引用却从未建立
（威胁模型、设计文档、测试分层、归档目录），说明文档里的"计划结构"很容易被后续文档
当成"既有事实"引用——引用一次，就开始积累误导。
