## 1. 本阶段目标

0012 把基准流水线跑通后，项目进入"要开始搭产品框架"的节点。但搭之前必须回答两个问题：

1. **我们的协作方式是什么？** 单人 + AI 角色，需要明确分工与成本纪律；
2. **地基平不平？** 60+ 份文档与实现之间有没有互相矛盾、误导决策的地方。

本篇记录这两件事的结论，以及由此暴露的"产品主体只有零散零件"的现状。

## 2. 关键决策与理由

### 2.1 协作方式：角色分工 + 文件域独占 + 实现与验证分离

落地为 `CODEBUDDY.md` / `AGENTS.md` 的 **§10**，并进一步落到**可执行配置**
（`.codebuddy/agents/*.md` 的 `model:` 字段）——"角色-模型绑定"不再靠人工切换。

六个角色的独占产出域见 §10.1。**核心不是"分活"，而是两条纪律**：
**实现与验证分离**（安全断言不得自证）、**文件域独占**（并行度不超过冲突控制能力）。

### 2.2 模型档位：按同口径分数 ÷ 倍率决定，不按档位名或价格

调研结论进了 [`notes/dev-agent-model-selection.md`](../notes/dev-agent-model-selection.md)：
同一批可用模型里，**倍率最低的档位在 Terminal-Bench 2.1 上分数最高**
（0.03x → 90.60，3/192），而一个中价档（0.25x）分数最低（66.0）。
⇒ 分配规则：机械档用 0 积分的档位，执行/规划档默认最便宜且够用的档位，卡住再按阶梯升级。

### 2.3 先修地基，再搭框架

一致性核查发现的问题里，有四条会**持续误导决策**，因此优先修：
状态矛盾（A-2）、合并策略与 ADR 冲突（A-3）、DoD 死项（A-7）、测试目标假失败（A-9）。

### 2.4 协作机制：主 Agent 恒为团队领导，五个角色统一 `agentic`

实测（见 §4）后明确了：`manual` 与 `agentic` **不是"保守 vs 激进"，而是两种不同的东西**
——`manual` 的语义是"人把它切成主 Agent 来用"，只有 `agentic` 能被主 Agent 派活。

⇒ 定案：**主 Agent 恒为团队领导**（派活、核对文件域、汇总、对所有者负责），
**五个角色统一 `agentic`**。设计类成员（总设计师 / 首席架构师）与执行类成员**不直接交接**，
一律经"**文件 + 领导核对**"——因为成员之间不共享上下文、且不跨会话恢复，
**未落盘的设计等于不存在**。所有者需要产品设计时，由领导把它拉成团队成员、
所有者与它直接对话，产出**先落盘**、再回流到领导。

**被放弃的替代方案**：混合模式（设计角色留 `manual`）。它的代价是"所有者要跟设计成员谈，
就得让出主对话"，等于放弃领导层，与"领导对全流程负责"直接冲突。

## 5. 问题与卡点

- ~~**自定义 agent 无法被 `Task` 调用**~~ ⇒ **已于 2026-09-18 结案，且原诊断是错的**。
  原文写的是"IDE 界面可用（已截图确认），但工具侧需要**重载会话**才能加载新建的 agent 定义"。
  新会话复验**依然报 `Subagent "verifier" not found`**，直接证伪"重载会话"这一归因；
  真正原因是 `agentMode: manual` 的语义与我们的用法不符（它不可被派活）。
  **这句错误诊断原文留存于此**：它是一次"看似合理的归因未经验证即写入日志"的实例——
  与 §6 记的"文档漂移"是同一类失败，只是发生在日志里。
  两条附带结论：① **界面上看得见 ≠ 能被调用**，原记录的"已截图确认"不能作为可用证据；
  ② 前台子任务会**冻结主对话**（实测 687 秒），"后台并行"必须走团队模式，而不是

- **门禁对安全回归零覆盖**：`make check` 里的 `security` 环节只是 `bandit` + `pip-audit`

## 6. 学到了什么

一句话：**文档会漂移，而漂移的文档比没有文档更危险——它会让人基于错误前提做决策。**

`adr/0003` 的 §0/§5.1 与 §6~§8 在同一份文件里指向两个不同的项目，`CONTRIBUTING.md` 的
合并策略与 `ADR-0013` 相反，README 说 Phase 0 已完成而基准里四项待办未勾——
**每一份单独看都自洽，只有横向对照才暴露矛盾**。这正是"记录员"这个角色存在的理由，
也是"把约定做成机器检查"（A-3 那类规则本可以写成测试）的价值所在。
（2026-09-18 更新：三例中 `CONTRIBUTING.md`↔`ADR-0013` 已由 `81282ea` 经 A-3 修复（改 merge commit）、`README` 的 Phase 0 状态已由 A-2 统一为"进行中 + 待办未完"（见 README §5）；仅 `adr/0003` 双项目指向仍为真，已改由 `ADR-0015 §5.5` 登记为历史残留而非改写正文——原句保留作"漂移曾发生"的证据。）

第二条：**"宣称已有"与"实际存在"之间要定期对账**。四项内容被反复引用却从未建立
（威胁模型、设计文档、测试分层、归档目录），说明文档里的"计划结构"很容易被后续文档
当成"既有事实"引用——引用一次，就开始积累误导。

第三条：**"归因"和"现象"要分开验证**。§5 那条"需要重载会话"当初看着很合理
（新建文件 → 需要重新加载），于是就被写进日志当结论；实际原因完全不同。
教训是：**现象是证据，归因只是假设**——写进日志时必须标明哪部分是观察、哪部分是推测，
并且**下一次会话第一件事就是复验推测**。这次能纠正，靠的正是上一轮把"新会话先验证"
写成了待办，而不是靠记忆。
