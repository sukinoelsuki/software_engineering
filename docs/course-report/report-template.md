# 1 问题定义

## 1.1 项目背景与意义

### 1.1.1 需求：端侧模型"能部署"与"能干活"之间的缺口

端侧部署已不是难题：`llama.cpp`、Ollama 让无 GPU 的普通机器也能跑 4B 级模型。缺口在部署之后——从"把模型跑起来"到"把模型用起来"之间，缺一层集成与治理。
现有方案各占一端，没有一个同时覆盖"本地推理 + 工具执行 + 权限治理"（表 1-1）。

[[tab:表1-1　现有方案的能力覆盖与缺口]]
| 类型 | 代表 | 已覆盖 | 缺口 |
| :--- | :--- | :--- | :--- |
| 模型运行时 | Ollama、llama.cpp | 部署与推理 | 无 agent 能力、无执行安全 |
| 云端智能体 | Cursor、Claude Code | 编排与工具 | 依赖网络与强模型 |
| 本地聊天界面 | Open WebUI | 交互界面 | 无工具执行与安全边界 |
| 开源编码 agent | Aider、Goose | 编排与工具 | 假设强模型，对低资源无针对性设计 |

### 1.1.2 做法：三层自研增量

项目在开源组件之上只做三件自研的事，其余全部复用（推理内核用 `llama.cpp`，CLI 用 Typer/Rich，日志用 structlog，构建用 uv + hatchling）。

[[tab:表1-2　三项自研增量与它们的立论]]
| 增量 | 内容 | 立论（可验证的假设） |
| :--- | :--- | :--- |
| 能力自适应 Harness | 工具集按能力档位裁剪、提示分级、检查点、错误分级 | 对给定小模型存在适配配置，同一任务成功率高于直接套用大模型 Harness |
| 能力边界感知的安全层 | 能力模型（默认拒绝）、策略判定、审批门、审计回放 | 小模型必然犯错，安全目标不是不犯错，而是不让错误造成不可逆后果 |
| 能力包内核 | 案例契约、判据自证、bundle 摘要、状态机、修复目录 | 八轮调教的经验可编译成可判定对象，修复动作可白名单化 |

### 1.1.3 好处与竞争位置

对用户的可观察好处有三条：离线可完成原本要联网才能做的任务；越权与越界操作被拦截并留下可回放记录；同一案例的成败由机器判据给出，不由模型自述。
与同类项目的差别不在"功能多少"，而在评价口径：本项目不比拼绝对能力，只回答"在给定小模型与受限资源下，相对纯对话基线提升了多少"。这一口径写进需求规格 §5.3，避免用最强模型的指标要求 2B 模型。

### 1.1.4 交付与推广

交付形态是命令行客户端 `agent-sec-perf`（wheel 分发）+ 示例案例 + 文档四件套（需求、设计、威胁模型、使用手册）。
推广路径按"可复现"设计：一条命令安装、一条命令体检（`doctor`）、一条命令跑演示（`demo --run`），环境不满足时如实降级而不是静默放行。仓库地址 <https://cnb.cool/Mybase_Le0n3rd/Native-Intelligent-Systems>，报告中的每处引用都可按路径检索。

## 1.3 可行性分析

### 1.3.1 技术可行性

依赖不是"看起来能用"就算通过：14 项组件核验逐条给出结论与出处，8 个运行期组件锁定在 `uv.lock`，`uv build` 实测可产出 wheel。
两项关键技术风险在开写前已被实测处置：沙箱方案在本环境证伪（`unshare`/`bwrap` 报错、`firejail` 为 fail-open），于是收敛为用户态 L1 分层；4B 模型在限定任务域内可用，由 W1 实验确认。

[[tab:表1-4　五维可行性]]
| 维度 | 结论 | 关键依据 |
| :--- | :--- | :--- |
| 技术 | 可行 | 组件核验 14 项、`mypy --strict` 通过、wheel 可安装 |
| 经济 | 可行 | 不采购 GPU；跑测走云原生开发桶，只消耗免费额度 |
| 操作 | 可行 | 一条命令安装；默认中文；无账号、无服务端 |
| 合规 | 可行 | 只用合成数据；无凭据入库；依赖许可证已登记 |

## 1.4 人员管理和项目进度管理

### 1.4.1 人员与分工

项目由一人完成，AI 承担实现与验证的辅助。分工按"谁对结论负责"划分，而不是按"谁写得多"划分。

[[tab:表1-6　角色与边界]]
| 角色 | 承担的工作 | 边界 |
| :--- | :--- | :--- |
| 所有者（本人） | 选题与范围、需求取舍、验收与判定、发布 | 判定由人完成：判据不事后修改，负结论保留 |
| 实现（AI） | 大部分代码、测试、文档整理、脚本与图表 | 不参与判定；产出经人复核 |
| 验证（AI） | 对抗性用例、复跑、独立复核 | 只依据证据与复现步骤判断 |
| 记录（AI） | 开发日志、变更日志、文档一致性核对 | 只记录已发生的事，不替决策补理由 |

协作有两条硬约束：文件域独占（同一文件同一时刻只有一个角色可写）；实现与验证分离（安全断言不得由实现者自证）。远端写入按可回退性分级：`develop` 与短期分支属 A 类，推送后立即报告；`main` 属 B 类，须事先批准；凭据入库属 C 类，一律禁止。

### 1.4.2 进度管理

阶段划分按软件生命周期走，里程碑时点是计划值，实际调整须记录原因。迭代为单周节奏：周一计划、周二至周四执行、周五收尾与回顾。

[[tab:表1-7　里程碑（计划与实际）]]
| 里程碑 | 内容 | 计划 | 实际 |
| :--- | :--- | :--- | :--- |
| M0 | 工程初始化完成、可开工 | 2026-09 | 09-19 |
| M1 | 需求规格 + 架构设计 + 威胁模型 | 2026-10 上旬 | 10-12 |
| M2 | 端到端主流程可运行（Alpha） | 2026-11 上旬 | 11-02 |
| M3 | 安全加固 + 性能优化（Beta） | 2026-12 上旬 | 未开始 |
| M4 | 交付版本与全部报告 | 2026-12 中下旬 | 未开始 |

进度控制用三个手段：**任务时间盒**（同一任务超过 3 天无实质进展就拆分或降级为实验）、**唯一任务清单**（最新一篇开发日志的"下一步"就是当前清单，不另建 backlog）、**功能冻结**（里程碑前只修不增）。

[[tab:表1-8　三次计划偏差与处置]]
| 偏差 | 表现 | 处置 |
| :--- | :--- | :--- |
| 沙箱方案报废 | 命名空间隔离在本环境不可用 | 收敛为 L1 分层，并新增 ADR 记录被否决方案 |

有两条需求的写法直接决定后续能否验收。`REQ-SEC-05` 规定"隔离档位可探测、失败即降级"，并明确**不得以命令退出码判定隔离是否成功**——这条规定来自实测：`firejail --net=none` 退出码为 0 而网络仍通，按退出码判定就会把 fail-open 记成"已隔离"。

## 2.3 原型系统设计

### 2.3.1 交互形态

原型确定为一套命令面，而不是图形界面。图 2-4 是 `--help` 的实取输出：命令按"体检 → 演示 → 手册 → 会话 → 能力包"排列，新人不必读文档也能找到入口。

[[fig:figures/fig-2-4-cli-help.png|图2-4　命令行入口（`agent-sec-perf --help` 实取）]]

`doctor` 是原型的第二个界面（图 2-5）：它把"环境能不能跑"摊开成一张表，逐项给出结论与说明，隔离能力一栏在只达到 L1 时显示为警告，并在下方写明原因。

[[fig:figures/fig-2-5-cli-doctor.png|图2-5　环境体检界面（`agent-sec-perf doctor` 实取）]]

原型阶段确定的第三条规则是退出码契约：脚本与 CI 通过退出码分支，因此每种失败必须有独立取值，不能都压成 1。

[[tab:表2-5　交互形态与退出码契约]]
| 形态 | 面向 | 关键约定 |
| :--- | :--- | :--- |
| 交互式 CLI | 开发者 | 人类可读渲染；权限确认展示风险说明与三个选项 |
| 非交互 CLI | 脚本 / CI | 指定 JSON 时 stdout 只出 JSONL |
| 声明式配置 | 用户 / 管理员 | 项目级、用户级、领域包均为 TOML，逐项校验后合并 |
| 退出码 | 脚本 / CI | `0` 完成 · `1` 任务失败 · `2` 步数用尽 · `3` 装配故障 · `4` 审计失败 · `5` 未预期异常 |
| 图形界面 | 非技术用户 | 规划中，本期不做 |

### 2.3.2 原型的取舍

不做图形界面的理由是成本与风险的对称性：多一个界面就多一个现场可能出故障的环节，而演示要证明的是"模型被约束着完成了一段真实工作"，不是界面美观。后续几次演示失败都出在模型行为与判据上，界面环节未出现故障，这个判断得到验证。

### 3.1.2 接口设计

模块边界共 6 份字段级契约（`model`/`tools`/`policy`/`audit`/`sandbox`/`harness`），每份写四件事：类型、错误语义、并发假设、资源生命周期。表 3-2 是其中四个最关键的边界。

[[tab:表3-2　关键边界的接口与错误语义]]
| 边界 | 接口形态 | 错误语义 |
| :--- | :--- | :--- |
| `cli` ↔ `harness` | `Session.run(task) -> Iterator[SessionEvent]`（同步） | 业务失败以 `kind="error"` 事件表达，不抛给 CLI；审计写入失败必须冒泡 |
| `harness` ↔ L2 | `ToolRegistry.resolve` / `Tool.invoke` / `ModelClient.chat` | `ToolResult.ok=False` 表达工具级失败可回喂；模型不可用触发降级 |
| L3/L2 ↔ `security` | `PolicyEngine.decide(PolicyRequest) -> PolicyDecision` | 求值异常收敛为拒绝，不得逃逸为放行；`emit()` 失败必须冒泡 |
| 任意 ↔ `observability` | `AuditSink.emit(AuditEvent)` / `flush()` | 写入失败必须冒泡（静默丢事件即验收失败） |

表 3-2 里有一处最容易实现错的对称：策略求值失败要**收敛为拒绝**，审计写入失败要**原样冒泡**。两者表象都是"没执行"，性质完全不同——前者是正常的默认拒绝，后者是审计基础设施故障；混为一谈会把系统坏了伪装成一次普通拒绝。

[[tab:表3-3　分层不变量与被检查方式]]
| 规则 | 内容 | 检查方式 |
| :--- | :--- | :--- |
| `R1` | 纵向层只能向下依赖 | 逐层 import 白名单（`ALLOWED_DEPENDENCIES`） |
| `R2` | 横切层不得 import 业务层 | 单独断言 `security`/`observability` 的 import 目标 |
| `R3` | `contracts/` 不依赖第三方与其它模块 | AST 扫描 import 集合 |
| `R4` | 子进程唯一入口 `proc.py`，路径唯一入口 `paths.py` | 全仓搜 `subprocess` 只许出现在 `proc.py`；无 `shell=True` |
| `R5` | 领域包只加载声明式配置，禁止加载其中的 Python 代码 | 静态守卫 + 行为用例（`.py`/`.pyc` 同拒） |

九条机器检查逐条对应这五条，其中"`subprocess` 只许出现在 `foundation/proc.py`"按**相对路径**判定，防止同名文件绕过。

## 3.3 关键数据结构定义
### 3.3.1 审计事件

审计是"可回放"的载体，字段一旦定死就不能随手加，否则历史事件无法比对。

[[tab:表3-5　AuditEvent 的字段]]
| 字段 | 类型 | 语义 |
| :--- | :--- | :--- |
| `event_id` | `str` | 事件唯一标识；策略决策事件即 `audit_id` |
| `kind` | `StrEnum` | 事件类别：策略决策、工具调用、审批 |
| `timestamp` | `str` | ISO 8601，带时区 |
| `session_id` / `call_id` | `str` | 会话与调用的关联键，用于把事件流与落盘记录对齐 |
| `outcome` | `StrEnum` | 允许、拒绝、错误 |
| `tool_name` / `capability` / `risk_level` | `str` / `Capability` / `RiskLevel` | 被判定对象的描述 |
| `detail` | `Mapping` | 细项：请求集合、缺失集合、异常类型等 |

`capability` 是单值而 `requested` 是集合，两者的取值规则必须确定：`missing` 非空时取缺失集合中字典序最小者，否则取请求集合中字典序最小者。用字典序而不是集合迭代顺序，是因为"同一输入在不同版本给出不同审计内容"会让历史事件无法比对。

### 3.3.2 请求与决策

[[tab:表3-6　策略相关的三个数据结构]]
| 类型 | 字段 | 设计要点 |
| :--- | :--- | :--- |
| `PolicyRequest` | `requested: frozenset[Capability]`、`arguments` | `requested` 必须非空且元素是 `Capability` 实例，两条都由引擎兜底 |
| `PolicyDecision` | `allow`、`requires_confirmation`、`risk_level`、`reason`、`audit_id` | 拒绝是返回值而非异常，因此可断言、可回放 |
| `ToolCallRequest` | `arguments_json: str` | 刻意保存**未解析的原始 JSON 文本**，把信任边界钉在 harness 侧 |

`arguments_json` 保持字符串是一个反直觉但必要的选择：如果类型里直接放已解析的字典，校验责任就分散到每个工具，绕过一处就等于绕过全部。工具拿到的 `args` 必须是"已校验的结构化参数"。

## 3.4 关键算法设计

### 3.4.1 策略判定

判定的分支顺序本身就是契约（图 3-4）：先判空集与非法成员（硬拒绝），再做常规四格。若把两者合并，人工确认就会变成绕过默认拒绝的通道——因为"所需能力未知"时审批门没有任何东西可以对照。

[[fig:figures/fig-3-4-decide.png|图3-4　策略判定流程（`PolicyEngine.decide`）]]

算法 1 给出去掉异常处理后的主干。第 5 步刻意不包 `try`，这是全仓唯一"故意让异常逃出去"的地方。
```text
算法 1  策略判定 decide(request)
输入：requested（能力集合）、arguments（已校验参数）
输出：PolicyDecision(allow, requires_confirmation, risk, reason, audit_id)

1  try:
2      if requested 为空集        → 硬拒绝（未声明所需能力）
3      if 含非 Capability 成员    → 硬拒绝（含非法能力成员）
4      missing ← requested − granted
5      if missing 非空           → 硬拒绝（能力未授予）
6      risk ← max(领域包前缀声明, 工具声明, 默认 HIGH)
7  except 任意异常 e:
8      return 可升级拒绝（"策略求值失败×" + 类型名(e)）
9  audit_id ← uuid4().hex
10 sink.emit(AuditEvent(event_id=audit_id, ...))   ← 不包 try，失败必须冒泡
11 return PolicyDecision(...)
```

### 3.4.2 判据自证与确定性打包

`pack build` 先跑自证：正例必须让全部内容判据通过，反例必须至少失败一项。正例不过说明判据过严，反例也过说明判据过宽，两种都拒绝发布。
这条规则来自一条方法论约定：没做过"正例必过、反例必败"的判据，不用于评估。它把"判据本身写错了"这类最难发现的失效挡在发布之前。

打包的确定性由两点保证：逐文件 `sha256` 写入清单；构建默认不写时间戳。实测改动一个字节后，校验返回 `ok=false`、`problems=["大小不一致：case/case.toml"]`、退出码 1；同输入重复构建字节一致。

### 3.4.3 工具裁剪

模型看到的工具集合由能力档位决定，而不是由权限决定。授权回答"能不能做"，暴露回答"看不看得见"。任何一层不满足，模型只能空转——这条区分来自一次真实失败：写工具在授权集合里，却从未出现在 `BASIC` 档的工具列表中。

## 3.5 数据管理说明

数据管理的原则是"落点集中、访问唯一、失败可见"。表 3-8 列出所有持久化落点与它们的访问约束。

[[tab:表3-8　数据落点与访问约束]]
| 数据 | 位置 | 访问约束 |
| :--- | :--- | :--- |
| 用户级配置 | `~/.lowspec/config.toml` | 逐项校验；未知键即拒绝启动 |
| 项目级配置 | `<项目>/.lowspec.toml` | 按外部输入对待；不改变审计落点 |
| 审计 | `<状态目录>/audit/audit.jsonl` | 根为常量白名单；只追加；`flush` 即 `fsync` |
| 案例 / bundle | 用户指定目录 | 路径经 `resolve_within`；符号链接与越界拒绝 |
| 基准数据 | `bench/data` 分支（脚本写入） | 人手不得直接提交；大文件走制品库 |

三条配套规定。**路径只有一个入口**：所有文件访问经 `resolve_within` 判定，绕开它就等于多一条无人审计的特权通道。**审计只追加**：一行一事件，崩溃最多影响正在写的那一行，因此不需要事务也能回放。
**回滚 = 换 wheel 版本 + 保留审计文件**：产品端没有数据库迁移，也没有服务端状态，回滚不需要数据修复。这一条是"无服务端"这个架构选择带来的直接好处。

### 4.3.3 测试纪律

三条纪律是从失败里换来的。**零用例即失败**：安全测试在收集到 0 条时直接返回失败，避免"没有用例"被误判为"全部通过"。**变异探针**：关键安全用例附带"把保护去掉后必须变红"的对照，确保用例真的在测东西。
**拒绝不等于失败**：工具拦下幻觉时，早期把"未执行"记成失败，导致一次正确的治理被判成缺陷；现在把"拒绝发生在执行前"单独报一行，两类结果不再混淆。

### 4.4.3 结果的可信边界

四条边界必须与结论一起读：隔离只到 L1，文件系统与网络靠应用层拦截；2B/4B 通过的是**一条案例**，不是通用 agent 能力；演示墙钟是观测值，不用于性能结论；`T-04`、`T-10` 在威胁模型中仍是"未缓解"。
威胁模型的整体分布为：已缓解并验证 1 条、部分缓解 12 条、未缓解 2 条。这是盘点结果，不是"安全已到位"的结论——升级到"已缓解并验证"的唯一途径是出现可执行的行为级证据。

# 6 体会

最有价值的收获来自几次被实测推翻的判断。第一次是"只读一个文件就编出配置值"：输出格式、语气、结论方向都正确，肉眼容易判为成功，机检查出了调用次数不足与事实未命中。此后"可验证"成了项目的基本要求——它是区分"会说话"与"读过文件"的唯一手段。
第二次是 `F1` 与 `F9` 的拆分：同一串失败信号对应两种相反的原因，0.6B 与 1.7B 的实跑才让这条歧义消除。第三次是判据自证的范围：设计时曾想声称"全部判据已自证"，实施时发现事件流判据无法静态证明，最终在清单里如实写下"覆盖 4 条、未覆盖 7 条"。
第二个体会关于"取消动作"。三次修改"写"的失败，最终都通过移除动作解决：修订只能换一行，报告只能填四个字段，诊断阶段看不到修订工具。这条经验后来固化为 `F1`~`F9` 修复目录，允许的结构性修法与禁止的"再改改提示"逐条写明。
第三个体会是结论的适用条件。隔离是 L1，2B 完成的是这一条案例，4 分钟是观测值，这些条件与结论一起写进正文。写清条件会让表述变长，但读者据此能判断结论能用到哪里，这正是一份工程报告该提供的信息。
关于 AI 协作，最深的体会是"分工要落在文件上，而不是落在口头约定上"。本项目让 AI 承担实现与验证，但把验收判定留给人；把安全断言交给独立的对抗性用例，而不是由实现者自证。把边界写成文件域独占、提交门禁与授权分级之后，协作才从"尽量别搞错"变成"搞错了会被拦住"。
