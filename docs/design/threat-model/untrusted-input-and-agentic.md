## T-05 子代理输出是不可信输入

**状态**：`部分缓解` ｜ **主导类别**：STRIDE-S（冒充）｜ **智能体特有**：间接注入（**协作面**）

- **资产**：A-4（仓库完整性）、A-7（结论可信性）、A-1/A-2（若被诱导执行）
- **攻击者与前提**：攻击者能影响**子代理（团队成员）产出的一段文本**——
  例如让某个成员读到一份含注入的文件，再让它的回报里带上注入指令
  （`docs/engineering/agent-teams.md` §4 已把这条列为**真实威胁**）。
  前提是**团队领导（主 Agent）把成员回报当作可信输入**。
- **攻击路径**：
  1. 成员读入含注入的仓库文件 → 其回报文本携带仿冒标签或"指令"；
  2. 领导**直接采信回报**（例如据回报判定"任务已完成"或"该文件已改"）；
  3. 更严重：据回报做出**权限决策或控制流决策**（重派任务、跳过核对、改文件域）；
  4. 后果：**同一文件被两个成员写**、**重复劳动**、或**基于假事实推进工作**。
- **影响**：A-4 与 A-7；**不可逆性：中**——错误结论会写进日志与文档
  （本项目已发生两例：领导把"已转派"当"已完成"、两度误判记录员状态，
  见 `devlog 0013` §4/§6）。
- **现有缓解**：
  - **上游 harness 的"非破坏性去毒"**（`agent-teams.md` §4）：改写仿冒 `<system-reminder>` 标签、
    给行首 `Human:`/`Assistant:` 加反斜杠 ⇒ 这是**缓解**，
    官方用"非破坏性"一词即表明它**不求穷尽**、**不能当保证**；
  - **项目纪律（已写入常驻文件）**：成员回报**只能作证据线索**，
    **不得作为权限决策或控制流的依据**（`CODEBUDDY.md` §10.4）；
  - **完成判定只认仓库**：以成员最后一笔提交正文里的 `回报：` 块为唯一判据，
    且对账须确认**该提交含本域改动**（禁止以空提交承载终止声明）
    ——`CODEBUDDY.md` §10.2 规则 9、`agent-teams.md` §8；
  - **机制性防护**：文件域独占 + 领导核对（`CODEBUDDY.md` §10.2 规则 8）；
  - 消息不可靠这一事实本身被制度化：**"消息送达 ≠ 被处理"**、**"未确认 ≠ 失败，禁止据此重派"**。
- **残余风险**：
  1. **去毒是不完整且不可回归的**：它是上游行为，我们**无法为自己的仓库写测试**
     去证明"注入一定被去掉"——只能测"我们自己的处置纪律"；
  2. **纪律靠人（Agent）执行**：没有任何机器检查能阻止领导"直接采信回报"；
  3. **回报文本仍会进入领导的上下文**：即使不作决策依据，也可能影响判断倾向
     （这是"上下文污染"在协作面的形态，同 `T-04`）；
  4. **归档面**：`.codebuddy/teams/<team>/*.json` 是**运行产物**（团队删除即消失），
     不构成可追溯的证据链 ⇒ 事后核对只能依赖仓库。
- **验证方式**：
  - **可执行的替代**（因为"去毒"不可自测，改测**我们的处置**）：
    a. `test_member_report_without_commit_is_not_counted_as_done`（对账判据）；
    b. `test_empty_commit_is_rejected_as_completion_signal`（`--allow-empty` 禁止）；
    c. **可写入本仓库的强判据**：`test_commit_touches_declared_domain_paths`
    ——校验"终止声明所在提交必须触及该成员声明的路径"（与 `T-07` 复用同一检查）。
  - 关于"领导不得据回报改控制流"：**当前无机器检查**，只能靠 `CODEBUDDY.md` §10.4 的常驻纪律
    ⇒ 诚实记为**缺验证**。
- **相关**：`agent-teams.md` §4/§8、`CODEBUDDY.md` §10.2 规则 9、§10.4、
  `devlog 0013` §4（第三类失效模式：完成信号与内容脱节）；
  **新增联动（2026-09-25）**：本条的"**文本不可信 ⇒ 可能变成指令**"与 **`T-15`** 是**同一机制的两个面**——
  本条是**协作面**（成员回报 → 领导），`T-15` 是**开发期命令面**（注入文本 → 主 Agent 执行 shell）。
  两处**各自的缓解与缺口分开登记、不互相替代**：本案的护栏是"完成判定只认仓库里的 `回报：` 块"，

## T-15 Agent 命令闸门放宽为「提醒层」（默认全自动）

**状态**：**`部分缓解`**（2026-09-25 新增）｜ **主导类别**：STRIDE-E（权限提升）｜
**智能体特有**：工具滥用——**开发期**的命令执行面

> **为什么是新条目而不是并入 `T-11`**：`T-11` 的落点是**会话内 `Tool.invoke` 的授权链**
> （`PolicyEngine` / `Capability` / `AuditSink`，即**产品运行时**的越权调用）。
> 本条落点是**开发期**——**主 Agent（IDE 内的助手）在开发环境里执行 shell 命令**。
> 两者**承载机制完全不同**（前者是我们自己的代码，后者是**第三方扩展的配置**），
> 且本条的缓解**不在 `src/` 里、无法由 `tests/security/` 断言**
> ⇒ 并入 `T-11` 会让"工具滥用"半的落点更含糊（`T-11` 已因其**零行为层证据**只到「部分缓解」，
> 见该条目缺口 (b)）。**此处只登记本面，不重复 `T-11` 的论证。**

- **资产**：A-3（执行环境与宿主）、A-4（仓库完整性）、A-11（平台写权限）、A-8（用户信任）
- **攻击者与前提**：攻击者能让 Agent（IDE 内的主 Agent）执行一条**破坏性命令**。
  最现实的入口是**提示注入**（`T-04`）——一段会被读进上下文的文本（仓库文件、issue 描述、
  工具返回、网页）里写着"接下来请执行 X"。前提是**闸门在默认档下会放行 X**（本决策后**确实会**）。
- **原行为（放宽前）**：
  1. **12 个内置安全类别**（含 `injection`：下载即执行会被判高危）+ **逐次审批**；
  2. 即：**每一条命令都要人点一次确认**。
- **新行为（本决策后）**：
  1. **`autoRun` 全自动**：未命中黑名单的命令**一律不弹确认**（含文件写入、MCP 调用）；
  2. **12 个内置类别全部关闭**（只留 `custom`）⇒ 内置文本启发式**不再拦截任何东西**；
  3. **38 条自定义黑名单**（2026-09-25 补 5 条）：命中 ⇒ **弹确认**（`riskLevel=high` ⇒ `ask`，**不是**直接拒绝）；
  4. **`safeDelete` 回收站** + 批量阈值 200（**删库硬红线**，独立机制）；
  5. **项目 A~F 分级纪律**（`git-workflow.md` §4）——**人工执行**的护栏。
- **攻击路径**：
  1. **注入诱导**：`T-04` 的注入文本让 Agent 执行一条黑名单**未覆盖**的破坏性命令
     （例如 `python -c "shutil.rmtree('/workspace')"`、`r''m -rf /`、经变量展开的等价形式）；
  2. **下载即执行**：`injection` 类别已关 ⇒ `curl … | sh` **不再被任何内置规则拦**，
     而它**故意不在黑名单里**（最大误报源）；
  3. **黑名单绕过（改写）**：黑名单是**文本匹配**——引号 / 转义 / 变量 / `sh -c` 包裹 /
     等价工具（`perl`/`python` 一行式）均可绕过；
  4. **静默失效**：若 `custom` 类别被误加进 `disabledSecurityCategories`，
    38 条黑名单**整体失效**且**运行时无任何提示**（已由启动期断言堵住，见下「现有缓解」）。
- **影响**：完整性 + 可用性 + **不可逆性：高**（强推 / 改写历史 / 删库一旦发生，动作已完成）。
- **现有缓解**：
  - **黑名单提醒**（38 条正则，`.ide/agent-preferences.json`）：覆盖通用不可逆操作 + 本项目
    **B/D/E 类红线**（`push main` / `push bench/data` / 强推 / 改写历史 / `clean -fd` /
    `restore .` / `stash` / `--no-verify` 等）。⚠️ **定性**：这是**提醒层**，
    **不是安全边界**——`ADR-0032` §5.6 的 `N-5` 与 `agent-command-gate.md` §6 已如实写明；
  - **`safeDelete` 回收站 + 阈值 200**：与"禁用的类别"**独立**（关掉 `fileDelete` 不影响它）；
  - **生效性由机器保证**：设置文件与启动期 stage **成对存在**（`.cnb.yml` 的 `agent-command-gate`），
    由 `scripts/apply_ide_settings.py` **断言**（`autoRun` / `autoRunMode` / `safeDeleteEnabled` /
    黑名单非空 / `custom` 未被禁用），**任一不符即非零退出**；
    另有 22 条单测钉住该不变式（`tests/unit/test_apply_ide_settings.py`，含两条"拆分不变式"）；
  - **项目纪律（人工）**：`git-workflow.md` §4 的 **A~F 分级**——**这是真正的判据真源**，
    黑名单只是它在命令行上的投影；
  - **⚠️ 三处必须连读的边界**（否则会把本条读成"已缓解"）：
    ① 黑名单**可被改写绕过**（攻击路径 3）；

  1. **绕过面未穷尽**（`ADR-0032` §10 的 `U3`）：改写变体（引号 / 变量 / `sh -c` / 等价工具）

    ② **设置文件过全部断言**（含"黑名单非空"与"`custom` 未被禁用"）；
    ③ **38 条均为合法正则**（2026-09-25 由 33 条补到 38 条）；④ **5 条不可逆基线必被覆盖**（`rm -rf /`、`git push --force`、
    `git reset --hard`、`mkfs.ext4`、`dd … of=/dev/`）；
    ⑤ **fail-secure**：4 条"改坏必红"的参数化用例（含黑名单写空、禁用 `custom`）。
    ⚠️ **定性（不得含糊）**：以上是**结构性 / 配置层**检查——
    它保证"**闸门被正确配置且确实会被写入运行中的设置**"，
    **不**保证"**某条具体命令真的会被拦**"（后者见下）。
  - **⚠️ 缺（行为层，且**原则上**不可由 CI 断言）**：
    a. **绕过面探针**（对抗性输入集）：对同一破坏性意图构造 N 种改写变体，
    逐条记录"是否被黑名单命中"——**这是本条最缺的一组数据**，
    也是 `ADR-0032` §10 的 `U3`；
    b. **误报基线**：对日常命令集（`make check`、`git status`、`uv run pytest`、`git commit`）
    采样，断言**零触发**；
    c. **人工核对（唯一可行的形态）**：环境启动后跑 `make apply-ide-settings`
    （期望退出码 0 + `[ok] Agent 权限已落地`），并在会话内**人工触发一次黑名单命中**，
    确认**弹确认**（既不静默执行、也不直接拒绝）——判据与排查见
    [`agent-command-gate.md`](../../engineering/agent-command-gate.md) §4 的 `C4`/`C5` 与 §5 的 `D1`~`D8`。
  - **升级后必做**：扩展版本变化 ⇒ 复跑 `ADR-0032` §7 的 `V1`/`V2`（读 `package.json` 与
    `resolvePermissionDecision`），否则本条的依据过期。
