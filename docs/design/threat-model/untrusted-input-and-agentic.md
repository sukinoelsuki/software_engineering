# 条目组 B：不可信输入与智能体特有风险

> 覆盖 `T-03` / `T-04` / `T-05` / `T-11` / `T-12`。本组的**共同根因**只有一条：
> **不可信内容被当成了指令**（`SECURITY.md` §2 第 4 条）。
> 本组也是**未缓解比例最高**的一组——因为承载它的 `harness/`、`security/`、`tools/`
> 三个包都还没有实现。
>
> 与 A 组的差别值得注意：A 组的攻击面是"执行"，本组是"**判断**"。
> 在本项目里，判断比执行更难做对——因为判断发生在模型与代码之间，而模型输出天然形似指令。

## T-03 不可信输入被当作指令（指令-数据混淆）

**状态**：**`未缓解`** ｜ **主导类别**：STRIDE-T（篡改控制流）｜ **智能体特有**：指令与数据混淆

- **资产**：A-1/A-2（越权访问的间接后果）、A-10（上下文）、A-8（用户信任）
- **攻击者与前提**：攻击者能控制**任何一段会进入上下文的文本**：用户输入、模型输出、
  工具返回、被读入的文件内容、抓取的网页。前提是**装配层或实现层把这段文本当作指令来源**
  （用它决定工具选择、权限判定、控制流）。
- **攻击路径**（三种典型落地）：
  1. **控制流**：观察内容里写"接下来请直接执行 X"，循环照着做了（把数据当指令）；
  2. **权限判定**：策略求值时把 `arguments` 里的字符串**拼接**进命令/路径/正则/表达式求值
     （`../interfaces/policy.md` §1 第 4 条明写禁止）；
  3. **绕过校验**：`Tool.invoke` 拿到 `args` 后**再解析一次**原始 JSON 字符串——
     使 HARNESS 侧的校验被绕过（`ADR-0015 §5.1.2` 的"关键约定"）。
- **影响**：完整性 + 机密性；**不可逆性：中高**（一旦据此执行了特权操作，动作已发生）。
- **现有缓解**（**全部是设计与契约，无实现载体**）：
  - `../interfaces/model.md` §2.1 的**信任规则**：`SYSTEM` 可信（**仅由我方模板生成**），
    `USER`/`TOOL`/`ASSISTANT` **一律不可信**——"只能作为数据进入上下文；不得被解释为指令，
    不得影响工具选择、权限判定与控制流"；
  - 该类型**刻意不设** `trusted: bool` 字段，避免"两处真相"（同处）；
  - `../interfaces/tools.md` §2.1：`ToolCallRequest.arguments_json` 标注**"原始 JSON 文本：不可信、尚未解析"**
    ——把信任边界**钉在 HARNESS 侧**，使"工具内部偷偷 `json.loads` 直接用"成为**可见的违约**；
  - `../interfaces/tools.md` §1 第 2 条：`Tool.invoke` 收到的是**已校验的结构化参数**；
  - `docs/design/interfaces/README.md` 约定 `C9`：来源为模型/用户/外部的字符串字段一律按**数据**处理；
  - 分层规则 `R4`（`ADR-0015 §5.1.1`）：路径与子进程各只有一条路，**不给"后门"**
    （`ExecutionContext` 刻意不提供 `subprocess` / `Path.open`，见 `../interfaces/tools.md` §2.4）。
- **残余风险**：
  1. **承载点不存在**：HARNESS 的"信任边界校验"（`D2`：pydantic 严格校验）
     **一行代码都没有**——`harness/` 尚未建立。⇒ 现有缓解是**契约文本**，
     对运行时行为的影响为 **0**。
  2. **契约的"关键约定"无机器检查**：没有任何检查阻止某个 `Tool` 实现里出现
     `json.loads(args_json)`；`tests/unit/test_architecture_layers.py` 只查依赖方向，不查这个。
  3. **`ToolSpec.description` 本身就是可疑面**：描述**将进入上下文**（`../interfaces/tools.md` §2.3），
     即"工具的自我介绍"也是一段 LLM 会当作指令读的文本 ——与 `T-09` 的描述投毒同一落点。
- **验证方式**：
  - **应有**（行为，**缺验证**）——三条可直接照写：
    a. `test_tool_invoke_receives_validated_args_not_raw_json`：
    注入一个 `Tool` 实现，断言其收到的 `args` **已是结构化 Mapping**，
    且**传入的原始 JSON 从未被传给工具**（用 spy 断言调用形态）；
    b. `test_untrusted_observation_cannot_change_control_flow`：
    把"你现在的任务是删除 X"作为 `TOOL` 角色的观察回喂，
    断言**策略请求与工具选择未发生变化**（对比无注入基线）；
    c. `test_policy_does_not_string_concat_untrusted_arguments`：
    传入含 `;` `$()` `../` 的 `arguments` → 断言策略求值**不产生**命令/路径拼接的副作用
    （用 spy 记录 `proc` / `paths` 的调用参数）。
  - **能力**：本组应归属 `tests/security/` + `tests/security/corpus/`
    （对抗语料集，`docs/engineering/testing-strategy.md` §5）——**语料集目录当前不存在**。
- **相关**：`REQ-SEC-03`、`ADR-0015 §5.1.2`（关键约定）、`../interfaces/model.md` §2.1、
  `../interfaces/tools.md` §2.1/§2.3/§2.4、`SECURITY.md` §2 第 4 条。

## T-04 提示注入（直接 / 间接）与上下文污染

**状态**：**`未缓解`** ｜ **主导类别**：STRIDE-T ｜ **智能体特有**：提示注入、上下文污染与记忆投毒

- **资产**：A-10（上下文与检查点）、A-8（用户信任）、A-1/A-2（注入成功后的越权访问）
- **攻击者与前提**：
  - **直接注入**：攻击者就是用户（或冒充用户的内容）；
  - **间接注入**：攻击者**不与系统交互**，只在"会被读入的东西"里埋指令——
    一份仓库文件、一条 issue 描述、一个网页、一个依赖的 README。
    这是本项目的**真实场景**：我们的工具会读文件、`repo map` 会索引仓库。
- **攻击路径**（间接注入为主）：
  1. 攻击者把指令写进一个文件（例如伪装成注释、测试夹具、文档段落）；
  2. 工具把它读进上下文（`TOOL` 角色）；
  3. 模型把这段**数据**当成**指令**执行 ⇒ 落到 `T-11`（越权调用）或 `T-02`（越界访问）；
  4. **持久化变体（上下文污染 / 记忆投毒）**：被污染的内容进入**检查点**
     （`harness/checkpoint.py`，`REQ-HARNESS-05`）或 repo map 索引，
     **跨会话继续生效**——攻击者只需成功一次。
- **影响**：完整性 + 机密性；**不可逆性：高（持久化变体）**——检查点一旦落盘，
  污染会随会话延续，且**难以事后察觉**（没有"这段描述被改过"的记录）。
- **现有缓解**（**设计层，无实现**）：
  - 同 `T-03` 的信任规则（`SYSTEM` 可信 / 其余一律数据）；
  - **工具裁剪 + 提示分级**（`REQ-HARNESS-03`/`04`）在设计上降低了暴露面；
  - **观察屏蔽与上下文压缩**（`ADR-0015 §5.3` 自研模块 4：`harness/context/`）
    ——"压缩"天然是一次**丢弃可疑内容的时机**；
  - `REQ-SEC-04`/`REQ-SEC-09`（输出侧防护与对抗回归）已列需求；
  - `ADR-0015 §5.2.6` 明确**不引入** `LLM Guard` / `garak` / `promptfoo`，
    理由是"**都要建立在威胁模型之上；威胁模型当前 0 条，先建模型再选工具**"。
- **残余风险**：
  1. **注入语料集不存在**（`tests/security/corpus/` 未建立）⇒ **没有任何回归能力**：
     今天拦住的注入，明天可能因为一句提示词改动而失效，且**无人知道**。
  2. **`ADR-0015 §5.2.6` 的阻塞条件已解除（本目录即威胁模型）**，但选型**尚未开始**
     ⇒ 输出侧防护当前为 **0**。
  3. **检查点的完整性无设计**：`harness/checkpoint.py` 尚未设计；
     "检查点内容是否可信"没有任何约定（它显然是**不可信**的——里面装的是模型与工具的产出）。
  4. **弱模型放大风险**：4B/8B 档位对"数据 vs 指令"的区分能力更弱（`R-1` 风险），
     而**按档位调整防护强度**这件事还没设计。
- **验证方式**：
  - **应有**（**缺验证**，本组最缺）：
    a. **注入语料集**（`tests/security/corpus/`）：直接注入 5~10 条 + 间接注入 5~10 条
    （文件内藏指令、文档段落藏指令、代码注释藏指令、工具描述藏指令），
    每条标注"期望行为 = 不改变工具选择/权限判定"。**可复用、可扩充、纳入版本管理**；
    b. `test_repo_file_with_embedded_instructions_does_not_change_tool_selection`（间接注入）；
    c. `test_checkpoint_roundtrip_does_not_promote_injected_text_to_instructions`
    （持久化变体的**专门**用例——检查点写入-读回后，注入文本仍必须是数据）。
  - **判据必须是"行为未变"**（对比基线），**不能**是"模型说了拒绝"——后者可被绕过且不稳定。
- **相关**：`REQ-SEC-04`/`REQ-SEC-09`、`REQ-HARNESS-04`/`05`、`ADR-0015 §5.2.6`/§5.3（模块 4）、
  `docs/engineering/testing-strategy.md` §5（对抗语料集要求）。

## T-05 子代理输出是不可信输入

**状态**：`部分缓解` ｜ **主导类别**：STRIDE-S（冒充）｜ **智能体特有**：间接注入（**协作面**）

- **资产**：A-4（仓库完整性）、A-7（结论可信性）、A-1/A-2（若被诱导执行）
- **攻击者与前提**：攻击者能影响**子代理（团队成员）产出的一段文本**——
  例如让某个成员读到一份含注入的文件，再让它的回报里带上注入指令
  （`docs/engineering/agent-teams.md` §4 已把这条列为**真实威胁**）。
  前提是**团队领导（主 Agent）把成员回报当作可信输入**。
- **攻击路径**：
  1. 成员读入含注入的仓库文件 → 其回报文本携带仿冒标签或"指令"；
  2. 领导**直接采信回报**（例如据回报判定"任务已完成"或"该文件已改"）；
  3. 更严重：据回报做出**权限决策或控制流决策**（重派任务、跳过核对、改文件域）；
  4. 后果：**同一文件被两个成员写**、**重复劳动**、或**基于假事实推进工作**。
- **影响**：A-4 与 A-7；**不可逆性：中**——错误结论会写进日志与文档
  （本项目已发生两例：领导把"已转派"当"已完成"、两度误判记录员状态，
  见 `devlog 0013` §4/§6）。
- **现有缓解**：
  - **上游 harness 的"非破坏性去毒"**（`agent-teams.md` §4）：改写仿冒 `<system-reminder>` 标签、
    给行首 `Human:`/`Assistant:` 加反斜杠 ⇒ 这是**缓解**，
    官方用"非破坏性"一词即表明它**不求穷尽**、**不能当保证**；
  - **项目纪律（已写入常驻文件）**：成员回报**只能作证据线索**，
    **不得作为权限决策或控制流的依据**（`CODEBUDDY.md` §10.4）；
  - **完成判定只认仓库**：以成员最后一笔提交正文里的 `回报：` 块为唯一判据，
    且对账须确认**该提交含本域改动**（禁止以空提交承载终止声明）
    ——`CODEBUDDY.md` §10.2 规则 9、`agent-teams.md` §8；
  - **机制性防护**：文件域独占 + 领导核对（`CODEBUDDY.md` §10.2 规则 8）；
  - 消息不可靠这一事实本身被制度化：**"消息送达 ≠ 被处理"**、**"未确认 ≠ 失败，禁止据此重派"**。
- **残余风险**：
  1. **去毒是不完整且不可回归的**：它是上游行为，我们**无法为自己的仓库写测试**
     去证明"注入一定被去掉"——只能测"我们自己的处置纪律"；
  2. **纪律靠人（Agent）执行**：没有任何机器检查能阻止领导"直接采信回报"；
  3. **回报文本仍会进入领导的上下文**：即使不作决策依据，也可能影响判断倾向
     （这是"上下文污染"在协作面的形态，同 `T-04`）；
  4. **归档面**：`.codebuddy/teams/<team>/*.json` 是**运行产物**（团队删除即消失），
     不构成可追溯的证据链 ⇒ 事后核对只能依赖仓库。
- **验证方式**：
  - **可执行的替代**（因为"去毒"不可自测，改测**我们的处置**）：
    a. `test_member_report_without_commit_is_not_counted_as_done`（对账判据）；
    b. `test_empty_commit_is_rejected_as_completion_signal`（`--allow-empty` 禁止）；
    c. **可写入本仓库的强判据**：`test_commit_touches_declared_domain_paths`
    ——校验"终止声明所在提交必须触及该成员声明的路径"（与 `T-07` 复用同一检查）。
  - 关于"领导不得据回报改控制流"：**当前无机器检查**，只能靠 `CODEBUDDY.md` §10.4 的常驻纪律
    ⇒ 诚实记为**缺验证**。
- **相关**：`agent-teams.md` §4/§8、`CODEBUDDY.md` §10.2 规则 9、§10.4、
  `devlog 0013` §4（第三类失效模式：完成信号与内容脱节）。

## T-11 越权工具调用与工具滥用

**状态**：**`未缓解`** ｜ **主导类别**：STRIDE-E ｜ **智能体特有**：工具滥用与越权调用

- **资产**：A-1/A-2（被越权访问/修改的文件）、A-3（被执行的危险命令）、A-6（审计）、A-8（用户信任）
- **攻击者与前提**：攻击者能让模型**请求一个它不该有的能力**——经提示注入（`T-04`）、
  经用户误操作、或**模型单纯幻觉出一个不存在的工具**（弱模型尤甚，
  `../interfaces/tools.md` §2.6 明确把这条列为**预期的不可信输入**）。
- **攻击路径**：
  1. 模型返回 `tool_calls`，`name` 指向未授予 `EXECUTE_COMMAND` / `WRITE_FILE` 的工具；
  2. 若"未知工具 / 未授权能力"没有被显式拒绝 ⇒ 执行；
  3. 变体 A：**诚实的能力请求被错误的策略放行**（策略求值出错却返回 allow）；
  4. 变体 B：**审计缺失** ⇒ 越权发生了但无法回放（`REQ-SEC-06` 的验收对象）。
- **影响**：完整性 + 机密性 + 不可抵赖性；**不可逆性：高**（特权操作已执行）。
- **现有缓解**（**契约完备、实现为零**）：
  - `default-deny` 默认值取向（`../interfaces/policy.md` §1 第 1 条）；
  - **四格语义**（`../interfaces/policy.md` §2.4）：`allow × requires_confirmation` 的四种组合，
    含 `False/False` = **硬拒绝**（`CRITICAL`：连人工确认也不接受）；
  - **求值失败的收敛**（`../interfaces/policy.md` §2.5）：任何异常 ⇒
    `allow=False, requires_confirmation=True, risk_level=CRITICAL`；**禁止**异常逃逸为 allow；
  - **审计失败必须冒泡**（同处；`../interfaces/audit.md` §2.4）——
    与"求值失败收敛为拒绝"**处置相反**，契约已把这条写成实现顺序；
  - **未知工具返回 `None`**（`../interfaces/tools.md` §2.6）：`resolve()` 返回可选值而非抛异常，
    使"未知工具 ⇒ 拒绝 + 审计"成为一条**显式可测**的路径；
  - **`PolicyDecision.audit_id` = 审计事件 `event_id`**（`../interfaces/policy.md` §2.4）：
    给"回放"一个**显式关联键**，不靠时间戳猜。
- **残余风险**：
  1. **`security/policy.py` 未实现** ⇒ 上述全部为**纸面**；`REQ-SEC-01`
     （"未授权操作拦截率 100%"）**当前拦截率不可测**；
  2. **审计未实现** ⇒ "被拒绝**且**有可回放记录"这一**双条件**验收中，
     第二个条件**必然失败**；
  3. **审批门（"本次/总是/拒绝"）的持久授权表示仍是未决项**
     （`../interfaces/README.md` U3）⇒ "总是允许"一旦落地，可能是**长期越权面**，
     且**撤销路径未设计**；
  4. **能力粒度刻意粗**（4 个 `Capability` 成员，`../interfaces/policy.md` §2.1）：
     `WRITE_FILE` 不区分"写工作目录"与"写 `/etc`"——差别由 `RiskLevel` 逐次求值承担，
     而 `RiskLevel` 的产生规则**尚未设计**（只有等级→处置的映射表）。
- **验证方式**：
  - **应有**（**缺验证**）——即 `ADR-0015 §7.2` 的 **`S1`**
    `test_unauthorized_tool_call_is_denied_and_audited`：
    ① 能力缺失时调用被拒；② **审计中存在可回放记录**（`audit_id` 能查回事件）。
    **落地位置 `tests/security/`；当前 `S1` 未落地**（验证工程师进行中）。
  - **建议补足**（契约已给判据，可直接写）：把 §2.4 的**四格**逐一断言
    （`True/False`、`True/True`、`False/True`、`False/False`），
    而不是只断言 `allow` 一个布尔；并加一条
    `test_policy_evaluation_error_is_denied_not_allowed`（注入会抛异常的规则 → 断言 deny）；
    再加一条 `test_audit_emit_failure_propagates_and_is_not_disguised_as_denial`
    （审计故障**不得**被伪装成普通拒绝——这是契约里最容易实现错的一处）。
- **相关**：`REQ-SEC-01`/`02`/`06`/`08`、`ADR-0015 §5.1.2`/§5.3（模块 3）/§7.2（`S1`）、
  `../interfaces/policy.md`、`../interfaces/audit.md`、`../interfaces/tools.md` §2.6。

## T-12 领域包加载代码（动态导入不可信模块）

**状态**：**`未缓解`** ｜ **主导类别**：STRIDE-E

- **资产**：A-3（宿主）、A-4（仓库）、A-8（用户信任）
- **攻击者与前提**：攻击者能提供一个**领域包目录**（Domain Pack）。
  领域包是"声明式配置包"（提示片段 / 工具白名单 / 安全策略 / 输出规范），
  但**目录里完全可以放一个 `.py` 文件**。前提是加载器"顺手支持一下 Python 扩展"。
- **攻击路径**：
  1. 攻击者交付一个功能完整的 pack，附一个 `pack_hooks.py`（或 `__init__.py`）；
  2. 加载器 `import` 它（或 `exec` 其内容）⇒ **任意代码执行**；
  3. 此时**没有任何沙箱**在场——因为这是在主进程里 `import`，不走 `foundation.proc`；
  4. 后果：完全等同于在宿主上运行攻击者代码（并吞掉 `T-01` 的全部隔离）。
- **影响**：机密性 + 完整性 + 可用性；**不可逆性：高**。
- **现有缓解**（**规则已定，无实现**）：
  - **硬规则 `R5`**（`ADR-0015 §5.1.1`）：领域包**只加载声明式配置**（TOML/JSON），
    **禁止加载其中的 Python 代码**；
  - `SECURITY.md` §3 硬性规则："禁止动态导入来自不可信来源的模块"；
  - 设计上把 pack 的能力限定为"**只能选择，不能新增**"：
    pack 只能**选择** `tools/` 注册表里已有的工具，**不能新增代码**
    （`ADR-0015 §5.3` 模块 5）；
  - pack 内容用 `D2` 的校验组件（pydantic）在**边界处**校验 schema。
- **残余风险**：
  1. **`harness/domain_pack.py` 不存在** ⇒ `R5` 目前**无被测对象**
     （`devlog 0013` §7 已登记："R5 暂无代码可测"）；`tests/unit/test_architecture_layers.py`
     的检查项里也**没有**"禁止动态导入"的检查；
  2. **"只加载 TOML/JSON"这条约定本身无机器检查**：没有检查阻止有人写
     `importlib.import_module(pack_dir / "hooks")`；
  3. **pack 的 schema 校验失败必须拒绝（fail-secure）**——这条同样只在设计里。
- **验证方式**：
  - **应有**（**缺验证**）——即 `ADR-0015 §7.2` 的 **`S3`**
    `test_domain_pack_python_code_is_never_imported`：
    在 pack 目录里放一个**含副作用**的 `.py`（例如写一个哨兵文件），
    加载后断言 ① 哨兵文件**不存在**（该文件从未被执行）；② 只接受声明式配置；
    ③ 配置非法时**加载失败即拒绝**（fail-secure，不是"跳过该项继续"）。
    **落地位置 `tests/security/`；当前 `S3` 未落地**，
    且**在被测对象（`domain_pack`）落地之前无法先行**——这是本轮**唯一一条"依赖实现才能验证"**的条目。
  - 建议同时加一条**静态**检查：`src/` 下不得出现 `importlib.import_module` / `__import__` /
    `exec(` / `eval(`（可复用 `test_architecture_layers.py` 的 AST 扫描框架，
    与 `T-01` 的 `subprocess` 唯一入口检查同一族）。**这条现在就能写**，不必等实现。
