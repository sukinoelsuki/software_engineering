## T-06 安全豁免被静默放宽

**状态**：`部分缓解` ｜ **主导类别**：检查的有效性（**本项目自有的类别**）

- **资产**：A-7（"检查确实在生效"这一结论）、A-4（仓库完整性）
- **攻击者与前提**：**不需要外部攻击者**。触发条件是**任何能改注释文本的人或模型**的一个无心写法
  ——包括被诱导的模型产出的一行"带理由的豁免注释"。**攻击面就是注释本身**，而注释是最不被审查的地方。
- **攻击路径**：
  1. 在 `# nosec` / `# noqa` 之后追加自由文本（例如"理由：见 `ADR-0014 §2.9`"）；
  2. 扫描器把标记后的词元当作**规则号候选**；
  3. 其中出现的**合法规则号**被采纳为该行的豁免集合 ⇒ 该规则在该行被**悄然豁免**；
  4. 门禁仍 `exit 0`、无任何报错 ⇒ 豁免登记表与实际豁免**不一致**，且**长期无人察觉**。
- **影响**：完整性（检查被削弱）；**不可逆性：低~中**——不是数据被毁，而是
  "这里检查过了"这一结论**永久为假**，并被后续设计引用（A-7）。
- **现有缓解**（**已生效**，是本组唯一有机器检查的一条）：
  - **格式 `F1` / 红线 `S-7`**：标记行**只写规则号**；理由写在**紧邻其上的独立注释行**；
    **理由中不得出现其它规则号**；两类标记（`# noqa` / `# nosec`）全场统一
    （`ADR-0014 §2.9.1`/§2.9.2、`SECURITY.md` §3 `S-7`、`pyproject.toml:176-178`）；
  - **E4 结构性机器检查**：`tests/unit/test_bench_encapsulation.py:129-153`——
    ① 豁免标记**只允许出现在** `foundation/proc.py`（`:139-143`）；
    ② 标记后**只能有规则号**（`:144-146`，正则见 `:44`）；
    ③ 每行 id 集合**恰好等于**预期（`:147-153`，期望集 `:33-39` = 1×`B404` + 3×`B603` + 3×`S603`）；
  - **变异探针**已证明该检查**非恒过**（`aedbcc8`：`# nosec B404, B101` 与"标记后加自由文本"两种违规均使用例失败）；
  - **逐点豁免理由 + 4↔4 承载关系**：豁免点与规则号一一对应、无多无少（`ADR-0014 §2.9.1(b)`）。
- **残余风险**：
  1. **E4 的扫描范围只有 `src/`**（`test_bench_encapsulation.py:25` 的 `SRC_ROOT`）
     ⇒ `tests/`、`scripts/`、`.cnb.yml`、`docs/` 里的豁免标记**完全不受检查**。
     配套地，`ruff` 对 `tests/**` **整体关闭了 `S` 规则集**（`pyproject.toml:96`），
     `bandit` 的 `exclude_dirs` 亦含 `tests`（`pyproject.toml:182`）⇒ 测试目录的双重豁免区。
  2. **`E1`~`E3` 靠人工执行、未纳入 `make check`**：`Makefile:88` 只跑 `bandit -q -r src`，
     **只看退出码**，**不断言** WARNING 计数 = 0、skip 计数 = 4、`--ignore-nosec` 恰好 4 条
     ⇒ "抑制仍然精确"这件事**没有自动回归**。
  3. **【本轮实测·新发现】`bandit` 不自动读取 `pyproject.toml` 的 `[tool.bandit]`**：
     `bandit` CLI 的自动发现**只针对 `.bandit`**（`.venv/.../bandit/cli/main.py:57` 的 `fnmatch`），
     toml 配置**仅在显式 `-c` 时**才被解析（`bandit/core/config.py:46` 的 `config_file.endswith(".toml")`），
     而**仓库内没有 `.bandit` 文件**（实测 `ls .bandit` → No such file）。
     ⇒ `Makefile:88` 的 `make security-bandit` **不适用** `skips` / `exclude_dirs` / `targets`。
     **方向上这是 fail-secure**（门禁比配置更严，`B101` 实际未豁免），
     但**配置声明的意图在门禁里不生效**——与一致性报告 A-9（"绿着但没生效"）**同一族**，
     必须登记，否则下次有人往 `skips` 里加一条就会以为它生效了。
  4. **`ruff` 的 `RUF100` 不在门禁语义内**：`# noqa: <不在当前选集中的规则号>` 不会报错
     （`S404` 处于 preview、当前未启用即为实例，`ADR-0014 §2.9.1(a)`）
     ⇒ 登记表里可能出现"**虚的规则号**"。
- **验证方式**：
  - **已有**：E4（结构性，`make check` 内自动跑）；E1/E2/E3（人工，命令与判据见 `ADR-0014 §2.9.1`）。
  - **本轮实测证据（可复现）**——原结论**已复现**，且**排除了一次可能的混淆**：

    ```text
    # 探针（bandit 1.9.4，在**无项目配置**的目录中运行，避免 pyproject 干扰）
    $ mkdir -p /tmp/tm-probe && cd /tmp/tm-probe
    $ printf 'assert True\n' > f.py
    $ printf 'assert True  # nosec NOPE mentions B101\n' > g.py
    $ bandit -q f.py >/dev/null 2>&1; echo rc_F=$?      # → 1  （B101 被报出）
    $ bandit -q g.py >/dev/null 2>&1; echo rc_G=$?      # → 0  （B101 被静默豁免）

    # 机制边界：只豁免"被提到的规则"，不波及未提到的规则
    $ printf 'eval("1")  # nosec NOPE mentions B101 and password\n' > b.py
    $ bandit -q b.py >/dev/null 2>&1; echo rc_b=$?      # → 1  （B307 仍被报出）
    $ printf 'eval("1")  # nosec B101\n' > c.py
    $ bandit -q c.py >/dev/null 2>&1; echo rc_c=$?      # → 1  （列了错的规则号 → 不豁免）
    $ printf 'eval("1")  # nosec\n' > d.py
    $ bandit -q d.py >/dev/null 2>&1; echo rc_d=$?      # → 0  （裸 nosec → 整行豁免）
    $ printf 'eval("1")  # nosec B307\n' > e.py
    $ bandit -q e.py >/dev/null 2>&1; echo rc_e=$?      # → 0  （精确豁免）

    # 配置发现：toml 只在 -c 时生效
    $ cd /workspace && bandit -q /tmp/tm-probe/f.py >/dev/null 2>&1; echo rc_noc=$?                  # → 1（配置未生效）
    $ cd /workspace && bandit -q -c pyproject.toml /tmp/tm-probe/f.py >/dev/null 2>&1; echo rc_cfg=$? # → 0（配置生效）
    ```

    **结论**：① `# nosec` 后的自由文本**确实**能静默豁免其中出现的合法规则号——**原结论成立**；
    ② 该机制**只影响被提到的规则**，因此**从退出码上看不出任何异常**
    （这正是它危险的原因，也是"探针必须覆盖退出码 / stderr / 实际抑制效果三类输出"的又一处印证）；
    ③ 仓库内**无 `.bandit`**，故 `[tool.bandit]` 在 `make check` 中**不生效**。
    **探针文件已清理**（`rm -rf /tmp/tm-probe`，复核为不存在）。
  - **应有（缺验证）**：
    a. 把 `E1`（`Test in comment` 告警计数 = 0）、`E2`（skip 计数 = 4）、
    `E3`（`--ignore-nosec` 恰好 4 条且位置为 `L26`/`L147`/`L191`/`L229`）写成
    **自动断言**（pytest 用例内调用 bandit 子进程并解析输出，经 `foundation.proc`）；
    b. 把 E4 的扫描范围从 `src/` 扩到 `tests/` `scripts/`，并把"允许出现豁免标记的文件"
    做成**显式白名单**（当前是写死的单文件，等同于隐式白名单）；
    c. **显式化配置发现**：给门禁的 bandit 命令加 `-c pyproject.toml`，**或**把配置迁到 `.bandit`
    ——**两者择一，不得两处各写一套**（`Makefile` 不在架构师域，需**领导裁决**）。

## T-07 共享 git 索引导致跨域混入

**状态**：`部分缓解` ｜ **主导类别**：流程完整性（提交历史与域归属）

- **资产**：A-4（提交历史的**域归属与可追溯性**）、A-7（"这笔改动归谁、改了什么"这一结论）
- **攻击者与前提**：**无外部攻击者**。触发条件 = **两个成员/角色在同一仓库内并发工作**。
  前提：**工作树与 git 索引在同一仓库内全局共享**，而"文件域独占"只保护**文件**、
  **覆盖不到索引**（`CODEBUDDY.md` §10.2 规则 8 已把这条写进规则，因为它真的发生过）。
- **攻击路径**：
  1. A 执行 `git add` 自己的文件（**已暂存、未提交**），开始下一步工作；
  2. B 执行 `git commit`（**不带 `-o` / 不带路径**）；
  3. **A 的暂存内容被 B 的提交一并带走** ⇒ 提交的文件集合与提交信息、域归属**不符**；
  4. 后果：域归属错位（历史失真）、对账时"这笔改动属于谁"无法判定、
     甚至**已完成的工作被误判为未完成**。
- **影响**：A-4 / A-7；**不可逆性：中**——不改写历史则错位永久；改写历史又会动**同一个共享索引**
  （与事故同源，正是当时决定"不改写历史、只登记纪律"的理由）。
- **现有缓解**（**人工纪律，已固化并有一正一反实例**）：
  - `git commit -o -m "<msg>" -- <显式路径>`（`--only`：只提交点名路径，不带走他人暂存）
    ——`CODEBUDDY.md` §10.2 规则 8、`agent-teams.md` §6；
  - **核对与提交必须是两条独立命令**：先单独 `git diff --cached --name-status`，**再**提交；
  - **改完尽快提交**以缩短暂存窗口（窗口极短：实例中对方在"两条命令之间"就完成了提交）；
  - **发现他人已暂存内容不碰**，只在回报中说明；
  - **反例（纪律未生效）**：`6fa010a` 把记录员的暂存内容一并带走（内容完整无缺失，但域归属错位）；
  - **正例（纪律生效）**：`20e7d49` 提交前 `git diff --cached --name-status` 发现索引里躺着
    **他人暂存 7 个文件 / 3 类**，靠"两阶段核对 + `-o` 显式路径"全部排除；
    提交后 `git show --stat` = **6 个文件、`docs/` 零命中**，且反向确认 `-o` **没有吞掉**他人内容。
- **残余风险**：
  1. **完全没有机器检查**：没有任何检查断言"本次提交的路径集合 ⊆ 该成员声明的路径白名单"。
     ⇒ 缓解**靠人每次都执行**，属"靠人执行"类，**不能当作机制**（状态为"部分缓解"正因于此）。
  2. **并发窗口无法靠纪律消除**：索引是全局资源，纪律只能**缩短**窗口、不能关闭它。
  3. **对账判据必须同时看两件事**：① 有没有 `回报：` 终止声明；② 该提交**是否含本域改动**。
     只看前者会把"信号已发、内容滞留工作区"误判为已完成（`devlog 0013` §4 第三类失效模式的实例）；
     该项目已把"禁止空提交承载终止声明"写进 `agent-teams.md` §8。
  4. **钩子读的是工作树而非索引**：pre-commit 在工作树状态下运行，因此"只暂存了 A 的文件、
     但工作树里有 B 的未提交改动"会让钩子扫描到 B 的内容——这是**反向问题**（可用性/噪声），
     本条目只登记安全侧，但知情人不应把它当成"索引被保护了"。
- **验证方式**：
  - **应有（缺验证）**：
    a. `test_commit_touches_only_declared_paths`：对指定提交区间用 `git show --name-only`
    逐笔断言路径集合 ⊆ 该笔提交信息声明的路径；
    b. 或（更强）在提交门禁加一条"提交路径 ⊆ 声明白名单"的检查——**需领导裁决**
    （`.pre-commit-config.yaml` 不在架构师域）。
  - **现在就能做的人工核对（本项目已固化，三步）**：
    `git diff --cached --name-status`（核对）→
    `git commit -o -m "<msg>" -- <显式路径>`（提交）→
    `git show --stat <sha>`（复核路径集合）。
- **相关**：`CODEBUDDY.md` §10.2 规则 8/规则 9、`agent-teams.md` §6/§8、`devlog 0013` §3/§4。

## T-08 基准数据分支的凭据暴露（`CNB_TOKEN`）

**状态**：`部分缓解` ｜ **主导类别**：STRIDE-I（信息泄漏）

- **资产**：A-5（CI 运行期 `CNB_TOKEN`：短时、**限本仓库**、构建结束销毁）、
  以及由其保护的 A-4（仓库与 `bench/data` 时间序列）
- **攻击者与前提**：攻击者能**让不可信代码在 CI 轮次里被执行**（模型产物），
  且该代码能读到宿主环境或逃出隔离（`T-01` 的残余风险）。
  前提的另一半是**执行路径上有"继承父进程环境"的分支**。
- **攻击路径**：
  1. 模型产物被 `bench` 轮次执行（`ADR-0014 §2.8` 的不可信边界：**执行它们 = 执行不可信代码**）；
  2. 若该路径经过 `proc.run(isolation="root")`（`proc.py:142` → `dict(os.environ)`）
     或 `proc.spawn()`（`proc.py:235`，`env=None` 时 `dict(os.environ)`）⇒ **凭据进入子进程**；
  3. 子进程把令牌外传（**出站无控制**，见 `T-10`）或写进产物；
  4. 用令牌推送/改写本仓库——`devlog 0013` §4 已**实证** crontab 事件的令牌具备 `repo-code:rw`。
- **影响**：完整性（仓库可被改）；**不可逆性：中高**——改动可回退，但若 `bench/data` 的
  **可比时间序列**被污染，历史结论全部可疑，那是**不可逆**的（`ADR-0014` 的可比性纪律）。
- **现有缓解**：
  - **干净路径（已实现）**：`proc.run(isolation="user")` 使用 `_isolated_env()`
    （`foundation/proc.py:97-110`）——**刻意不继承 `os.environ`**；
    `ADR-0014 §2.8` 的隔离方式 = 非特权 uid（nobody）+ **清空环境变量** + setrlimit + 一次性工作目录；
    默认值 `BENCH_ISOLATION ?= user`（`Makefile:136`，"CI 必须用这个"）；
  - **凭据纪律**：只用运行期 `CNB_TOKEN`（构建结束销毁）、**不新增任何密钥**、
    经 credential helper 传入、**不写入 remote URL / git config**（`ADR-0014 §2.8`）；
    `SECURITY.md` §3 `S-3`/`S-4`/`S-5`（不可信事件触发的 CI 不得访问密钥）；
  - **推送范围收敛**：固定 `HEAD:bench/data`、**禁止 force**、来源分支白名单（`bench/nightly`）
    （`ADR-0014 §2.1`/§2.8）⇒ 即使令牌泄露，**可写面**被限制在数据分支；
  - rlimit（`proc.py:113-118`）限制泄漏与放大的规模；一次性工作目录限定可读范围。
- **残余风险**（**含本轮读代码得到的两条**）：
  1. **`ADR-0014 §2.8` 自己登记的残余风险**："若非特权子进程逃逸，理论上仍可读到宿主进程的
     `CNB_TOKEN`（短时、限本仓库）"——**未缓解**；
  2. **【本轮读代码得到】`spawn()` 的默认语义是"继承凭据"**：
     `proc.py:218` 的 `env: Mapping[str, str] | None = None`，`:235` 在 `env is None` 时
     `dict(os.environ)`。当前唯一调用者是启动 `llama-server`（**自有二进制、绝对路径**），
     **现状风险低**；但这是一个**容易被误用的默认值**：将来任何"用 `spawn` 跑模型产物"的写法
     都会**静默**把凭据交出去，而**没有任何检查会提示**。
  3. **【本轮读代码得到】`isolation="root"` 无机器检查**：`proc.py:135` 只在 docstring 声明
     "在 CI 中不得使用"；`bench` 侧由 `Makefile:136` 的变量控制，**可被命令行覆盖**
     ⇒ "CI 必须用 `user`"这条**只是默认值，不是约束**。
  4. **无 canary 用例**：没有任何测试证明"子进程看不到凭据"。
- **验证方式**：
  - **应有（缺验证，且可立即写）**——**canary 断言**，这是本仓库唯一可自证的凭据隔离判据：
    `test_child_process_environment_does_not_contain_credentials`：
    在父进程环境注入 `CNB_TOKEN=__canary__` →
    `proc.run([<python>, "-c", "import os;print(sorted(os.environ))"], isolation="user")`
    → 断言 ① `__canary__` **不出现在** stdout/stderr；② 子进程环境**不含** `CNB_TOKEN` 键。
    落地位置：`tests/security/`。
  - **可立即写的静态检查**：断言 `proc.spawn(...)` 的调用点**必须显式传 `env=`**
    （把"继承凭据"从默认行为改成显式选择）；以及断言 `src/` 内 `os.environ` 的使用点落在白名单内。
  - **进一步硬化方向**（`ADR-0014 §2.8` 已列，**未做**）：把"执行"与"发布"拆成两条流水线
    ——执行侧 `sandbox: true`、**无令牌**；代价是编排复杂，留待需要时评估。
- **相关**：`ADR-0014 §2.1`/§2.8/§2.9、`REQ-PERF-08`、`SECURITY.md` §3 `S-3`/`S-4`/`S-5`、
  `foundation/proc.py:97-110`/`:142`/`:218`/`:235`、`Makefile:136`。

## T-09 供应链投毒（依赖 / 权重 / 二进制 / 工具描述）

**状态**：`部分缓解` ｜ **主导类别**：STRIDE-T ｜ **智能体特有**：供应链投毒

- **资产**：A-9（依赖、GGUF 权重、`llama-server` 二进制、外部工具描述）、A-4、A-3
- **攻击者与前提**：攻击者能影响以下任一环：
  ① 一个依赖包的版本或内容（typosquatting / dependency confusion / 被投毒的上游发布）；
  ② 一个模型权重或二进制（**它就是被执行的程序**，比依赖更直接）；
  ③（Should 阶段）一个 MCP server 暴露的**工具描述**。
- **攻击路径**：
  1. **依赖**：未固定版本 / 未核验来源 ⇒ 装到被投毒的版本；
  2. **权重 / 二进制**：来源不明或摘要不匹配 ⇒ 直接在执行路径上植入代码；
     `llama-server` 由 `foundation.proc` 启动（`proc.py:229-236`），
     **它的可信性等价于整个推理链的可信性**；
  3. **工具描述投毒（rug-pull）**：MCP server 首次注册时描述正常、之后改成含注入或误导的描述
     ⇒ 同时触发**上下文污染**（`T-04`）与**越权调用**（`T-11`）；
     注意 `ToolSpec.description` **将进入上下文**（`../interfaces/tools.md` §2.3）。
- **影响**：完整性 + 机密性 + 可用性；**不可逆性：高**——投毒位于执行路径，
  一旦成立则"所有本地结论都不可信"；对 `bench/data` 还可能污染可比时间序列（不可逆）。
- **现有缓解**：
  - `SECURITY.md` §3：`S-3`（依赖锁定版本并记录来源 → `uv.lock` + `make security`）、
    `S-4`（禁止来源不明的权重 / 二进制 / 脚本 → PR 模板必填项）、
    `S-5`（不可信事件触发的 CI 不访问密钥）；
  - **`dependencies = []`**（`pyproject.toml:27`）⇒ **当前运行期依赖为零**，
    供应链面极小。这是"技术栈尚未冻结"的**意外收益，应如实承认**——
    它会在首个依赖写入时消失；
  - `ADR-0015 §5.2` 的**核验纪律**：已核验项注明 PyPI 出处与访问日期，未核验一律标【待核验】，
    **不写印象中的数字**；§5.2.6 的"本期不引入"清单（含 `openai` SDK、MCP SDK、
    任何 agent 编排框架）**主动缩小**了供应链面；
  - **资产摘要校验**：`make bench-verify-assets`（复用构建期脚本，**不引入第二个真源**）；
  - **`description_digest`**（`../interfaces/tools.md` §2.3）：`name + description + parameters_schema`
    规范化后取 sha256；首次见到某 `source` 时记录摘要，之后不一致即**告警并默认拒绝**（fail-secure）；
  - **`pip-audit`** 纳入 `make security`（`Makefile:85-91`）。
- **残余风险**：
  1. **多项【待核验】未完成**（`ADR-0015 §8.2` 的 `V-a`~`V-o`）⇒ `D3` 改选 `urllib3` 的结论
     仍属"**证据不完整**"状态，**不是**"已证优"；
  2. **权重 / 二进制的"来源 + 摘要记录"未落地到产品**：`model/assets.py`
     （GGUF 发现 / sha256 校验 / 预算推荐，`REQ-MODEL-01/02`）**未实现**；
     当前只有**基准侧**的构建期校验脚本 —— 产品侧**无载体**；
  3. **`description_digest` 是"初始口径"**（`../interfaces/README.md` U2 未定稿）：
     覆盖范围与规范化尚未定；`builtin` 工具允许 `None`；**MCP 未接入**
     ⇒ 防 rug-pull 的**能力当前为零**（既无实现、也无被测对象）；
  4. **`pip-audit` 的能力边界必须写清**：它只能匹配**已知漏洞签名**，
     对**尚未披露的投毒无效**；把 `make security` 绿当作"供应链安全"是**探针覆盖不足**的老毛病；
  5. **本条的验证本质上是"登记 + 复核"**：供应链风险的验证依赖外部服务
     （PyPI 页面、平台策略），**不满足"确定性测试"**要求（`docs/engineering/testing-strategy.md` §3）。
     ⇒ **诚实标注：这条不能算作"已被自动化覆盖"**，只能算"有登记纪律 + 有事后复核点"。
- **验证方式**：
  - **已有（部分）**：`make security`（`bandit` + `pip-audit`）；`make bench-verify-assets`（资产摘要）。
  - **应有（缺验证）**：
    a. `test_tool_description_change_is_rejected`：注册期摘要不一致 ⇒ **拒绝使用**（fail-secure）
    ——**依赖 `ToolRegistry` 实现**；
    b. `test_weight_digest_mismatch_is_rejected`：GGUF 摘要不匹配 ⇒ **拒绝加载**
    ——**依赖 `model/assets.py`**；
    c. 每次新增依赖时记录**来源 / 版本 / 许可证 / 体积 / 安全影响**（`D-7`）
    ——**流程性检查，无机器强制**（诚实记为缺验证）。
  - **【待核验】清单与验证方式**：`ADR-0015 §8.2` 的 `V-a`~`V-o`
    （尤其 `V-m`/`V-n`/`V-o`）——访问 PyPI 官方页抄录 `License` / `Requires-Dist` /
    最新版本，读 wheel `METADATA`，并写最小样例验证代理行为与流式读取。
