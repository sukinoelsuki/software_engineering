# 冲突取舍会按内容丢东西：一次分叉合并的复盘

> 主题：解决合并冲突时"整文件取一侧"是危险的——**取舍是按文件做的，丢失是按内容发生的**。
> 来源：2026-09-16 本项目 `chore/env-verification` 与 `develop` 的分叉合并
> （远端合并提交 `7741c75`，PR #3；被丢弃的一侧为 `e2b0594`）。
> 关联：[devlog 0011](../devlog/0011-2026-09-16-分支分叉与开发环境重建.md)。

---

## 我以为

冲突解决时"一律取 develop 一侧"是安全的：develop 更新、更全，
旧分支的工作既然已经在 develop 上"重做并扩展"过，那它就是旧版本的子集。

合并提交里也是这么写的：*"无 PR 分支独有内容丢失（develop 为超集）"*。

## 实际是

**"更新"不等于"包含"**。这次合并丢了三类东西，而且**在合并当时完全看不出来**：

| 丢了什么 | 为什么会被丢 | 证据 |
| --- | --- | --- |
| `.ide/Dockerfile` 的 llama.cpp 版本固定（V-6，commit `69eb250`） | 该文件两侧都改过，按文件取了 develop 侧；develop 侧当时仍是 `git clone --depth 1` 跟随 master | develop 第 177 行 vs 旧分支 `db42ab8` |
| `post-build-checklist.md` 的第 6/7 步（重启后验证清单 + DSpark 实验，135 行实测命令与判据） | 同上；develop 版清单只写到第 5 步，这两步是**旧分支独有** | `grep "重启后\|DSpark" docs/engineering/post-build-checklist.md` 合并后 0 命中 |
| `docs/learning/0002`、`0003` 两篇笔记 | 目录在 develop 上被重命名为 `notes/` 并改用主题命名，取 develop 侧 = 删除旧目录；而 `notes/` 里**没有**这两个主题的对应篇 | `git log develop..e2b0594` 列出 12 个独有提交 |

**最危险的地方**：`git diff c849953 7741c75` 是**空的**——合并结果树与 develop 完全一致。
也就是说，所有"合并成功"的检查（能合、树一致、无冲突标记、链接校验通过）**全部会给出绿灯**，
它们检查的是"合并是否成立"，不是"另一侧有没有被丢掉的东西"。

`git cherry -v develop e2b0594` 同样帮不上忙：12 个提交全部标 `+`（无等价补丁），
但对重命名/重写过的文档来说，`+` 既可能是"丢了"，也可能是"改写了"——**它只比较补丁，不比较内容**。

## 因此

1. **禁止整文件取一侧**。冲突必须按 hunk 判断；若确实要整文件取一侧，
   必须在提交信息里**逐条列出被丢弃的内容**，并说明为什么它是可丢弃的。
2. **合并后必须做"反向核对"**：`git log --oneline <base>..<other>` 拿出另一侧的全部提交，
   逐项确认每一条在合并结果里**有对应物**（可能是重命名、重写、或明确判断为过时）。
   这一步无法用 diff 替代——**树的相等恰恰是丢失的证据，不是安全的证据**。
3. **重命名 + 重写是丢内容的高发组合**：一旦 develop 侧重命名了目录/文件，
   取 develop 侧就等于静默删除另一侧的独有篇目。遇到重命名，先问"旧路径下有没有新路径没有的内容"。
4. **单人 + 云开发环境的额外约束**：环境每次从固定分支（develop）拉起、重启即清空上下文，
   因此"留在分支上没合入"的工作，在下一次会话里**等于不存在**。
   这不是纪律问题，是机制问题——应当用启动自检（列出未合入分支与开放 PR）来兜底，
   而不是靠人记。
