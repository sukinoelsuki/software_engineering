# 探针方法论：如何验证"控制是否真的生效"

> 主题：**验证本身会骗人**。本文记录一套可复用的探针写法，以及踩过的坑。
> 来源：devlog [0007](../devlog/0007-2026-09-15-开发环境验证与W1风险验证.md)、
> [0008](../devlog/0008-2026-09-15-环境资产预置与沙箱后端修正.md)；
> 决策：[ADR-0007](../adr/0007-sandbox-capability-matrix.md)

## 我以为

一条命令退出码是 0、没有报错，就说明它做的事**生效**了。

## 实际是

**在本项目里，"退出码 0 但控制为零"出现了三次，而且全部是我自己误判过或差点误判的：**

| # | 控制手段 | 表面现象 | 真实情况 |
| --- | --- | --- | --- |
| 1 | `firejail --net=none curl example.com` | 退出码 0，输出正常 | **完全没隔离**，出站仍返回 HTTP 200。仅在不加 `--quiet` 时打一行警告 |
| 2 | `docker --memory=64m` + 分配 200 MB | 分配成功，无报错 | **限制未生效**（rootless + `Cgroup Driver: none`） |
| 3 | `docker --pids-limit=16` + 起 50 个进程 | 50 个全部起来 | **限制未生效** |

也就是说：**"命令成功"与"控制生效"是两个独立的事实**，
而失败的方式往往是**沉默**——不报错、不警告、退出码 0。

## 两次自我纠错：探针设计错了，结论就错了

这两次比上面三次更值得记录，因为**错在我，不在工具**。

| 轮次 | 我的做法 | 我当时的结论 | 错在哪 |
| --- | --- | --- | --- |
| 第 1 次 | `--memory=64m` + `dd` 写 `/dev/shm`，写到 64 MB 就停 | "内存限制生效" | 64 MB 恰好是 Docker `--shm-size` 的**默认值**，与内存限制无关。加 `--shm-size=1g` 后同一探针写满 300 MB |
| 第 2 次 | `--memory=64m` + `bytearray(200 MB)` | "限制未生效"（结论对，但推理不牢） | `bytearray` 可能只拿到共享零页，**没有真正触碰物理内存**。改为逐页写入后，结论才可靠 |

**共同点**：探针给出的现象，能被**两种解释**同时产生。我选了其中一种，没有排除另一种。

### 由此得出的写法（核心）

> **写探针时先问：还有哪种解释能产生同样的观测？**
> 若存在竞争解释，必须先设计一个能把它们**分开**的实验，再下结论。

具体手法：

| 手法 | 例子 |
| --- | --- |
| **加一个"必须失败"的用例** | 只验证"正常路径能跑通"是不够的；必须验证"越界时确实被拒" |
| **让两种解释给出不同观测** | 用 `--shm-size=1g` 把"默认 shm 大小"这一解释排除掉 |
| **真正触发目标行为** | 内存要**逐页写**（否则只是拿到了虚拟地址）；网络要**实际发起请求**；文件系统要**实际写** |
| **排除"参数写错"** | 我第一次跑 `--ulimit as=…` 得到的是**用法错误**，不是"限制无效"——差点据此记错一条结论。**先确认命令本身被正确接受，再解释它的效果** |
| **验证结果对称** | 不仅要测"限制生效时会被阻止"，还要测"不设限制时确实不被阻止" |

## 因此（对今后的约束）

1. **任何安全断言都必须有"主动探针"**：尝试越界操作并确认被拒绝。
   **禁止**以"命令退出码为 0""配置写进去了""工具文档这么写"作为生效依据。
2. **探针必须包含负向用例**，且负向用例未通过即判定该控制**不可用**（fail-secure）。
3. **一次探针只能回答一个问题**。想同时验证"内存 + pids + 网络"，就要三个独立探针，
   否则一个"通过"会掩盖另外两个的失败。
4. **控制是否生效取决于宿主是否委派了权限**，与工具本身好坏无关。
   换环境必须重跑探针，不能沿用结论。
5. **记录"我原本以为"**：只有写清错在哪，这条经验才可复用
   （这也是本目录要求三段式写法的原因）。
