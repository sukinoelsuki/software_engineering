# 开发期模型选型：档位名不能推断能力，自报分数不能直接比较

> 主题：给协作 agent 分配模型档位时，怎么判断"哪个模型更强"——以及为什么
> **官方档位名（Flash / Pro）、厂商自报分数、第三方收录站**都不能单独作为依据。
> 来源：2026-09-18 对 CodeBuddy 可用模型的调研（厂商 model card、第三方收录站、
> 社区实测），**全部是二手数据**，出处见文末 §6。
> 关联：[on-device-model-selection.md](on-device-model-selection.md)（那篇讲端侧模型选型）
> ——两篇结论同源：**选型只能由自己的实测给出**，榜单只能当线索。

---

## 1. 一句话结论

**"档位更高 / 单价更贵 / 参数更大"都不能推断能力更强。**
两个模型之间做选择，只能用**同一基准、同一口径**的数字；
且引用时必须标注这个数字是**厂商自报**还是**第三方独立复现**。

---

## 2. 三段式

| | 内容 |
| --- | --- |
| **我以为** | "Flash" 是缩水档（速度优先、能力打折），"Pro / 旗舰"才代表能力上限；贵的自然更强 |
| **实际是** | 同一批可用模型里，**倍率最低的那档（0.03x）在 Terminal-Bench 2.1 上分数最高**（90.60，3/192），高于同批的旗舰档；而一个中价档（0.25x）分数最低（66.0）。**价格与能力在两个方向上都不成比例** |
| **因此** | ① 分配档位**不能按价格或档位名排序**，要按同口径基准 + 价格双维决定；② 看到任何一个模型分数，先问"这是满血口径吗"；③ 最终只有自己的实测算数 |

---

## 3. 可比数据（统一口径：Terminal-Bench 2.1，越高越好）

| 模型 | Terminal-Bench 2.1 | CodeBuddy 倍率 | 数据性质 |
| --- | --- | --- | --- |
| **DeepSeek-V4.1-Flash** | **90.60**（3/192） | **0.03x** | 收录站汇总 |
| Claude Opus 5 | 89.10 | —（不在可用列表） | 收录站汇总 |
| Kimi K3 | 85.00 | 1.62x | 收录站汇总 |
| Hy4 preview | 85.4 | 0.29x 白天 / **0（夜间）** | 厂商 model card |
| GLM-5.3-Flash | 84.3（11/46） | 0.06x | 厂商自报 |
| GLM-5.3（旗舰） | 83.90 ~ **88.2**（两源不一致） | 0.79x | 收录站 / 第三方站 |
| **MiniMax-M3** | **66.0** | **0.25x** | 厂商自报 |

**读法**：把"倍率"和"同口径分数"并排看，才能发现
**0.25x 的那个（M3）比 0.06x 的那个弱 18 个点**——即"贵四倍、弱一截"。
单看价格或单看分数都看不出来。

---

## 4. 四个容易踩的坑

1. **档位名会骗人**：同系列里 Flash 可以是"重新训练的新架构 + 新配方"，
   而不是"旗舰蒸馏出来的小模型"；也有厂商把 Flash 用在超长上下文场景上。
   **档位名描述的是定位，不是能力排名。**
2. **厂商自报分数是"满血口径"**：所有厂商自报的 agent 类分数都是
   **带工具 + 最高思考档**跑出来的；裸调 API（不挂工具、降思考档）会显著下降。
   把它当作"上限"而不是"你的实际体验"。
3. **同一模型跨源不一致**：同一款模型的 Terminal-Bench 在两个来源分别给出
   **83.90 与 88.2**（差 4 个点）。**引用时必须带来源**，否则无法判断差异是"模型变了"
   还是"口径变了"。
4. **收录站会有时效错乱**：给出具体分数的收录页，同时标注"这些型号尚未公开发布"。
   收录站的**横向排列**有价值，**单点数字**不可直接采信。

---

## 5. 出处可信度分级

| 级别 | 特征 | 本次遇到的例子 |
| --- | --- | --- |
| **第三方独立复测** | 最可信，无立场 | Artificial Analysis 的 Intelligence Index（57 分 @ $0.045/task） |
| **厂商自报** | 有立场 + 满血口径 | 厂商博客里的 agent 基准表 |
| **收录站汇总** | 便于横向比较，可能过时/口径混杂 | 收录站给出的多项分数与排名 |
| **社区实测** | 反映真实体感，样本小、易受个人环境干扰 | CSDN / 知乎的部署与使用实录 |

---

## 6. 因此（对项目的约束）

1. **档位分配规则**：按"同口径分数 ÷ 倍率"决定，而不是按价格或档位名；
   先用最便宜的档位，卡住再按阶梯升级。
2. **引用纪律**：任何写进文档的模型分数，必须同时写明**口径**（是否带工具/思考档）
   与**来源性质**（厂商自报 / 第三方 / 收录站 / 社区）。只有单一来源的数字，标注"待交叉验证"。
3. **不要只看分数**：便宜档位可能有**可用性缺陷**（例如已知的"工具调用死循环 /
   空输出"），对多轮 agent 工作流是实质风险——**分数之外还要看"失败模式"**。
4. **长期方向**："哪个模型更强"正是本项目产品要自动回答的问题（`REQ-MODEL-06` 模型能力探测）。
   现在的人工判断是**临时手段**，最终应由自己的探测链路给出。
