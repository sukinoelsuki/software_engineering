# 推理模型的"思考模式"与 token 预算：为什么模型会一个字都不输出

> 主题：推理模型有"思考"与"答案"两条输出通道，共用同一个 `max_tokens` 预算；
> 预算被思考吃光时，表现是"一个字都不输出"。
> 来源：2026-09-15 本项目对 MiniCPM5-2B 与 Qwen3.5-4B 的实测

## 1. 一句话结论

**"模型没有输出"最常见的原因不是"它不会"，而是"它把预算花在了你看不见的地方"。**
新一代推理模型有**两条输出通道**（思考 + 答案），而 `max_tokens` 是**两条通道共用的总预算**。
预算被思考吃光时，答案通道就是空的——用户看到的是**一个字都没有**。

## 2. 直觉模型：答题纸与草稿纸

想象考试时**草稿纸和答题纸共用同一本本子**，而且有个规定：
"写满这本本子就必须停笔"。

- 审题马虎的人：草稿写 2 行，答题纸写满 —— 得分。
- 特别谨慎的人：草稿写了 30 页，把本子用完了 —— **答题纸上一个字都没有，得零分。**

**这不是他不会做这道题，是"答题策略 + 资源限制"的组合出了问题。**

我们的实测就是这个场景的真实版本：

| 模型 | 同一道简单题（抽取 JSON）的"草稿"长度 | 结果 |
| --- | --- | --- |
| MiniCPM5-2B | 125 字符 | ✅ 答对 |
| Qwen3.5-4B | **3689 字符** | ❌ 预算耗尽，**答案为空** |

## 3. 原理

### 3.1 什么是"思考模式"

近两年的推理模型（reasoning model）在生成答案之前，会先生成一段**中间推理**——
通常包在 `…` 或模板自带的思考标记里。这段内容的作用是提升复杂任务的成功率。

关键点：**它也是"生成的 token"，同样要计费、同样要花时间、同样占用 `max_tokens`。**

### 3.2 两条通道怎么暴露出来

在 llama.cpp 的 OpenAI 兼容端点里，两条通道被拆成两个字段：

```json
{
  "choices": [{
    "finish_reason": "stop",
    "message": {
      "content": "{\"name\": \"张三\", ...}",     // ← 答案通道
      "reasoning_content": "让我先想想……"          // ← 思考通道
    }
  }]
}
```

- `content` 是**用户要的答案**；
- `reasoning_content` 是**中间过程**（llama-server 默认会保留它，可用 `--no-reasoning-preserve` 关闭）。

### 3.3 失败时的可观测信号

失败不是"静默"的，有明确信号——**必须去看这两个字段的组合**：

| `finish_reason` | `content` | 含义 |
| --- | --- | --- |
| `stop` | 有内容 | ✅ 正常完成 |
| **`length`** | **空或截断** | ❌ **预算耗尽**（思考吃光了 token） |
| `tool_calls` | 空（正常） | ✅ 工具调用请求，答案在 `tool_calls` 里 |

**这就是为什么"只看输出文本"会误判**：你必须同时看 `finish_reason`。

### 3.4 怎么控制它

| 手段 | 做法 | 适用 |
| --- | --- | --- |
| 关闭思考 | 请求里带 `"chat_template_kwargs": {"enable_thinking": false}` | 结构化抽取、格式转换、简单问答 |
| 放大预算 | 提高 `max_tokens` | 复杂推理、代码生成 |
| 按任务切换 | 由编排层根据任务类型决定上面两者 | **agent 的标准做法** |

**注意**：不同模型控制方式不同。MiniCPM5-2B 与 Qwen3.5-4B 都认 `enable_thinking`；
但 Qwen3.5-4B 官方说明它**不支持** Qwen3 那种 `/think`、`/nothink` 软开关，
必须通过模板参数。**所以"怎么关思考"本身也是需要逐个模型确认的工程细节。**

## 4. 我们项目里的真实例子

### 4.1 一次差点误判的结论

第一轮测试时，Qwen3.5-4B 在"抽取 JSON"这个简单任务上返回：

```text
finish_reason = length
content       = ''        ← 空
reasoning 长度 = 3689 字符
```

如果只看输出，会写下"Qwen3.5-4B 连 JSON 都抽不出来"——
**这是一个完全错误的结论**。

补一次对照（只改 `enable_thinking: false`）：

```text
finish_reason = stop
content       = {"name": "张三", "age": 34, "city": "杭州"}   ← 完全正确，只用了 20 个 token
```

**同一个模型、同一个任务，只差一个开关：从"零输出"变成"完全正确"。**

### 4.2 反过来，另一个模型也有"非预算型失败"

MiniCPM5-2B 在关闭思考后做代码任务时：既没有空输出，也没有报错，
**`finish_reason=stop`，但输出的是原样的代码，一个类型标注都没加。**

这提醒我们：**"没有失败信号"也不等于"任务完成"**。
判定必须回到**任务本身是否达成**，而不能只看服务端返回。

于是失败被分成三类，处理方式完全不同：

| 失败类型 | 表征 | 该怎么处理 |
| --- | --- | --- |
| 预算耗尽 | `finish_reason=length` + 空 | 调预算 / 关思考 / 重试 |
| 未执行指令 | `finish_reason=stop` 但结果不符合要求 | 改提示、换模型、加校验 |
| 真的不会 | 稳定失败（多次重试均失败） | 才是"能力不足"，才考虑换模型 |

**只有第三类才该触发"换模型"这种结论。** 前两类都是工程问题。

### 4.3 对系统设计的直接约束

1. 编排层必须**显式**决定每个任务用哪种思考模式，不能依赖默认值；
2. 必须把 `finish_reason` 纳入判定逻辑，**不能只看 `content`**；
3. 失败的"空输出"应当触发**可控降级**（关思考重试 / 扩预算 / 换更小的专家），
   而不是把错误直接抛给用户；
4. 输出预算要按任务类型配置：结构化抽取给小预算（并关思考），
   代码/推理给大预算（思考可按需开）。

## 5. 术语表

| 术语 | 含义 |
| --- | --- |
| reasoning / thinking 模式 | 模型先输出中间推理、再输出答案的运行模式 |
| `reasoning_content` | OpenAI 兼容接口中承载"思考通道"文本的字段 |
| `max_tokens` | **本次请求允许生成的总 token 上限**（思考 + 答案共用） |
| `finish_reason` | 本次生成为何结束：`stop`（自然结束）/ `length`（达上限）/ `tool_calls`（请求调用工具） |
| `enable_thinking` | 聊天模板参数，用于开关思考模式（具体名称随模型而异） |
| 采样参数 | `temperature` / `top_p` / `min_p` 等，控制随机性与候选裁剪 |

## 6. 我原来的误解 / 容易踩的坑

| 误解 | 事实 |
| --- | --- |
| "模型输出空 = 模型能力差" | 最常见原因是预算耗尽或配置错误，**先排除配置** |
| "`max_tokens` 只是限制答案长度" | 它限制的是**思考 + 答案的总和** |
| "`finish_reason=stop` 就说明任务完成了" | 只说明"模型认为该结束了"，**不代表满足你的要求** |
| "所有模型的思考模式开关都一样" | 参数名与可用性都不同，`/think` 这类软开关并非通杀 |
| "默认参数是安全的选择" | 恰好相反：默认值往往导致**简单任务上最差的表现**（如 `min_p=0.05` 引起重复） |
| "多试几次总有一次对" | 先分清是预算问题还是能力问题；前者重试也无效，必须先改配置 |

## 9. 因此（对项目的约束）

1. **编排层必须显式设置思考模式开关与 token 预算**，不能依赖默认值——默认值因模型而异，
   依赖默认值等于把行为交给运气。
2. **`finish_reason=length` 且 `content` 为空 = 预算耗尽，不是能力不足**：
   不得据此下调对模型的评价（与 [evaluation-pitfalls.md](evaluation-pitfalls.md) 属同一类误判）。
3. **结构化抽取类任务默认关闭思考**，并用 JSON 合法性作为判据，而不是"看起来像"。
4. 任何性能或能力结论都必须标注 llama.cpp 版本与启动参数，否则不可复现。
