## 一、同一套代码，可以有**两个不同版本**的检查工具

### 我以为

`make check` 通过 + 提交钩子通过 = 门禁是一致的。

### 实际是

pre-commit 的钩子运行在**各自独立的虚拟环境**里，因此它和项目环境可以装到
**不同版本**的工具。2026-09-15 的归档提交就因此被卡住：

| 使用方 | ruff 版本 | 行为差异 |
| --- | --- | --- |
| pre-commit 钩子 | 0.6.9 | **不**格式化 Markdown 内嵌的 Python 代码块 |
| `uv sync` / `make check` | 0.16.7 | **会**格式化 |

结果：**钩子绿、`make check` 红**——而且是在提交成功之后才发现。

### 因此

1. **工具链版本以 `uv.lock` 为唯一事实来源**，pre-commit 各钩子的 `rev`
   必须与锁定版本一致；升级依赖时同步更新（规则已写入 `.pre-commit-config.yaml` 头部）。
2. **提交前跑两条路**：钩子（`pre-commit run --all-files`）+ 门禁（`make check`）。
   只跑一条不足以发现此类分叉。
3. 更彻底的做法是把钩子改成 `repo: local` + `uv run <tool>`，
   使版本只由 `uv.lock` 决定（**待评估**，属门禁实现方式变更）。

### 附：同类问题还有一个更隐蔽的版本——"钩子只在改动文件上跑"

本地钩子默认只检查**被改动的文件**，因此 `src/` 里既有的一处 lint 违规
可以长期存在而不被发现（它只在第一次提交那个文件时才有机会被拦）。
**门禁的"全量"只在 CI / `make check` 里发生**——这是必须保留 CI 全量检查的原因。

## 二、归档的证据**不能**为了通过检查而变形

### 我以为

归档进仓库的东西，自然要符合仓库的规范（比如通过 lint）。

### 实际是

把 W1 实验的 harness 脚本作为 `.py` 归档时，被 `ruff` 拦下
（`T201 print`、`S310 urlopen`）。此时有三条路，代价完全不同：

| 方案 | 问题 |
| --- | --- |
| 改写脚本使其通过 lint | ❌ **证据被改写就不再是证据**——归档的意义正是"这是当时真实运行的东西" |
| 为它加 `# noqa` / 放宽规则 | ❌ 为一份一次性实验脚本放宽**安全类**规则（S310）不划算，且豁免需登记 |
| **换载体**：数据用 `.txt`、脚本以 Markdown 逐字附录收录 | ✅ 采纳 |

### 因此

1. **原则：作者撰写的文档用 `.md`（受格式化约束）；采集得到的原始产物用 `.txt`（逐字保留）。**
2. 当"规范"与"证据保全"冲突时，**优先保全证据**，通过**换载体**而不是**改内容**解决。
3. 归档必须能回答："这份东西是**运行时的原样**吗？" 若不能，它就不是证据。

### 补充：归档仍会被"文件卫生"钩子轻微改动（必须披露）

即便换了载体，`.txt` 归档仍要经过通用文件卫生钩子：
`end-of-file-fixer`（补末尾换行）、`trailing-whitespace`（去行尾空白）、`mixed-line-ending`（统一为 LF）。

因此归档的原始产物与"模型直接输出"之间存在**空白与行尾层面的规范化差异**。
**这不影响结论**（代码语义不变、也不会被 hash 引用），但**不能声称逐字节一致**。

> 若某天需要真正逐字节的证据（例如要对外声明输出哈希），
> 就必须把该文件从这些钩子中排除，或改为在钩子之外存放。
> 现在的取舍是：**接受空白规范化，换取归档可正常入库与 lint 全绿**。

## 三、构建期的失败**默认是静默的**

### 我以为

镜像构建成功 = 里面的东西都在。

### 实际是

已经遇到两次"**构建成功但组件缺失**"：

| 事件 | 表现 | 后果 |
| --- | --- | --- |
| 首版镜像漏装 CodeBuddy | 构建正常结束 | CNB 入口页**静默隐藏** CodeBuddy Web 入口（不报错） |
| `ms-python.vscode-pylance` 在 Open VSX 上 404 | 该行"安装失败但不阻断构建" | 进入环境后才发现缺少类型检查引擎 |

共同点：**安装/下载步骤被设计为"失败不阻断"**（避免构建期网络抖动炸掉整个镜像），
代价是失败被推迟到"人进入环境之后"才暴露。

### 因此

1. **凡是"失败不阻断"的步骤，都必须在构建末尾用一个显式的自检阶段再校验一次**
   （现状：Dockerfile 第 12 阶段校验关键命令、关键扩展、模型 sha256、参考资料存在）。
2. **校验要指向"具体产物"而不是"命令是否成功"**：
   例如校验扩展 ID 出现在 `--list-extensions` 输出里，而**不是**只看安装命令的退出码。
3. **能给出摘要的就给摘要**：下载的资产一律带 `sha256` 并在构建期比对，
   失败即**中断构建**（fail-secure）——宁可构建失败，也不交付一个装了错资产的镜像。

## 四、同一份配置，在**不同基础镜像**里语义不同（而且会随时间漂移）

### 我以为

流水线挂掉只有两种原因：脚本写错了，或者代码有问题。

### 实际是

2026-09-16 新增的基准流水线，**第一行**就退出码 2：

```text
$ set -euo pipefail
sh: 1: set: Illegal option -o pipefail
```

三条各自实测过的事实叠起来才解释得通（不猜，逐条验证）：

| 事实 | 证据 |
| --- | --- |
| 阶段脚本由镜像的 `/bin/sh` 执行 | 报错前缀 `sh: 1:` 是 dash 的格式 |
| **Debian 12 的 dash 不支持 `pipefail`** | 开发容器（`/bin/sh -> dash`，dash `0.5.12-2`）执行 `set -o pipefail` 直接报错 |
| **Debian 13 的 dash 支持它** | 同一条命令在 `python:3.12` 镜像（Debian 13，dash `0.5.12-12`）里成功 |
| **门禁用的 `python:3.12` 已经漂到 Debian 13** | `docker run python:3.12` 的 `/etc/os-release` 显示 trixie |

于是同一个 `set -euo pipefail`：**门禁（浮动标签 → trixie）能跑，
基准流水线（`.ide/Dockerfile` 的 bookworm）挂**。`develop` 的门禁是 success、
新流水线是 failure——差别不在脚本，在**镜像**。

还有一处放大了伤害的写法：`endStages` 里写的是 `set -uo pipefail`（没有 `-e`），
本意是"失败也继续"，实际是**整段脚本被中止**：连数据发布都没执行，
从外部看像是"什么都没发生"。**没有 `-e` 的 `set` 失败同样致命。**

### 因此

1. **阶段脚本按 POSIX 写**：用 `set -eu`；确实需要 `pipefail` 时显式切 bash
   （`if [ -n "${BASH_VERSION:-}" ]`）。
2. **镜像钉到发行版**：`python:3.12` 这类浮动标签会随时间更换整套基础系统；
   统一为 `python:3.12-bookworm`，与开发镜像同源，保证本地与 CI 环境一致。
3. **把规则变成机器检查**：`tests/unit/test_cnb_config.py` 禁止 `pipefail`
   与未钉发行版的 python 镜像——约定只写在注释里就会再次被绕过。
4. **"同一份配置昨天能跑"是警报，不是安慰**：先比环境（镜像/工具版本），再比脚本。

## 五、平台的"无输出超时"会把**网络卡顿**伪装成"Dockerfile 写错了"

### 我以为

构建日志末尾的 `ERROR: failed to solve: Canceled: context canceled` +
`exit code: -1, signal: 9` 是镜像构建本身出错。

### 实际是

**这是被平台杀掉，不是某一步返回了非零退出码。** 判据一条就够：

| 日志形态 | 含义 |
| --- | --- |
| `process "/bin/sh -c …" did not complete successfully: exit code: 1` | **Dockerfile 自己错**（本项目见过两次：清单路径、`$$(...)` 断言） |
| `… CANCELED` + `Canceled: context canceled` + `signal: 9` | **被外部杀掉** |

凶手是 CNB 的**无输出超时**：*Job 连续 10 分钟无任何输出即超时*，超时后整个构建被
SIGKILL（出处：<https://docs.cnb.cool/zh/build/timeout.md>「无输出超时」，访问 2026-09-21；
同页另有"流水线 20 h / Job 默认 2 h"两条上限，本次都不是它们）。
时间线对得上——这是"不猜"的部分：

| 时刻 | 事件 |
| --- | --- |
| `00:09:16` | 最后一次输出：`[assets] 克隆 openharness（MIT，端侧·核心）→ 9b2efd795c6a` |
| `00:19:17` | `#24 CANCELED` / `Canceled: context canceled` / `signal: 9` |
| 差值 | **10m01s** |

那 10 分钟里脚本在执行 `git fetch`。它**没有任何超时**，GitHub 侧连接 stall 后 git 会一直等
（内核 TCP 重传可拖十几分钟）；而脚本用 `-q` 静默拉取 ⇒ **一行都不打印 ⇒ 正好把 10 分钟填满**。
对照同机上一次成功的构建（`cnb-j4r-1k2qgnopp`，2026-09-18）：同样 9 个仓库、合计 447 MB，
**全部克隆只花 40.5 s**，openharness 单个 1.7 s。⇒ 这次卡的不是构造时间，是**网络 stall**。

顺带被日志钉住的另一条（与"Dockerfile 注释里写的"相反）：

| 我以为 | 实际是 |
| --- | --- |
| Dockerfile 靠层序缓存复用 GB 级资产（本文件注释里就是这么写的） | 平台下发的是 **`docker build --no-cache …`**（`cnb-j4r-1k2qgnopp` 与 `cnb-rjo-1k3263rlg` 两次日志逐字核对）⇒ 层序只剩可读性价值 |
| 改一行 Dockerfile 只重建后面几层 | 该文件的**输入哈希**变了 ⇒ 制品库里没有对应镜像 ⇒ **完整重建**（重下 11.8 GB + 重编 llama.cpp） |
| 首次构建 5~15 分钟 | 实测完整构建约 11~20 分钟；真正省时的只有"上次构建成功过、输入哈希没变"这一条（实测 `cnb-738-1k31psn59` 仅 41 s） |

### 因此

1. **构建期一切网络访问都必须有界**：curl 带 `--retry` / `--connect-timeout`；
   `git fetch` 用 `timeout` 兜底 + `http.lowSpeedLimit/lowSpeedTime` 抓 stall + 重试，
   且**每次尝试前后都打日志** ⇒ "最长静默"变成一个**可计算的量**（现在 ≈ 300 s + 5 s），
   而不是"看运气"。
2. **不要把平台的静默杀掉当成"偶发超时"**：先按**退出码形态**分类
   （`context canceled` + `signal 9` = 被杀；`exit code: N` = 自己错），再决定是"重试"还是"改代码"。
3. **"总时长不够"要先算再断言**：本次构建在 `00:09:16` 的进度与 09-18 那次几乎同步
   （模型下载 310.6 s vs 318.1 s），完全不像超预算 —— 只算一次对照就能排除这条假设。

## 六、`curl URL | sh` 会把**致命失败**变成"这一步成功"

### 我以为

`curl -fsSL URL | sh` 是上游文档的推荐写法；失败会报错。

### 实际是

管道**不传播 curl 的退出码**，而这里没有 `pipefail`（Debian 的 dash 不支持它，
`.cnb.yml` 已明令禁止；`sh` 又是 Dockerfile `RUN` 的默认解释器）⇒
**curl 失败时 `sh` 收到空输入、以 0 退出、整步被判为成功**。
同一次构建（`cnb-rjo-1k3263rlg`）实测：

```text
#11 RUN curl -fsSL https://code-server.dev/install.sh | sh
   59.92 curl: (35) OpenSSL SSL_connect: SSL_ERROR_SYSCALL in connection to code-server.dev:443
   DONE 60.0s                                  ← 判为成功
#12 … 16 个扩展
   /bin/sh: 1: code-server: not found          ← 全部失败，又被 `|| echo "[warn] …"` 吞掉
```

对照实验（目标故意不可达，本仓库开发容器，2026-09-21）：

| 写法 | 退出码 |
| --- | --- |
| `curl -fsSL https://127.0.0.1:9/x.sh \| sh` | **0**（失败被吞） |
| `curl -fsSL --output /tmp/x.sh https://127.0.0.1:9/x.sh` | **7**（会被 `set -e` 抓住） |

### 因此

1. **构建期执行远程脚本一律"先落盘、再执行"**，并在**同一步显式断言结果**
   （`.ide/Dockerfile` 现在下载后执行，再跑 `code-server --version`）。
2. **静默失败的代价要算出来**：这次白付了约 9 分钟（含 11.8 GB 模型下载）才在自检里暴露，
   在此之前一路"绿"—— 与第三节"构建期的失败默认是静默的"是同一个失效模式，
   只是成因从"被设计成不阻断"变成了"退出码被管道吃掉"。
3. **末尾自检不能替代就地失败**：自检的职责是兜住"设计上允许失败"的步骤（第三节），
   而不是兜住"本该当场失败却被吞掉"的错误。两者都要有，但不能互相顶替。
