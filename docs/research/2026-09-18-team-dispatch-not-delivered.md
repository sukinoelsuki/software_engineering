## 3. 判定

### 3.1 判定谓词：**spawn 调用同步返回错误** + 仓库零改动

本案的判据只有两条，且**都不依赖消息通道**：

1. **派活调用的返回值**：`architect-authz` / `architect-skills` 两次调用**同步**返回
   `Tool execution failed: No result found`（不是超时，也不是"稍后才失败"）；
2. **仓库零改动**：在上述时点，`git log` 停在上一笔提交（`62ccec7`）、`git status --short` 为空。

> 🔴 **更正（同日稍后）——本节初稿提出的另一条判据已被实测证伪，不得再使用。**
>
> 初稿写的是："**成员信箱为 0 条消息 ⇒ 派活未投递**"。**该判据是错的。**
>
> **证伪过程（可复现）**：同一会话稍后重新派活三名成员
> （`arch-authz` / `arch-skills` / `arch-hygiene`），三次 spawn **均返回成功**，
> 且它们**确实在产出**——`git log` 出现 `b4f6772`（`docs(git-workflow): 远端写入授权改为
> 按可回退性分级`）与 `feb2e17`（`docs(engineering): 补 CNB 接入相关的运维口径与自检项`）；
> **而在它们工作期间，三个成员的信箱一律是 0 条消息**。
> ⇒ 空信箱**既非"未投递"的充分条件、也非必要条件**，作为判据**已被推翻**。
>
> **危害方向必须写清（这是更正的原因）**：按那条错判据行事会导向
> "**对正在工作的成员重派**"——正是 §8.3 机制 2 明令禁止的结果：
> **重复劳动 + 同一文件被两人写**。
>
> **方法论**：本条按项目一贯口径处理——**现象是证据，归因只是假设**；
> 归因被证伪就改归因，**不改现象**（信箱确实是空的、成员确实在干活，两者同时为真）。

### 3.2 因此**本案不适用**「禁止据'未确认'重派」

§8.3 机制 2 的禁令针对的是这种情形：

> 成员**可能已经干完**、只是**回报丢了**——此时"没做完"与"做完了但消息丢了"**观测上无法区分**，
> 重派会造成**重复劳动**与**同一文件被两人写**。

本案的观测与它**不同**：投递本身失败（信箱为空），成员**不可能**基于一个它没收到的提示去干活。
⇒ 两点风险（重复劳动 / 并发写同一文件）在本案中**均不成立**。

> **边界（不得过度推广）**：本条**不**放宽 §8.3 机制 2。它只是给出一条**可物证的例外判据**——
> 只有在"**信箱为空**"这种客观证据成立时，才可立即重派；**只要信箱非空**，
> 就回到"未确认 ≠ 失败，不得重派"的默认纪律。

## 4. 这是一种**新的**失效模式（第 3 类之外）

`agent-teams.md` 已有的失效模式清单与本案的关系：

| 既有条目 | 它的前提 | 本案是否属于它 |
| --- | --- | --- |
| §8.1「投递失败 / 仅延迟到达」 | **消息已发出** | ❌ 本案连"发"都没发生 |
| §8.1 第三类「完成信号与内容脱节」（空提交） | 成员**已完成并提交** | ❌ |
| §8.9「登记表重置 ⇒ 通道不可达」 | 成员**曾在活动名单里**、地址失效 | ❌ 本案成员**在活动名单里却从未收到过**东西 |
| §8.12「会话级 auto run 失效」 | 判据是**出现审批取消原文**，且要求**禁止开工** | ❌ **本节的 §8.12 预检两次都通过**（无任何取消原文） |

⇒ 本案是**第 3 类以外**的一种：**登记表里有它、收件箱里没有它**。

### 4.1 与 §8.12 预检的关系（重要，防止误读）

`§8.12` 的预检（跑一条无害命令、匹配 `Permission request timed out` 原文）**在本案中两次都通过**：

| 时点 | §8.12 预检 | 结果 |
| --- | --- | --- |
| 首次派活 `architect-cnb-skills` 之前 | 无取消原文 | ✅ 通过，且成员**成功完成**（3 笔提交） |
| 重派之前 | 无取消原文 | ✅ 通过，**但派活投递失败** |

⇒ **结论：§8.12 的预检通过，不保证派活能投递。** 该预检覆盖的是"审批通道"，
覆盖不到"spawn / 投递通道"。两者**可能独立失效**。

> 这条与 §6「两道防线可能同时为空」是**同一族教训**：
> **"某处会查"是危险假设**——不能因为预检绿了就假设派活一定成功。

### 4.2 派活之后如何判"已投递"——**结论：目前没有可靠的"仓库外"判据**

⚠️ 本小节初稿给出的"**核成员收件箱**"办法，**已被 §3.1 的更正推翻**
（成员正常工作时信箱也可以是空的）⇒ **不得作为判据使用**。此处只保留可用的部分：

| # | 可用信号 | 它到底能证明什么 |
| --- | --- | --- |
| ① | **派活调用的返回值** | 同步报错 ⇒ **投递失败**（本案的判据）；返回成功**不保证**成员一定开始工作 |
| ② | `git log` / `git status` | 仓库是**权威载体**，但它只证明"**有没有产出**"，**不证明**"有没有投递" |
| ③ | 成员信箱条数 | ❌ **不可作为投递判据**（已被证伪，见 §3.1） |
| ④ | 登记表 `members` / `validMembers` | ❌ 已知不可靠（§8.11.1：两数组差异即"登记表重置"的直接证据） |

⇒ **正确做法是回到 §8.3 机制 2 的默认纪律**：

- **投递与否** 以 **①（调用返回值）** 判定；
- 调用**成功**而仓库暂时无产出时，一律按"**未确认**"处理，**不得重派**——
  因为"没做完"与"做完了但回报丢了（或还没提交）"在观测上**不可区分**（§8.2 谓词层）；
- 调用**同步报错**时，才可判"投递失败"，此时重派**不构成**重复劳动
  （本案即属此类，判断依据是 ①，**不是** ③）。
