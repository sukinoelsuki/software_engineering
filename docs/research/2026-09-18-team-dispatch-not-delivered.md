## 3. 判定

### 3.1 判定谓词：**派活未投递**，而非"成员没干活"

判据是 §8.3 机制 2 的口径（**判定只认仓库**）加上本次新增的一条**直接物证**：

> **成员信箱为"空数组（0 条消息）"⇒ 该成员从未收到过任何派活。**

这条判据比"没有新提交"强得多：§8.1 第三类失效模式（**空提交 + 终止声明**）已经证明
"仓库里没有"**不能**单独推出"成员没干活"；而**空的收件箱**是**单成员层面**的直接证据——
消息必须先进入收件箱才可能被读取，收件箱为空 ⇒ 投递这一步就不成立。

### 3.2 因此**本案不适用**「禁止据'未确认'重派」

§8.3 机制 2 的禁令针对的是这种情形：

> 成员**可能已经干完**、只是**回报丢了**——此时"没做完"与"做完了但消息丢了"**观测上无法区分**，
> 重派会造成**重复劳动**与**同一文件被两人写**。

本案的观测与它**不同**：投递本身失败（信箱为空），成员**不可能**基于一个它没收到的提示去干活。
⇒ 两点风险（重复劳动 / 并发写同一文件）在本案中**均不成立**。

> **边界（不得过度推广）**：本条**不**放宽 §8.3 机制 2。它只是给出一条**可物证的例外判据**——
> 只有在"**信箱为空**"这种客观证据成立时，才可立即重派；**只要信箱非空**，
> 就回到"未确认 ≠ 失败，不得重派"的默认纪律。

## 4. 这是一种**新的**失效模式（第 3 类之外）

`agent-teams.md` 已有的失效模式清单与本案的关系：

| 既有条目 | 它的前提 | 本案是否属于它 |
| --- | --- | --- |
| §8.1「投递失败 / 仅延迟到达」 | **消息已发出** | ❌ 本案连"发"都没发生 |
| §8.1 第三类「完成信号与内容脱节」（空提交） | 成员**已完成并提交** | ❌ |
| §8.9「登记表重置 ⇒ 通道不可达」 | 成员**曾在活动名单里**、地址失效 | ❌ 本案成员**在活动名单里却从未收到过**东西 |
| §8.12「会话级 auto run 失效」 | 判据是**出现审批取消原文**，且要求**禁止开工** | ❌ **本节的 §8.12 预检两次都通过**（无任何取消原文） |

⇒ 本案是**第 3 类以外**的一种：**登记表里有它、收件箱里没有它**。

### 4.1 与 §8.12 预检的关系（重要，防止误读）

`§8.12` 的预检（跑一条无害命令、匹配 `Permission request timed out` 原文）**在本案中两次都通过**：

| 时点 | §8.12 预检 | 结果 |
| --- | --- | --- |
| 首次派活 `architect-cnb-skills` 之前 | 无取消原文 | ✅ 通过，且成员**成功完成**（3 笔提交） |
| 重派之前 | 无取消原文 | ✅ 通过，**但派活投递失败** |

⇒ **结论：§8.12 的预检通过，不保证派活能投递。** 该预检覆盖的是"审批通道"，
覆盖不到"spawn / 投递通道"。两者**可能独立失效**。

> 这条与 §6「两道防线可能同时为空」是**同一族教训**：
> **"某处会查"是危险假设**——不能因为预检绿了就假设派活一定成功。

### 4.2 本次可用的**可观测判据**（供后续复用）

派活之后**立刻**核一次成员收件箱：

```bash
# 派活后立即执行；任一成员为 0 条 ⇒ 投递失败
for f in .codebuddy/teams/*/*/architect-*.json; do
  printf '%-28s %s\n' "$(basename "$f" .json)" "$(python3 -c "import json,sys;print(len(json.load(open(sys.argv[1]))))" "$f")"
done
```

判据：**空数组 ⇒ 投递未发生**（不是"还没干完"）。
