## 1. 研究问题

两个**可证伪**的问题：

- **Q1（能力）**：4B 级、4-bit 量化的端侧模型，在**限定任务域**内能否完成有实际意义的
  工程任务（改代码 / 修 bug / 写测试），使 SRS 的假设 A-1 成立？
  → 若 3 项任务的**一次通过率**长期低于 30%，则判定风险 `R-1` 触发。
- **Q2（性能）**：在 8 核纯 CPU、16 GiB 内存的受限环境下，该模型的
  加载耗时、prefill 吞吐、生成速度与常驻内存是多少？这决定了后续调度策略的
  「切换成本」是否可接受（见 [0003 §6](../devlog/0003-2026-09-15-单专家调度与上下文迁移.md)）。

## 2. 环境与工具（可复现）

| 项 | 值 |
| --- | --- |
| 平台 | CNB 云原生开发容器，`runner.cpus: 8` |
| CPU / 内存 | 8 vCPU / 16 GiB（`free -h` 实测可用 14 GiB） |
| 推理后端 | `llama-server`，`version: 0.4.1-dev (build 1, commit 69eb250)` |
| 模型 | `Qwen/Qwen3-4B-GGUF` → `Qwen3-4B-Q4_K_M.gguf`（2.50 GB） |
| 运行时参数 | `-c 4096 -t 8 -tb 8 --reasoning off --no-webui`（关闭思考链，模拟低延迟档位） |
| 采样 | `temperature=0`，`max_tokens=2048`，非流式 |
| 评估工具 | `mypy --strict`、`pytest`、`pytest-cov`（均来自工程虚拟环境 `.venv`） |

**为什么关闭思考链**：Qwen3 系列默认输出长思考链，会显著放大延迟与 token 消耗。
本项目面向低资源设备，`--reasoning off` 代表一种现实的部署档位。
**注意**：这意味着结论**只代表"非思考模式"下的能力**，思考模式下的上限更高（见 §7）。

### 复现命令


## 3. 方法

**三项任务**（覆盖"读改写"到"生成"的连续谱，全部可自动判定）：

| # | 任务 | 输入 | 客观判据 |
| --- | --- | --- | --- |
| T1 | 为 33 行模块**补全类型标注** | 无类型标注的传感器聚合模块 | ① 标注完备性（AST 检查）② 行为等价（对照原实现）③ `mypy --strict` |
| T2 | **修复 bug** 使失败测试通过 | 含 off-by-one 缺陷的分页函数 + 5 个测试 | `pytest` 全绿 |
| T3 | **生成单元测试** | 纯函数 `merge_intervals`（区间合并） | ① 交付物可直接运行 ② 断言正确（对正确实现全绿）③ 分支覆盖率 ④ 变异测试（能否杀死变异体） |

**为什么这样设计**：三项任务的判据都**不依赖人工打分**，避免"看起来对"的自我安慰。
额外加入**变异测试**（把 `<=` 改成 `<`），用于检验生成的测试是否真有检出力——
一个"全绿但什么都测不出来"的测试文件不应被记为成功。

## 4. 结果与数据

### 4.1 性能（Q2）

| 指标 | 实测 | 备注 |
| --- | --- | --- |
| 模型下载 | 2.50 GB / 383 s（≈6.7 MB/s） | 从 Hugging Face |
| **模型加载耗时** | **1.73 ~ 1.75 s** | ⚠️ **热缓存**测量；容器只读，无法 `drop_caches` 做冷启动对照 |
| **prefill（提示处理）** | **66.4 ~ 67.6 tok/s**（14.8 ~ 15.1 ms/token） | llama.cpp 自报 |
| **生成速度** | **16.1 ~ 16.8 tok/s**（59.6 ~ 62.2 ms/token） | llama.cpp 自报 |
| 常驻内存（加载后） | 4,804,440 ~ 4,805,768 kB ≈ **4.58 GiB**（VmHWM） | 含 mmap 权重与计算缓冲 |
| 常驻内存（生成后） | 5,186,700 kB ≈ **4.95 GiB**（VmHWM） | 3 轮任务后峰值 |

**推论（重要）**：生成速度 16.5 tok/s 意味着**每次专家切换都要重新 prefill 上下文**，
按 1000 token 上下文计，单次切换约 `1000 / 67 ≈ 15 s`（prefill）。
这从数据上支持 [0003](../devlog/0003-2026-09-15-单专家调度与上下文迁移.md) 的结论：
**切换成本 ≈ 切换次数 × 上下文长度**，因此"减少切换次数"（S-6 / R4 粘性路由）是高优先级优化。

另注：4.95 GiB 的常驻内存已占 16 GiB 环境的 31%，在 **8 GiB 目标设备**上会非常紧张——
这为 `REQ-MODEL-02`（按内存预算推荐量化档）提供了第一个真实基线。

### 4.2 能力（Q1）

| 任务 | 交付即可运行 | 客观正确性 | 备注 |
| --- | --- | --- | --- |
| **T1** 类型标注 | ✅ | **通过**（行为等价、签名标注完备） | 仅 `mypy --strict` 残留 1 处：局部变量 `buckets = {}` 缺注解 `[var-annotated]` |
| **T2** 修 bug | ✅ | **通过**（5/5 测试） | 修复为最小改动 `range(0, len(items), size)`，未见附带改动 |
| **T3** 生成测试 | ❌ | 断言**完全正确** | **漏写 import**（`from t3_pure import merge_intervals`），交付即 `NameError`；注入 import 后 5/5 通过，**分支覆盖率 100%**，且**杀死变异体** |

**一次通过率的三种口径**（诚实列出，避免选择性表述）：

| 口径 | 结果 | 说明 |
| --- | --- | --- |
| 严格：交付原样、零修改、全部客观判据通过 | **1 / 3 = 33%** | 仅 T2 完全达标 |
| 实用：允许"一行级"且**可自动化**的修补 | **3 / 3 = 100%** | T1 补 1 处局部注解；T3 补 1 行 import |
| 任务语义：按提示词字面要求 | **2 / 3 ≈ 67%** | T1 要求的是"函数类型标注"（已达），T3 要求"完整测试"（未达） |

**其他观察**：

- 三项任务**均一次输出成功**，无格式错误、无拒答、无幻觉 API、无跑题；
  三个产物都规范地包在 ```` ```python ```` 代码块中，**可用正则稳定抽取**。
- 失败模式**高度集中且可枚举**：① 漏写 import（T3）；② 局部变量缺类型注解（T1）。
  两者都不是"能力不足"，而是**工程完备性**的细节疏漏。

### 4.3 一次失败的评估修正（必须记录）

首轮 T1 的"行为等价"判据报 `RecursionError`。**排查后确认是我的夹具缺陷**——
夹具的 `convert_temperature` 在 `unit="kelvin"` 时走
`return convert_temperature(value, "kelvin", "celsius") - 273.15`，**无限递归**。
模型并未引入该缺陷（它与原实现一致）。修正夹具后重跑，行为等价通过。

记录此事的原因：**当自动判据报失败时，第一嫌疑应是判据本身**。
若不排查就直接记为"模型失败"，会得到偏差很大的结论（本例中会把 1 处夹具 bug
误记为模型能力缺陷）。

## 5. 结论

| 问题 | 结论 | 置信度 | 依据强度 |
| --- | --- | --- | --- |
| Q1：能力是否够用 | **风险 R-1 未触发**。最严格口径下 33%（**略高于** 30% 阈值），实用口径 100%。 | **中** | 3 项任务、每项单次采样、`--reasoning off` 单一档位 |
| Q2：性能是否可接受 | 生成 16.5 tok/s、prefill 67 tok/s；模型加载快（热缓存 1.7 s）；**常驻内存 ~4.95 GiB 是关键瓶颈**。 | **中高** | llama.cpp 自报计时 + VmHWM，硬数据 |

**倾向性判断**：模型**能干活**，但**几乎每次都需要一层自动校验与修复**才能交付。
这恰好是本项目核心论点（Harness 必须补偿模型能力）的**直接经验证据**——
不是"模型不行"，而是"裸模型不行，加了验证-修复环才行"。

## 6. 对本项目的影响

1. **`R-1` 维持"中高概率"但不上调**；应对措施从"④ 若不可行则收敛为问答助手"
   继续后移，主线不变。
2. **验证与自动修复环的优先级上调**：T1/T3 的失败都被"跑一次客观检查"捕获，
   且都可自动修复（补 import / 补注解）。这直接支撑 `REQ-HARNESS-07`
   （可验证任务自动校验）从 Should 提升为**优先实现**。
3. **性能基线首个数据点落地**（供 `REQ-PERF-01` / `REQ-MODEL-02` 使用）：
   16.5 tok/s 生成、67 tok/s prefill、~5 GiB 常驻。
4. **切换成本获得实测支撑**：单次切换的 prefill 开销约 15 s/1000 tok，
   强化了"降低切换次数优先于降低单次加载耗时"（S-6）的判断。
5. **8 GiB 设备内存将成为约束点**：需在模型管理阶段做量化档推荐与内存预算校验。
