## 1. A. `0.1.0` 端到端实跑取证（核心）

### 1.1 重要前提：派发配方（`--max-completion-tokens 384`）在 Qwen3-4B 上失败

派发任务声明该配方"已验证可用"，但**对本模型不成立**——这是独立复现才发现的事实：

- **第一跑（配方原样）**：`E2E_EXIT=1`（`TASK_FINISHED.status == FAILED`），事件流仅 2 条
  （`error(protocol)` + `task_finished(failed)`）；`llama-server.log` 显示
  `n_gen = 384`、`stop processing: n_tokens = 1161, truncated = 0`——即模型把 **384** 个补全
  token 全部耗尽于推理，**未产出任何工具调用**。
- **根因（用真实客户端复现确认，见 §1.1.1）**：Qwen3-4B 是思考模型（reasoning）。在更长的系统提示
  + 4 个工具的上下文下，它在 384 token 预算内只做推理、`finish_reason` 前未发出工具调用；
  `llama-server` 返回 `content=null` 且 `tool_calls` 为空 ⇒ 客户端按契约
  （`src/agent_sec_perf/model/client.py:_parse_response` 的 "content 与 tool_calls 皆空 ⇒
  `ModelProtocolError`"）正确拒绝。
- **这不是产品缺陷**，是补全预算不足。修复：把 `--max-completion-tokens` 提到 **1536**，
  并相应把 `--model-request-timeout-s` 放宽到 **600**（1536 token ÷ ~3.4 tok/s ≈ 450s > 240s 原超时）。
- **需领导/实现者裁决**：派发配方里 `384` 的预算对 Qwen3-4B 不成立，应在配方或 ADR 中注明该模型的
  最低 token 预算，或改默认。

#### 1.1.1 根因复现命令与输出（真实客户端，无替身）

```python
# /tmp/repro.py（独立于产品装配，直接调 LocalLlamaClient，证明客户端+Qwen3-4B 本身可用）
import sys, pathlib

sys.path.insert(0, "/workspace/src")
from agent_sec_perf.model.client import LocalLlamaClient
from agent_sec_perf.tools.files import ReadFileTool
from agent_sec_perf.contracts.model import ChatMessage, Role
from agent_sec_perf.foundation.errors import ModelProtocolError

spec = ReadFileTool(sink=None).spec
client = LocalLlamaClient(
    binary="llama-server",
    model_path=pathlib.Path("/opt/models/Qwen3-4B-Q4_K_M.gguf"),
    log_path=pathlib.Path("/tmp/repro_llama.log"),
    host="127.0.0.1",
    port=8081,
    ready_timeout_s=180,
)
msgs = [ChatMessage(role=Role.USER, content="读取 hello.txt 并返回内容")]
try:
    resp = client.chat(msgs, tools=[spec], max_tokens=384, timeout_s=240)
    print("CHAT_OK content=", repr(resp.content), "tool_calls=", resp.tool_calls)
except ModelProtocolError as e:
    print("MODEL_PROTOCOL_ERROR:", repr(e.args[0]))
finally:
    client.close()
```

输出：`CHAT_OK content= None tool_calls= (ToolCallRequest(call_id='...', name='read_file',
arguments_json='{"path": "hello.txt"}'),)` —— 即**简单提示下客户端能正常解析 Qwen3-4B 的工具调用**；
失败只在"更丰富提示 + 384 预算"的组合出现，进一步指向 token 预算而非产品 bug。

### 1.3 退出码

`E2E_EXIT=0` ⇒ 对应退出码表（`src/agent_sec_perf/cli/app.py` 模块 docstring）的
`EXIT_OK = 0`（`TASK_FINISHED.status is COMPLETED`）。不是装配失败（3）、不是审计失败（4）、
不是未预期异常（5）。

### 1.4 事件流（`--output-format json` 的 6 条）

解析 `run.jsonl` 得：

- **事件条数**：6
- **`kind` 序列**：
  `['model_response', 'tool_call', 'policy_decision', 'tool_result', 'model_response', 'task_finished']`
- **`seq`**：`[0, 1, 2, 3, 4, 5]` —— **从 0 连续**（0..N-1 无缺号、无重复）
- **`TASK_FINISHED`**：恰好 **1** 条，且位于**最后**（满足契约 `I6`：恰好一条 `TASK_FINISHED` 且在末尾）

### 1.5 工具真的执行过（证据：读到的是磁盘上的哨兵文件内容，非编造）

会话事件流中 `kind=tool_result` 事件：

```
TOOL_RESULT: read_file ok= True audit_id= 6eb6d039d4ca4f1c930cd84f52df2c4b
TOOL_RESULT_CONTENT_HAS_SENTINEL: True
TOOL_RESULT_CONTENT_HEAD: 'E2E-SENTINEL-VERIFIER-7C2D\n'
```

即 `read_file` 工具返回的 `result.content` 正是磁盘上 `hello.txt` 的内容
（`E2E-SENTINEL-VERIFIER-7C2D\n`）。模型**不可能凭空猜出**这个我方生成的哨兵串，
因此可判定工具**真实读取了白名单根内的磁盘文件**，而非模型编造。

最终回答（最后一条 `model_response` 的 `content`）同样包含该哨兵串
（`FINAL_ANSWER_HAS_SENTINEL: True`），即模型把工具读到的内容原样回传——完成"调用工具 + 引用结果"。

### 1.6 审计可回放（这是 `0.1.0` 判据里唯一的安全侧要求）

- **审计文件路径**：`/root/.local/state/lowspec/audit/audit.jsonl`
  （默认审计目录 = `platformdirs.PlatformDirs("lowspec").user_state_path / "audit"`，
  落在 `ALLOWED_AUDIT_ROOTS` 内；未自定义 `--audit-directory` 以免触发路径白名单拒绝）
- **行数**：2；**每行均可 `json.loads`**：`ALL_LINES_JSONL: True N= 2`
- **session 关联**：2 行 `session_id` 均匹配本次 `SESSION_ID=994b933685b74403b16452e9e97bbf23`
  （`SESSION_MATCH_LINES=2`），即这 2 行审计事件确属本次会话
  （1 条 `POLICY_DECISION` = 该次 `read_file` 的风险求值；1 条 `TOOL_CALL` = 工具调用）
- **回放命令（`query_by_id` 入口：`src/agent_sec_perf/observability/audit.py:142`
  `JsonlAuditSink.query_by_id`）**：

```bash
uv run --project /workspace python -c "
from agent_sec_perf.observability.audit import JsonlAuditSink
from agent_sec_perf.foundation.config import default_audit_directory
sink = JsonlAuditSink(default_audit_directory())
ev = sink.query_by_id('6eb6d039d4ca4f1c930cd84f52df2c4b')
print('REPLAY event_id=', ev.event_id)
print('REPLAY kind=', ev.kind, 'tool_name=', ev.tool_name, 'outcome=', ev.outcome)
print('REPLAY session_id=', ev.session_id)
print('REPLAY detail=', dict(ev.detail))
print('REPLAY timestamp=', ev.timestamp)
"
```

输出（真实从磁盘 JSONL 还原）：

```
REPLAY event_id= 6eb6d039d4ca4f1c930cd84f52df2c4b
REPLAY kind= tool_call tool_name= read_file outcome= ok
REPLAY session_id= 994b933685b74403b16452e9e97bbf23
REPLAY detail= {'truncated': False}
REPLAY timestamp= 2026-09-20T10:46:53.381241+00:00
```

- **说明**：审计事件按设计只记录工具调用的元信息（`kind`/`tool_name`/`outcome`/`detail`），
  **不复制文件正文**——这是 `audit.md` 的隐私取舍（正文在会话事件流的 `tool_result` 中，见 §1.5）。
  `query_by_id` 以 `TOOL_CALL` 审计事件的 `event_id` 为关联键，从磁盘 JSONL 成功还原，
  证明"审计可回放"这一判据成立。

## 5. 复现要点小结（他人照做可重现）

1. 环境：8 核 / 16Gi；模型 `/opt/models/Qwen3-4B-Q4_K_M.gguf`；`llama-server` 在 PATH。
2. 临时目录用 `mktemp -d`（绝不在仓库内）；放 `hello.txt`（哨兵）与 `.lowspec.toml`
   （`granted_capabilities = ["read_file"]`）。
3. **必须用 `--max-completion-tokens 1536`（或更大）** 跑 Qwen3-4B；`384` 会 `ModelProtocolError`
   失败（见 §1.1）。`--model-request-timeout-s` 同步放宽到 ≥ 450。
4. `--pack /workspace/examples/packs/coding-readonly`；`--allowed-root` 含工作目录与 `/workspace/examples`。
5. `--output-format json` 抓事件流；审计在 `~/.local/state/lowspec/audit/audit.jsonl`，
   用 `JsonlAuditSink.query_by_id(<tool_result.audit_id>)` 回放。

## 6. 主要发现与需领导裁决

  `ModelProtocolError` 失败；应更正配方或 ADR 注明该模型最低预算（建议 ≥ 1536）。

- **（信息）B/C 结论**：wheel 不含 `examples/`（与 ADR 预测一致，无需改 ADR）；`src/` 未 import
  `examples/`（无机器检查，建议补）。
- **（不证明）** 见 §1.7：本次仅证明"一次只读会话可跑通 + 审计可回放"，不构成安全到位 / 性能 / 其它模型档位的证据。
