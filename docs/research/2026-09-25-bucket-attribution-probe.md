## 1. 额度口径更正（**本次第一条硬更正**）

`cnb charge get-quota --slug Mybase_Le0n3rd` 实测（2026-09-25 06:1x）：

| 计费项 | `total` | `free` | 换算 | 真实处境 |
| --- | --- | --- | --- | --- |
| `ci_in_sec`（构建-CPU） | 576000 s | 576000 s | **160 核时** | `total == free` ⇒ **160 是硬顶，无提升空间** |
| `dev_in_sec`（开发-CPU） | 63360000 s | 5760000 s | 总量 **17600** / 免费 **1600** | 超出免费部分**计费**（¥0.125/核时），但**容量充足** |
| `ci_gpu_in_sec` / `dev_gpu_in_sec` | 0 | 0 | **0 核时** | ⚠️ **完全没有额度**，一开即付费且无上限额度 |
| `credit_in_milli` | 7166000 | 500000 | 7166 / 500 | AI credits（NPC、内置 CodeBuddy 等） |

### 1.1 [ADR-0024](../../docs/adr/0024-quota-discipline-and-cost-model.md) 的口径错误

ADR-0024 §1.2 写：「开发桶 **2512.7 / 1600 = 157%，已超额 912.7 核时**」，
并由 §4 第 1 条推出「本 ADR 不能把组织账单降到 0；要回到免费额度内需全组织一起降」。

**该表述拿 `used` 比 `free`，口径错了。** 正确表述：

- **容量**口径：2512.7 / **17600** = 14.3% ⇒ **余 ≈15000 核时，容量不是约束**；
- **成本**口径：超出免费部分 912.7 核时 × ¥0.125 ≈ **¥114/月**，**会花钱，但能力不受限**。

⇒ 由此推出的结论也要改：

| ADR-0024 的结论 | 更正后 |
| --- | --- |
| 「开发桶已超额」 | **不成立**；应为「超出免费额度、产生计费，但余量充足」 |
| 「真正的超支点在开发桶」（§1.2 标题） | **不成立**；真正的**硬约束**是构建桶 160（`total == free`） |
| 「本 ADR 不能把组织账单降到 0」 | **成本侧仍成立**（912.7 核时会计费），但它**不是容量约束**，不构成"必须削减"的理由 |
| D-C1「环境用完即关」 | **仍成立**（省的是钱，不是额度），但**降级**为成本纪律而非生存纪律 |

⚠️ 连带需更正的载体（本次一并处理）：ADR-0024 §1.2/§4.1、
[devlog 0022](../../docs/devlog/0022-2026-09-24-CI降级与跑测环境内自动化.md) §4.5/§5.11、
`.cnb.yml` 头部注释第 6 条（"开发桶本月已超免费额度"）。

## 3. ADR-0023 / ADR-0024 中「建立在自动化必烧构建桶之上」的结论复核（问题 2、3）

### 3.1 被事实 A/B 推翻的（**不再成立**）

| # | 原结论 | 位置 | 为什么不再成立 |
| --- | --- | --- | --- |
| R1 | 「自动跑测 ⇒ 必然占用构建桶 160」 | ADR-0023 §2.1、§4 | 判据是**有没有 `services: [vscode]`**，不是"是不是自动触发"。自动触发 + `vscode` ⇒ 开发桶 |
| R2 | 「`crontab` 是最不可控的消耗源，一条不留」 | ADR-0023 §2.1 | 前提是"烧构建桶"。走开发桶后**不可控性下降**（容量余 ≈15000）；但**定时本身的不可控仍在**（不等人、不看当天有事没事）⇒ 判据改为"是否值得定时"，而非"一律禁止" |
| R3 | 「跑测只能人工触发（`make bench`）」 | ADR-0023 §2.3 | 可保留人工入口，但不再是**唯一**入口 |
| R4 | 「开发桶是紧张的桶，要省」 | ADR-0024 §1.2 | 见 §1.1：**容量不紧张** |
| R5 | 「降核/分片是为了省构建桶」 | ADR-0023 §3 | 动机变了：现在是为**成本**（¥/核时）与**存活上限**（§4 的三条回收机制） |

### 3.2 仍然成立的（**不受影响**）

| # | 结论 | 为什么仍成立 |
| --- | --- | --- |
| K1 | 四道可信闸门一条不少 | 判据与承载无关；迁移到脚本后 ②③ 反而变强（ADR-0023 §2.4） |
| K2 | `bench/data` 只由跑测脚本写；**禁止把测试数据推到代码分支** | 与桶无关，是**数据来源可追溯**的要求 |
| K3 | `test/<slug>` **零提交** | 与桶无关；且它是"环境从与 `develop` 一致的提交拉起 ⇒ 命中镜像缓存"的载体 |
| K4 | 门禁一律 1 核（不声明即按 8 核计费） | 构建桶仍是硬顶 160 |
| K5 | `ifModify` 路径过滤 + `lock` 去抖 | 同上 |
| K6 | 不可信产物（模型产物）的执行宿主风险需重估 | **与桶无关**，且自动化后宿主变成"无人值守的长时环境"，风险面**变大**（见 §6） |
| K7 | 成本模型「开发 = `cpus` × 存活时长」 | 仍成立——只是它现在对应**钱**而不是**额度** |

## 4. 新发现的平台机制（**在此之前本仓库不知道**）

出处均为 [grammar.md](https://docs.cnb.cool/zh/build/grammar.md)，访问日期 2026-09-25。

### 4.1 `services.vscode.options.keepAliveTimeout` —— 保活时间**可声明**

原文（grammar.md §service:vscode）：

> 如需指定开发环境离线保活时间（超过指定时长，则回收开发环境），可使用 `keepAliveTimeout` 参数
> ……默认值 `600000`（ms, 10 分钟）……
> **不设置默认 10 分钟没有心跳（检测不到开发环境内的 http/ssh 连接）就关闭开发环境**

⭐ 两条推论，都是对既往认识的更正：

1. **心跳的判据是「环境内的 http/ssh 连接」，不是「人有没有打开页面」。**
   [workspace-recycling.md](https://docs.cnb.cool/zh/workspaces/workspace-recycling.md)
   面向用户写的是"10 分钟内未进入 VS Code 页面"，那是**简化表述**；
   grammar 给出的**机制**是连接检测。
2. **10 分钟是默认值，不是固定值** —— 支持 `ms`/`s`/`m`/`h`。
   ⇒ 无人值守跑测**不需要**"模拟心跳"（那是用脆弱手段对抗平台机制，属已知反模式），
   只需**声明** `keepAliveTimeout`。

⚠️ **待实测**：`keepAliveTimeout` 能否突破另外两条（18h 最大保持、不过夜 4-6 点）。
文档未说明它与这两条的关系 ⇒ **不得假定它能**。

### 4.2 Job `timeout` —— **无输出 10 分钟即超时**

原文：「默认单个任务的超时时间为 2 小时，最大不能超过 12 小时，**无输出超时时间为 10 分钟**」。

⇒ 跑测脚本**必须持续输出**（每片内输出间隔 < 10 分钟），否则被判超时。
这与 `keepAliveTimeout` 是**两个独立的 10 分钟**，都要满足。

### 4.3 `sandbox: true` ⇒ `CNB_TOKEN` 无效

原文：「设为 `true` 时，流水线以下环境变量无效：`CNB_TOKEN`」。

⇒ 与 §6 的安全后果直接相关：**能**让自动化跑测环境不持令牌；
**但**发布到 `bench/data` 需要令牌 ⇒ 二者冲突，需显式权衡（见 §6.2）。

### 4.4 `lock` 在 Pipeline / Stage / Job 三级都可用

⇒ ADR-0023 §4.2「并发控制从机制退化为纪律」**可被消除**：
自动化后可用 `lock.key` 机械保证"同时只有一轮"。
（`cancel-in-progress` / `wait` / `cancel-in-wait` 均可选。）

### 4.5 GPU 节点不可用

`get-quota` 实测：`ci_gpu_in_sec.total = dev_gpu_in_sec.total = 0`。
⇒ `cnb:arch:amd64:gpu` / `gpu:L40` 虽存在于
[build-node.md](https://docs.cnb.cool/zh/build/build-node.md)，
但**没有额度** ⇒ 机器矩阵里记"不可用"，不进任何方案。

### 4.6 本仓库此前不知道的既有事实（平台注入值，实测）

`CNB_PIPELINE_MAX_RUN_TIME=72000000`（= **20 h**，构建）与
`CNB_VSCODE_MAX_RUN_TIME=64800000`（= **18 h**，开发）——
与文档「构建 20h / 开发 18h」一致，且**是平台注入的运行期值**，比文档更硬。

## 5. 2026-09-25 05:35 的强制回收事件（**实测样本，n=1**）

| 项 | 值 |
| --- | --- |
| 旧环境被回收 | **05:35**（`CNB_BUILD_START_TIME` 显示新环境起于 `2026-09-24T21:35:48Z` = 北京 09-25 05:35:48） |
| 时刻落在 | **凌晨 4–6 点禁区内** |
| 推断存活时长 | ≈ **8.0 h**（上一会话 09-24 21:3x 拉起，末笔提交 09-25 00:31） |
| 不是 | 18 h 上限（容器重建时仅 10 分钟） |
| 所有者补充 | **当时 Web IDE 页面是开着的** ⇒ 排除"关闭页面"分支 |

⇒ 判定：**不过夜机制**（使用 > 8 h 且处于 4–6 点）**触发，置信度高**。

⭐ 由此得到一条**对既往认识的反证**：环境在 **00:31 → 05:35 无人操作**的 5 小时里**存活**。
若"无操作 10 分钟即回收"字面成立，它应在 00:41 前后就被回收。
⇒ **"开着页面但无操作"不会触发心跳**（至少本次如此，n=1）。
**未实测**的只剩：**从未进入页面**的自动拉起环境能否存活（这正是 §6 的 P2）。

## 6. 实验协议 E1（一次实验，三个判据）

### 6.1 待测命题

| # | 命题 | 判据 | 若成立 |
| --- | --- | --- | --- |
| **P1** | 非 `vscode` 事件 + `services: [vscode]` ⇒ 计入**开发桶** | `cnb charge get-volume` 的 `dev_in_sec` 增量 > 0 且 `ci_in_sec` 增量 ≈ 0 | 事实 A 的推论**实测成立** |
| **P2** | `keepAliveTimeout: 20m` 能让**从未进入页面**的环境活过 12 分钟 | 探针在 t+12 min 仍有输出 | 默认 10 分钟心跳**被覆盖** |
| **P3** | 环境可被**程序化关闭**（`cnb workspace workspace-stop`） | 调用后 `list-workspaces` 不再返回该环境 | "跑完即止"**可机制化**，开发桶计费与构建桶同构 |

另附观测（不设判据，只记录）：stages 结束后环境是否**自动**销毁（`P3'`，
若自动销毁则 P3 不必做）。

### 6.2 配置（实验段，分支键 `test/*`，事件 `api_trigger_quota_probe`，放在 TODO 块之后）

```yaml
test/*:
  api_trigger_quota_probe:
    - name: quota-probe
      runner:
        cpus: 1
      services:
        - name: vscode
          options:
            keepAliveTimeout: 20m
      docker:
        image: python:3.12-bookworm
      stages:
        - name: probe-timeline
          script: |
            set -eu
            ... 每 60 s 打一次时间戳，共 12 次 ...
      endStages:
        - name: probe-end
          script: |
            set -eu
            echo "[probe][endStages] ..."
```

设计取舍（逐条为什么）：

| 选择 | 理由 |
| --- | --- |
| `cpus: 1` | 探针不跑模型，只测平台行为 ⇒ 不浪费核时 |
| 分支键 `test/*` 而非 `develop` | **关键**：`"**"` 与 `develop:` 会**同时命中并并行执行**（`.cnb.yml` 头部第 8 行）⇒ 加 `develop:` 键会让门禁跑两遍 |
| 不写 `docker.build` | 避免触发镜像重建（每改一次所有环境下次拉起都要重建） |
| `python:3.12-bookworm` | 与门禁/开发镜像同源，且满足"镜像钉到发行版"的检查 |
| 每 60 s 输出 | 规避 §4.2 的"无输出 10 分钟超时" |
| `endStages` | 观测"销毁前钩子是否执行"（事实 F 的兜底外推能力） |

### 6.3 触发与观测步骤

```text
t0    cnb build start-build --repo <slug> --branch test/quota-probe --event api_trigger_quota_probe
      → 记 sn
t0+2  cnb build get-build-status --repo <slug> --sn <sn>
t0+5  cnb workspace list-workspaces --slug <slug> --status running
t0+11 同上
t0+13 同上；读构建日志取探针时间线
t0+14 cnb workspace workspace-stop --sn <sn>            # 无论是否已自动销毁，都验证一次
t0+15 cnb charge get-volume                              # 与 t0 前的读数对比
```

### 6.4 成本与风险

| 项 | 值 |
| --- | --- |
| 预期成本 | 1 核 × ~15 min ≈ **0.25 核时**（开发桶） |
| 最坏成本 | 未及时关闭 ⇒ 1 核 × 18 h = 18 核时（对余 ≈15000 的桶**可接受**） |
| 不触碰 | 构建桶（实验目标是证明它**不**走构建桶）、历史数据、已推送历史 |
| 失败处置 | 环境失控时用 `workspace-stop` / `delete-workspace` 收尾；**不强推、不改历史** |

⚠️ **单臂实验、无对照**：为省额度不跑"默认 `keepAliveTimeout`"的对照组。
⇒ P2 成立只能证明"声明 `20m` 后能活过 12 分钟"，**不能**证明"默认会被杀"
（后者由 §5 的 n=1 事件与文档共同支持）。
