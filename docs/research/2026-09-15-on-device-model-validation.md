# W1 风险验证：MiniCPM5-2B 与 Qwen3.5-4B 在 CPU 端侧的可运行性与能力边界

- 时间盒：≤ 3 小时（实际使用约 1.5 小时）

## 1. 研究问题

三个**可证伪**的问题（不是"哪个模型更好用"这类无法回答的问题）：

| 编号 | 问题 | 判定标准 |
| --- | --- | --- |
| Q1 | 两个候选模型能否在我们**既有**的 llama.cpp（CPU-only、8 线程）上加载并完成生成？ | 能加载 + 能生成 → 通过；不能 → 该候选直接出局 |
| Q2 | 它们的 prefill / decode 性能与内存占用是否落在"端侧可接受"区间？ | 与项目计划中的 4B 级预算（Q4_K_M、≤ 3 GB、≥ 10 tok/s）比较 |
| Q3 | 端侧 agent 最关键的两项能力——**工具调用**与**受限预算下的结构化输出**——能否稳定工作？ | 同一批任务、同一 token 预算下逐项判定 |

**为什么要做**：这直接决定风险项 **R-1（4B 级模型能力不足）** 是否触发，
以及主力模型选谁。在拿到自有数据之前，任何选择都建立在厂商自述之上。

## 2. 现状扫查

| 对象 | 来源与版本 | 关键事实 |
| --- | --- | --- |
| MiniCPM5-2B | HF `openbmb/MiniCPM5-2B`、`openbmb/MiniCPM5-2B-GGUF`（访问日期 2026-09-15） | 2.52B（非嵌入 1.98B）、42 层、GQA 16/2、上下文 128K、Apache-2.0、标准 `LlamaForCausalLM` |
| Qwen3.5-4B | HF `Qwen/Qwen3.5-4B`（访问日期 2026-09-15） | 4B（GGUF 元信息 4.21B 参数）、32 层、混合 Gated DeltaNet + Gated Attention、**原生多模态**、上下文 262K、Apache-2.0 |
| Qwen3.5-4B 量化 | HF `unsloth/Qwen3.5-4B-GGUF`，revision `e87f176` | 社区量化（**官方未提供 GGUF**） |
| 官方部署文档缺口 | `OpenBMB/MiniCPM` 的 `skills/minicpm5-deploy-llama-cpp/SKILL.md`、`docs/deployment/llama_cpp.md` | 只出现 `--jinja`，**没有任何工具调用示例**；**完全未提及**投机解码（DSpark）；**未指定** llama.cpp 最低版本 |
| Qwen 侧部署文档缺口 | HF 模型卡 | 推荐 vLLM / SGLang；llama.cpp 路径依赖社区量化 |

**扫查就得到的判断**：两个候选的"官方支持"都集中在 vLLM/SGLang（GPU 场景），
而我们只有 CPU + llama.cpp。**因此"能不能用"必须自己实测，官方文档给不出答案。**

## 3. 方法

### 3.1 环境（与本项目开发环境一致，即目标测试环境）

| 项 | 值 |
| --- | --- |
| llama.cpp | build **`69eb250`**（`0.4.1-dev`，镜像内源码构建） |
| 构建参数 | `GGML_NATIVE=OFF`、`GGML_CUDA=OFF`、`LLAMA_CURL=ON` |
| CPU / 内存 | 8 vCPU / 16 GiB（`-t 8`） |
| 量测工具 | `llama-bench`（性能）、`llama-server`（能力）、`/proc/<pid>/status` 的 `VmHWM`（内存） |

### 3.2 模型文件（**均固定来源并校验摘要**）

| 模型 | 文件与大小 | sha256 |
| --- | --- | --- |
| MiniCPM5-2B | `MiniCPM5-2B-Q4_K_M.gguf`，1,561,318,368 B（1.45 GiB） | `ec2d5801640099e97d8d7e8003ad4d81f336e757811f03a26173dddf386602fd` |
| Qwen3.5-4B | `Qwen3.5-4B-Q4_K_M.gguf`，2,740,937,888 B（2.54 GiB） | `00fe7986ff5f6b463e62455821146049db6f9313603938a70800d1fb69ef11a4`（与 HF `x-linked-etag` **完全一致**） |

### 3.3 受控条件

- **同一量化档位**（均 Q4_K_M）——避免把"量化差异"误读为"模型差异"；
- **同一引擎与同一构建**（build 69eb250）；
- **同一线程数**（8）；
- **串行执行**：任一时刻只有一个模型驻留在内存中，避免 CPU 争用污染性能数据；
- 采样参数按各自官方推荐：思考模式 `temp=1.0, top_p=0.95, min_p=0.0`；
  非思考模式 `temp=0.7, top_p=0.95, min_p=0.0`（`min_p=0.0` 是 MiniCPM5-2B 官方明确要求的防重复设置）。

### 3.4 命令（可复现）

```bash
# 性能基准（3 次取中位）
llama-bench -m models/MiniCPM5-2B-Q4_K_M.gguf -t 8 -p 512 -n 128 -r 3
llama-bench -m models/Qwen3.5-4B-Q4_K_M.gguf  -t 8 -p 512 -n 128 -r 3

# 能力测试（OpenAI 兼容端点）
llama-server -m <model>.gguf -c 8192 -t 8 --port <8080|8081> --no-webui
# 请求：tools 定义 + tool_choice=auto；结构化抽取；代码类型标注
# 通过 chat_template_kwargs.enable_thinking 切换思考模式
```

## 4. 结果与数据

### 4.1 Q1：可加载性 —— **两个模型均通过**

| 模型 | GGUF 架构 | 加载结果 |
| --- | --- | --- |
| MiniCPM5-2B | `llama` | ✅ 正常加载并生成 |
| Qwen3.5-4B | `qwen35` | ✅ 正常加载并生成（含混合 Gated DeltaNet） |

> 说明：llama-bench 对 MiniCPM5-2B 显示 `llama ?B`（模型名未识别），
> 但**加载、prefill、decode 全部正常**，属显示信息缺失，不影响功能。

### 4.2 Q2：性能与内存

`pp512` / `tg128`，8 线程，3 次重复（`±` 为重复间波动）：

| 指标 | MiniCPM5-2B | Qwen3.5-4B | 倍率 |
| --- | --- | --- | --- |
| 文件体积 | 1.45 GiB | 2.54 GiB | 1.75× |
| 参数量 | 2.52 B | 4.21 B | 1.67× |
| **prefill** `pp512` | **92.79 ± 10.63 t/s** | 45.64 ± 0.78 t/s | 2.03× |
| **decode** `tg128` | **33.86 ± 0.16 t/s** | 15.75 ± 0.25 t/s | 2.15× |
| 峰值内存（`VmHWM`，单次） | 2,519 MB | 4,148 MB | 1.65× |
| 端到端（加载+基准，单次） | 15.0 s | 32.2 s | 2.15× |

**观察**：MiniCPM5-2B 用 **约 57% 的体积**换到 **约 2 倍的速度**，
这与"端侧 decode 受内存带宽支配"的机理一致（要搬的数据更少）。

### 4.3 Q3：能力矩阵（**本次最具价值的发现**）

统一任务、统一最大 token 预算（`max_tokens` 见下表），`finish_reason` 取服务端返回值：

| 测试 | 预算 | MiniCPM5-2B | Qwen3.5-4B |
| --- | --- | --- | --- |
| **T1 工具调用**（`tools` + `tool_choice=auto`） | 512 | ✅ `finish=tool_calls`，参数 `{"city":"Beijing"}` | ✅ `finish=tool_calls`，参数 `{"city":"北京"}` |
| **T2a 结构化抽取·默认思考** | 1024 | ✅ `finish=stop`，正确 JSON；思考仅 **125** 字符 | ❌ **`finish=length`，content 为空**；思考 **3689** 字符 |
| **T2b 结构化抽取·关闭思考** | 256 | ✅ 正确 JSON（20 token） | ✅ 正确 JSON（20 token） |
| **T3a 代码类型标注·默认思考** | 768 | ❌ **`finish=length`，content 为空** | ❌ **`finish=length`，content 为空**；思考 2664 字符 |
| **T3b 代码类型标注·关闭思考** | 768 | ❌ **未执行指令**：原样返回代码，未加任何标注 | ✅ `finish=stop`，补出了完整标注 |

### 4.4 失败模式的机制

两个模型出现了**同一个机制**的失败：

```text
任务 → [思考通道] 消耗全部 token 预算 → max_tokens 用尽 → finish_reason=length
      → 最终 content 为空（用户看到"什么都没输出"）
```

差异只在**思考的"啰嗦程度"**：

| 模型 | 简单任务（T2）的思考长度 | 后果 |
| --- | --- | --- |
| MiniCPM5-2B | 125 字符 | 预算充足 → 一次通过 |
| Qwen3.5-4B | **3689 字符** | 预算被吃光 → 输出为空 |

**关键判断：这不是"模型能力不足"，而是"配置与编排缺失"。**
证据：同一个 Qwen3.5-4B，仅把 `enable_thinking` 设为 `false`，
T3b 就从"空输出"变为"正确补全类型标注"；T2b 也从失败变为成功。

### 4.5 其他观测

- 服务端默认 `n_slots = 4`、`n_ctx_slot = 8192`：即 `-c 8192` 实际被按槽位分配，
  做正式基准时必须显式固定 `-np`，否则内存与吞吐口径不一致。
- 服务端日志提示：`chat template supports preserving reasoning, it is enabled by default`
  （可用 `--no-reasoning-preserve` 关闭）——说明推理内容默认会**占用输出预算**。
- MiniCPM5-2B 在工具调用时把用户的中文参数 `北京` 归一化为英文 `Beijing`。
  对天气类 API 无影响，但对中文知识库类工具会造成检索偏差——**属于需上游防护的行为**。

## 5. 结论

| # | 结论 | 置信度 | 依据 |
| --- | --- | --- | --- |
| 1 | 两个候选都能在既有 CPU llama.cpp 上运行，**R-1（无可用模型）未触发** | **高** | 本机实测（Q1） |
| 2 | MiniCPM5-2B 在速度、内存、默认思考克制程度上均占优（速度约 2×） | **高** | 本机实测（Q2、T2a） |
| 3 | Qwen3.5-4B 在"关闭思考后的代码类任务"上更强 | **中** | 单任务实测（T3b），样本量小 |
| 4 | **两个模型都必须显式配置思考模式与 token 预算**，否则会出现"空输出" | **高** | 对照实验（T2/T3 开关对比） |
| 5 | 厂商汇总分（MiniCPM5-2B 53.9 > Qwen3.5-4B 51.1）**不能预测**本场景下的逐项胜负 | **高** | 本次矩阵与厂商排序不一致 |
| 6 | "Qwen3.5-4B 是当前最好的开源端侧模型"这一说法**不成立** | **中** | 见 §6.1；受限于检索范围，属"未找到证据支持"而非"已证伪" |

## 6. 对本项目的影响

### 6.1 模型选型（回答"Qwen3.5-4B 是不是最好的"）

**不是**，理由分三层：

1. **口径层**：二手来源给出的 MiniCPM5-2B 的 AA 指数出现 **23 / 17 / 15** 三个版本，
   另有站点给 Qwen3.5-4B 的 AA 智能指数 **0.11**（另一套归一化）——
   **数字不可比**，因此"谁第一"这个问题在公开信息层面无法回答。
2. **时间层**：Qwen3.5-4B 发布于 2026-02（7 个月前），而 MiniCPM5-2B 发布于 2026-09-07；
   Qwen 自身已推进到 3.6 / 3.8 代际（其≤4B 小尺寸是否刷新 **【待验证】**）。
3. **定位层**：Qwen3.5-4B 是**原生多模态**（文本/图像/视频）的通用模型，
   并非"端侧文本 agent"定位；其代价是本项目场景下 2 倍的体积与耗时。

**建议**（供决策）：**主 = MiniCPM5-2B，辅 = Qwen3.5-4B**，但**职责分工按本次数据重写**：

| 角色 | 模型 | 依据 |
| --- | --- | --- |
| 端侧主 Agent（默认路径） | MiniCPM5-2B | 速度/内存占优、默认思考克制、工具调用可用 |
| 代码类/复杂推理的专家模型 | Qwen3.5-4B（**关闭思考**） | T3b 表现最好；但 2× 耗时，只按需调用 |

> 这正好契合项目既有的"主 Agent + 按需专家调度"设计：
> **便宜的先做，贵的只在必要时介入。**

### 6.2 对系统设计的硬性要求（本次最重要的产出）

1. **执行器/编排层必须显式管理思考模式**：按任务类型切换 `enable_thinking`，
   并对 `finish_reason=length && content 为空` **做显式处理**（重试/扩预算/降级），
   否则 agent 会把"预算耗尽"误判为"模型不会"。
2. **性能基准必须标注配置**：`-np`、`-c`、线程数、量化档位、采样参数缺一不可。
3. **模型文件必须固定 revision 并记录 sha256**（本次已做到，Qwen 侧与官方 etag 一致）。
4. **llama.cpp 版本必须固定**：本次数据绑定 build `69eb250`；
   镜像仍跟随 master（V-6），**在写任何"优化"结论前必须先把版本钉住**。
