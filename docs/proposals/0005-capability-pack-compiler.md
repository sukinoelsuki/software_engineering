## 0. 所有者裁决（2026-10-27）与一处更正

| 项 | 裁决 |
| --- | --- |
| `Q1` 定位 | **内核即当前产品**（与运行时并列的第二产品线，不替换 `run`/`demo`） |
| `Q2` 命名 | **`pack`**（与既有 `pack.toml` 一致） |
| `Q3` 代码落点 | 新增 **`src/agent_sec_perf/pack/`**，见 [`ADR-0034`](../adr/0034-capability-pack-kernel.md) |
| `Q4` 可拒绝 | **接受**：判据自证是发布闸门，"不适合"是合法输出 |
| `Q5` 第二案例 | **暂缓**（环境与资源受限）；本期的"验证"只到冒烟 |

**更正（重要）**：本文件初稿把大模型写成"产出候选包的组件"，这是**理解偏差**。
大模型的真实角色是**整个内核的总控**——读 `status` / `plan` 的 JSON、决定下一步、
修改声明式文件，再让内核重新判定。因此 §5.1 的 `M-C` 不是"接一个大模型来生成包"，
而是"让总控进入循环"；也正因如此，`status` / `plan` 的接口必须先于 `M-C` 稳定下来。

## 0.1 一句话结论

**能做，但必须先改述。**

老师的判断（"过程值得沉淀成方法论/框架/插件"）成立；但把它叫 **RSI** 会误导评审，
也会误导我们自己的验收方式。本项目真正在做、也真正可产品化的是：

> **在固定判据下，为一个给定端侧模型搜索并冻结一套"可执行的行动边界"**
> （工具子集 × 阶段划分 × 参数形状 × 提示结构 × 机检判据），
> 产出一个**带证据、可复现、可拒绝**的能力包。

模型权重不变、模型不变强；变的是**它能看见什么、能做什么、做错时会不会被发现**。
这条路径每一步都可判定，因而**可以自动化**；RSI 那条路径目前无法给出可判定的收敛依据。

## 1. 问题与目标

### 1.1 触发

过去六周的实做里，真正花时间的不是"写 harness"，而是**反复调教同一个 4B 模型**：
`devlog 0031` §4.5 记录了八轮迭代，每轮都是"模型没做到 → 改一处 → 复跑 → 记录"。
这些修改**有稳定的模式**（§3.2 的表），而它们目前只存在于人的经验与一篇 devlog 里。

**这就是可产品化的部分**：把"人调模型"变成"编译器 + 判据 + 证据"。

### 1.2 先把三个词钉死（否则后文会被读成另一件事）

| 词 | 本文的含义 | **不是**什么 |
| --- | --- | --- |
| **能力集** | 模型在会话里**可见可用的动作面**：工具子集 + 每阶段暴露面 + 参数 schema + 提示结构 + 判据 | 不是模型权重、不是量化档、不是 LoRA |
| **剪枝** | 收窄动作面（`trimming.TIER_CAPABILITY_BUDGET` / `pack.tools.allowlist` / 按阶段拆包） | 不是剪枝神经网络 |
| **丰富（加手）** | 增加**受限**的领域工具（如 `write_incident_report`），把"要模型做对"变成"工具保证对" | 不是给模型加参数、不是开放通用 `write_file` |

> 依据：`src/agent_sec_perf/harness/trimming.py` 的档位预算、`harness/domain_pack.py` 的包加载、
> `tools/files.py` 的三个受限写工具。**"能力"在本项目里一直是外部脚手架的概念，不是权重。**

### 1.3 它不是什么（防范围失控）

- **不是 RSI**：没有"改进改进能力本身"的自指闭环；我们的闭环是"判据 → 候选 → 验证 → 拒绝"。
- **不是模型训练/微调**（SRS `Won't`）。
- **不是通用 agent 框架**（`ADR-0015` §3.3 明令不引入 LangChain/LangGraph 等）。
- **不是插件市场/云服务**：单机、无服务、无账号（`architecture.md` §1.2 四条硬约束）。

### 1.4 目标（可核对，不是愿景）

1. 给定「端侧模型 + 任务 + 可用工具集」，能产出一个**可被现有 `run`/`demo` 直接消费**的能力包；
2. 产出附**证据**：判据版本、模型摘要、每次运行的逐项检查、已知失败模式；
3. 能给出**否定结论**："这个模型做不了这个任务"，并指出在哪一类失效上失败；
4. 整个过程**离线可复现**（教师模型可缺省，见 §5.1 的 M-A/M-B 分期）。

## 3. 方法论：五阶段 + 失效模式 → 修复动作

### 3.1 流水线（`C0`~`C5`）

```text
C0 任务契约化 → C1 能力探针 → C2 装配设计 → C3 验证 → C4 归因修复 ↺ → C5 打包
                                        ↑__________________|
                                   最多 N 轮，每轮留证据
```

| 阶段 | 输入 | 输出（必须可机读） | 判定 | 现状 |
| --- | --- | --- | --- | --- |
| **C0 契约化** | 自然语言任务、现场文件 | `case.toml`：允许动作、产物、判据、失败分级 | 判据能对"已知正确/已知错误"各给一次结果 | 已有 `case.toml`，但**没有自证机制** |
| **C1 探针** | 候选模型、探针集 | `profile.json`：动作级能力（单工具选择/两步不跳步/参数合规/证据引用） | 每项 ≥3 次，报区间不报总分 | **无载体**（`model/probe.py` 未开工） |
| **C2 设计** | 任务契约 + profile + 工具清单 | `pack.toml`（每阶段一份）+ 提示片段 + 参数 schema | 静态校验：不新增工具、不放宽风险、不产生代码 | 领域包已有，**生成器没有** |
| **C3 验证** | 包 + 模型 | `evidence.json`：逐项机检 + 事件流摘要 + 审计摘要 | 判据先自证；关键项 0 容忍 | `cli/demo.py` 已有 12 条机检，**未泛化** |
| **C4 归因修复** | 失败证据 | 失效模式标签 + **允许的修复动作** | 只允许 §3.2 表内的结构性动作 | **完全是人的经验** |
| **C5 打包** | 包 + 契约 + 证据 | `manifest.json` + 摘要 + 能力边界声明 | 篡改即拒；同输入同产物 | **无** |

**顺序不可颠倒**：C0/C1 没有之前做 C2，等于让教师模型"凭空写 prompt"——
这正是 `0031` §4.5 前几轮反复失败的原因。

### 3.2 失效模式表（本提案的核心资产）

下表**逐条来自** `devlog 0031` §4.5 的实测，不是推演。左列是观测信号，右列是
**允许的结构性修复**——它的价值在于：**同一类失效只允许用同一类修法**，
从而把"再改改提示"这种无效循环挡在流程外。

| # | 失效模式 | 观测信号（机检可抓） | 允许的结构性修复 | **禁止**的修法 |
| --- | --- | --- | --- | --- |
| `F1` | **未暴露**（授权 ≠ 暴露） | 目标工具 0 次调用 / 反复调同一读工具直到 `LIMIT_REACHED` | 调档位预算；把工具的能力声明改到与阶段匹配 | 提高全局权限；把风险统一降成 `low` |
| `F2` | **格式不合规** | 参数校验失败；占位符 `<...>` 被原样写入 | 封闭字段 schema；工具侧格式闸门（写入时就拒） | 在提示里重复"不要写尖括号" |
| `F3` | **拒绝后放弃** | 一次 `ok=False` 后直接 `FAILED` | 错误信息可执行（指出字段 + 可选值）；重试预算 | 放宽校验让它过 |
| `F4` | **阶段串味** | 调用了不属于本阶段的工具 | 按阶段拆包（会话级暴露面固定） | 在提示里写"现在不要用 X" |
| `F5` | **参数形状不封闭** | 全部 `deny / invalid_arguments`，工具从未被调用 | 工具参数改成封闭字段表（`additionalProperties: false`） | 让校验器接受任意键 |
| `F6` | **值幻觉** | 格式对，但取值不在现场文件里 | 工具内证据校验（值须逐字出现）；拒绝时点名字段 | 在提示里写"不要编造" |
| `F7` | **幂等重复** | 同一写调用 N 次（内容相同） | 工具成功消息引导；把它记为"重复但幂等"，不判失败 | 在 harness 层去重（改核心循环） |
| `F8` | **判据误伤** | 仅排版/空白差异导致 fail | 判据归一化；判据自证（正例必过、反例必败） | 放宽到"看起来对" |

> 三条例证（均见 `0031` §4.5）：
> ① 档位 `BASIC` 只含 `READ_FILE` ⇒ `write_report` 对模型**不存在**（`F1`）；
> ② 模型把 `<...>` 当字面量写进文件（`F2`），加了格式闸门后改为"被拒 → 放弃"（`F3`）；
> ③ 格式全对但写出 `PAY001` / `1200`（`F6`），工具加证据校验后自我纠正。

### 3.3 三条不变式（比任何 prompt 技巧都重要）

1. **能用结构保证的，不要用文字叮嘱。** `0031` 的三次"从提示改到结构"都验证了这一条：
   取消"重写全文"这个动作（`revise_report`）比写十遍"只改一行"可靠。
2. **判据先自证，再用于评估。** 没有"已知正确必过、已知错误必败"这一步的判据，
   不得进入流水线（`evaluation-pitfalls.md` 第 1 条）。
3. **"不适合"是合法输出。** 编译失败必须能归因到 `F1`~`F8` 中的一类；
   给不出归因就说明判据不够，而不是模型不行。

## 4. 产品形态候选

### 4.1 三个候选

| 候选 | 形态 | 增量 | 主要风险 |
| --- | --- | --- | --- |
| **A. CLI 内建编译器** | `agent-sec-perf pack {verify,build,probe,compile}` | 复用现有 harness/领域包/机检；无新依赖 | 与"安全与性能基线"的主叙事争位置 |
| **B. 独立插件（MCP / IDE / CI）** | 把编译能力暴露给外部工具 | 易推广、"插件"直觉强 | MCP 明确未纳入（`ADR-0015` §3.3）；且现在没有稳定的包格式可暴露 |
| **C. 能力包市场/平台** | 分发、评分、签名 | 网络效应 | 违反 C1；需要信任基础设施（`T-09`） |

### 4.2 对比矩阵（1~5 分，越高越好）

| 标准 | 权重 | A | B | C |
| --- | --- | --- | --- | --- |
| 与现有架构契合（`R1`~`R5`） | 0.25 | 5 | 3 | 1 |
| 可验证性（能否机检） | 0.25 | 5 | 4 | 2 |
| 推广成本（他人能否用起来） | 0.20 | 3 | 5 | 5 |
| 安全面（新增信任边界） | 0.20 | 5 | 2 | 1 |
| 本期工作量（越小越高） | 0.10 | 4 | 3 | 1 |
| **加权** | | **4.60** | **3.50** | **1.90** |

### 4.3 推荐：内核 + 三个接缝（**A 为内核，B 为下一阶段适配器**）

"插件"不等于"现在写一个 MCP server"。**先让内核有稳定的插件边界**，适配器才有一层可写：

| 接缝 | 现在 | 将来可替换为 |
| --- | --- | --- |
| **模型后端**（教师 / 学生） | 本地 `llama-server`（回环） | 云端 OpenAI 兼容端点（须先解决 `T-10`） |
| **工具提供者** | 内置 7 个工具 | MCP / 领域工具（须先过策略与审计） |
| **判据提供者** | `case.toml` 的机检项 | 任务模板库（按任务类型给默认判据） |

**这条推荐的关键判断**：B/C 的价值都建立在"包格式 + 判据 + 证据"之上；
这三样没有之前做插件，只是把不稳定接口暴露得更早。

## 5. MVP：三期，按"是否需要模型"切

### 5.1 分期

| 期 | 命令 | 需要模型？ | 价值 | 估工作量 |
| --- | --- | --- | --- | --- |
| **M-A** | `pack verify` / `pack build` | 否 | 把"包"变成**可校验、可分发、可拒绝**的产物；判据自证落地 | 1.5~2 天 |
| **M-B** | `pack probe` | 是（离线） | 动作级能力画像，替代"感觉这个模型不太行" | 1~2 天 |
| **M-C** | 总控循环（大模型读 `status` / `plan`） | 是 | 让总控跑完整流程：判定 → 选动作 → 改声明式文件 → 重新判定 | 2~3 天 |

**为什么把"总控进入循环"放在最后**：没有判据与证据时，大模型的产出一律"看起来对"，
内核无法拒绝，流程就退化成"生成 prompt 的对话框"——那正是本项目刻意不做的形态。
先把判定与证据做实，总控才有**可被拒绝**的动作空间。

### 5.2 M-A 的验收判据（可执行，全部不需要模型）

1. `agent-sec-perf pack build examples/showcase/incident-01 --out dist/incident-01.pack`
   成功；`manifest.json` 含**每个文件的 sha256**、harness 版本、判据版本、模型要求。
2. **确定性**：同输入重复 build，除显式时间戳字段外**字节一致**。
3. **篡改即拒**：改动 bundle 内任意文件后 `pack verify` 退出码 `3`，并**指出**是哪个文件。
4. **判据自证**：bundle 内含 `selftest/`（正例必须全过、反例必须至少失败一项）；
   若反例也全过 ⇒ 判据无效，**拒绝发布**（退出码 `3`）。
5. **编译期拒绝**：以下情形必须拒绝——
   - 判据只引用模型输出、没有任何落盘产物可核对；
   - 某阶段的 `tools.allowlist` 含未注册工具，或包含需要但未授予的能力；
   - 包内出现 `.py` / `.pyc` / `__pycache__`（复用 `R5` 判定）。
6. **零新增依赖**；`make check` 全绿；新增单测 ≥ 12 条。

> 判据 3 与 4 是 M-A 的**存在理由**：它们把 `notes/` 里的两条教训
> （判据自证、证据可核）变成机器检查，而不是又一篇文档。

### 5.3 与现有代码的映射

| 需要的能力 | 复用 | 需新增 |
| --- | --- | --- |
| 包加载与校验 | `harness/domain_pack.py::load_pack` | — |
| 机检 | `cli/demo.py::verify_stages`（**需从 demo 泛化**成"按 case 类型选择判据"） | 判据框架（纯函数） |
| 案例声明 | `examples/showcase/incident-01/case.toml` | `selftest` 段 + 判据版本字段 |
| 摘要/来源校验 | `tools/registry.py` 的 `description_digest` 思路 | `manifest.json` 生成与校验 |
| 执行 | `cli/app.py::execute` | `pack run` 的薄包装 |
| 路径安全 | `foundation/paths.py::resolve_within` | — |

**新增代码的落点必须在 ADR 中定**（候选：新包 `src/agent_sec_perf/pack/`，或并入 `harness/`）。
不预设答案：这是 §7 的裁决项之一。

### 5.4 明确不做

- 不做模型评分排行榜（单一总分会让"能做什么"重新变成"看起来行"）。
- 不做自动修改 `src/` 代码（编译器只能产出**声明式**包；改代码属人）。
- 不做插件市场、上传、账号、云编译。
- 不在 M-A/M-B 完成前接云端教师模型（`T-10` 未缓解）。

## 6. 风险与对策

| # | 风险 | 为什么真实 | 对策 |
| --- | --- | --- | --- |
| `R1` | **单例过拟合** | 目前只有 `incident-01` 一个案例，方法论可能只适用于"读日志写报告" | M-A 之后必须再做**一个非日志案例**（如配置核对/表格抽取），否则只宣称"单案例可行" |
| `R2` | **叙事分叉** | 已交付的 SRS/课程文档写的是"安全与性能基线" | 定位为**同一内核的第二条产品线**（运行时 + 生产工具），SRS 增补而非改写 |
| `R3` | **教师模型 = 新的网络出口** | `T-10`（出站默认拒绝失效）仍是未缓解 | 教师模型先**离线/人工**；自动接入须走白名单 + 审计 + 超时/体积上限 |
| `R4` | **bundle 是不可信输入** | 包可能来自他人（未来分发） | manifest 摘要 + schema + 拒绝代码 + 路径白名单；全部复用现有机制 |
| `R5` | **指标化误导** | 一旦有"分数"，就会被当成能力排名 | 只报"动作级能做/不能做 + 证据"；禁止总分与跨模型排序 |
