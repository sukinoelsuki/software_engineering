### 3.1 `S-1` 工具分层授予（主 Agent 持通用工具 + 全局权限模型；专家持领域受限工具集）

**① 议题**：工具是否按"控制面（主 Agent）/ 数据面（专家）"分两层授予，还是维持单一权限模型？

**② 现状**
- **`SRS`**：**没有**"按 agent 角色分层授予"的条目。最接近的是
  `REQ-TOOL-01`（内置工具 + 权限声明，Must，`srs.md:270`）、
  `REQ-HARNESS-03`（**工具集按能力档位动态裁剪**，Must，`srs.md:244`）、
  `REQ-SEC-01`（默认拒绝，Must，`srs.md:251`）。**SRS §7 全文无"主 Agent"/"专家"角色概念**（2026-09-21 读）。
- **契约**：只有**一套**授权模型——`policy.md` §2.1 的 `Capability` 4 个成员
  （`READ_FILE`/`WRITE_FILE`/`EXECUTE_COMMAND`/`NETWORK_OUTBOUND`，`policy.md:32`~`policy.md:37`），
  且注明"**扩展需 ADR**"（`policy.md:51`）。裁剪维度是"**能力档位 + 领域包白名单**"
  （`harness.md` §3.1 `trimming.select_tools(specs, *, tier, allowlist)`，`harness.md:586`），
  **不是**"agent 角色"。契约里**没有**"授权主体"字段。
- **实现**：`src/agent_sec_perf/harness/trimming.py::select_tools`（`trimming.py:83`）按
  档位 + 白名单裁剪；`harness/session.py:110` 装配时算一次 `exposed`；
  `security/policy.py` 是**单一** `PolicyEngine`、**单一** `granted` 集合。
  全仓 `grep 专家|expert` **零命中**（2026-09-21）⇒ **无"主 Agent/专家"实体**。
- **落点判断**：实现落在"**不采纳分层**"一侧（但以"领域包收窄"部分承担了 `S-1` 的动机——
  `examples/README.md:23`~`examples/README.md:26` 的 `tools.allowlist` + `security.capabilities`）。

**③ 分叉点**：`devlog 0004` §2.3（`0004:63`~`0004:69`）提出"两层"；
现行 SRS + 契约 + 实现只有"**单层权限模型 + 场景化收窄**"。**分歧 = 是否存在"授权主体"这一维度。**

**④ 需所有者回答**：是否采纳"工具分层授予"？
- **选项 A：不采纳**（判定"领域包收窄"已覆盖其动机，`S-1` 否决并记录理由）。
  → 后果：**零** `REQ` 变更、**零**契约变更、**零** `src/` 变更；`0005` 的 `S-1` 状态标"否决"。
- **选项 B：采纳为 SRS 需求**（新增 `REQ-HARNESS-*` "按 agent 角色分层工具授予"）。
  → 后果：① 新增需求，须给验收标准与验证方式（`requirements/README.md:58`）；
  ② **必须新增 ADR**（`policy.md:51` 明文"扩展需 ADR"，且属 `ADR-0003 §5.1` 之外的新自研模块）；
  ③ **公开契约变更**：`policy.md` §2.1 需加"授权主体"维度、`harness.md` §3.1 的
  `select_tools` 签名需加角色参数 ⇒ **须所有者确认**；
  ④ **已实现代码受影响**：`harness/trimming.py`、`harness/session.py`、`security/policy.py`。
- **选项 C：只登记为设计意图，不进 SRS**（写入 `docs/design/`，SRS 不新增条目）。
  → 后果：不产生新 `REQ`；但**须在 SRS 或 ADR 注明"未纳入本期"**，否则后续会被反复重提。

**⑤ 置信度**：**高**（对现状的每条断言均有文件/行号或 grep 依据）；对"是否该采纳"不作判断（属所有者）。
