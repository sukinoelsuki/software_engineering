## 1. 问题与目标

### 问题

项目方向已定为**原生智能系统（Native Intelligent Systems）**，主线是**系统安全** +
**模型/系统加速与优化**，希望通过在一个前沿开源项目上做增量研发，达成两个目标：

1. **研究目标**：切入前沿 AI 生态，形成有技术含量的研究点；
2. **工程目标**：交付一个完整、规范、便捷、安全、高效的软件，同时锻炼工程能力。

现在需要回答：**在众多候选项目中，选哪一个作为 base project 最合适？**

### 选型的本质

这不是"选最火的项目"，而是**在"研究价值"与"单人可交付性"之间找最优解**。
大热的项目往往意味着：代码库巨大、上游 PR 门槛高、需要昂贵硬件——
对一个人、2~3 个月、以工程规范为核心的课程项目而言，这些是**实质约束而非借口**。

## 4. 候选方案

### 候选 A：Agent 操作系统内核 —— AIOS

| 项 | 内容 |
| --- | --- |
| 上游 | `agiresearch/AIOS`（AI Agent Operating System）+ Cerebrum SDK |
| 链接 | <https://github.com/agiresearch/AIOS> |
| 理论支撑 | 《LLM as OS, Agents as Apps》(2023)、《AIOS: LLM Agent Operating System》(2024) |

**定位**：把 LLM Agent 当作"应用"，为其提供操作系统级抽象——**调度器、上下文管理器、
内存管理器、存储管理器、工具管理器**。Agent 通过"系统调用"访问 LLM 与工具，
内核负责资源分配与并发管理。

**本项目可做的增量（安全 × 性能）**：

| 维度 | 可做的工作 |
| --- | --- |
| 安全 | 在工具调用（syscall）层引入**能力（capability）权限模型**，default-deny；工具执行的**沙箱化**与最小权限；**审计日志**；工具/插件的**供应链可信校验**（签名、来源、权限声明） |
| 性能 | 调度器改造（FIFO → 优先级 / 多级反馈 / 抢占式）；**上下文与 KV 缓存复用**；内存管理器优化（分页、淘汰策略、共享）；并发吞吐与 P95/P99 尾延迟 |

**优势**：

- 与研究方向的**字面契合度最高**——"原生智能系统"最直接的落点就是 Agent OS；
- 安全（能力模型、隔离、审计）与性能（调度、缓存、并发）**天然落在同一个内核里**，
  不需要硬凑；
- **纯 Python + 系统设计**，无 GPU 依赖、无虚拟化依赖，任何开发环境都能跑通；
- 研究叙事强：Agent OS 是 2024~2026 的持续热点，且工程化程度仍低，**改进空间大**。

**风险**：

- 上游工程质量与文档完善度参差【待验证：需实际阅读源码与 issue 区】；
- 模块边界可能不清晰，需要较多重构才能做出"规范"的系统；
- 上游近期重心可能已转向 SDK（Cerebrum）而非内核，需确认【待验证】。

**可行性评估**：中等偏上。工作量集中在架构重构与调度/权限模块，均可增量交付。

### 候选 B：Agent 代码执行沙箱运行时

| 项 | 内容 |
| --- | --- |
| 上游（二选一） | `e2b-dev/E2B` —— <https://github.com/e2b-dev/E2B> |
| | `superradcompany/microsandbox` —— <https://github.com/superradcompany/microsandbox> |

**定位**：为 AI 生成的代码与工具调用提供**强隔离**的执行环境。
E2B 的云版本基于 **Firecracker MicroVM**（专用内核 + 自定义内存管理）；
microsandbox 是**自托管**的轻量 microVM 沙箱，且**原生提供 MCP 接口**，
定位为 agent 的"执行底座"。

**本项目可做的增量（安全 × 性能）**：

| 维度 | 可做的工作 |
| --- | --- |
| 安全 | 隔离加固（seccomp / LSM 策略、只读 rootfs、**网络 egress 白名单**）；凭据注入与**防数据外泄**；执行**审计与可回放**；逃逸对抗测试集 |
| 性能 | **冷启动优化**（snapshot/restore、预热池、内存 CoW 去重）；并发执行吞吐；资源配额与超卖策略；文件系统与 I/O 效率 |

**优势**：

- **安全与性能最自然的统一体**：隔离强度 ↑ 通常意味着性能 ↓，
  这个方向的核心研究问题就是"**如何在保持隔离强度的同时降低开销**"——正是本项目要的张力；
- **指标高度可量化**：冷启动毫秒数、吞吐、隔离强度（逃逸测试通过率），
  便于形成有说服力的报告；
- 系统功底锻炼**最强**：KVM、Firecracker、cgroups/namespaces、seccomp、文件系统。

**风险**：

- **强依赖 KVM / 嵌套虚拟化**。若开发环境为容器，Firecracker 无法运行（见 C-6）；
- E2B 的**核心 runtime（MicroVM 部分）开源程度有限**【待验证：需确认哪些组件在仓库内】；
- microsandbox 相对新、社区规模小，长期维护性需评估【待验证】；
- 学习成本最高：需要 Linux 内核与虚拟化基础。

**可行性评估**：**条件性可行**——硬件允许则性价比极高，否则不可行。

### 候选 C：Agent 安全网关 / 策略执行层

| 项 | 内容 |
| --- | --- |
| 上游（可选） | `OpenHands/OpenHands`、`langchain-ai/langgraph`、`SWE-agent/SWE-agent`，或 MCP 生态 |

**定位**：在 **Agent ↔ 模型/工具** 之间插入一层**策略与可观测性中间件**（sidecar/代理形态），
使安全策略与 agent 框架解耦。

**本项目可做的增量（安全 × 性能）**：

| 维度 | 可做的工作 |
| --- | --- |
| 安全 | **工具调用策略引擎**（声明式策略 + default-deny）；**指令/数据分离**与提示注入检测；MCP **工具描述投毒 / rug-pull 检测**；数据流**污点追踪**；人工审批与审计回放 |
| 性能 | 模型调用**缓存与路由**；请求批处理；上下文裁剪；策略判定开销优化（目标：不成为瓶颈） |

**优势**：

- **可行性最高**：纯用户态、可独立部署、不需要特殊硬件；
- 安全研究方向**极其前沿**：MCP 安全、工具投毒、间接提示注入是 **2026 年最活跃的
  安全议题之一**（CSA、Microsoft 等 2026 年均有专门披露）；
- 交付物天然是**独立完整软件**（一个网关/中间件），易测试、易演示、易写报告；
- 以中间件形态存在，**与上游解耦**，不受上游代码库复杂度拖累。

**风险**：

- **性能维度较弱**：安全网关的性能空间主要是"降低自身开销 + 缓存"，
  不如 A/B 那样有系统级性能问题可攻；
- 生态碎片化：MCP 安全领域已有多个小型项目，需**明确定位差异**才能体现增量价值
  【待验证：需梳理竞品并找到空白点】；
- 上游若选 OpenHands 等大型框架，需仔细选择切入点，避免陷入复杂度。

**可行性评估**：高。可增量交付，风险最低。

### 候选 D：LLM 推理引擎的多租户安全与加速

| 项 | 内容 |
| --- | --- |
| 上游 | `vllm-project/vllm`、`sgl-project/sglang` |

**定位**：在推理服务引擎层面做**多租户隔离**与**调度/缓存加速**。

**可做的增量**：多租户 KV Cache 隔离与**侧信道防护**；前缀缓存**跨租户污染防御**；
调度公平性与 SLA 保证；量化 / 投机解码等推理加速。

**优势**：技术最前沿；性能研究空间最大；社区影响力最高。

**风险（决定性）**：

- **必须有 GPU**，且通常需要较新架构的卡；
- 代码库规模巨大（数十万行，含大量 CUDA/C++），**上手周期以月计**；
- 上游 PR 门槛极高（核心路径被少数维护者把关），单人 2~3 个月内做出
  **可被接受的实质改动**概率低；
- 与 C-9（CUDA 经验有限）、C-2（2~3 个月）冲突严重。

**可行性评估**：**低**。作为远期或备选，不建议作为本项目 base。

### 候选 E：Agent 记忆操作系统

| 项 | 内容 |
| --- | --- |
| 上游 | `MemTensor/MemOS` —— <https://github.com/MemTensor/MemOS> |
| | `letta-ai/letta`（原 MemGPT）—— <https://github.com/letta-ai/letta> |

**定位**：把"记忆"当作**可管理的系统资源**。MemOS 提出记忆操作系统概念，
以 **MemCube** 为基本管理单元，统一文本记忆、激活记忆（KV/激活态）与参数记忆的
**存储 / 检索 / 调度 / 演化**，并支持多层记忆结构与生命周期管理。

**本项目可做的增量（安全 × 性能）**：

| 维度 | 可做的工作 |
| --- | --- |
| 安全 | **记忆投毒防御**（写入校验、来源溯源、写入权限、隔离）；跨会话/跨租户**记忆泄漏防护**；记忆的**一致性与可回滚**（污染后如何回退）；记忆检索的**访问控制** |
| 性能 | 记忆**检索加速**（索引结构、缓存、分层存储）；记忆**调度与淘汰策略**；激活记忆与 KV 复用；大规模记忆下的 P95 检索延迟 |

**优势**：

- 叙事极佳：**"记忆子系统"是智能体 OS 的核心组件**，与候选 A 同属"原生智能系统"谱系，
  但生态更年轻、空白更多；
- 安全（**记忆投毒**是 2025~2026 新兴攻击面）与性能（检索/缓存/调度）**都有真实抓手**；
- 纯 Python，无特殊硬件依赖；
- 上游较新且仍在快速演进，**贡献窗口期相对友好**【待验证：需确认活跃度与代码质量】。

**风险**：

- 上游较新、生态变动快，API 可能频繁破坏性变更；
- "记忆 OS"概念宽泛，**任务边界必须仔细收敛**，否则容易范围失控；
- 上游与候选 A 可能存在概念重叠，需确认是否可以组合（见第 7 节）。

**可行性评估**：中等偏上。

## 7. 推荐

### 首选：候选 A —— 以 AIOS 为代表，构建「可安全隔离、可调度加速的智能体运行时」

**推荐理由**：

1. **与研究方向同构**：项目方向是"原生智能系统"，而 Agent OS 正是该方向最直接的实现形态。
   安全（能力模型、隔离、审计）与性能（调度、缓存、并发）**落在同一内核里**，
   不需要为凑主线而硬造需求。
2. **可行性可控**：纯 Python 与系统设计，**无 GPU、无虚拟化依赖**（规避了 C-6 的风险），
   可在任何环境推进；工作量可拆分为多个单迭代可交付的增量。
3. **工程规范化空间最大**：一个"运行时/内核"天然具备清晰的模块边界、接口契约、
   可测试性与可观测性需求——非常适合作为"完整规范软件"的载体。

### 建议的项目定义（用于写入 ADR-0003）

> **方向**：在 AIOS 类 Agent 内核之上，构建一个**安全隔离且调度高效的智能体运行时**。
>
> **安全主线**：引入能力（capability）权限模型与默认拒绝策略，使工具调用受最小权限约束；
> 实现工具执行的隔离与审计；建立对抗性测试集验证越权与逃逸防护。
>
> **性能主线**：改造调度策略并优化上下文/缓存复用，在固定基准下量化
> P95/P99 延迟与吞吐的改进。
>
> **工程主线**：完整生命周期文档（需求 → 设计 → 威胁模型 → 测试 → 发布）、
> CI 门禁、可复现基准。

**预期可量化指标（示例，Phase 1 细化）**：

| 主线 | 指标 |
| --- | --- |
| 安全 | 预定义越权/逃逸场景集的拦截率 100%；所有拒绝均产生审计记录 |
| 性能 | N 并发 agent 下 P95 延迟相对基线下降 ≥ 30%；吞吐提升 ≥ 1.5×（须有基准数据） |
| 工程 | `make check` 全绿；关键路径测试覆盖；完整文档与发布版本 |

### 备选一：候选 E —— 记忆 OS 方向

若候选 A 经源码核验后发现上游质量不可用（C-6 之外的 R-1 风险），
则转向候选 E：**记忆投毒防御 + 记忆检索加速**。
它与 A 同属"原生智能系统"谱系，且同样无硬件依赖。

> **组合可能性**：A 与 E 并非互斥——"记忆管理器"是 Agent OS 的内核组件之一。
> 若时间允许，可将 E 作为 A 的一个子系统深入（**建议不要同时铺开，先做好 A 的主线**）。

### 备选二：候选 C —— Agent 安全网关
