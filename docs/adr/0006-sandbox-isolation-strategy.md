## 1. 背景与问题

本项目（原生智能系统）的核心能力之一是**让模型生成命令并执行**。
模型输出属于**不可信输入**，因此执行前必须存在一个**隔离边界**，
否则一次提示注入就等于把宿主机交给攻击者。

原计划（[devlog 0006](../devlog/0006-2026-09-15-开发环境搭建与技术栈定案.md) §2.3）
把 `bubblewrap` 定为主方案、`firejail` 定为备选方案，二者都是
**基于 Linux namespace 的用户态沙箱**。

在执行环境验证清单时实测发现：**这两个方案在本项目的目标运行环境中都不可用**，
其中 `firejail` 的失败方式尤其危险（见 §2 与 §3 方案 B）。
因此必须在写第一行执行器代码**之前**重新决策，否则会写出一个"看起来有沙箱、
实际没有"的系统——这比明确没有沙箱更糟，因为它会让后续所有安全论证失效。

## 2. 决策驱动因素

| 因素 | 说明 | 类型 |
| --- | --- | --- |
| 不可信输入的处置 | 模型输出、网页/文件内容一律不可信，必须视为数据而非指令 | 硬约束 |
| fail-secure | 隔离失败时必须**拒绝执行**，不允许"降级为直接执行" | 硬约束 |
| 平台能力 | CNB 容器内 `Seccomp=2`、`CapEff` 不含 `CAP_SYS_ADMIN`，`unshare(CLONE_NEWUSER)` 与 `unshare(CLONE_NEWNS)` 均返回 `EPERM` | 硬约束 |
| 内核版本 | 5.4.241（TLinux4）→ **Landlock（需 ≥5.13）不可用** | 硬约束 |
| 可用设施 | CNB 已提供 Docker（`services: [docker]`），实测 daemon 可用 | 偏好 |
| 工期 | 单人开发，Phase 0 需尽快冻结工程基线 | 硬约束 |
| 端侧目标 | 产品最终形态可能运行于 Termux/Android，届时隔离手段又不同 | 约束（后续决策） |
| 优先级 | 安全 > 可维护性 > 性能；性能仅要求"交互可接受" | 偏好 |

## 3. 候选方案

### 方案 A：bubblewrap（原主方案）

- 简述：非特权 user namespace 沙箱，Flatpak 同款，参数化程度高、无守护进程。
- 优点：轻量、启动快（毫秒级）、无 setuid、可按需 bind-mount 白名单。
- 缺点：**本环境完全不可用**——`bwrap: No permissions to create new namespace`。
  根因：容器内 `unshare` 被 seccomp 拦截且 `CapBnd` 中无 `CAP_SYS_ADMIN`，
  该限制**无法从容器内部解除**。bwrap 二进制本身也非 setuid（无回退路径）。

### 方案 B：firejail（原备选方案）

- 简述：setuid 沙箱，自带 profile 体系。
- 优点：安装即用、profile 生态成熟。
- 缺点：**不能用，而且是最危险的一种失败方式**。
  实测它在检测到"已处于沙箱中"后打印一行警告，然后
  **不加任何隔离地直接执行命令**，退出码仍为 0：

  ```text
  Warning: an existing sandbox was detected. /bin/sh will run without any additional sandboxing features
  ```

  对抗性验证：firejail 内 `user/mnt/pid/net/ipc/uts/cgroup` 的 namespace inode
  与宿主**逐项相同**，`--net=none` 下仍能看到 `eth0`。
  即"输出 `sandbox-ok`"是**假阳性**：它没失败，但也没隔离。

### 方案 C：以容器为隔离边界（Docker）

- 简述：把不可信命令投进一个**一次性容器**执行：
  `--network none --read-only --tmpfs /tmp --cap-drop=ALL
  --security-opt=no-new-privileges --pids-limit --memory --user 非 root`，
  只把受限的工作目录作为 volume 挂入，用完即删。
- 优点：隔离边界由**容器运行时**（运行在宿主侧，不受本容器 seccomp 约束）建立，
  实测所有加固参数**逐项生效**；镜像可固定 digest，供应链可审计；
  与 CNB 已有的 `services: [docker]` 契合，无需新增依赖；端侧虽不可用，
  但"命令执行器"本身是接口，将来换实现不影响上层。
- 缺点：每次执行有容器启动开销；依赖 Docker daemon（平台设施，非本项目可控）；
  需要管理精简基础镜像；volume 是唯一双向数据通道，权限设计必须显式。

### 方案 D：nsjail / 其他 namespace 型沙箱

- 简述：能力更强的 namespace 沙箱（本机已装其构建依赖）。
- 优点：支持 cgroup、seccomp 策略更细。
- 缺点：**与方案 A/B 同因不可用**（仍需创建 namespace）。
  构建它只会得到一个同样跑不起来的二进制，属于无效投入。

### 方案 E：无强隔离的降级链（子进程 + 限制 + 白名单 + 人工确认）

- 简述：`shell=False` 子进程 + `resource` 限制（CPU/内存/文件数/时间）+
  路径白名单 + 危险操作一律人工确认。
- 优点：无外部依赖、端侧（Termux）也能用；实现简单、行为可预测。
- 缺点：**不构成隔离**，只降低事故概率，无法抵御主动逃逸；
  因此安全等级明显低于方案 C，不能作为唯一防线。

## 4. 权衡对比

| 评估维度 | 权重 | A bwrap | B firejail | C Docker 容器 | E 降级链 |
| --- | --- | --- | --- | --- | --- |
| 本环境可用性 | 高 | ❌ 不可用 | ❌ 不可用（假阳性） | ✅ 实测可用 | ✅ 可用 |
| 隔离强度 | 高 | 高（若可用） | 高（若可用） | 高（内核级边界） | 低 |
| fail-secure 可达性 | 高 | ✅ | ❌ **静默放行** | ✅ 启动失败即拒绝 | ⚠️ 需自行保证 |
| 启动开销 | 中 | 毫秒 | 毫秒 | 百毫秒~秒级 | 毫秒 |
| 端侧可移植性 | 中 | ⚠️ 取决于平台 | ⚠️ | ❌ 端侧无 Docker | ✅ |
| 新增依赖/设施 | 中 | 已有 | 已有 | 已有（平台提供） | 无 |
| 实现与维护成本 | 中 | 低 | 中（profile） | 中 | 低 |

## 5. 决策

**决定采用：方案 C（以容器为隔离边界）作为主方案，方案 E 作为容器不可用时的显式降级，
方案 A/B/D 不再作为候选。**

理由：

1. **只有 C 在本项目的目标环境中被实测证明可用**，且加固参数逐项生效；
   A/B/D 的失败源于平台硬约束，不可绕开。
2. **C 天然满足 fail-secure**：容器创建失败即拒绝执行，
   不存在 B 那种"警告后放行"的中间态。
3. **C 的隔离强度足以支撑后续安全论证**（威胁模型可以引用一条真实的边界），
   而 E 只能降低概率，无法作为主线防线。

## 6. 后果

### 正面

- 获得一条**可被威胁模型引用**的真实隔离边界，安全论述不再悬空。
- 执行器接口与"用容器实现"解耦后，端侧换实现不影响上层调用方。
- 提前暴露并杀掉了"假阳性沙箱"这一隐蔽风险。

### 负面（必须填写）

- **每次执行支付容器启动成本**；在高频工具调用场景下需要评估是否引入常驻容器池
  （这会削弱"一次性"带来的隔离优势，届时必须重新权衡并记录）。
- **依赖平台的 Docker 服务**：若目标部署环境无 Docker，主线隔离能力直接失效，
  只能退到方案 E，安全等级下降一档。
- **端侧（Termux/Android）无法复用该方案**，需要另行决策，产品叙事上
  必须把"端侧隔离能力"与"开发/演示环境隔离能力"分开陈述，不能混为一谈。
- 新增了**容器镜像的供应链面**：基础镜像、拉取来源与 digest 都必须锁定并留痕。
- 工作量增加：需要写容器生命周期管理、volume 权限设计、超时与清理逻辑。

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 容器逃逸（内核漏洞） | 高 | 基础镜像最小化、`--cap-drop=ALL`、`no-new-privileges`、非 root 用户、及时更新运行时 |
| 忘记加隔离参数导致"裸跑" | 高 | 把所有参数封装进**唯一**的启动函数，禁止调用点自行拼装；并加对抗性测试断言参数存在 |
| 平台 Docker 不可用 | 中 | 启动时探测；不可用则**显式降级并告知用户**，绝不静默以无隔离方式执行 |
| 基础镜像被投毒 | 中 | 固定 digest、记录来源与摘要、必要时构建自有最小镜像 |
| volume 挂载过大导致越权访问 | 高 | 只挂载单次任务需要的子目录，只读优先，路径经规范化与白名单校验 |
| 常驻容器为省开销而复用 | 中 | 若引入容器池，必须新增 ADR 记录隔离降级与其补偿措施 |

## 7. 验证方式

- **对抗性用例（必须全过）**：容器内不得写入根文件系统；不得访问网络；
  不得获得任何 capability；不得 fork 炸弹；不得读写未挂载的宿主路径。
- **fail-secure 用例**：故意让容器创建失败（如错误的镜像名），
  执行器必须**拒绝执行并返回失败**，且审计日志中留下记录。
- **可观察判据**：上述用例成为 `tests/security/` 中的常驻测试，
  在 `make test-security` 中执行；任何一次隔离参数退化都会被测试拦住。
