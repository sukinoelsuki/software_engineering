## 1. 背景与问题

项目的开发环境是 **CNB 云原生开发容器**，其特性带来三个具体焦虑：

1. **无记忆**：环境重启后容器内的一切（含 AI 代理的会话上下文）都不保留；
2. **成果风险**：极端测试（资源耗尽、递归删除、填满磁盘）可能拖垮开发容器，
   进而丢失**尚未落盘**的成果；
3. **反馈成本**：为了安全而"另拉一个容器测试"，两个容器互相看不见，
   反馈链路过长——而单人开发更需要"一边开发一边测"。

需要决策的是：

> 开发与测试**要不要隔离**？如果要，隔离的**边界**划在哪里？
> 以及如何在允许"把安全推向极端"的前提下，保证成果不丢、工作不中断？

---

## 2. 关键判断：要隔离的不是代码，而是**执行场所**

这是本决策的支点，先说结论再说理由：

| 隔离对象 | 是否隔离 | 理由 |
| --- | --- | --- |
| **源码与成果** | ❌ **不隔离** | 单人开发的测试对象就是这份代码；隔离源码只会带来同步成本与反馈延迟 |
| **执行场所** | ✅ **隔离** | 破坏性测试可能杀死进程、耗尽内存、删文件；这些必须在一次性的地方发生 |
| **依赖与工具链** | ✅ **隔离（按需）** | 需要"干净环境"回归时，用与 CI 同源的容器 |

**并且**：隔离执行场所**不必**以牺牲反馈为代价——容器可以**共享工作区**。
这一点此前被默认忽略了（原假设是"两个容器是隔开的"），实测证明不成立。

---

## 3. 实测依据（2026-09-15）

| 能力 | 探针 | 结果 |
| --- | --- | --- |
| docker 可用 | `docker version` | ✅ Client/Server 29.6.2（`services: [docker]`） |
| **工作区可共享** | `-v /workspace:/work:ro` 后读 `README.md` | ✅ **可读**，说明与开发容器共享同一份文件 |
| **只读保护生效** | 同上容器内 `echo x > /work/probe.txt` | ✅ **`Read-only file system`**——破坏性测试**物理上无法改源码** |
| 网络隔离 | `--network=none` + `wget` | ✅ 被阻止 |
| 一次性 | `--rm` | ✅ 退出即销毁，不留状态 |
| 资源限制 | `--memory` / `--pids-limit` | ❌ **静默失效**（cgroup 无委派，见 ADR-0007） |
| 资源限制（替代） | `setrlimit`（`--ulimit` / 进程内） | ✅ 有效 |

**两条直接推论**：

1. **只读挂载工作区** = 用内核（mount 命名空间）而不是靠"自觉"来保护成果。
   这比任何流程约束都可靠。
2. **资源维度必须靠 setrlimit**，不能靠 `--memory`；因此
   "故意耗尽整机资源"类测试在本环境**仍可能伤到开发容器**，必须区别对待（见 §4 的 T2/T3 分界）。

---

## 4. 决策

### 4.1 采用四层测试环境（T0 ~ T3），按"影响范围"而非"测试类型"划分

| 层级 | 影响范围 | 执行场所 | 资源/网络 | 典型用例 |
| --- | --- | --- | --- | --- |
| **T0** | 仅进程内 | 开发容器内 `uv run pytest` | 无限制 | 纯逻辑单测、格式/类型检查 |
| **T1** | 子进程 + 临时文件 | 开发容器内的**受限子进程**（L1 档本身） | rlimit + 路径白名单 | 工具调用权限、路径穿越、rlimit 生效性 |
| **T2** | **可能影响容器自身** | **一次性容器** `docker run --rm`，工作区 `:ro` + `--tmpfs` 暂存 + `--network=none` | rlimit（**不用** `--memory/--pids`） | 越权出站、越界写、危险命令、超限分配（有界） |
| **T3** | 宿主 / 需要干净环境 | **独立容器**（CI 或本地 CI 预演）/ 本地 VM | 由载体决定 | "耗尽整机资源"的极端用例、`bwrap` 等命名空间特性验证 |

规则：

- **默认落地层级应尽量低**：能在 T0 说清的事不要放到 T2。
- **T2 是不可省略的**：安全需求（`REQ-SEC-05`/`REQ-SEC-09`）的价值在于"越界真的被挡住"，
  必须在真实隔离载体上验证，而不是在模拟里验证。
- **T3 才需要"另拉容器"**，且只在两类情况下使用：① 需要干净环境；
  ② 需要命名空间特性。日常不进入 T3。

### 4.2 三条成果保护硬规则

| 编号 | 规则 | 理由 |
| --- | --- | --- |
| **P-1** | **破坏性测试（T2 及以上）之前，工作树必须干净**（已提交或已 `stash`） | 未提交的改动是唯一无法从 git 恢复的东西。容器可以死，改动不能丢 |
| **P-2** | **测试产出的原始数据必须写入仓库内**（`docs/research/reports/`）**才算完成**，不得只留在容器内 | 容器无记忆；只存在容器里的数据等同于不存在 |
| **P-3** | **每次会话结束前把状态写入 devlog** | AI 代理上下文不持久；仓库是唯一跨会话记忆。这也是 devlog 存在的首要目的 |

> P-1 与 P-2 是 [`definition-of-done.md`](../engineering/definition-of-done.md) 的补充条款。
> **不加自动门禁**（不在 pre-commit 里强制检查 T2 前置条件）——理由见 §6 风险表：
> 该约束是**执行者纪律**，误报会诱使绕过，反而降低整体安全性。

### 4.3 明确不做的

| 项 | 不做的理由 |
| --- | --- |
| 为每次测试新建独立**开发**容器 | 反馈延迟与同步成本不可接受；单人开发不需要"环境即代码"的隔离 |
| 为安全而把源码拆到多个容器 | 测试对象就是这份代码，隔离源码等于自我阻断 |
| 依赖 `--memory` / `--pids-limit` 做资源防护 | **实测静默失效**（ADR-0007）；必须用 setrlimit |
| 把 T2/T3 纳入每次提交的默认路径 | 会显著拖慢日常循环；破坏性测试应是**显式、按需**的 |

## 5. 后果

### 正面

- **成果风险被结构性消除**：T2 的只读挂载使"测试毁掉源码"在内核层不可能发生。
- **反馈链没有变长**：执行场所隔离，但工作区共享——结果直接落在同一个仓库里，
  不存在"两个容器互相看不见"的问题。
- 与 CI 同源：CI 已经在容器里跑 `make check`，本地 T3 可用同一镜像复现，
  不需要推送即可预演（正是"测试即 CI"的思路）。
- 允许**把安全推向极端**：越极端的用例越应该放进 `--rm` 的一次性容器，
  成本极低（退出即销毁），而收益是真实的对抗性验证。

### 负面（必须填写）

- **资源类极端测试仍可能伤到开发容器**：cgroup 限制失效意味着
  "把内存吃光"类测试能拖垮整个开发环境。只能靠 setrlimit + 用例规模自律来规避，
  **这是本方案最薄弱的环节**（缓解见下）。
- T2/T3 需要**人工切换心智**（"这个测试该放哪层"），存在判断成本与误判可能。
- 三层载体（开发容器 / 一次性容器 / 独立容器）意味着**四套环境行为可能漂移**，
  需要额外的维护纪律（例如探针必须每层都跑）。
- docker 依赖平台提供；平台若变更 `services` 配置，T2/T3 需重新规划。

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 资源耗尽测试拖垮开发容器 | **高** | ① T2 一律用 setrlimit 设上界；② 把"无上界耗尽"类用例**显式归入 T3**；③ 关键成果遵循 P-1 先提交 |
| 误判层级（把 T3 内容放 T2 跑） | 中 | 在 `test-environments.md` 给出**判定清单**（问三个问题即可归类）；CI 中只跑 T0/T1 |
| 执行者为省事绕过 T2 直接在生产环境跑危险用例 | 中 | P-1 使其至少可恢复；不设自动强制，避免"绕过规则"成为常态 |
| 四套环境行为漂移导致结论不可比 | 中 | 探针矩阵（ADR-0007）在每层都运行并记录；测试报告必须写明**在哪一层**取得 |
| 会话中断导致上下文丢失 | 中 | P-3；且 devlog 索引本身就是"恢复入口" |

---

## 6. 验证方式

1. **成果保护可验证**：在 T2 容器内尝试 `rm -rf /work/*` 与写 `README.md`，
   必须失败；同时确认开发容器的文件**逐字未变**（`git status` 干净 + 文件哈希一致）。
2. **反馈链路可验证**：T2 的测试日志与结果文件能被开发容器直接读取
   （写入可写暂存区后再取回，或直接输出到 stdout）。
3. **层级判定可验证**：给定若干真实用例，两名执行者独立归类结果一致
   （单人项目下即"隔一周后自己重新归类仍一致"）。
4. **M2 里程碑**：`REQ-SEC-05` / `REQ-SEC-09` 的对抗性用例在 T2 载体上可复现通过，
   且测试报告明确标注层级与载体。
