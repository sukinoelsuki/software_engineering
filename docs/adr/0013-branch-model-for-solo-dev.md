# 0013. 分支模型：develop 改为工作主干，并用分支卫生自检兜底

## 1. 背景与问题

2026-09-16 重建开发环境时，暴露了一次协作事故：

1. 分支 `chore/env-verification`（PR #3）上产生了一批工作，**没有及时合入 develop**；
2. 项目所有者在 develop 上**重做并扩展**了同一批工作，经 PR #2 合入（`c849953`）；
3. 之后在平台网页端对 PR #3 执行"合并 develop 并解决冲突"（`7741c75`），
   6 个冲突文件一律取 develop 一侧，结果是**丢了三类内容**：
   llama.cpp 版本固定（V-6）、验证清单第 6/7 步、`docs/learning/0002` 与 `0003` 两篇笔记
   （因目录重命名 `learning/` → `notes/` 被静默删除）。

根因不是"忘了合"，而是三条机制叠加：

| # | 机制 | 后果 |
| --- | --- | --- |
| 1 | 云开发环境每次**从 develop 拉起**，重启即清空上下文 | 留在未合入分支上的工作，在下一次会话里**等于不存在** |
| 2 | 分支保护要求所有工作走分支 | 每次会话都可能留下一个未合入的分支，且无人察觉 |
| 3 | 没有任何机制在会话结束时检查"是否有未合入的工作" | 遗忘不会被发现，只会累积成冲突 |

---

## 2. 决策驱动因素

- **单人开发**，不存在并行工作流 ⇒ 分支"隔离并行工作"的核心价值≈0；
- 云环境固定从 develop 拉起 ⇒ develop **事实上已经是工作主干**，保护它只是让流程与事实脱节；
- 课程与项目要求"变更可追溯" ⇒ 不能取消提交规范与 `make check`，也不能放弃 PR 这类评审单元；
- **不引入新依赖、新服务、新凭据**（见 `CODEBUDDY.md` 与 `SECURITY.md`）；
- 失败模式必须"**被发现**"，而不是依赖记性——这一点由安全基线的 fail-secure 原则直接推出。

---

## 3. 候选方案

| 方案 | 内容 |
| --- | --- |
| A | 保持 `main` + `develop` 双保护，在开发环境里**提醒**合并（甚至自动合并 develop → 工作分支） |
| B | `develop` **取消保护**、直接开发；`main` 仍保护 |
| C | 保持双保护，新增**分支卫生自检**（列出未合入 develop 的分支与开放 PR），挂到环境启动与 CI |
| D | **B + C**（本 ADR 采用） |

---

## 4. 权衡对比

| 维度 | A 提醒合并 | B 去保护 | C 自检 | **D = B + C** |
| --- | --- | --- | --- | --- |
| 冲突风险 | 中（分支仍会长期存在） | **低** | 中 | **低** |
| 遗忘风险 | 中（依赖"有人看到提醒"） | **无**（不存在未合入状态） | 低（机器发现） | **无 + 兜底** |
| 可追溯性 | 高（全部走 PR） | 中（部分改为直推） | 高 | 中（重要改动仍走 PR） |
| 与事实一致 | 否（develop 已是主干却受保护） | **是** | 否 | **是** |
| 改造成本 | 低 | 中 | 中 | 中 |
| 关键缺陷 | 提醒随环境重启消失 | 单次坏提交直达集成线 | 保护带来的分叉问题依旧 | 同 B，且需维护脚本 |

> A 的致命弱点：**提醒机制依赖"有人在环境里看到它"，而环境正是重启即清空的**。

---

## 5. 决策

1. **`main` 保持保护**（发布线 + SemVer 标签），不做改动；
2. **`develop` 取消"禁止直推"，定位为工作主干**。仍受以下约束（与分支保护无关）：
   Conventional Commits、pre-commit 全量钩子、`make check`、`ci` 流水线；
3. **短期分支只用于两类场景**：`exp/*` 隔离实验、以及需要评审的大改动；
   且**必须在同一次会话内合回 develop**；
4. 新增 `scripts/check-branch-hygiene.sh` 与 `make branch-status`，挂载到
   **开发环境启动**与 **CI**；定位是**报告**，默认不阻断构建与流水线；
5. **合并方式**：文档（devlog / CHANGELOG）中引用了具体提交哈希的分支一律用
   **merge commit**（squash 会让这些引用指向不存在的对象）；
   单个提交、无引用的分支可用 squash；
6. **会话收尾义务**：Agent 在结束工作前必须确认"本次产出已落在 develop"，
   若有未合入分支，登记到最新一篇 devlog 的 §7。

---

## 6. 后果

**正面**

- 消除"未合入分支"这一整类事故：工作直接在 develop 上，不存在"下次会话看不见"的状态；
- 流程与实际工作方式一致，减少"保护形同虚设"的认知负担；
- 自检脚本同时覆盖**仍会存在的** `exp/*` 与远端遗留分支。

**负面（必须承认）**

| 负面 | 缓解 |
| --- | --- |
| develop 上出现坏提交会直达集成线 | pre-commit + `make check` + CI 三道门禁不依赖分支保护；单提交粒度可精确回滚 |
| PR 不再是唯一路径，变更记录密度下降 | 重要/跨模块改动仍走 PR；每次提交必写 devlog（已有强制义务） |
| 新增脚本需要维护 | 纯只读、零依赖、可单独摘除；离线降级为本地视图 |
| 自检依赖 `git ls-remote`（需要网络） | 网络不可用时输出"**未知**"而非"干净"；`--strict` 下未知按失败处理（fail-secure） |

---

## 7. 验证方式

- `make branch-status` 在本地与 CI 都能列出未合入 develop 的分支与开放 PR；
- 在 develop 上直推一条 `chore` 提交，pre-commit 放行（证明去保护生效）；
- 人为留一条未合入分支 → 环境启动与 CI 两处都能看到它；
- ADR、[`git-workflow.md`](../engineering/git-workflow.md)、`CODEBUDDY.md` / `AGENTS.md`
  三处表述一致，无矛盾；
- **30 天后回顾**：是否再次出现"分支遗留"。若再次出现，说明自检挂载点选错，应改为
  更前置的位置（如 push 时的服务端钩子）而非回到分支保护。

---

## 8. 回退

- 恢复保护：`.pre-commit-config.yaml` 的 `no-commit-to-branch` 加回 `--branch=develop`；
- 摘除自检：从 `.cnb.yml` 移除对应 stage（`make branch-status` 与脚本可保留，无副作用）。

两者互相独立，可分别回退。

### 9.1 增补：两条长驻基准分支（2026-09-18）

- **依据**：[ADR-0014 §2.1](0014-benchmark-automation.md)（基准自动化：数据分支与测量纪律）。
- **缺口**：[ADR-0014](0014-benchmark-automation.md) §2.1 建立了 `bench/nightly` 与 `bench/data`
  两条**长驻分支**，并声明其为"对 ADR-0013『短期分支、当次会话合回』的**显式例外**"；
  但**本文 §5.3 与 [`engineering/git-workflow.md`](../engineering/git-workflow.md) §2 的分支表
  都未包含这两条分支**。后果是：读者（与代理）按本文正文执行，会把它们误判为
  "**应当合回 develop / 应当删除**"——而它们**恰恰相反**。
- **来源**：[`doc-consistency-report.md`](../engineering/doc-consistency-report.md) **A-14**、
  [`devlog 0013`](../devlog/0013-2026-09-18-一致性核查与地基修复.md) §7 优先级 A 末项。

本节把这两条分支及其例外条件登记进本文的分支模型，口径与 ADR-0014 §2.1 完全一致。

| 分支 | 来源 | 合入 | 生命周期 | 谁写 | 依据 |
| --- | --- | --- | --- | --- | --- |
| `bench/nightly` | `develop`（初次拉出） | **不合入 `develop`** | **长驻** | 人（正常提交，仍受 `make check` 约束） | ADR-0014 §2.1 |
| `bench/data` | `bench/nightly`（由 CI 推入） | **不合入 `develop`** | **长驻** | **只有 CI 机器人** | ADR-0014 §2.1 |

### 9.2 例外条件（不得放宽）

1. **不得合入 `develop`**。`bench/data` 的内容是机器产出（JSON、报告、日志、模型产物），
   合入会污染主线历史；`bench/nightly` 是协议锚点，合入会让"协议会不会被顺手改"重新变成未决问题。
2. **不得删除**。删除等于丢掉可比时间序列与协议锚点（`bench-v2` 的跨夜序列是本项目
   目前唯一的时间序列数据，见 ADR-0014 §2.4）。
3. **`bench/data` 只由 CI 机器人写入**：固定 `HEAD:bench/data` 的**快进推送**，
   **禁止 force**；来源分支白名单为 `bench/nightly`。人手**不得**直接向 `bench/data` 提交。
4. **`bench/nightly` 不回写代码到 `develop`**。其上的改动若要进入产品线，
   须以普通提交（`chore(bench):` / `test(bench):`）另行落入 `develop`——即
   "基准代码"与"产品代码"是两份载体，不是同一条链路。
5. **例外不外溢**：除上述两条分支外，本文 §5.3「短期分支必须在同一次会话内合回 `develop`」
   **继续完全有效**。新增任何长驻分支都必须先新增 ADR 说明理由，不得以"ADR-0014 已有先例"为由自行扩张。

### 9.3 与本文 §7 验证方式的关系

§7 要求"ADR、`git-workflow.md`、`CODEBUDDY.md` / `AGENTS.md` 三处表述一致，无矛盾"。
本次增补只涉及前两处：第三条（常驻摘要）按项目既有的"**常驻摘要只写必须始终生效的内容**"模式，
**只列短期功能分支**（`exp/*`、`release/*`、`hotfix/*` 同样未列入），因此**不构成本节引入的矛盾**。
若后续把"跨文件一致性"做成机器检查（见 devlog 0013 §7 优先级 D），
该检查的口径应包含本节的两条分支。
