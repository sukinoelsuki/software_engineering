# 0007. 建立学习笔记目录（docs/learning）

- **状态**：已接受
- **日期**：2026-09-15
- **决策者**：Le0n3rd
- **相关**：[CODEBUDDY.md](../../CODEBUDDY.md)、
  [`docs/learning/README.md`](../learning/README.md)、
  项目约定「新目录的建立必须先在 ADR 中说明理由」

---

## 1. 背景与问题

本项目由**初次接触该方向**的开发者推进（端侧智能系统 / 系统安全 / 推理加速）。
推进过程中会产生大量"当时理解了、过两周就忘了为什么"的概念与讨论——
例如"为什么容器里不能再套容器""为什么厂商的评测分数不能横向比较"。

现有文档体系**都不适合承载这类内容**：

| 现有目录 | 为什么不合适 |
| --- | --- |
| `docs/adr/` | 只记录**已定决策**，且要求"只增不改"；学习过程充满试探与修正，塞进去会污染决策记录 |
| `docs/devlog/` | 记录**发生了什么**，默认读者懂背景，不解释概念 |
| `docs/research/` | 记录**调研结论**，面向"选型依据"，不是教学材料 |
| `docs/engineering/` | 记录**流程规范**，与知识理解无关 |

结果是：知识只以"结论"的形式散落在 ADR 与 devlog 里，**缺少"为什么"这一层**，
导致复习成本高、难以举一反三。

**问题陈述**：需要一个**不承担交付责任、只承担"讲明白"责任**的文档空间。

---

## 2. 决策驱动因素

| 因素 | 说明 | 类型 |
| --- | --- | --- |
| 学习者是初学者 | 需要"直觉 → 原理 → 实例"的递进，而非结论堆砌 | 硬约束 |
| 课程考核过程 | 学习痕迹本身是过程证据，有独立价值 | 硬约束 |
| 避免事实分叉 | 同一结论若在多处各写一遍，必然出现不一致 | 硬约束 |
| 变更最小化 | 优先复用既有目录结构 | 偏好 |
| 可检索性 | 复习时应能按主题快速定位 | 偏好 |

---

## 3. 候选方案

### 方案 A：新建 `docs/learning/`

- 简述：独立目录，按主题分篇，单篇有固定模板（直觉 → 原理 → 项目实例 → 术语 → 误解 → 自测）。
- 优点：与既有文档职责边界清晰；可独立演进；模板保证"面向初学者"的质量下限。
- 缺点：**新增一个目录**（按项目约定必须写本 ADR）；存在与 devlog 内容重复的风险，需要纪律约束。

### 方案 B：并入 `docs/devlog/`，作为特殊子系列

- 简述：在 devlog 中按 `L-<slug>.md` 命名开学习篇章。
- 优点：不新增目录，改动最小。
- 缺点：devlog 是**按时间演进**的过程记录，学习笔记是**按主题**的知识记录，
  两者的检索方式与生命周期完全不同；混在一起会让 devlog 的分篇规则（≤300 行、按议题）
  与学习笔记（按概念、可长期修订）互相冲突。

### 方案 C：并入 `docs/research/`

- 简述：把学习内容写进调研笔记。
- 优点：不新增目录，且调研本身就是学习。
- 缺点：research 的定位是"**得出选型结论**"，读者假设"半懂"；
  把基础概念解释混进去会冲淡其结论密度，两头不讨好。

### 方案 D：不建文档，只在对话中讲解

- 简述：需要时随时问，不落盘。
- 优点：零成本。
- 缺点：**违背项目"过程可追溯"的原则**；知识不沉淀，复习成本永远居高不下。

## 4. 权衡对比

| 评估维度 | 权重 | A 独立目录 | B 并入 devlog | C 并入 research | D 不落盘 |
| --- | --- | --- | --- | --- | --- |
| 职责边界清晰度 | 高 | ✅ 高 | ❌ 冲突 | ⚠️ 模糊 | — |
| 面向初学者的适配度 | 高 | ✅ 高（模板保证） | ⚠️ 中 | ❌ 低 | ⚠️ 一次性 |
| 与既有规则冲突 | 高 | ⚠️ 需本 ADR | ✅ 无 | ✅ 无 | ✅ 无 |
| 复习检索效率 | 中 | ✅ 按主题 | ❌ 按时间 | ⚠️ 混杂 | ❌ 无 |
| 长期维护成本 | 中 | 中 | 高（两套规则打架） | 中 | 低 |

## 5. 决策

**决定采用：方案 A（新建 `docs/learning/`）**

理由：

1. **职责边界是这类文档的生命线**：学习笔记回答"为什么/是什么"，与 ADR（决策）、
   devlog（过程）、research（结论）互不替代；混入任一目录都会让两者的读者假设失效。
2. **模板能兜住质量下限**：初学者最大的困难不是缺资料，而是**不知道一个知识该被理解到什么程度**。
   固定模板（直觉 → 原理 → **本项目真实实例** → 术语 → 误解 → 自测）直接解决这个问题。
3. **成本可控**：仅新增一个目录与一份 README，不引入任何依赖、工具或流程变更；
   内容按需增长，不设交付期限。

## 6. 后果

### 正面

- 知识以"可复习"的形式沉淀，降低重复理解同一概念的成本。
- 学习痕迹成为课程过程考核的直接证据。
- 通过"记录误解"这一节，把踩过的坑固化为长期记忆锚点。

### 负面（必须填写）

- **多了一处需要维护的文档**：小项目最容易死于文档数量超过维护能力。
  缓解：不设强制产出节奏，**只在有真实值得记的内容时写**，允许长期只有少数几篇。
- **存在与 devlog 重复的风险**：同一事件会被两个视角各写一次。
  缓解：明确分工——devlog 写"发生了什么"，learning 写"从中该学到什么"，
  且 learning **不产生新结论**，涉及决策必须回指 ADR/devlog。
- **教学性写作更耗时**：写"讲明白"比写"记录事实"慢得多。
  缓解：单篇控制在 300 行内，写不动就拆篇，宁可短而通透。

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 内容与事实分叉（笔记里写了自己臆想的原理） | 高 | 事实必须有出处；二手来源标注；不确定写 **【待验证】** |
| 笔记长期不更新而信息过期 | 中 | 涉及外部事实的段落注明"访问日期"与版本 |
| 目录空置（写了 README 就没了） | 低 | 已确立触发时机：每次出现值得记的概念/讨论/踩坑即追加 |

---

## 7. 验证方式

- **可观察判据**：在本 ADR 之后的**两个开发阶段**内，
  `docs/learning/` 中至少存在 3 篇主题笔记，且每篇都能独立读懂（不依赖 devlog 上下文）。
- **反例判据**：若某一篇笔记的内容在 ADR/devlog 中已完整表达且无需面向初学者解释，
  说明该篇不该存在，应合并或删除。
- 若两个阶段后仍未新增任何笔记，说明该目录的假设不成立，应重新评估其存留。
