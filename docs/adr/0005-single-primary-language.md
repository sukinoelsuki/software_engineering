# 0005. 技术栈定案：Python 单一主语言

- **状态**：已接受

## 1. 背景与问题

项目确定方向为"低资源受限环境下的能力感知智能体运行时"（见 [ADR-0003](0003-select-base-project.md)），
需要选定**实现语言**。

项目所有者提出疑问：既然参考对象是 [Ollama](https://github.com/ollama/ollama)（**Go**）与
CodeBuddy / Cursor（**TypeScript / Electron**），那么本项目是否需要 **Go** 或 **TypeScript**？

ADR-0004 已确定 Python 作为"工程基线"，但那是在方向尚未冻结时做出的**可逆决策**。
现在方向已定，需要**正式确认或推翻**它，否则会持续产生"要不要换语言"的摇摆。

---

## 2. 决策驱动因素

| 编号 | 因素 | 说明 | 类型 |
| --- | --- | --- | --- |
| D-1 | **差异化能力所在的生态** | 本项目的自研增量是上下文引擎、护栏、评估、检索——这些库几乎全在 Python 生态 | 硬约束 |
| D-2 | 单人 + 2~3 个月 | 项目所有者的首要目标是"**能完成**"；引入第二门语言会显著消耗时间 | 硬约束 |
| D-3 | 已有工具链基线 | `pyproject.toml` / `Makefile` / CI / pre-commit 均已按 Python 配置完毕 | 硬约束 |
| D-4 | 现有开源参照 | llama.cpp（C/C++，只通过 HTTP 调用）、MCP 官方 server、promptfoo（Node）、LLM Guard / garak（Python） | 参考 |
| D-5 | 分发形态（未来） | 若将来要装到老人手机上，单二进制分发更友好——Go 的优势所在 | 偏好（非本期） |
| D-6 | 性能关切 | Python 编排性能不如 Go/Rust——但本项目的瓶颈是**推理**（llama.cpp），不是编排逻辑 | 参考 |

---

## 3. 候选方案

### 方案 A：Python 单一主语言

- 优点：生态最契合（D-1）；零切换成本（D-3）；开发速度最快，最利于"能完成"（D-2）。
- 缺点：分发需额外打包工作；移动端原生支持弱；理论性能一般。

### 方案 B：Go 作为主语言（对标 Ollama）

- 优点：**单二进制分发**、跨平台交叉编译、启动快、并发模型适合服务端调度。
- 缺点：**放弃整个 Python AI 生态**（D-1）——护栏、评估、红队、检索、向量库绑定
  大多只有 Python 版或 Python 版最成熟。要用 Go 就得自己重写或用 HTTP 调 Python 服务，
  **等于同时维护两门语言**。

### 方案 C：TypeScript 作为主语言（对标 CodeBuddy / Cursor）

- 优点：若要做 VS Code 插件或 Web 前端可一体化；MCP 官方 TS SDK 成熟。
- 缺点：同样脱离 Python AI 生态；且本项目的形态是**终端 + 本地运行时**，
  不是 IDE 插件（IDE 插件已在范围边界中列为 Won't）。为 TS 而 TS 属于本末倒置。

### 方案 D：Python 为主 + 性能热点用 Rust/C++ 扩展

- 优点：兼顾开发速度与性能上限。
- 缺点：本期**没有识别出需要原生扩展的热点**——真正的性能瓶颈是模型推理，
  而它已经由 llama.cpp（C++）承担。提前引入属过度设计。

## 4. 权衡对比

| 评估维度 | 权重 | A 全 Python | B Go | C TypeScript | D Python+原生扩展 |
| --- | --- | --- | --- | --- | --- |
| 与差异化能力的生态契合度（D-1） | 高 | **5** | 2 | 2 | 5 |
| 单人可完成性（D-2） | 高 | **5** | 3 | 3.5 | 3.5 |
| 复用已有工具链（D-3） | 中 | **5** | 1 | 2 | 5 |
| 分发友好度（D-5，非本期） | 低 | 2 | **5** | 3 | 2 |
| 性能上限（D-6） | 低 | 3 | 4 | 3.5 | **5** |
| **加权倾向** | | **首选** | 备选 | 不采纳 | 暂不采纳 |

## 5. 决策

**决定采用方案 A：Python 作为唯一主语言。**

理由：

1. **差异化能力的生态绑定**：本项目的自研增量集中在上下文工程、安全护栏与评估，
   这些正是 Python 生态最强的领域；换语言等于放弃我们唯一的技术优势。
2. **与"能完成"这一首要目标一致**：单人不引入第二门语言是最重要的时间保护措施。
3. **分发与性能的短板在当前阶段不构成阻塞**：本期交付是 demo 而非最终产品；
   真正的性能瓶颈由 llama.cpp（C++）承担，不由编排层承担。

**配套约定**：

| 项 | 决定 |
| --- | --- |
| 主语言 | **Python ≥ 3.12** |
| 推理后端 | llama.cpp（C++，**通过 HTTP 调用，不做语言绑定**） |
| **Node.js / pnpm** | **预装但非主语言**，仅用于：MCP 官方 server、promptfoo、以及将来可能的 Web UI |
| Rust / C++ | 本期**不引入**；若将来出现明确热点再单独决策 |
| Go | **不引入** |

> **说明**：Go 的"单二进制分发"优势是真实的，但它是**产品化阶段**的问题。
> 若本 Demo 成功后要真正装进老人手机，届时应新增 ADR 重新评估——
> 届时要么用打包工具（PyInstaller / uv）产出可执行文件，
> 要么把运行时重写为 Go 而保留 Python 做开发工具。**本决策不排除那种演进路径。**

## 6. 后果

### 正面

- 开发速度最快，时间风险最低；心智能全部放在设计与工程上，而非语言迁移。
- 可直接复用已有工程基线（CI、pre-commit、Makefile、测试骨架）。
- 可无障碍使用 MCP Python SDK、LLM Guard、garak、promptfoo（Node 侧）、LanceDB 等生态组件。

### 负面

- **分发是明确短板**：要把产品装到没有 Python 环境的设备上，需额外打包工作
  （体积大、启动慢、部分库对 PyInstaller 不友好）。本期不解决。
- 移动端没有原生支持。已确认走 Termux 路线（Termux 提供 Python 环境），
  但这意味着移动端形态是**终端**而非 App。
- 编排层性能弱于 Go/Rust。若将来出现大量并发会话，需重新评估。

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 出现 Python 无法实现的需求 | 中 | 用 HTTP 调用外部服务（MCP、llama.cpp）或子进程；本期未识别出此类需求 |
| 将来必须换语言导致重写 | 中 | 保持**接口层与实现层分离**：核心能力通过稳定的本地接口暴露，便于未来替换实现 |
| 团队成员（未来）不熟悉 Python | 低 | 单人项目，不适用 |

---

## 7. 验证方式

- **Phase 2 结束时自检**：是否存在"因为选择了 Python 而无法实现或明显劣化"的需求条目。
  若不存在，则本决策成立。
- **若出现**：评估能否用"调用外部服务/子进程/原生扩展"解决；
  若仍不可行，则新增 ADR 重新评估语言选型。
