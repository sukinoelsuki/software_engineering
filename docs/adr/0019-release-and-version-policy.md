## 1. 背景与问题

### 1.1 触发

PR #6 合并进 `main` 后，"要不要在 `main` 上打标签"这个问题暴露了一处**结构性空洞**：
**没有人能回答"现在该是哪个版本"**——`git tag` 列表为空、`pyproject.toml` 写着 `0.1.0`、
而 `0.1.0` 这个数字**从未被任何规则决定过**。

所有者的口径（2026-09-19）：

> 「不打标签，因为当前这个框架还没搭完对吧，搭完后发布的版本可以作为一个 0.0.1 的版本，
> 要到 v0.1.0，至少要能跑起来，能进行简单的 CLI 交互使用 agent 功能」

随后授权代理**自行设计并落地**一套发布方案，不必拘泥于上述具体档位。

### 1.2 真正的问题不是"配置写错了"

一致性报告 `A-17` 只描述了症状（`[tool.commitizen]` 缺 `major_version_zero` ⇒
`feat!:` 会把 `0.1.0` 推到 `1.0.0`）。但盘点后有三个更基础的事实：

| # | 事实 | 后果 |
| --- | --- | --- |
| 1 | `git-workflow.md` §5 只有一句"Phase 0 ~ 首个稳定版之前统一使用 `0.x.y`" | **没有任何版本号对应任何判据** ⇒ "什么时候发哪个版本"无法判定 |
| 2 | 实际值 `0.1.0` 是工程初始化时**手写**的默认值 | 它**不是任何决策的产物**，也没被任何检查覆盖 —— 一个纯装饰性字段 |
| 3 | 版本号在仓库里有 **4 处副本**（`[project].version` / `[tool.commitizen].version` / `src/agent_sec_perf/__init__.py:__version__` / `uv.lock`），而 `version_files` **只同步其中一处** | "改了忘同步"**不会报错**：某个载体从此长期说错话 |

⇒ 结论：**版本号没有 owner、没有判据、没有检查**。修 `A-17` 的配置只是把三个里的一个补上，
不会让"该不该发版"变得可判定——所以本 ADR 处理的是**整条发布口径**，而不是那一行配置。

## 2. 决策驱动因素

| # | 因素 | 说明 | 类型 |
| --- | --- | --- | --- |
| D-1 | **版本号要能回答"能不能用"** | 使用者的预期是"`0.1.0` = 能跑"，而提交类型（`feat`/`fix`）回答的是"改了什么" | 硬约束 |
| D-2 | **规则必须机器可核对** | 本项目已四例同类失效（`A-11`/`A-15`/`A-16`/`A-17`），共同形状是"写进文档就以为生效"（`SECURITY.md` `S-8` 同族） | 硬约束 |
| D-3 | **不可回退动作要有前置门禁** | 版本语义一旦被标签固化，回退代价高（`main` 上的历史不易改写） | 硬约束 |
| D-4 | **多副本必须有权威 + 一致性检查** | 见 §1.2 事实 3 | 硬约束 |
| D-5 | **不引入新依赖、不动已验过的构建链** | 依赖纪律（`F` 类）；`[build-system]` 刚于同日落装并实测（`uv build` 通过） | 硬约束 |
| D-6 | **与既有授权分级不冲突** | 发布只应**放大**"`main` 需事先批准"这一条，不得放松（`ADR-0016` §5.1） | 硬约束 |
| D-7 | 单人开发、时间预算有限 | 方案本身的维护成本必须低于它消除的风险 | 偏好 |

## 3. 候选方案

**A. 维持自动推导**：保留 `cz bump` 作为唯一机制，只补 `major_version_zero = true`。

**B. 纯人工**：在 §5 写清"版本号要表达里程碑"与 4 处副本的清单，靠人记得都改对。

**C. 里程碑驱动（本决策）**：台账（机器真源）+ `make release` 显式落定 +
4 副本一致性机器检查 + `cz bump` 关闭并设安全网。

**D. 单副本化**：`[project]` 改 `dynamic = ["version"]`，由 hatchling
（`[tool.hatch.version] path = "src/agent_sec_perf/__init__.py"`）从包内读取，其余全部派生。

## 4. 权衡对比

| 维度 | A 自动推导 | B 纯人工 | **C 里程碑驱动（推荐）** | D 单副本化 |
| --- | --- | --- | --- | --- |
| 版本号能否表达"能不能用" | ❌ 由提交类型决定 | ✅（但无强制） | ✅ | ✅ |
| 忘记同步副本会否报错 | ❌ | ❌ | ✅ 机器检查 | ✅ 结构上消除 |
| 发布是不是**显式**动作 | ❌ 谁跑 `bump` 都会动版本 | ✅ | ✅ 过台账校验 + 门禁 | ✅ |
| 判据是否需要可核对 | ❌ 无判据 | 文档层面 | ✅ 台账强制 `criteria` 非空 | ✅ |
| 是否改构建配置 | 否 | 否 | **否** | **是**（`dynamic` + 版本路径，需重验 `uv build` / `uv lock`） |
| 新依赖 | 无 | 无 | **无** | 无 |
| `A-17` 是否真正消解 | ❌ 只解决"越到 1.0.0"，不解决"`feat` 自动到达 `0.1.0`" | ✅ | ✅ | ✅ |
| 可核对性 | 中（只核配置键） | ❌ | **高**（5 组断言） | 高 |

**选 C**。理由：

1. **A 解决不了核心问题**：即使加了 `major_version_zero`，普通 `feat:` 仍会把版本推到
   `0.1.0`——而按 D-1，`0.1.0` 必须有"能跑起来"的判据；
2. **B 是本项目已证伪过的形态**（`A-11`~`A-17` 全是"写下来但没执行"）；
3. **D 的收益低于它的代价**：它只消除 1 份副本，却要改动刚验证过的构建链
   （`uv.lock` 的版本取值会改为构建期求值）⇒ 违反 D-5 的保守取向。**记为后续可选**（见 §8）；
4. **C 与 `A-16` 的既有处置同构**：多副本 + 一份机器检查把"必须一致"钉住——
   同一形状在本项目已被验证有效。

## 5. 决策

### 5.1 口径：版本号表达里程碑，不表达提交

**版本号只回答"到达了哪个里程碑"，提交历史只回答"做了什么"。** 两者不再有推导关系。

### 5.2 权威：`[tool.lowspec.releases]` 台账是唯一机器真源

```text
[[tool.lowspec.releases.milestones]]   # version / name / criteria，逐条必填
version = "0.0.1"
name = "框架搭完"
criteria = "M0 出口准则全部达成（docs/engineering/sdlc.md §3.1 的 G1~G9）"
```

规则（由机器检查强制，见 §5.4）：

- 当前版本**必须**是台账中声明的值之一；
- 里程碑版本形如 `0.x.y`、**严格递增**、`name` 与 `criteria` 非空；
- **Phase 0 内不接受 `1.x`**：进入 `1.0.0`（首个稳定版）必须先改机器检查本身
  —— 改检查是一次显式决策，而不是顺手在台账里加一行；
- **新增里程碑 = 一次显式决策**：必须给出可核对判据，并在 PR / ADR 中说明来源。

### 5.3 落定：`make release VERSION=x.y.z`（唯一入口）

流程与失败行为：

```text
1. 人工逐条核对目标里程碑的 criteria          ← 机器不判定判据是否为真（见 §5.6 边界）
2. make release VERSION=x.y.z
     ├─ 校验：目标在台账中、严格大于当前版本（否则中止，且不写任何文件）
     ├─ 编辑：4 处副本（pyproject ×2 / 包内 __version__ / CHANGELOG 段落）
     ├─ uv lock（第 4 处副本由锁文件承载）
     ├─ make check：红则 **回滚工作树**，版本号不变，非零退出
     └─ 本地提交 chore(release): x.y.z（**不推送、不打标签**）
3. 所有者动作：开 PR → main（Merge commit）→ CI 全绿 → 合并 → git tag -a v<x.y.z> → main 回合 develop
```

**`make bump` 已被改为"拒绝执行"**：它会按提交历史推导版本，绕过里程碑判据。
另设安全网 `major_version_zero = true`——即使有人直接跑 `cz bump`，破坏性变更也只动 MINOR，
**越不过 `0.x`**。

### 5.4 检查：4 副本一致 + 台账良构（`tests/unit/test_release_policy.py`）

| 组 | 断言 |
| --- | --- |
| 1 | 4 处副本逐一相等（`[project]` / `[tool.commitizen]` / `__version__` / `uv.lock`） |
| 2 | 当前版本 ∈ 台账 |
| 3 | 台账良构：`0.x.y`、严格递增、`name`/`criteria` 非空 |
| 4 | `major_version_zero is True` 且 `version_files` 覆盖包内 `__version__` |
| 5 | CHANGELOG 的版本段落 ⊆ 台账，且 `[Unreleased]` 在最前 |

另有对 `scripts/release_edit.py` 的**不变式回归**：每处替换必须"恰好命中预期次数"——
版本号"只改对一半"比不改更坏（某个载体开始说错话且不报错）。

### 5.5 产物清单（联动更新）

| 类别 | 文件 |
| --- | --- |
| 机器真源 | `pyproject.toml`（`[tool.lowspec.releases]`、`major_version_zero`、`version_files`） |
| 工具 | `scripts/release_edit.py`（纯编辑逻辑）、`scripts/release.sh`（编排）、`Makefile`（`release` / `bump`） |
| 检查 | `tests/unit/test_release_policy.py` |
| 流程口径 | `docs/engineering/git-workflow.md` §5 |
| 常驻结论 | `CODEBUDDY.md` / `AGENTS.md` §3、`.codebuddy/rules/git-workflow/RULE.mdc` |
| 一致性报告 | `docs/engineering/doc-consistency-report.md` 的 `A-17` 行（状态改为已处置） |
| 面向使用者 | `CHANGELOG.md` 的 `[Unreleased]` → `### Changed` |

### 5.6 明确不做（边界，**不得**表述为机制）

- 本方案**不判定里程碑判据是否为真**。脚本只保证"版本号合法 + 门禁全绿 + 是显式动作"；
  "`M0` 的 `G1`~`G9` 是否真的达成"仍由人逐条核对与审查承担。
  ⇒ 按威胁模型口径（`docs/design/threat-model/README.md` §4.1）这属**部分缓解**，
  **不得**写成"发布已由机制保障"。
- 本方案**不改变**远端授权分级：`main` 写入、打标签仍为所有者动作（`ADR-0016` §5.1）。

## 6. 后果

### 正面

- 版本号从"装饰性字段"变为**有判据、有 owner、有检查**的发布口径；
- `A-17` 消解，且**同类失效模式被结构性关闭**："忘记同步某一处副本"从此会红；
- 发布动作**可回滚**：门禁红即还原工作树，版本号不变；
- 当前版本由 `0.1.0` 更正为 `0.0.0`（按新口径，`0.1.0` 是**尚未到达**的里程碑）。

### 负面（必须承认）

1. **多了一步人工**：发版前要先把里程碑写进台账（换来的是判据明确）；
2. **4 份副本仍然存在**，靠检查兜底而非结构消除（D 方案记为后续可选）；
3. **台账的 `criteria` 是自然语言**：机器只保证"写了判据"，不保证判据可判定
   —— 若某天写出"基本能用"这种判据，检查不会拦下（缓解：PR 审查 + §5.2 的显式决策要求）；
4. **`make bump` 被废除**：若将来确实想回到自动推导，需要新增 ADR（不是改一行配置）。

### 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 有人直接跑 `cz bump` 绕过 `make release` | `major_version_zero` 兜住不越 `0.x`；且版本落到非台账值会被第 2 组断言拦下 |
| 有人为图快在台账里加一个 `1.0.0` | 第 3 组断言拒绝 `1.x`；越界必须改检查本身（= 显式决策 + 走 `F` 类） |
| 发布提交夹带无关改动 | `release.sh` 在工作树不干净时**拒绝执行**；提交用 `git commit -o` 点名 4 个路径 |

## 7. 验证方式

1. **机器检查**：`uv run pytest tests/unit/test_release_policy.py`（16 例，含 4 类非法目标版本）；
2. **反向验证（变异探针）**：故意把包内 `__version__` 改错 ⇒ 第 1 组断言必须**红**；
   还原后必须**绿**（证明检查非恒过）；
3. **拒绝路径**：`make bump` 必须拒绝且非零退出；`make release VERSION=0.5.0`（不在台账）
   必须拒绝；`make release VERSION=0.0.0`（不递增）必须拒绝；
4. **干跑**：`DRY_RUN=1 make release VERSION=0.0.1` 只打印 diff、不写任何文件；
5. **一致性**：`uv lock` 后 `uv.lock` 的版本与其余 3 处一致（第 1 组断言覆盖）；
6. **实战演练（2026-09-19，`M0` 达成时首次真正执行 `make release VERSION=0.0.1`）**：
   第一次执行**被自己的用例挡下**——`test_release_plan_is_consistent_and_does_not_touch_the_ladder`
   把目标版本**写死为 `0.0.1`**，而编辑完成后当前版本已是 `0.0.1` ⇒ 触发"目标必须严格大于当前"
   ⇒ 门禁红 ⇒ **脚本按 §5.3 回滚，版本号一字未改**。
   **这次失败同时验证了两件事**：门禁真的拦得住、回滚真的生效（这比任何"设计上应该能回滚"
   的说明都强）。修法是让用例**从台账动态取"当前版本之上的最小里程碑"**（不再与版本耦合），
   随后重跑成功（`ed4861e`：4 处副本同步为 `0.0.1`，`make check` 全绿）。
   ⇒ **一般性教训**：**检查自身的输入不得写死"当前状态"**，否则检查会随状态推进自行失效
   ——这与 §5.2 台账要"可核对"是同一件事的两面；
7. 实测记录见 `docs/devlog/0016-2026-09-19-M0出口准则与依赖落装.md` §3.15 与 §3.16。
