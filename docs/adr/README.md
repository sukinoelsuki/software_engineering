# 架构决策记录（ADR）

本目录记录项目的**每一个重要决策**及其论证过程。

---

## 为什么需要 ADR

单人项目最大的问题不是"做了错误决策"，而是**半年后不记得当初为什么这么决定**，
于是要么不敢改，要么反复推翻自己。ADR 的作用是：

1. **留痕**：记录决策时的约束、候选方案与权衡依据；
2. **防止反复**：想推翻旧决策时，先看当初为什么否决了它；
3. **交接与验收**：让评审者/未来的自己快速理解系统演进的逻辑。

---

## 何时必须写 ADR

| 触发场景 | 必须写 |
| --- | --- |
| 技术选型（基础项目、框架、库、工具链） | ✅ |
| 架构或模块边界变更 | ✅ |
| 引入 / 移除依赖、外部服务 | ✅ |
| 目录结构调整 | ✅ |
| 工程流程变更（分支模型、CI 门禁强度、测试策略） | ✅ |
| 安全相关的设计权衡 | ✅ |
| 绕过或豁免某项检查（`# nosec`、跳过测试） | ✅ |
| 纯文档修正、格式调整、无行为变化的内部重构 | ❌ |

## 命名与编号

- 文件名：`NNNN-<slug>.md`，编号**四位递增**，从 `0001` 开始，**不复用已用编号**。
- `<slug>` 用英文小写短横线，如 `0003-adopt-aios-as-base-project.md`。

---

## 状态机

```text
提议中 (Proposed) ──► 已接受 (Accepted) ──► 已废弃 (Deprecated)
                              │
                              └──► 已被 NNNN 取代 (Superseded by NNNN)
```

- **决策变更时不要修改旧 ADR 的结论**，而应：
  1. 新增一份 ADR 记录新决策；
  2. 在旧 ADR 的状态栏改为"已被 NNNN 取代"，并加一行指向新 ADR。
- 只有**状态栏与指针**可以被后续修改，正文的论证内容保持原样（它是历史证据）。

---

## 写作要求

必须包含：**背景 → 驱动因素 → 候选方案 → 权衡对比 → 决策 → 后果（含负面）→ 验证方式**。

其中最容易偷懒、也最关键的三个部分：

- **驱动因素**：写清约束（时间、硬件、能力、课程要求）。约束变了，结论可能就该变。
- **负面后果**：只写优点的 ADR 是宣传，不是决策记录。
- **验证方式**：写清"如何确认这个决策是对的"。没有可验证条件的决策无法复盘。
