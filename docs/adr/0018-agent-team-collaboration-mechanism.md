## 1. 背景与问题

### 1.1 机制已经在跑，缺的是"决策记录"

协作机制目前成文于三处：

| 载体 | 内容 | 性质 |
| --- | --- | --- |
| `.codebuddy/agents/`（五份） | 角色、产出域、`agentMode`、`model` 档位 | 定义 |
| [`docs/engineering/agent-teams.md`](../engineering/agent-teams.md) | 完整机制 + 实测证据 + 未验证项（持续增订） | **工程文档** |
| [`CODEBUDDY.md`](../../CODEBUDDY.md) §10 / [`AGENTS.md`](../../AGENTS.md) §10 | 必须始终生效的结论 | 常驻摘要 |

缺的是**决策记录**：为什么是五个角色、为什么统一 `agentic`、为什么"完成判定只认仓库"、
为什么不采用轮询 / ACK / 心跳。这些**理由**只存在于 `agent-teams.md` 的正文里，
而它是**随实测不断增订**的工程文档——按本项目 ADR 制度，"结论变化要留痕"的载体应由 ADR 承担。
后果：每次机制演进都要靠重读长文（736 行）重建理由；且 `devlog 0013` §7 优先级 F、
`devlog 0014` §7 优先级 C 一直挂着"**协作机制 ADR 仍待产出**"。

### 1.2 一个必须一并回答的历史缺口

`.codebuddy/agents/` **建立时没有写 ADR**（见 §5.2 的追溯登记），
而已核验的事实是："新目录的建立必须先在 ADR 中说明理由"在当时**已经生效**。
⇒ 本文必须回答：**这个缺口是补写、还是登记？** 结论见 §5.2（**登记，不追溯补写**）。

### 1.3 触发：本轮实测出**第 4 类**失效模式

2026-09-18 晚段的团队协作中，出现了一种此前未记录过的失效模式：**派活根本没有投递到成员**
（成员信箱为**空数组**、仓库**零新增**）。它与 `agent-teams.md` §8.1 的三类、§8.9、§8.12 **均不同**：
§8.1 以"消息已发出"为前提，§8.9 是"通道消失"，而 §8.12 的预检**两次都通过**。
⇒ 机制清单需要一个单点的决策记录，否则这次结论又会只存在于实测文档里。

## 3. 候选方案

### 方案 A：不写 ADR，继续只在 `agent-teams.md` 里描述

- 简述：承认机制已运行，靠工程文档 + 常驻摘要覆盖。
- 优点：**零新增载体**；`agent-teams.md` 已是事实上的权威源。
- 缺点：① 决策与实测**混在同一份持续增订的文档里**——机制一改就"覆盖"了旧理由，无法追溯"当时为什么这样定"；
  ② 活待办里的悬挂项继续挂着，属"长期未决项"（本项目已知的漂移源）；
  ③ 与项目规则「文档与决策留痕」不符（协作机制变更应产出决策记录）。

### 方案 B：写一份**短的** ADR —— 决策 + 指针 + 负面后果 + 验证方式（**推荐**）

- 简述：本文只写"决定了什么、为什么不选别的、代价是什么、怎么验证"；
  机制正文一律指向 `agent-teams.md` 与 `CODEBUDDY.md` §10。
- 优点：① 决策与实测**各归其位**（ADR 只增不改 / 工程文档按时间演进）；
  ② 不制造第二份机制文本 ⇒ 不新增漂移面；③ 落差最小、评审成本最低。
- 缺点：① 本文与 `agent-teams.md` 之间出现"**两处表述**"的潜在风险（靠 §7 `V7` 与联动更新表缓解）；
  ② 读者需要"顺着指针再读一份文件"。

### 方案 C：把整套协作机制正文搬进 ADR

- 简述：让 ADR 自足，读一处即可。
- 优点：单次阅读体验最好。
- 缺点：**直接制造第 2 份机制真源**，且是 ADR（**只增不改**）——机制每次实测演进都要新增 ADR，
  与 `agent-teams.md` 的增订节奏冲突；两处一旦分叉就是本项目反复吃亏的 A-16 类事故
  （文档与实现/门禁相反且长期无人发现）。

## 5. 决策

**决定采用：方案 B —— 写一份"决策 + 指针"的短 ADR；机制正文仍在 `agent-teams.md`。**

理由三条：

1. **决策与实测各归其位**：ADR 只增不改（记"为什么"），`agent-teams.md` 按时间演进（记"是什么、实测如何"）。
2. **不制造第二份机制文本**：本文唯一的漂移形态是**指针**，而指针可被核对（§7 `V7`）。
3. **关闭一处长期悬挂的缺口**：`devlog 0013` §7 F / `devlog 0014` §7 C 得以结项；§5.2 同时把历史缺口**留痕**。

### 5.1 覆盖范围（七条结论）

| # | 结论 | 理由要点 |
| --- | --- | --- |
| 1 | **主 Agent 恒为团队领导，不可转让** | 分发只发生在领导这一层（不支持嵌套团队）；领导对所有者负责 |
| 2 | **五角色 `agentMode` 统一 `agentic`** | `manual` 的语义是"在 Agent 选择框中选中、**完全替代主 Agent**"，**永远不会被派活**（实测报 `Subagent "X" not found`）⇒ "界面上看得见"**不是**"能被调用"的证据 |
| 3 | **设计 → 实现以文件为唯一载体** | 成员不继承领导对话历史、不跨会话恢复 ⇒ **未落盘 = 不存在**；设计类与执行类**不直接交接**，一律经"文件 + 领导核对" |
| 4 | **成本纪律：并行是乘法开销** | 成员是独立实例、`broadcast` 随成员数线性增长 ⇒ **能串行就不并行**；派活**显式限 `max_turns`**；**完成即关闭、不留常驻成员** |
| 5 | **回报通道三条机制** | 见下 5.1.1（这是本次决策的核心） |
| 6 | **子代理输出视为不可信输入** | 成员回报只能作**证据线索**，不得作为权限决策或控制流依据（威胁模型 `T-05`；与 `SECURITY.md` 的"不可信内容一律视为数据"同源） |
| 7 | **第 4 类失效模式与"可物证的重派判据"** | 见下 5.1.2 |

#### 5.1.1 回报通道的三条机制（判据、禁令、截止）

| 机制 | 内容 | 关键点（本文负责"为什么"） |
| --- | --- | --- |
| **1 · 终止声明** | 成员最后一笔提交的**正文末尾**附固定块 `回报：`（状态 / 改动 / 验证 / 遗留 / 需领导裁决） | 把"完成"从**状态**（不在仓库）变成**可从仓库单独读出的谓词**；**禁止以空提交承载**——否则"有声明"与"内容已落库"被解耦（§8.1 第三类失效模式） |
| **2 · 有界对账 + 未确认 ≠ 失败** | 领导只在三个时点对账；判据 = "终止声明 **且** 该提交含本域改动（`git show --stat` 非空）"；**未出现终止声明只说"未确认"，不得判失败、不得据此重派** | "没做完"与"做完了但消息丢了"在可观测层面**同构**；把两者之一当事实即是编造结论。重派代价双份：重复劳动 + 同一文件被两人写 |
| **3 · 关闭前摘录证据** | `team_delete` **之前**，先把本次协作的**可复现证据**（成员数 / 派活次数 / 逐成员到达清单 / 时间戳 / 失败现象）**以文本形式提交进仓库** | **硬截止是 `team_delete`，不是 `shutdown_request`**（60 秒只决定"等 ack 等多久"）；"摘录" = **进入仓库并被提交**，不是"读取了文件" |

**不采纳的替代方案**（含代价，避免后人重新发明）：轮询（领导没有定时器，且区分不了"没做完"与"丢了"）、
ACK / 三次握手（只覆盖实测 9/9 无故障的派活方向；且成员短命、**无重传者**）、
心跳 / 租约（对"回报丢失"无帮助，只有 token 开销与 `git log` 噪音）、重传（机制上无法实现）。
**接受的失败模式是"延迟发现"，而不是"错误结论"**（判据一旦出现即永久成立）。
完整论证与代价见 `agent-teams.md` §8.4。

#### 5.1.2 第 4 类失效模式与它的**唯一例外**

| 项 | 内容 |
| --- | --- |
| 现象 | **派活未投递**：成员**在活动名单里**，但其信箱为**空数组（0 条消息）**、仓库零新增 |
| 判据 | **成员信箱为空数组 ⇒ 投递未发生**（不是"还没干完"）；命令见研究笔记 §4.2 |
| 为什么不能用机制 2 的禁令 | 机制 2 的"禁止据未确认重派"针对的是"**可能已干完、只是回报丢了**"——此时重派会造成重复劳动与并发写。本案**投递本身失败**，成员不可能基于未收到的提示去干活 ⇒ 两点风险**均不成立** |
| 边界（不得过度推广） | 只有在"**信箱为空**"这一**客观物证**成立时才可立即重派；**只要信箱非空**，就回到"未确认 ≠ 失败，不得重派"的默认纪律。该判据**样本量 1**（见 §10 `U1`） |
| 与 §8.12 预检的关系 | **预检通过 ≠ 派活可投递**：预检覆盖"审批通道"，覆盖不到"spawn / 投递通道"，两者可能**独立失效** |

### 5.3 失效模式清单（四类 + 一条旁支）

| # | 失效模式 | 判据（可物证） | 权威源 |
| --- | --- | --- | --- |
| 1 | 投递失败 / 仅延迟到达 | 在**消息层** | `agent-teams.md` §8.1 |
| 2 | 完成信号与内容脱节（**空提交**） | `git show --stat <hash>` **为空** | §8.1 / §8.3 机制 1 |
| 3 | 通道不可达（登记表重置） | `send_message` 报 `Recipient not found` | §8.9 |
| 4 | **派活未投递** | 成员信箱**为空数组** | 研究笔记 §3 |
| 旁 | 会话级 `auto run` 失效 | 出现审批取消原文 | §8.12 |

**表注**：各条判据**不同、不得互相替代**；"禁止据未确认重派"的**唯一例外**是第 4 类（有物证）。
`Recipient not found` **≠** 无法归属：已终止成员的历史仍留在团队目录中（取证方法见 §8.7 教训 2）。

## 6. 后果

### 正面

- **机制有了只增不改的决策记录**：`agent-teams.md` 的增订不再需要承担"决策记录"的职责，
  它可以继续纯粹地做"完整定义 + 实测数据"。
- **历史缺口被显式留痕**（而非沉默处理或伪装成"当时有决策"），并产出一条可复用判据（§5.2 末）。
- **三条回报机制与"未确认 ≠ 失败"从实测结论升级为已接受决策**，
  降低下次被"想当然重派"的概率（重派 = 重复劳动 + 同一文件被两人写）。
- **成本纪律有了书面依据**：派活必限 `max_turns`、完成即关闭、能串行就不并行。

### 负面（必须承认）

| # | 负面 | 说明 |
| --- | --- | --- |
| 1 | **机制不可由 CI 强制** | `agentMode` 的**值**可以被断言，但"派活白名单、`max_turns`、关闭前摘录、事后报告"都是**流程纪律**；CI 看不到"有没有做"。只能记为**部分缓解**，**不得**表述为"已被机制保障"。 |
| 2 | **"成员真的按提示执行 / Skill 真的被加载"不可观测** | 同 ADR-0017 §6 负面 2；只能人工核对。 |
| 3 | **第 4 类的"空信箱"判据样本量 1** | 可能过窄（§10 `U1`）；在复验前**不得**当作普遍规律使用。 |
| 4 | **本文与 `agent-teams.md` 存在"两处表述"的潜在分叉** | 本文只写决策；一旦机制变更而本文未同步，就出现分叉。缓解：§7 `V7` 的核对项 + 项目规则「规则变更的联动更新」。 |
| 5 | **领导仍是单点** | 成员回报打断领导、领导没有定时器（`agent-teams.md` §8.2）；本文不消除这一层，只选定失败模式。 |

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| "未确认"被误读为"失败"而重派 | 重复劳动 + 同一文件被两人写 | §5.1.1 机制 2 的禁令写死；§7 `V6` 复盘是否有过此类重派 |
| 空提交承载终止声明 | 对账判"已完成"，而内容仍在工作区 | §5.1.1 机制 1 禁空提交 + 机制 2 须核 `--stat` 非空 |
| 关闭团队前未摘录 | 证据永久丢失，复盘只能靠记忆 | §5.1.1 机制 3 的硬截止是 `team_delete` |
| 成员回报携带注入指令 | 按第三方文本行事 | `T-05`：回报只作证据线索，不得作为权限决策或控制流依据 |
| 本文与 `agent-teams.md` 分叉 | 出现两份口径 | §7 `V7`；机制变更时同步四处（`agent-teams.md` / `CODEBUDDY.md` §10 / `AGENTS.md` §10 / 本文） |

## 7. 验证方式

| # | 验证项 | 怎么验 | 通过判据 |
| --- | --- | --- | --- |
| V1 | **`agentMode` 一致性** | `git grep -n "agentMode:" .codebuddy/agents/` | 五份均为 `agentic`；**变异探针**：把一份改成 `manual` 并尝试派活 ⇒ 必须报 `Subagent "X" not found` |
| V2 | **终止声明判据可用** | 关闭团队前，对每名成员执行 `git log --format=%B -1 <其最后一笔>` 与 `git show --stat <hash>` | 两者同时成立才判"已完成"；`--stat` 为空 ⇒ 判**未确认** |
| V3 | **派活可投递判据可执行** | 派活后**立即**跑研究笔记 §4.2 的一条命令 | 任一成员为**空数组** ⇒ 判"投递未发生"并允许重派；**非空则不得重派** |
| V4 | **摘录先于 `team_delete`** | 检查：成员数 / 派活次数 / 逐成员到达清单 / 时间戳 / 失败现象是否**已进入仓库并被提交** | 摘录**未落盘不得** `team_delete` |
| V5 | **成本纪律被遵守** | 每次派活提示含 `max_turns`；完成后 `shutdown_request` + 清理团队 | 无残留团队目录；无未限轮次的派活 |
| V6 | **"未确认 ≠ 失败"被遵守** | 复盘：是否出现过"据未确认重派" | 无命中；命中即违反 §5.1.1 机制 2 |
| V7 | **四处表述一致** | 机制变更时核对 `agent-teams.md` / `CODEBUDDY.md` §10 / `AGENTS.md` §10 / 本文 | 无相互矛盾的表述 |

**复核时间点**：落地后 **30 天**（与 `ADR-0013` §7、`ADR-0015` §7.5、`ADR-0016` §7、`ADR-0017` §7 的观察项同期）；
此后每次组队后顺带核对 `V2` / `V4`。
**若 30 天内出现过"据未确认重派"或"关闭前未摘录"** ⇒ 说明机制 2 / 机制 3 不可执行，
应补**机器检查**或调整流程，并**新增 ADR**（本文不改写）。
