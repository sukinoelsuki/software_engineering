## 1. 背景与问题

`test/<slug>` 是本仓库**唯一零提交**的分支：它只用来"借一台云原生开发环境"。由此产生一个
此前没被写下来的推论：

> **它的引用（ref）不会自己前进。**

而跑测有两条硬前提都指向"引用必须与 `develop` 一致"：

1. **镜像缓存**：环境须从与 `develop` 一致的提交拉起才命中镜像缓存（否则多花一次构建）；
2. **测的是被测代码**：从陈旧提交拉起，会让"同一份协议"这一可比性前提失效。

2026-09-25 实测暴露了两件事：

| 观测 | 结果 |
| --- | --- |
| `test/amd64-8` 的实际指向 | **停在 `006ff4f`**，落后 `develop` 3 笔（其中一笔是本轮的**修复本身**） |
| 用 `--sha` 指向别的分支的提交 | ❌ **不可行**：平台的 git-clone **只 fetch `--branch` 的那个 ref**，随后 `git checkout <sha>` ⇒ `fatal: reference is not a tree`（退出码 128，Prepare 阶段失败，`sn=cnb-k12-1k3av99mv`） |
| 若不察觉会怎样 | **用旧代码测新修复**，而且**日志、流水线状态、报告全都看不出区别**（结果"看起来正常"） |

⇒ 缺的不是"某次操作失误"，而是**一条没写下来的前置动作**。

## 2. 决策驱动因素

| 因素 | 说明 | 类型 |
| --- | --- | --- |
| 零提交原则不可破 | `test/<slug>` 上不得有提交（提交在上面的工作"下次会话不存在"） | **硬约束** |
| 引用必须新鲜 | 环境须从被测提交拉起（镜像缓存 + 可比性） | **硬约束** |
| 触发是常规动作 | ADR-0025 之后跑测**按需触发**⇒ 每次触发都要保证引用新鲜 | 硬约束 |
| 可回退 | 只动引用、不改历史、可追溯 | 偏好 |
| 不加维护负担 | 分支矩阵会增长（`test/arm64-8` 等）⇒ 机制要能套用 | 偏好 |

## 3. 候选方案

### 方案 A：**触发前快进引用**（`git push origin HEAD:refs/heads/test/<slug>`）

- 简述：只更新引用，让它等于被测提交（`develop` 的 tip）；**不新增任何提交**。
- 优点：零提交原则原样保留；fast-forward（**不需要 force**，也**不是**改写历史）；
  一条命令、可套用到任意 `test/<slug>`；操作本身可核对（`git ls-remote`）。
- 缺点：**靠人记得做**（无机器强制）；若并发/推送被拒，仍需人工判断。

### 方案 B：**流水线内断言**（启动期 `test/<slug>` 的 tip == `develop` 的 tip，否则 fail）

- 简述：把"引用是否新鲜"变成 fail-secure 的机器检查。
- 优点：不依赖人记得；失败是**显式**的，不会"测了旧代码还说成功"。
- 缺点：需要改写 `.cnb.yml` 的跑测段（新增一个 stage 与判据）；
  且"tip 相等"是**较强**的判据——若只想跑某个历史提交，会被误拒（需另开口子）。

### 方案 C：每次新建一条跑测分支（不复用 `test/amd64-8`）

- 简述：每次触发前从 `develop` 建一条新分支。
- 优点：引用天然新鲜。
- 缺点：**每建一条就多一个远端分支，而 D 类禁止删远端分支** ⇒ 分支只会堆积，
  且 `.cnb.yml` 的机器分派是**按精确分支名**写的 ⇒ 新分支名要么不命中、要么得往配置里加键。

### 方案 D：允许把脚本改动提交到 `test/<slug>`

- 简述：把跑测用的改动直接提交在这条分支上。
- 优点：引用自然前进。
- 缺点：**直接违反零提交原则**；且该分支不参与合入 ⇒ 改动"下次会话不存在"。

## 4. 权衡对比

| 评估维度 | 权重 | A | B | C | D |
| --- | --- | --- | --- | --- | --- |
| 不破坏零提交原则 | 高 | ✅ | ✅ | ✅ | ❌ |
| 引用新鲜度 | 高 | ✅（靠人执行） | ✅（机器强制） | ✅ | ✅ |
| 不需要额外远端分支 | 中 | ✅ | ✅ | ❌（且不可删） | ✅ |
| 改动面 / 维护成本 | 中 | 极小（一条命令） | 中（改配置 + 判据边界） | 小 | 小 |
| 可回退 | 中 | ✅ | ✅ | ✅ | ⚠️ 提交在废弃分支上 |

## 5. 决策

**决定采用：方案 A**（所有者裁定），**B 保留为后续可选硬化**。

理由：

1. A 在**不破零提交原则**的前提下把两难解开——"引用前进"与"分支零提交"并不冲突，
   此前只是没人把它写下来；
2. 实测已证明**没有别的路**：`--sha` 跨分支不可用（§1），C 会堆积不可删的分支，D 直接违规；
3. 成本最低、可套用到后续的 `test/arm64-8`（分支矩阵增长时不必重写机制）。

## 6. 后果

### 正面

- 环境分支与 `develop` 一致 ⇒ **镜像缓存命中**（不额外花构建桶）+ **测的是被测代码**；
- 操作是 fast-forward ⇒ 不改写历史、不需要 force、随时可核对（`git ls-remote`）；
- "零提交"这条规则**不必为了可用性而放宽**。

### 负面（必须填写）

1. **靠人执行**：A 是**流程纪律**，不是机制 ⇒ 忘了做**不会报错**，
   症状是"用旧代码测新修复、结果看起来正常"（这正是本次踩到的形态）
   ⇒ 按威胁模型口径只能记**部分缓解**，**不得**表述为机制。
2. **`tip == develop` 是必须维持的不变量**：每次 `develop` 前进，`test/<slug>` 就落后一点
   ⇒ 需要"**触发前**做一次"这个固定动作，而不是"想起来才做"。
3. **写命令有个易踩的坑**：`git push origin "$SHA:refs/heads/…"` 在 zsh 下会被当成参数修饰符
   （`$SHA:r`）⇒ 用 `HEAD:refs/heads/…` 或 `${SHA}:refs/...`；
   且**不要把 `git push` 接进管道**（`| tail` 会让退出码变成 `tail` 的，失败被吞掉——
   本次即因此按旧配置误触发了一次，靠 `cnb build stop-build` 止损）。

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 忘记快进 ⇒ 测旧代码 | 结论无效且**看起来正常** | 写进运行手册 §3 的触发前置步骤；**候选硬化见 B**（未落地） |
| 在 `test/<slug>` 上不小心提交 | 工作"下次会话不存在" | 零提交原则不变；本条**只动引用**，不新增提交 |
| 快进被拒（非 fast-forward） | 说明有人在上面提交了 | **停下、报告**；**禁止 force**（D 类） |
