# 0007. 修正沙箱可用性结论：引入容器后端，并按"机制类别"而非"工具"划分隔离能力

## 1. 背景与问题

[ADR-0006](0006-sandbox-execution-degradation.md) 在实测 `bwrap` / `firejail` / `unshare` 全部失败后，
判定"L2 命名空间档在当前 CNB 环境不可用"，只保留 L1 受限进程档。

该判定**不完整**。同日为规划测试环境而核实时发现：**开发环境内可以完整使用 docker**
（Client/Server 29.6.2，overlayfs，buildx 与 compose 均在；`.cnb.yml` 的
`services: [docker]` 正是为此提供）。实测表明**容器后端可以提供真实隔离**。

因此问题重述为：

> 不是"当前环境无法提供强隔离"，而是"**用户态命名空间工具**无法直接调用，
> 但**经由 docker daemon** 可以"。而**资源限制**这一维度在两条路径上都不可靠。

这是一个必须先说清的事实区分，否则会把"隔离可用性"错误地当成单一布尔值。

---

## 2. 决策驱动因素

| 因素 | 说明 | 类型 |
| --- | --- | --- |
| 安全断言不得建立在幻觉上 | 已出现三次"看起来成功、实际没生效"（firejail、`--memory`、`--pids-limit`） | 硬约束 |
| 目标设备能力未知 | 手机 / Termux 既无 docker 也多半没有命名空间 → **产品不能依赖容器后端** | 硬约束 |
| 开发与测试需要一个可信的破坏性测试载体 | 极端测试不能直接跑在开发容器里 | 硬约束 |
| 可验证性 | 结论必须可用**当前环境**中的探针复现，不能只靠文档 | 硬约束 |
| 不引入新依赖 | docker 是平台已提供的服务，不是新依赖 | 偏好 |

## 3. 实测证据（探针矩阵，2026-09-15）

### 3.1 容器后端（`docker run`，镜像 `alpine:3.20` / `python:3.12-slim`）

| 维度 | 命令要点 | 实测结果 | 判定 |
| --- | --- | --- | --- |
| 基本运行 | `docker run --rm alpine:3.20 sh -c 'echo sandbox-ok'` | 输出 `sandbox-ok` | ✅ |
| **文件系统** | `--read-only` 后 `touch /test-write` | `Read-only file system` | ✅ **真实阻止** |
| **网络** | `--network=none` 后 `wget http://example.com` | `bad address 'example.com'` | ✅ **真实阻止** |
| 权限 | `--user 65534:65534 --cap-drop=ALL` | `uid=65534`，能力被丢弃 | ✅ |
| **内存** | `--memory=64m --shm-size=1g`，写 300 MB | **写满 300 MB 成功** | ❌ **静默失效** |
| **内存（旁证）** | `--memory=64m` + Python 分配 200 MB | **分配成功** | ❌ **静默失效** |
| **进程数** | `--pids-limit=16`，起 50 个后台进程 | **50 个全部起来** | ❌ **静默失效** |
| cgroup 可见性 | 容器内读 `/sys/fs/cgroup/{pids,max,memory.max}` | **读不到**；`/sys/fs/cgroup` 为 tmpfs，无 cgroup v2 委派 | 根因确认 |
| 进程数（rlimit） | `--ulimit nproc=16:16` | `can't fork: Resource temporarily unavailable` | ✅ **真实阻止** |
| 文件大小（rlimit） | `--ulimit fsize=1048576:1048576` | `File size limit exceeded` | ✅ **真实阻止** |
| 地址空间（进程内） | `resource.setrlimit(RLIMIT_AS, 64 MiB)` 后分配 200 MB | `MemoryError` | ✅ **真实阻止** |
| 文件大小（进程内） | `resource.setrlimit(RLIMIT_FSIZE, 1 MiB)` 后写 5 MB | `File size limit exceeded` | ✅ **真实阻止** |

> ⚠️ **一次必须记录的自我纠错**：`--memory=64m` 下 `dd` 写到 64 MB 就停了，
> 我最初据此判断"内存限制生效"。**这个判断是错的**——64 MB 恰好是 Docker
> `--shm-size` 的**默认值**，与内存限制无关。加上 `--shm-size=1g` 后同一探针
> 写满 300 MB 成功，才暴露真实行为。**结论：探针必须能把两种解释区分开，
> 否则"验证通过"本身就是误判。**

### 3.2 与 ADR-0006 中 firejail 的对照

| 工具 | 表面行为 | 实际隔离 | 失败方式 |
| --- | --- | --- | --- |
| `firejail --net=none` | 退出码 0、输出正常 | **无**（出站仍 200） | **静默失效** |
| `docker --network=none` | 退出码 0 | **有**（出站被拒） | 正常 |
| `docker --memory=64m` | 退出码 0 | **无** | **静默失效** |
| `docker --pids-limit=16` | 退出码 0 | **无** | **静默失效** |

**四种情况里三种是"退出码 0 但不生效"** —— 这是本项目目前最有力的经验证据：
**隔离能力必须逐维度实测，不能由工具的"成功"推断。**

## 4. 决策

**修正 ADR-0006 的档位模型：隔离能力按"机制类别"划分，并要求逐维度探针。**

### 4.1 三个机制类别（本决策的核心）

| 机制类别 | 依赖 | 在当前环境的有效性 | 由谁承担 |
| --- | --- | --- | --- |
| **命名空间 / mount 类**（文件系统、网络、PID、用户、能力） | 内核命名空间 | ✅ **有效**（经 docker daemon 创建，daemon 不受本容器 seccomp 限制） | `ContainerBackend` |
| **cgroup 类**（内存、pids、CPU 配额） | cgroup v2 委派 | ❌ **静默失效** | 弃用，改由 setrlimit 承担 |
| **setrlimit 类**（地址空间、文件大小、进程数、CPU 时间） | 内核 per-process rlimit | ✅ **有效**（容器外与容器内均有效） | `RestrictedProcessBackend`（L1）与 `ContainerBackend` 的资源维度 |

### 4.2 档位表（修订 ADR-0006 §5.3）

| 档位 | 后端 | 隔离维度 | 可用条件 |
| --- | --- | --- | --- |
| **L2-N** | `NamespaceBackend`（bwrap / firejail） | 文件系统 + 网络 + PID + rlimit | 命名空间探针通过（**当前环境不可用**；预期在普通 Linux 主机 / 本地 VM 可用） |
| **L2-C** | `ContainerBackend`（docker，**新增**） | 文件系统 + 网络 + 用户 + 能力 + **rlimit 承担资源维度** | docker 可用且逐维度探针通过（**当前环境可用**；不适合手机等无 docker 的目标设备） |
| **L1** | `RestrictedProcessBackend` | rlimit + 路径白名单 + 网络默认拒绝 + 审计 + 人工确认 | **始终可用**（当前环境实际生效档位） |
| L0 | 拒绝执行 | — | 所有探针均未通过时 |

> **重要**：档位选择是**逐维度**的（`isolation_matrix()` 返回每个维度的布尔值 + 由谁提供），
> 不再是单一的"档位 = 枚举值"。这样才能表达"文件系统隔离由容器提供、
> 资源限制由 rlimit 提供"这种真实组合。

### 4.3 对产品的约束（不得越界）

`L2-C` 是**开发与测试环境的工具**，**不能作为产品唯一隔离手段**：
目标设备（手机 / Termux）没有 docker。产品必须能在**只有 L1** 的情况下运行，
`L2-N` 作为可选增强。这与 ADR-0006 的原则一致：**不把产品正确性绑定到宿主能力**。

## 5. 后果

### 正面

- 修正了一个会误导后续设计的错误结论（"当前环境无法提供强隔离"）。
- 得到可执行的**探针矩阵**，可直接作为 CI 断言与 `SandboxBackend` 的能力探测实现。
- 明确了资源维度的可靠机制是 **setrlimit 而非 cgroup**——这直接决定 L1 档的实现方式。
- 容器后端为开发/测试提供了可信的**破坏性测试载体**（见 [ADR-0008](0008-dev-test-environment-strategy.md)）。

### 负面（必须填写）

- **容器后端与目标设备能力不匹配**，验证过的隔离在交付环境里可能无法复现；
  容易产生"我们已经验证过强隔离"的错觉，必须在文档中反复标注适用范围。
- 逐维度探针矩阵比"单一布尔"复杂，实现与测试工作量增加。
- 依赖平台提供的 docker 服务；若平台策略变化（取消 `services: [docker]`），L2-C 直接失效。
- 容器启动与镜像拉取有开销（首次拉取 alpine 约数秒），不适合高频细粒度执行。

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 把 L2-C 当作产品能力对外表述 | 高 | 在 SRS / 设计中标注"L2-C 仅用于开发与测试环境"；输出与文档禁止暗示目标设备具备同等隔离 |
| cgroup 类限制在某环境"看似可用" | 高 | 任何 cgroup 类限制都必须配**区分性探针**（如 `--shm-size` 对照），不能用默认值下的现象判定 |
| 平台取消 docker 服务 | 中 | 探针失败即降级到 L1；产品路径不依赖 L2-C |
| 镜像层缓存在平台侧被清理 | 低 | 资产脚本幂等且带校验，重建即可恢复 |

## 6. 验证方式

1. **探针矩阵纳入 CI**：以脚本形式固化 §3.1 的探针（含"区分性探针"），
   在支持的运行器上断言：文件系统/网络维度**必须被阻止**，资源维度**必须由 rlimit 提供**。
2. **反向验证（关键）**：探针必须包含**必须失败**的用例（越界写、未授权出站、
   超限分配），任何一项"意外成功"即判定该维度不可用——这是对 §3.1 中三次 fail-open 的直接防御。
3. **目标设备阶段**：在无 docker 的环境（本地 VM / Termux）上运行同一探针集，
   确认 L1 单独可用、L2-N 的可用性结论。
4. **M2 里程碑**：`REQ-SEC-05` 的验收在 L1 与（可用时）L2-C 两种组合下均能复现通过。
