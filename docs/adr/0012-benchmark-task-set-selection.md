## 1. 背景与问题

三档实测（2B/4B/8B）证明：**现有三项任务对最小的 2B 也偏易，三档几乎打平**，
降级曲线在能力维度是一条平线。因此需要引入任务集，作为后续开发与实验的基准。

项目所有者提出两点要求：任务集应作为**环境 assets**（随镜像固化）引入；
且希望它是**能体现模型能力上限**的集合。

需要决策三个问题：

1. **选哪些**任务集？
2. 以什么**形式**引入——是否连带采用它们的 agent harness？
3. 放在**哪里**、如何**获取**（不引入新依赖）？

---

## 2. 决策驱动因素

| 因素 | 说明 | 类型 |
| --- | --- | --- |
| **离线可跑** | 产品定位是离线低资源环境；在线评测的分数与真实场景不符 | 硬约束 |
| **判定客观** | 弱模型不能既当被测又当裁判；须单元测试等客观判定 | 硬约束 |
| **不引入新依赖** | 项目对依赖极度克制；为评测引入 pyarrow 等重量级依赖不划算 | 硬约束 |
| **可区分性** | 当前最大痛点：任务过易导致平线结论 | 硬约束 |
| **许可证明确** | 供应链条款；无许可证即排除 | 硬约束 |
| **必须能回答"Harness 增益"** | 这是本项目核心论点，决定引入形式 | 硬约束 |
| **体积与构建时间可控** | 资产随镜像固化，影响重建成本 | 偏好 |
| **上限可探测** | 项目所有者的明确诉求 | 偏好 |

## 3. 候选方案

### 方案 A：采用自带 harness 的完整基准（官方链路）

- 简述：直接使用 SWE-bench / Terminal-Bench / aider 的官方评测框架。
- 优点：结果与公开榜单可比；实现成本最低（别人写好了）。
- 缺点：**测出的是"别人的 Harness + 我们的模型"**，无法回答本项目的核心问题；
  多数还需要容器/网络/真实 API；SWE-bench Lite 的许可证未标注。

### 方案 B：只取任务与客观判定字段 + 自研执行链路（**采纳**）

- 简述：从公开基准中只取**任务数据与判定所需字段**（`test`、`entry_point`、`libs`），
  由自研链路驱动模型与执行，产出报告。
- 优点：能直接回答"我们的 Harness vs 裸模型"；判定客观；数据体积小（合计约 23 MB）；
  许可证清晰（Apache-2.0）；离线可跑；为后续自研 Harness 提供统一的输入格式。
- 缺点：自研判定链路**可能与官方判据有细微偏差**，分数不可直接与榜单对照（须显式标注）。

### 方案 C：只用自建任务集

- 简述：完全自己构造任务，不用任何公开基准。
- 优点：最贴合本项目分布；零许可与体积问题。
- 缺点：**缺外部参照**——无法判断"我们的评测链路是否本身有 bug"，
  也无法与公开分数对照；且自建任务容易无意识地"贴合我们的实现"。

### 方案 D：不引入，每次临时构造任务

- 优点：无维护成本。
- 缺点：这正是当前状态，已证明会产生**不可比的实验结果**（每次任务不同 → 曲线不可叠加）。

## 4. 权衡对比

权重：离线可跑 5、判定客观 5、可区分性 5、许可证明确 5、能回答 Harness 增益 5、
不引入新依赖 4、上限可探测 4、体积与成本 3。

| 维度 | 权重 | A 官方链路 | **B 只取任务+自研判定** | C 纯自建 | D 不引入 |
| --- | --- | --- | --- | --- | --- |
| 离线可跑 | 5 | 2 | **5** | 5 | 5 |
| 判定客观 | 5 | 5 | **4**（自研需自证） | 5 | 3 |
| 可区分性 | 5 | 4 | **4** | 3（易贴合自身实现） | 1 |
| 许可证明确 | 5 | 2 | **5** | 5 | 5 |
| **能回答 Harness 增益** | 5 | **1** | **5** | 5 | 3 |
| 不引入新依赖 | 4 | 1 | **5** | 5 | 5 |
| 上限可探测 | 4 | 5 | **3** | 5 | 1 |
| 体积与构建成本 | 3 | 2 | **5** | 5 | 5 |
| **加权合计** | | **91** | **149** | **152** | **107** |

> 方案 C 的加权分与 B 接近（152 vs 149），说明"自建"在本项目的判据下**同样强**。
> 因此决策不是二选一，而是**组合**：以自建为上限探测主力，同时保留少量外部锚点
> 用于校准评测链路。见 §5.1 的三层结构。

## 5. 决策

### 5.1 采用三层结构

| 层 | 内容 | 作用 | 是否默认执行 |
| --- | --- | --- | --- |
| **L0 外部锚点** | HumanEval+（164）、MBPP+（378）、BigCodeBench v0.1.4（1140，**抽子集**） | 与公开分数对照；校准评测链路；提供难度梯度 | ✅ 默认 |
| **L1 自建阶梯任务集** | 10~20 条贴合本项目分布的任务，按难度分阶：单函数 → 多文件改动 → 需检索 → 多步工具调用 | **真正探测能力上限**；验证 Harness 增益 | ✅ 默认 |
| **L2 上限探测** | Terminal-Bench-1、SWE-bench（按需抽题） | 展示"离真正的 agent 任务还有多远" | ⚠️ 可选，不纳入默认循环 |

**为什么上限主要靠 L1**：L0 的任务分布与我们的实际用途不同，且对 2B~8B 的难度梯度有限；
L1 用**我们自己真实遇到的需求**构造，难度可控、判定客观，能直接暴露"从哪一阶开始崩"。

### 5.2 引入形式（关键约定）

> **只取任务定义与客观判定字段，不连带采用它们的 agent harness。**

理由：跑别人的 harness 会得到"**别人的 Harness + 我们的模型**"，
从而无法回答"我们自己的 Harness 相对裸模型提升多少"这一核心问题。
官方 harness 仅作为**可选的外部参照**另行评估，不进默认链路。

### 5.3 数据获取方式（避免新依赖）

允许两类来源，均带 sha256 校验、失败即中断构建：

| 类型 | 适用 | 说明 |
| --- | --- | --- |
| `file` | 提供 JSONL 的数据集 | 直接下载官方文件 |
| `hf-rows` | **仅提供 parquet** 的数据集 | 经 HF datasets-server 的 rows API 取全部行落为 JSONL；标准库即可处理，**不引入 pyarrow** |

`hf-rows` 的摘要固定的是**我们生成后的 JSONL 摘要**，已通过"两次独立生成得到同一摘要"验证可复现。

### 5.4 存放位置

镜像内 **`/opt/benchmarks`**（在 `/workspace` 之外），理由同模型与参考资料：
数据不进入版本管理，也不随工作区重克隆而丢失；清单与校验值在仓库内受版本管理。

### 5.5 抽样与可比性

BigCodeBench 等大集**必须抽样**（全集在 M 档约 7.3 小时，见研究笔记 §6）。
抽样规则：

- **固定随机种子**；
- **子集索引必须与结果一并归档**（否则跨轮结果不可比）；
- 同一实验内所有档位/配置使用**同一子集**。

### 5.6 明确不做

- ❌ 不引入需要运行时网络或真实 API 的评测（BFCL 可执行类目、部分在线基准）；
- ❌ 不引入需要 LLM 扮演用户的评测（τ-bench）——与"离线 + 弱模型"前提冲突；
- ❌ 不引入许可证未标注的数据集（如 SWE-bench Lite）；
- ❌ 不用自带 harness 的结果作为本项目结论（仅可作外部参照）；
- ❌ 不做全集评测（成本不可接受）。

## 6. 后果

### 正面

- 评测**离线可跑且零新依赖**（23 MB 数据 + 标准库），与产品场景一致。
- 评测链路与自研 Harness 共用同一套任务输入格式，**评估即 Harness 的真实用例**：
  模型生成的代码要在我们的受限执行层里跑起来才算通过——这同时成为安全主线的实战场景。
- 外部锚点 + 自建阶梯的组合，既保证"链路没坏"可被检出，又保证"能探到上限"。
- 清单化 + sha256 固定 + 失败即中断，延续了既有资产机制，无新增维护范式。

### 负面（必须填写）

- **自研判定链路可能与官方判据有偏差**，分数不可直接与公开榜单对照；
  若对外引用必须显式标注"自研判定，非官方分数"。
- **`hf-rows` 摘要绑定了上游 split 内容**：上游一旦更新，构建会失败（需重新生成并记录）；
  这是刻意的 fail-secure，但会带来偶发的维护打断。
- **L1 自建任务集尚未实现**，而它才是上限探测的主力——当前只完成了 L0，
  "能力上限"这一诉求**尚未真正满足**。
- 抽样虽是必要妥协，但引入了"抽样偏差"这一新的解释负担（不同子集可能得出不同排序）。

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 把自研判定分数当官方分数引用 | 高 | 报告中强制标注判定来源；关键结论需与官方实现抽样比对（B-3） |
| L1 迟迟不做，上限始终测不出 | 高 | 在 ADR-0012 的后续行动中列为最高优先级 |
| `hf-rows` 上游变更导致构建中断 | 中 | 摘要失败即中断（不静默）；重新生成并在 devlog 记录 |
| 抽样偏差导致档位排序不稳 | 中 | 固定多套种子复测（B-2）；结论标注子集索引 |
| 评测时间挤占开发时间 | 中 | 默认只跑 L0 的子集 + L1；全集与 L2 按需 |

## 7. 验证方式

1. **链路正确性**：抽取若干题，将自研判定结果与官方（EvalPlus / BigCodeBench）结果比对，
   一致率不足则先修链路、不得用于结论。
2. **可复现性**：同一子集、同一配置重复运行，分数波动应在可解释范围内（记录方差）。
3. **区分度**（本轮的核心目的）：三档在 HumanEval+/BigCodeBench 上的分数**必须形成梯度**；
   若仍为平线，说明任务集仍不足，需回到 L1 加难度。
4. **离线可验证**：断网运行（本环境 `--network=none` 无法用于此，可用受限执行层验证）
   或至少确认评测过程不发起网络请求。
