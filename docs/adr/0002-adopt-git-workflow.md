# 0002. 采用简化 Git Flow 工作流

- **状态**：已接受
- **日期**：2026-09-14
- **决策者**：Le0n3rd
- **相关**：Issue #2、[`docs/engineering/git-workflow.md`](../engineering/git-workflow.md)

---

## 1. 背景与问题

项目为单人独立开发，但需要满足"规范的软件工程过程"。核心矛盾是：

- **一方面**，单人开发没有协作开销，理论上可以直接在 `main` 上提交，最简单；
- **另一方面**，课程要求体现规范流程，且项目周期长（2~3 个月）、会频繁引入前沿依赖，
  需要**可回滚、可追溯、有门禁**的开发方式。

问题：应该采用多重的分支策略？如何在不制造形式主义负担的前提下，获得流程的实际收益？

## 2. 决策驱动因素

| 因素 | 说明 | 类型 |
| --- | --- | --- |
| 单人 | 无并发写入冲突，分支主要用于**隔离风险**而非协作 | 硬约束 |
| 长周期 | 需要稳定的发布线与可回滚的能力 | 硬约束 |
| 研究性质 | 存在大量探索性尝试，需要允许"失败"的分支出口 | 硬约束 |
| 课程验收 | 需要体现规范的变更管理与发布管理 | 硬约束 |
| 时间成本 | 流程开销必须可控，不能挤压实现时间 | 硬约束 |
| 流程退化风险 | 单人极易"图省事直接推 main" | 硬约束 |

## 3. 候选方案

### 方案 A：Trunk-Based（单主干）

- 做法：只保留 `main`，所有改动直接提交或用极短分支。
- 优点：最简单、速度最快；被现代大厂广泛采用。
- 缺点：**CI 门禁与 PR 记录被弱化**；没有发布准备分支，发布过程与开发过程交织；
  对"研究型、需求频繁变动"的项目，缺乏隔离手段。

### 方案 B：完整 Git Flow（含 long-lived develop + release + hotfix）

- 优点：隔离最彻底，发布管理最规范。
- 缺点：分支数量多、合并路径长；单人项目下大量分支会带来显著的**管理负担与合并摩擦**，
  且 `develop` 长期存在会造成"两条线同时演进"的认知成本。

### 方案 C：简化 Git Flow（main + develop + 短期分支）

- 做法：保留 `main`（发布）与 `develop`（集成）两条长期分支，其余均为短期分支；
  短期分支 squash 合入 `develop`，发布时 `develop` 以 merge commit 合入 `main`。
- 优点：保留了发布隔离与集成验证两个关键收益；分支数量可控；
  单人也能维护；天然支持 `exp/*` 作为探索出口。
- 缺点：比单主干多一层合并；需要遵守纪律否则退化为"直接推 develop"。

## 4. 权衡对比

| 评估维度 | 权重 | A 单主干 | B 完整 Git Flow | C 简化 Git Flow |
| --- | --- | --- | --- | --- |
| 变更隔离与可回滚 | 高 | 3 | 5 | 4 |
| 发布管理清晰度 | 高 | 2 | 5 | 5 |
| 单人维护成本（越低越好） | 高 | 5 | 2 | 4 |
| 与 CI 门禁的配合 | 高 | 3 | 5 | 5 |
| 支持探索性分支 | 中 | 3 | 5 | 4 |
| 流程退化风险（越低越好） | 高 | 2 | 4 | 4 |

## 5. 决策

**决定采用方案 C：简化 Git Flow。**

理由：

1. **保留两个关键收益**：`main` 永远是"可发布状态"（发布隔离）；
   `develop` 承担集成验证职责（集成隔离）。
2. **成本可控**：只多维护一条长期分支，短期分支生命周期通常不超过一周。
3. **配套机器约束可对抗退化**：`pre-commit` 的 `no-commit-to-branch` 直接拦截对
   `main` / `develop` 的直接提交，使流程无法被"图省事"绕过。

## 6. 后果

### 正面

- `main` 上的每个提交都对应一次发布，可用于构建可靠的可复现基线。
- 集成风险被集中到 `develop`，`main` 不受半成品影响。
- 变更记录完整，每次改动都能回答"为什么、怎么验证、如何回滚"。

### 负面

- 比单主干多一次合并操作（短期分支 → `develop`），存在固定开销。
- 需要**自觉**在合并后删除分支，否则分支列表会脏。
- 若长期在 `develop` 上直接提交（而非开短期分支），本工作流会退化为"双主干"，
  失去隔离收益。这是本方案最主要的失效模式。

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 退化为直接推 `develop` | 高 | `no-commit-to-branch` 钩子拦截；自评审清单 |
| 分支忘记删除 | 低 | 合并后立即删除；每周迭代收尾时检查 |
| squash 导致细粒度历史丢失 | 低 | 依赖 PR 描述与 ADR 记录过程细节；提交信息在 PR 中可查 |

## 7. 验证方式

- **M1 里程碑**时检查：`git log --first-parent main` 中每个提交都对应一次发布；
  `main` 上不存在未发布的功能提交。
- 检查是否存在"直接提交到 `main` / `develop` 而未走 PR"的记录。若存在则为流程失效，
  需分析原因（是流程太重，还是纪律问题）并修正。
