## 1. 背景与问题

### 1.1 触发事件

项目所有者提出：把 **CNB 官方 Skills** 与 **`cnb-cli`** 接入本项目开发环境镜像，
以便代理能直接完成平台侧操作（建 PR、查构建日志、触发流水线等）。这立刻撞上一条现行硬规则：

> **任何写入远端的操作都必须事先获得批准，且推送前必须先把"将要推送的实际文件与变更内容"
> 提交所有者审查**（[`CODEBUDDY.md`](../../CODEBUDDY.md) §2、
> [`git-workflow.md`](../engineering/git-workflow.md) §4、`.codebuddy/rules/git-workflow/RULE.mdc`）。

`cnb-cli` 具备**平台远端写能力**（文档示例含 `cnb issues create-issue`、`cnb pulls merge-pull`、
`cnb build start-build`）⇒ 不调整规则就直接接入，等于**在一条"未经批准禁止远端写入"的规则旁边，
放一个随时可写远端的工具**。所有者倾向把规则改为"**事后报告 + 可回退**"，
并要求**同步更新所有关联位置**（项目规则「规则变更的联动更新」）。

### 1.2 真正的问题不是"装不装工具"

一个已核实的事实改变了问题的形状：

| 事实 | 来源 |
| --- | --- |
| 本项目**已经在用令牌直接调 CNB OpenAPI**（`curl -H "Authorization: Bearer $CNB_TOKEN" …`） | [`benchmark-automation.md`](../engineering/benchmark-automation.md) §6.1/§6.1 更正注 |
| 环境变量 `CNB_TOKEN` **已设置且长期存活**（平台写权限凭据），本会话已发生一次误显示 | 本会话实测；处置建议见 §5.5 |
| CI 夜轮曾让常驻 `llama-server` **继承含 `CNB_TOKEN` 的完整父环境**（已修，属 `T-08`） | [`devlog 0014`](../devlog/0014-2026-09-18-威胁模型与安全修复.md) §3 |

⇒ **"不接入 CLI"并不能消除"平台写权限存在并被使用"这一事实**，它只是让这件事**更隐式、更不可审计**
（手工 `curl`、无结构化记录、无统一入口）。因此本 ADR 的问题应表述为：

> **在"平台写权限已经存在"的前提下，如何让它的使用被规则覆盖、被事后核对，
> 同时不让真正不可回退的操作（凭据入库、改写已推送历史、`main`、`bench/data`）被顺手放松？**

### 1.3 第二条冲突：官方安装方式与本项目的依赖纪律

官方文档给出的镜像构建命令为：

```text
npm install -g @cnbcool/cnb-cli skills
npx skills add https://cnb.cool/cnb/skills/cnb-skill.git -g -y
```

该命令**未锁任何版本**（npm 包未写精确版本；`skills add` 的 git 地址不带 tag / 分支 / commit）。
而本项目规则要求 **依赖必须锁定版本并记录来源**（`SECURITY.md` §3 `S-3`、
`.codebuddy/rules/project-conventions/RULE.mdc`「依赖管理」）。
⇒ 接入动作本身就是一次**需要论证的依赖引入 + 供应链决策**，不能以"照官方命令抄一行"落地。

## 2. 决策驱动因素

| 编号 | 因素 | 说明 | 类型 |
| --- | --- | --- | --- |
| D-1 | **可回退性才是分级依据** | 所有者的诉求是"改成事后报告 + 可回退"，那么判据必须写成**可判定**的条件，而不是"感觉安全" | 硬约束 |
| D-2 | **安全基线最高优先级** | `SECURITY.md` §2：最小权限、默认拒绝、fail-secure、可审计。凭据类改动**不可回退** | 硬约束 |
| D-3 | **规则必须可执行（S-8 同族）** | 本项目已多次吃"写着但没执行"的亏（A-11/A-15/A-16/A-17）。新规则若不可核对，等于把问题从"过严"换成"空转" | 硬约束 |
| D-4 | **不可回退操作的拦截层有已登记漏洞** | `pre-commit run --all-files` **只覆盖已跟踪文件**；未 `git add` 的新文件不在扫描范围内 | 硬约束 |
| D-5 | **镜像重建代价** | 任何插在 GB 级模型层**之前**的新层都会使模型层缓存失效，重建约 20~25 分钟 | 硬约束 |
| D-6 | **单人 + 时间预算** | 自动化收益必须真实（减少手工网页操作），否则不值得引入新供应链面 | 偏好 |
| D-7 | **既有"事实执行"** | 2026-09-18 的推送实际以"文件清单 + 改动规模 + 关键点摘要"呈报，**未逐文件全文呈现**（所有者明确指示） | 参考（见 §5.2 第 4 条） |
| D-8 | **不新增"两套口径"** | 密钥扫描只有一份实现（`detect-private-key`）；规则不得在文档里出现互斥的两份表述 | 硬约束 |
| D-9 | **平台自身的能力边界** | `pull_request` 是**不可信事件**（配置取自源分支）⇒ 该事件下**不得使用任何密钥**（`SECURITY.md` `S-5`） | 硬约束 |

## 3. 候选方案

### 方案 A：不接入（只写项目内知识型 Skill）

- 简述：镜像与规则**都不动**；把平台操作继续留给人工网页操作；
  项目内的流程沉淀只走 `.codebuddy/skills/`（见 [ADR-0017](0017-project-level-agent-skills.md)，
  那是本地文件、不需要 CLI）。
- 优点：**不新增任何第三方代码**，供应链暴露面最小；不动规则 ⇒ 无联动更新成本。
- 缺点：① 平台侧操作仍靠手工，且**现状的 `curl` 直调 API 依旧存在却没有统一入口与审计**；
  ② 现行"任何远端写入均需事先批准"的规则**已被实际执行偏离过一次**（D-7）⇒ 继续保留它，
  等于保留一条"写着但打折执行"的规则；③ 放弃了 Skill 机制带来的结构化能力。

### 方案 B：接入 + **按可回退性分级**授权（**推荐**）

- 简述：接入 `cnb-cli` 与官方 `cnb-skill`；把远端授权规则从"一律事先批准"改为
  **按操作的可回退性分级**——可回退类（A）改为"推送后立即报告"，不可回退类（B~F）**全部保持**。
- 优点：① 分类依据是**客观属性**（能否自动、等价、廉价地撤销），可判定、可复核；
  ② 不放松任何不可回退类的拦截 ⇒ 与"安全基线最高优先级"一致；
  ③ 把"其实已经在做的事"（令牌直调 API、摘要式呈报）写进规则，消除规则空转；
  ④ 平台能力可用于日常流程（建 PR、查日志），效率收益真实。
- 缺点：① 新增第三方代码进镜像（供应链面扩大，且版本/许可证/摘要**均未核验**）；
  ② A 类"事后 revert"意味着**坏内容会先到远端**；③ 分级规则**不可由 CI 强制**（见 §6 负面）。

### 方案 C：接入 + 完全取消事先批准（事后报告覆盖所有操作）

- 简述：任何分支、任何操作都只需事后报告；`main`、凭据类、强推同样按此处理。
- 优点：规则最简单，摩擦最低。
- 缺点：**把不可回退的操作也交给了"事后"**。凭据一旦入库，revert **收不回来**
  （远端历史 / 平台缓存 / 他人 fork 均留存）；改写已推送历史会让
  devlog / CHANGELOG 里**逐条写死的提交哈希引用全部失效**（本项目证据链的核心载体）。

### 方案 D：接入 + 规则完全不变

- 简述：装上工具，但远端写入仍逐次事先批准 + 全文呈报。
- 优点：不放松任何东西；无需联动更新文档。
- 缺点：① 自动化收益被"逐次全文审查"吃掉大半（读写都要过闸）；
  ② 继续维持一条**已被实际执行偏离**的规则（D-7）⇒ 规则的权威性继续被消耗，
  而这正是本项目反复记录的失效模式（"写进文档不等于被执行"）。

## 4. 权衡对比

评分 1~5（越高越好），权重体现本项目"安全优先级最高"的既有排序。

| 评估维度 | 权重 | A 不接入 | **B 接入+分级** | C 接入+全取消 | D 接入+规则不变 |
| --- | --- | --- | --- | --- | --- |
| 效率：平台能力带来的手工操作减少 | 3 | 1 → 3 | **5 → 15** | 5 → 15 | 3 → 9 |
| 不可回退类（B/C/D/E/F）是否仍被拦住 | 5 | 4 → 20 | **5 → 25** | 1 → 5 | 5 → 25 |
| 可回退类（A）的摩擦成本（越低越高分） | 4 | 1 → 4 | **5 → 20** | 5 → 20 | 2 → 8 |
| 规则可执行性（是否制造"写着但没执行"） | 4 | 2 → 8 | **5 → 20** | 2 → 8 | 2 → 8 |
| 暴露面（第三方代码进镜像 + 平台写权限） | 3 | **4 → 12** | 2 → 6 | 2 → 6 | 2 → 6 |
| 可审计性（远端操作能否留下可核对记录） | 3 | 1 → 3 | **4 → 12** | 3 → 9 | 4 → 12 |
| 实现与维护成本（越低越高分） | 2 | **4 → 8** | 3 → 6 | 3 → 6 | 3 → 6 |
| **加权合计** | **24** | **58** | **104** | 69 | 74 |

三点必须写清，否则这张表会被误读：

1. **B 胜出的方式不是"放松检查"，而是"把防护集中到真正不可回退的地方"。**
   它在"不可回退类是否仍被拦住"这一维度拿**满分**（与 D 同分），
   靠效率、摩擦成本与规则可执行性拉开差距。
2. **D 被 B 严格支配**（每一项都不优于 B）⇒ 若采纳 B，**D 不需要被重新讨论**。
   D 唯一的优点是"不用改文档"，而"不改文档"在本项目恰恰是一个**负资产**（规则已偏离执行）。
3. **A 的分数不低**（58，高于 C 的 69 之下但差距有限）——它是本方案的**对照组**：
   如果所有者认为"平台能力不值得引入任何新供应链面"，A 是完全正当的选择，
   且**本 ADR 的 §5.2 分级判据在 A 下同样成立**（它是对现状的描述，不是 B 的专属产物）。
   A 的致命弱点不是安全，而是**它保留了规则与执行不一致的状态，并把令牌直调 API 留在暗处**。

## 5. 决策

**决定采用：方案 B —— 接入 CNB 官方 Skills 与 `cnb-cli`，并把远端写入授权改为「按可回退性分级」。**

理由（三条）：

1. **分级的判据是客观属性，不依赖判断者的谨慎程度**。可回退性可以用三条可检验的条件写死
   （§5.2），因此分级本身可复核、可解释，比"一律事先批准"更不容易在执行中走形。
2. **不放松任何不可回退类**：凭据类（C）、改写历史（D）、`main`（B）、`bench/data`（E）、
   配置类变更（F）**全部保持原规则**。安全基线的优先级因此没有被交易掉。
3. **消除规则空转**：把"其实已经在做的事"写进规则（§5.2 第 4 条），
   让授权分级与实际执行一致——这与本项目一贯立场一致（`SECURITY.md` `S-8`：
   声称已生效的缓解措施必须能被实测，**只有文档描述不算缓解措施**）。

> **落地前置条件（硬性）**：本节 §5.3~§5.6 的核验项在完成前，**接入动作不得开始**——
> 依赖锁定、来源与摘要、许可证、`skills -g` 落点、可检查性断言，**逐项都要有结果**。
> 这沿用 [ADR-0015](0015-layering-and-reuse-boundary.md) §7.4 的口径：**已批准 ≠ 已可安装**。

### 5.1 分级授权规则（A~F）

| 类别 | 范围 | 现规则 | **建议新规则** | 变更？ |
| --- | --- | --- | --- | --- |
| **A** | `develop` 与短期分支上的**代码 / 文档 / 测试 / 配置** | 事先审查（全文呈现）后才可推送 | **改为事后报告**：推送后立即报「分支 / 提交列表 / 文件清单 / 验证方式」；不同意则 `git revert` | **是** |
| **B** | `main` | 事先批准 | **保持**（发布线，写权限维持事先批准） | 否 |
| **C** | 任何**凭据类**改动（`*.env` / `*.key` / token / 证书） | 禁止入库 | **保持事先拦截 + 保持禁止** | 否 |
| **D** | 强推 / 删除远端分支 / 改写已推送历史 | 禁止 | **保持禁止** | 否 |
| **E** | `bench/data`（CI 机器数据分支） | 只由 CI 写 | **保持**（人手不得直接提交） | 否 |
| **F** | 新增依赖 / 改 CI 门禁强度 / 改规则本身 | 事先确认 | **保持**（独立规则，不随本次并入 A） | 否 |

**A 类的附加不变量（不变）**：`make check` 全绿是推送前的必要条件；
**事后报告不得替代门禁**，也不得替代 `git-workflow.md` §4 的"提交粒度单一、可回滚"要求。

**事后报告的载体与格式（所有者 2026-09-18 采纳本 ADR 时一并确认）**：

1. **落点**：本次推送所在会话的 `docs/devlog/` **当前篇**新增一条记录，含四项：
   **分支名 / 提交列表（`A..B`）/ 文件清单 / 验证方式（`make check` 结果）**；
2. **时点**：推送后**同一会话内立即**落盘；**不得晚于下一次远端写入**；
3. **可核对性**：核对方式是拿报告里的提交列表与 `git log` 实际区间比对——
   **报告与仓库不一致即视为未报告**；
4. **回退**：所有者不同意时，用 `git revert`（A 类永远是"一次提交量级"的操作）。
   若内容已越过 `develop` 被他人/CI 消费（短窗口），按 §6 的负面条目处置。

> **本规则的已知边界（必须写进规则本身，而不是只写在 ADR 里）**：
> **CI 看不到"是否事先批准"，也看不到"是否事后报告"** ⇒ A 类规则的**唯一护栏是事后可核对**，
> 属"流程纪律"而非"机制"。按威胁模型的口径（`README.md` §4.1），
> 这类缓解只能记为**部分缓解**，**不得**被表述为"已被机制保障"。

### 5.2 论证：为什么 A 类可事后报告，而 C 类不可

**判据（本文定义，供规则正文引用）**：

> 一个**已推送**的变更属于「**可回退**」，当且仅当同时满足三条：
> **(1)** 存在一条**语义等价**的逆操作（`git revert` 或等价手段）；
> **(2)** 逆操作的代价与**一次普通提交**同量级；
> **(3)** 逆操作后，该内容**不残留于任何其它可达载体**（远端对象库、平台缓存、他人克隆/fork、CI 产物）。

逐类对照：

| 类别 | 判据 (1) | 判据 (2) | 判据 (3) | 结论 |
| --- | --- | --- | --- | --- |
| **A** 代码/文档/测试/配置 | ✅ | ✅ 一次 `revert` | ✅（内容本身**不机密**，残留不构成损失） | **可回退** ⇒ 事后报告足够 |
| **C** 凭据类 | ✅ | ✅ | ❌ **revert 只在新提交里删掉它，远端历史 / 平台缓存 / 他人 fork 均留存** | **不可回退** ⇒ 必须事先拦截 |
| **D** 改写已推送历史 | ❌ 逆操作不存在（改写本身消灭被引用的对象） | — | — | **不可回退** |
| **B** `main` | ✅ | ❌ 撤销会改变"已发布"的语义（已打标签的版本只能发新版本，不能"撤回"） | — | 不列为可回退 ⇒ 保持事先批准 |
| **E** `bench/data` | ❌ 数据分支**禁止 force**，只能前进 | — | ❌ 坏点永久污染"同签名序列"（可比时间序列是本项目目前唯一的趋势数据） | 不适用 ⇒ 保持"只由 CI 写" |
| **F** 依赖 / 门禁强度 / 规则 | — | — | — | 不是 git 操作，属**配置变更** ⇒ 独立规则 |

**C 类为什么连"事先报告 + 自动拦截"都不够**（这是本 ADR 最关键的一段）：

- 唯一能**自动**拦住凭据入库的本地检查是 `pre-commit` 的 `detect-private-key`，
  它已由三处防线复用（提交时钩子 / `make check` 的 `security-secrets` / CI 具名 `secret-scan`）；
- **但它有已登记的漏洞**：`pre-commit run --all-files` 走 `git ls-files`，
  因此 **只覆盖已跟踪文件**——**未 `git add` 的新文件不在扫描范围内**
  （[`devlog 0014`](../devlog/0014-2026-09-18-威胁模型与安全修复.md) §5 残余 2、
  [`security-scan-gate-config.md`](../engineering/security-scan-gate-config.md) §7 边界 1）；
- 🔎 **推论（本 ADR 的核心）**：**改 A 类是安全的，改 C 类不是**——
  两者用的是同一套"事后"思路，但 A 类的失败模式是"可撤销一次提交"，
  C 类的失败模式是"一个永久扩散的机密"。**把这两类并进同一条规则，就是把不可逆风险
  交给一个已知有覆盖漏洞的检查。**

**第 4 条理由（回应"现行规则已被实际执行偏离"这一事实）**：

2026-09-18 的一次推送，依据是所有者两次明确指示"可以推送"，
而呈报形式是**文件清单 + 改动规模（17 个文件、+907/−43）+ 关键点摘要**，**未逐文件全文呈现**
（[`devlog 0013`](../devlog/0013-2026-09-18-一致性核查与地基修复.md) §3 的"一处流程偏差"）。
⇒ 现行规则的两阶段要求在**真实执行中被跳过了一次**。这不构成"规则错了"，
但它说明**规则与实际执行已经不一致**；本次分级的价值之一即是把这个不一致消掉
（要么写进规则，要么明确例外），而不是继续留着一份"打折执行"的文本。

### 5.3 接入范围与镜像层序

**接入范围（建议；版本、许可证与落点已于 2026-09-18 实测核验，见 §10）**：

| 项 | 装什么 | 装在哪 | 理由 |
| --- | --- | --- | --- |
| CLI | `@cnbcool/cnb-cli@1.15.36`（**精确版本已核验**；MIT） | 镜像全局（`npm install -g`） | 提供 `cnb` 命令，是调用平台 OpenAPI 的统一入口 |
| 官方 Skill | `cnb/skills` 的 `cnb-skill` 中的 **5 个子集**（`cnb-api`、`cnb-docs`、`cnb-code-review`、`cnb-pr-analysis`、`cnb-pipeline`），**钉 commit**（落地时按取到时的 SHA 钉死并登记摘要） | 全局：canonical 落点 `~/.agents/skills/<name>/`，并建 `~/.codebuddy/skills/<name>` **符号链接**指向它 | 把平台 API 用法结构化，避免每次手写 `curl` |
| 项目内 Skill | 本仓库 `.codebuddy/skills/` 下的 4 个 | **仓库内**（随仓库走） | 见 [ADR-0017](0017-project-level-agent-skills.md)；**不依赖镜像** |

> **子集裁决（2026-09-18）**：官方仓库 `cnb/skills/cnb-skill` 实含 **11 个 Skill**
> （`cnb-api`、`cnb-code-commit`、`cnb-code-review`、`cnb-docs`、`cnb-npc-search`、
> `cnb-pipeline`、`cnb-pr-analysis`、`cnb-repo-knowledge-base`、`cnb-tapd-resource-fetcher`、
> `cnb-text-path-converter`、`cnb-upload-attachment`，共 **11 个**，**不是起草时以为的 1 个**）。
> 本项目**只装 5 个**（见上表）；排除 `cnb-code-commit`（它引导建 PR，与项目 PR 模板 /
> Conventional Commits 门禁**重叠**，属"两处口径"），其余 5 个本项目用不上。
> 理由：官方 Skill 的 `description` 是**常驻上下文**，**11→5 可将常驻量减半**。

> **分工（不得重复）**：官方 `cnb-skill` 管"**调平台 API**"；
> 项目内的 `repo-ci-conventions`（ADR-0017；**2026-09-18 由 `cnb-pipeline` 改名**——
> 因官方 Skill 集合中已存在同名 `cnb-pipeline`）只管"**本仓库 `.cnb.yml` 的约定**"。
> 两者**不得互相复述**，各自在文首放一行指向对方。

**层序安排（本 ADR 对 `.ide/Dockerfile` 的唯一要求）**：

`.ide/Dockerfile` 的现状（2026-09-18）：第 5 阶段 = CodeBuddy；第 10~12 阶段 = **GB 级资产下载**
（模型 / 参考仓库 / 基准集）；第 13 阶段 = 构建期自检。文件内已载明两条**实测代价**：

- GB 级下载必须靠后放，否则"改文档 / 改设置都会触发重新下载"；
- 脚本的 `COPY` 位于模型下载层**之前** ⇒ **改动脚本本身也会使模型层失效（约 20~25 分钟）**。

⇒ **建议：把新阶段插入在第 12 阶段之后、第 13 阶段（自检）之前。**

理由：前序层（含 GB 级第 10~12 阶段）的输入完全不变 ⇒ **命中 Docker 层缓存**，
后续重建只需重跑"新阶段 + 自检"两层；同时能**复用既有的"构建期自检"模式**
（该模式的两条来历正是"静默失败"事故：CodeBuddy 漏装、扩展在 Open VSX 上 404）。

**明确不要做的事**：把新阶段插在第 10 阶段之前（或并入第 5 阶段）——
那会让模型层缓存失效，每次改动都要付 20~25 分钟。

> **本判断的性质**：它是**基于 Docker 层缓存语义的推论**，依据是 `.ide/Dockerfile`
> 自身注释记录过的两次实测（缓存失效的确切触发条件）。
> ⚠️ **在本平台未实测**（本 ADR 不含任何构建动作）⇒ 其验证方式见 §7 `V6`（观测一次重建耗时）。

### 5.4 依赖锁定与供应链

**问题**：官方命令未锁版本（§1.3），与本项目"依赖必须锁定版本"冲突。

**候选与处置（建议）**：

| # | 手段 | 可行性 | 建议 |
| --- | --- | --- | --- |
| L1 | npm 精确版本：`npm install -g @cnbcool/cnb-cli@1.15.36 skills@1.5.0` | ✅ 标准能力 | **必做**。**已核验（2026-09-18）**：`@cnbcool/cnb-cli` = **1.15.36**；`skills` 最新 = **1.7.0**，但受 node 版本约束（见下"新阻塞"）⇒ 实际钉 **`skills@1.5.0`** |
| L2 | 官方 Skill 钉 commit：`npx skills add <url>#<sha>`（或等价参数） | ❌ **不可行（2026-09-18 实测）**：`skills add` 的 help **无 ref / commit 选项**；`pkg@X` 的 `@` 是**技能名**、不是 ref | **改走 L3** |
| L3 | 退路：`git clone <url>` → `git checkout <sha>` → 落到 `skills` 的全局目录 | ✅ **落点已实测**：canonical `~/.agents/skills/<name>/` + `~/.codebuddy/skills/<name>` 符号链接 | **采用**；必须**复刻两层结构**（只落一层则代理侧不可见） |
| L4 | **摘要登记**：把包与 Skill 仓库的摘要记进 `.ide/assets/` 下的清单，构建期校验、失败即中断 | ✅ 项目已有成熟模式（模型 / 基准资产） | **推荐采用**，复用 `.ide/fetch-assets.sh` 的校验机制，**不引入第二个真源** |

⇒ **推荐组合：L1 + L3 + L4**（L2 已实测不可行）。

> **新阻塞（2026-09-18 实测）**：`skills@1.7.0` / `1.6.0` 要求 **`node ≥ 22.20.0`**，
> 而镜像实为 **node 20.20.2** ⇒ 安装报 **`EBADENGINE`**。所有者裁决：**钉 `skills@1.5.0`**
> （engines `>=18`），并**不动 `.ide/Dockerfile` 第 3 阶段**（避免 GB 级模型层缓存失效）。

> **Skill 仓库可钉 commit（2026-09-18 实测）**：`cnb-skill` 在取到时的 HEAD =
> `bcd25870ed100db43c257c3c5feca6c776645914`。⚠️ **HEAD 会漂** ⇒ 落地时按**取到时的 SHA
> 钉死**并把摘要登记进 `.ide/assets/` 清单，**不得**把本行的 SHA 当作长期常量。

**若某项无法锁定**：**显式登记为风险**（进本 ADR 的 §10 未验证项与 §6 风险表），
**不得**以"官方就是这么装的"为由跳过；也不得在未锁定的情况下对外声称"供应链已受控"。

**供应链要求（逐条对齐 `SECURITY.md` §2.7 / §3 `S-3`/`S-4`）**：

| 要求 | 本项目怎么做 |
| --- | --- |
| 来源可追溯 | 记录**来源 URL + 组织**（`cnb.cool` 的官方组织 `cnb/skills`；npm 包 `@cnbcool/cnb-cli`），写进 `.ide/assets/` 清单的注释与 Dockerfile 注释 |
| 固定版本 / 摘要 | L1 + L3 + L4；Skill 仓库钉 commit（落地时按取到的 SHA） |
| 许可证 | ✅ **已核验（2026-09-18）**：`cnb/skills` 仓库与 `@cnbcool/cnb-cli` 均为 **MIT**，与本项目 Apache-2.0 兼容 |
| 体积 | ✅ **已核验（2026-09-18）**：`cnb-cli` 解包 **1,413,046 B ≈ 1.35 MB**、**无传递依赖**；`skills` 解包 **≈578 KB**、传递依赖 `tar ^7.5.20` + `yaml ^2.8.3` |
| 二次真源 | 校验逻辑**复用** `fetch-assets.sh`；版本号**只在清单里写一次**，Dockerfile 从清单取值（或注释指向清单） |

> **一条容易被忽略的供应链面**：**Skill 内容本身是"指令"**。
> `description` 常驻上下文、`SKILL.md` 在触发时被加载 ⇒ 官方 `cnb-skill` 的文本会**进入代理的
> 指令面**。因此"从 cnb.cool 官方组织拉取"这一事实**只能降低**风险，**不能消除**它：
> 仍需固定 commit（防静默变更），并且**不得**让 Skill 内容覆盖项目自己的规则
> （项目内 Skill 与官方 Skill 的边界见 §5.3 的"分工"）。
> 这条同时进威胁模型待办（§5.7）。

### 5.5 令牌作用域

**已核实（CNB 文档「访问令牌」页，2026-09-18 访问）**：

- 令牌创建时可配置 5 项：**令牌名称 / 到期时间 / 使用范围 / 授权范围 / 常见场景**；
- **默认权限是"最小"的**：**公开**的组织 / 仓库 / 制品库 / 任务集默认**只读**；
  **私有**仓库 / 制品库默认**无权限**；账号相关默认**无权限**；
- CI 场景由流水线注入**临时令牌**，**构建结束后自动销毁**；
- 代码仓库 / 制品库认证方式：用户名固定 `cnb`，密码填访问令牌。

⇒ **收窄方案（建议，可立即执行）**：

| # | 动作 | 理由 |
| --- | --- | --- |
| T1 | 为"代理日常开发"单独建**受限令牌**：只勾选本仓库、只勾必要范围、设**较短到期时间** | 最小权限；与"发布 / 管理"用途的令牌分离 |
| T2 | 先套用"常见场景"预设，再**逐项删减**到最小集（默认拒绝） | 令牌的默认值是"只读 / 无权限"⇒ 删减是顺着默认值走 |
| T3 | **轮换本会话已误显示的令牌**：作废旧令牌、新建并替换注入处 | 已发生一次误显示；凭据一旦可能外泄即应视为已泄露 |
| T4 | 令牌**只经环境变量注入**，不入库、不入日志、不进错误信息 | 既有规则（`SECURITY.md` §3、`T-08` 的凭据 canary 已覆盖） |

**未核实（不得编造，全部进 §10）**：具体授权项的**名称**（例如 `repo-code:rw` 这类字符串
**未出现在** CNB 文档页上；`repo-code:rw` 是本项目 `benchmark-automation.md` §7 的**项目侧观察**，
不是平台文档口径）；`cnb-cli` / `skills` 各自所需的**最小 scope**；
令牌**撤销 / 轮换**的操作入口（文档页未覆盖）。

> **无论 scope 细节如何都成立的结论**：令牌的存在本身就是"平台写权限"的载体，
> 而本项目**已经**把它注入开发环境与基准流水线。
> ⇒ **接入 CLI 没有新增一类权限，只是让既有权限更容易被使用**。
> 因此 T1~T4 应当作为**独立的安全动作**推进，**不应被"是否接入 CLI"这一决策遮盖**。

> **回填（2026-09-18 实测｜只补事实、不改结论）**：接入范围与版本已核验（见 §5.3 / §5.4），
> 但 `cnb-cli` / `skills` 所需的**最小 scope** 仍未核验 ⇒ `U8` **保持【待核验】**；
> `U7` / `U9`~`U12` 同样**保持原状**。
> **不得**由"已确定要装什么"推断"权限已收窄"——`T1`/`T2`/`T3` 仍是**独立且未完成**的安全动作。

### 5.6 可检查性（`SECURITY.md` `S-8`）

`S-8` 要求"**声称已生效的缓解措施必须能被实测**"。本次要声称三件事，逐条给检查方式：

| 声称 | 可检查方式 | 可否由 CI 断言 |
| --- | --- | --- |
| `cnb-cli` 真的可用 | 构建期与运行期 `cnb --help` 退出码 0；**`cnb --version` 已实测存在**（返回 `1.15.36`），可一并断言并与清单版本比对 | ✅（构建期自检 + `post-build-checklist`） |
| 官方 Skill 真的装了 | 落点目录**非空**（路径**已实测**：canonical `~/.agents/skills/<name>/`，见 §10 `U3`）；若 `skills` CLI 提供列表子命令则用它（**子命令名未验证**） | ✅（构建期自检） |
| **分级授权规则真的在运行** | 下一次 A 类推送后，`docs/devlog/` 当前篇**存在**对应报告，且其提交列表与 `git log` 区间**一致** | ❌ **不能**：CI 无法判定"是否事先批准 / 是否事后报告" ⇒ 只能**事后人工核对**（§5.1 的已知边界） |
| 项目内 Skill 结构合法 | 建议落 `tests/unit/` 断言：目录 / `SKILL.md` 存在、frontmatter 含 `name` 与 `description`、`name` 与目录名一致 | ✅（见 ADR-0017 §7） |

> **诚实结论（勿美化）**：**"Skill 真的被加载"与"A 类的授权纪律被遵守"这两件事，
> 在仓库内不可观测** ⇒ 它们**不能**被写成"satisfied by CI"，只能写成"由人工在会话内核对"。
> 这与 `S-8` 存在**张力**，必须留在规则与 ADR 里，而不是用"已检查"四个字盖过去。

## 6. 后果

### 正面

- **授权规则从"一刀切"变为"可判定的分级"**：判据是"可回退性"这一客观属性，
  可写、可解释、可复核，比依赖谨慎程度的口头规则更稳。
- **不可回退类全部保持**：凭据、改写历史、`main`、`bench/data`、配置类变更一处都没放松，
  且新增 `S-9` 把这条界线写成可引用的硬规则。
- **消除规则空转**：现行"两阶段全文审查"实际已被跳过一次（§5.2 第 4 条），
  本次把它改成与实际执行一致的规则，并附可核对的报告格式。
- **平台操作有了统一入口**：`cnb` 命令替代散落的 `curl`，读操作的记录与权限更好收敛。

### 负面（必须承认）

| # | 负面 | 说明 |
| --- | --- | --- |
| 1 | **A 类"事后 revert" = 坏内容先到远端** | 短窗口内 CI 可能已消费它、另一会话可能已 `git pull` ⇒ 恢复代价不是"一次提交"，而是"一次提交 + 下游已受影响的处置"。**本 ADR 不主张这个窗口可忽略**，只主张它在 A 类上**可接受**（内容不机密、可由后续提交纠正） |
| 2 | **分级规则不可由 CI 强制** | CI 看不到"是否事先批准 / 是否事后报告"⇒ 唯一护栏是事后核对。按威胁模型口径，这是一条**流程纪律**，只能记为**部分缓解**，**不得**被宣传为机制 |
| 3 | **新增第三方代码进镜像** | 精确版本、Skill 仓库 commit、许可证、摘要、`skills -g` 落点——**起草时五项均未核验**；2026-09-18 已实测核验四项（版本 `cnb-cli@1.15.36` / `skills@1.5.0`、许可证 MIT、落点 `~/.agents/skills/`、体积与传递依赖，事实回填 §5.3/§5.4/§10）。仅 **摘要校验（L4）** 尚待落地实现 ⇒ 采纳时它**仍是敞口**；§5.3 已把前置条件写死 |
| 4 | **Skill 文本进入指令面** | 官方 Skill 的 `description` 常驻、`SKILL.md` 触发时加载 ⇒ 第三方文本成为代理的指令来源。缓解是"钉 commit + 项目内 Skill 不复述规范"，**不是**"来源可信所以无害" |
| 5 | **联动面大（17 处）** | 任一处漏改就出现"同一事实两份表述"。本项目已有多起同类事故（A-3/A-14/A-16/A-17）⇒ §5.8 的反向搜索是**必需动作**，不是可选动作 |
| 6 | **首次仍需一次真实重建** | 改动 `.ide/Dockerfile` 与（可能）`build.by` 会触发构建；§5.3 的层序安排只降低**后续**改动成本 |
| 7 | **令牌轮换会中断现有自动化** | T3 是所有者动作；轮换需同步更新注入处（开发环境 / CI / 本地），**在替换完成前不得宣布"已轮换"** |
| 8 | **`bench/data` 与 `main` 的写操作并未因此变简单** | 这是刻意的：本 ADR 不追求"全流程自动化"，只追求"把防护集中到不可回退处" |

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 未锁版本的第三方代码进镜像 | 供应链投毒 / 静默变更 | §5.4 的 L1+L2+L4；**许可证与摘要未补齐前不得进镜像** |
| Skill 文本覆盖项目规则 | 代理按第三方文本行事 | 项目内 Skill 不复述规范、一律指向权威源（ADR-0017 §5.1）；官方 Skill 只提供 API 用法 |
| A 类事后报告被漏写或打折 | 分级规则退化为空转 | 报告的**载体 + 时点 + 核对方式**写死在 §5.1；`S-9` 把"不可回退类必须事先拦截"与 A 类分开；**并明确登记本规则靠人**（不假装它是机制） |
| 文档联动漏改 | 出现互斥的两份规则 | §5.8 的反向搜索（三条旧措辞）；建议进一步落一条机器检查（见 §8 待办 7） |
| 令牌权限过宽 | 一次误用即可能改写平台状态 | T1/T2 的受限令牌 + T3 轮换 + T4 只经环境变量 |
| 层序安排判断错误 | 每次改动重建 20~25 分钟 | §7 `V6` 观测一次重建耗时；若超 20 分钟 ⇒ 回到本 ADR 重评层序 |

**复核时间点**：

- **接入后的第一次 A 类推送**：检查 `V7`（这是分级规则唯一的实测机会）。
- **接入后 30 天**（与 `ADR-0013` §7、`ADR-0015` §7.5 的观察项同期）：
  检查是否出现过"A 类推送但无报告""报告与仓库不一致"。
  **若出现过 ⇒ 说明该分级不可执行**，应回到"事先批准"或**补机器检查**，并**新增 ADR**（不改写本文）。
- **镜像重建一次之后**：检查 `V6`。
