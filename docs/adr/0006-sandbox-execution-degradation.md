## 1. 背景与问题

`REQ-SEC-05` 要求"命令/代码在受限环境执行（文件/网络/资源限制）"，
验收标准是"越界文件访问与未授权出站被阻止"。

原定的沙箱路线是**用户态命名空间隔离**：主方案 `bubblewrap`，备选 `firejail`
（见 SRS §9 环境约束与 §11 复用清单）。该路线建立在一个**未经验证的假设**上：

> A-2：CNB 容器内可使用 nsjail / bubblewrap / firejail。

2026-09-15 在真实 CNB 开发环境（8 核 / 16 GiB，`runner.cpus: 8`）中实测，
该假设**不成立**，且失败方式比预期更危险——**其中一个方案是静默失效（fail-open）**。
本 ADR 记录实测证据并定案替代方案。

## 2. 决策驱动因素

| 因素 | 说明 | 类型 |
| --- | --- | --- |
| 安全基线（最高优先级） | `SECURITY.md` 要求**失败即拒绝（fail-secure）**；静默放行视为缺陷 | 硬约束 |
| 安全是主线之一 | 沙箱是本项目"安全层"的执行侧支柱，不是可选项 | 硬约束 |
| 开发环境能力受限 | CNB 容器**禁止创建任何命名空间**（实测证据见 §4） | 硬约束 |
| 交付形态是 CLI + 目标设备 | 目标设备（Linux 桌面 / 手机 Termux）能力未知，可能同样受限 | 硬约束 |
| 不依赖 KVM | microVM 路线已在 SRS §6.2 的 Won't 列表中 | 硬约束 |
| 单人、2~3 个月 | 方案必须能拆分、能逐档实现、能独立验证 | 硬约束 |
| 可演示、可测试 | 沙箱必须能在**当前可用的环境**中被测试，否则是纸面防护 | 硬约束 |

## 3. 候选方案

### 方案 A：继续绑定命名空间沙箱（bwrap / firejail），仅在 CNB 之外开发测试

- 简述：接受"CNB 内无法测试沙箱"，把沙箱开发与验证放到本地 VM（VMware + Ubuntu 22.04）。
- 优点：隔离强度最高；复用成熟项目；不改变原设计。
- 缺点：**开发环境（主环境）里无法验证安全需求**，REQ-SEC-05 与 REQ-SEC-09
  在 CNB 的 CI 中不可回归；安全测试与日常开发环境长期分叉。

### 方案 B：分层沙箱抽象 + 能力探测 + fail-secure 降级（**采纳**）

- 简述：定义统一的 `SandboxBackend` 接口，提供**至少两档实现**：
  - `NamespaceBackend`：bwrap / firejail，在能力可用时使用（**目标档位**）；
  - `RestrictedProcessBackend`：**始终可用**的降级档——不经 shell 的子进程 +
    资源限制（CPU 时间、地址空间、文件大小、进程/文件描述符数）+ 路径白名单
    （规范化 + 前缀校验，防目录穿越）+ 网络默认拒绝 + 结构化审计 + 危险操作人工确认。
  - 启动时执行**有效性自检（capability probe）**：不仅看退出码，还要**实际尝试越界
    操作并确认其被阻止**（如尝试出站、尝试写白名单外路径）。任一探针未通过即降级到下一档。
- 优点：安全语义在接口层统一；**当前环境即可测试降级档**；能覆盖能力未知的目标设备；
  无新依赖（`resource`、`subprocess` 均为标准库）。
- 缺点：降级档的隔离强度**显著低于**命名空间隔离（无法真正隔离网络与文件系统，
  只能"拦截 + 审计 + 拒绝"）；实现与测试工作量增加。

### 方案 C：容器内嵌套容器 / microVM（Docker-in-Docker、E2B、microsandbox）

- 简述：在容器内再起一个容器或 microVM 作为沙箱。
- 优点：隔离强度最高，语义最清晰。
- 缺点：**依赖 KVM 或特权容器**，与"不依赖 KVM"硬约束冲突；体积与冷启动代价大；
  CNB 容器内是否可用同样未经验证。

### 方案 D：不做沙箱，仅靠权限模型 + 人工确认

- 简述：删除执行隔离，所有危险操作由用户显式确认。
- 优点：实现成本最低。
- 缺点：**与项目定位直接冲突**——安全层是两条主线之一；"人工确认"在批量/自动化
  场景下会被用户点击成习惯（告警疲劳），不构成有效防护。

## 4. 权衡对比

### 4.1 实测证据（2026-09-15，CNB 开发环境）

| 探针 | 命令 | 结果 | 判定 |
| --- | --- | --- | --- |
| bwrap 基本隔离 | `bwrap --bind / / --tmpfs /tmp --proc /proc --dev /dev /bin/echo sandbox-ok` | `bwrap: Creating new namespace failed: Operation not permitted` | ❌ **硬失败**（fail-secure，行为正确但不可用） |
| firejail 基本执行 | `firejail --quiet --noprofile /bin/echo sandbox-ok` | 输出 `sandbox-ok`，退出码 0 | ⚠️ 表面成功 |
| firejail 网络隔离 | `firejail --quiet --noprofile --net=none curl https://example.com` | **`HTTP 200`**（网络未被阻断） | ❌ **静默失效** |
| firejail 诊断输出 | 去掉 `--quiet` 重跑 | `Warning: an existing sandbox was detected. /bin/sh will run without any additional sandboxing features` | ❌ 根因确认 |
| 网络接口 | 沙箱内 `ls /sys/class/net` | 与宿主一致（`eth0 lo`） | ❌ 未隔离 |
| user namespace | `unshare --user --map-root-user echo ok` | `unshare failed: Operation not permitted` | ❌ |
| network namespace | `unshare --net echo ok` | `unshare failed: Operation not permitted` | ❌ |
| mount namespace | `unshare --mount echo ok` | `unshare failed: Operation not permitted` | ❌ |
| 内核参数 | `cat /proc/sys/user/max_user_namespaces` | `2147483647`（**非**限制来源） | — |

**根因**：`max_user_namespaces` 数值很大，但 `unshare` 全部返回 `EPERM`，
说明限制来自**容器的 seccomp / 安全配置**（拦截了相关系统调用），而非内核参数。
在此前提下，**任何基于命名空间的用户态沙箱都不可能生效**。

**关键教训（安全）**：`firejail` 的失败方式是 **fail-open** ——
退出码为 0、标准输出正常、仅在非 `--quiet` 时才打印一行警告。
若只以"命令是否成功"判断沙箱可用性，会得出"沙箱可用"的**错误结论**，
从而让整套安全设计建立在幻觉之上。这一条已上升为通用规则（见 §5.2）。

### 4.2 加权矩阵

权重（1~5，越高越重要）：安全强度 5、可测试性 5、可完成性 4、与硬约束一致性 5、复现成本 3。

| 维度 | 权重 | A | B（采纳） | C | D |
| --- | --- | --- | --- | --- | --- |
| 安全强度 | 5 | 5 | 3 | 5 | 1 |
| 在当前环境可测试 | 5 | 1 | **5** | 1 | 5 |
| 可完成性（单人 2~3 月） | 4 | 4 | 4 | 1 | 5 |
| 与硬约束一致（无 KVM/无特权） | 5 | 5 | 5 | 1 | 3 |
| 实现与复现成本（越低越高分） | 3 | 4 | 3 | 1 | 5 |
| **加权合计** | | 89 | **102** | 64 | 71 |

> A 与 B 的差距主要来自"在当前环境可测试"这一项。安全需求若无法被**持续回归**，
> 会随时间腐化；这是本项目把可测试性权重设为 5 的原因。

## 5. 决策

**决定采用：方案 B —— 分层沙箱抽象 + 能力探测 + fail-secure 降级。**

理由：

1. **安全基线要求 fail-secure**，而实测表明"是否真的隔离"必须由**主动探针**判定，
   不能由工具退出码判定；分层抽象把这一判定收敛到唯一位置。
2. **当前开发环境无法提供命名空间隔离**，若无降级档，`REQ-SEC-05` 与 `REQ-SEC-09`
   在本环境将**无法被测试与回归**，安全需求会退回纸面。
3. 降级档只用标准库（无新依赖），且其"拦截 + 审计 + 确认"语义同时适用于
   能力未知的目标设备，**不把产品正确性绑定到宿主能力**。

### 5.2 派生硬规则（写入安全基线）

- **规则 S-1**：任何沙箱/隔离后端都必须实现**有效性自检探针**（尝试越界操作并
  确认被阻止），探针未通过即视为**不可用**并按 fail-secure 降级。
  **禁止**以"命令退出码为 0"作为隔离生效的判据。
- **规则 S-2**：降级发生时必须**结构化记录**（当前档位、降级原因、未满足的隔离维度），
  并在审计日志与用户可见输出中显式提示——**禁止静默降级**。

### 5.3 档位定义（接口语义）

| 档位 | 后端 | 隔离维度 | 可用条件 |
| --- | --- | --- | --- |
| L2 | `NamespaceBackend`（bwrap / firejail） | 文件系统 + 网络 + PID + 资源 | 探针全部通过（**当前 CNB 环境不可用**） |
| L1 | `RestrictedProcessBackend` | 资源限制 + 路径白名单 + 网络默认拒绝 + 审计 + 人工确认 | 始终可用（**当前实际生效档位**） |
| L0 | 拒绝执行 | — | L1 探针亦未通过时（当前不会发生） |

## 6. 后果

### 正面

- 安全需求在**当前环境即可测试与回归**，不再与开发环境分叉。
- "隔离是否生效"由探针回答，消除了 fail-open 类缺陷（本次已实际捕获一次）。
- 降级档只用标准库，不增加依赖与体积，符合 SRS 的资源与可移植性约束。
- 档位语义统一后，目标设备（手机 / Termux）复用同一条路径，无需另写一套。

### 负面（必须填写）

- **隔离强度下降**：L1 档无法真正阻止网络出站与文件系统越界，只能"在第 N 层拦截"。
  这意味着在此环境下的安全断言是**中等强度**的，不能对外宣称"命令被隔离执行"。
- **实现与测试成本上升**：需要抽象层、探针、两档实现与各自的安全测试（含对抗性用例）。
- **可演示性受限**：无法在本环境演示"越界被内核阻止"，只能演示"越界被拦截并审计"。
- 需要在目标设备上补充 L2 档的真实验证，该验证**尚未进行**【待验证】。

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| L1 被误当作"完整沙箱"宣传 | 高 | 在 SRS 与设计中显式标注隔离强度档位；输出与文档中禁止使用"已隔离"表述 |
| L1 的路径白名单被绕过（符号链接 / `..`） | 高 | 路径规范化 + 前缀校验 + **符号链接解析后**再校验；配套对抗性测试（`REQ-SEC-09`） |
| L2 档在目标设备上同样不可用 | 中 | 该风险正是分层设计的目的；届时产品按 L1 运行，并记录降级 |
| 探针自身误判（假阳性"可用"） | 高 | 探针必须包含**正向与负向**两类断言；负向断言（越界应被拒）未通过即判不可用 |

## 7. 验证方式

1. **立即**：L1 档在 CNB 环境可运行，且探针能正确报告当前为 L1、L2 不可用
   （探针在本 ADR 中已有可用形式：`unshare --net`、`bwrap ...`、`firejail --net=none` + 出站尝试）。
2. **对抗性测试**：为 L1 编写攻击者视角用例——目录穿越（`../../etc/passwd`）、
   符号链接逃逸、绕过白名单的网络出站；要求**全部被拦截并留有审计记录**。
3. **M2 里程碑**：`REQ-SEC-05` 的验收在 L1 档下可复现通过；
   若届时仍无法通过，触发重新评估并新增 ADR。
4. **目标设备阶段**：在具备命名空间能力的设备（本地 Ubuntu VM / Termux）上运行同一探针，
   确认 L2 档可被激活。若不可激活，则本决策的"目标档位"需要修订并新增 ADR。
