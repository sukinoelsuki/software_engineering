## 1. 背景与问题

项目方向为**原生智能系统**，主线为**系统安全** + **模型/系统加速与优化**，
要求在一个前沿开源项目上做增量研发，并交付**完整、规范、便捷、安全、高效**的软件。

需要决策：**选哪个开源项目作为 base，以及在其之上做什么具体增量。**

完整的候选调研、评估标准、对比矩阵与推荐理由见
[提案 `0001-base-project-selection.md`](../proposals/0001-base-project-selection.md)。
本文只记录结论与约束，不重复论证过程。

## 2. 决策驱动因素

| 因素 | 说明 | 类型 |
| --- | --- | --- |
| 单人 2~3 个月交付 | 代码库规模、上游门槛必须可控 | 硬约束 |
| 安全 × 性能双主线 | 两个维度需在同一系统内自然发力 | 硬约束 |
| 硬件约束未确认（C-6） | 是否支持 KVM / 是否有 GPU 影响候选可行性 | 硬约束 |
| 课程要求可能变化（C-10） | 架构需可裁剪，Must 级需求优先 | 硬约束 |
| 纯 Python 生态 | 自身工程能力匹配度高，学习成本可控 | 偏好 |
| 系统功底锻炼 | 希望触及调度、隔离、内存、并发 | 偏好 |

## 3. 候选方案

| 方案 | 简述 | 加权得分 |
| --- | --- | --- |
| **A. Agent OS 内核（AIOS）** | 在智能体内核上做能力权限模型 + 调度/缓存优化 | **4.75** |
| B. Agent 沙箱运行时（E2B / microsandbox） | microVM 隔离 + 冷启动优化 | 4.38（强依赖 KVM） |
| C. Agent 安全网关 | 工具调用策略引擎 + 注入防护 | 4.40 |
| D. 推理引擎安全与加速（vLLM / SGLang） | 多租户 KV 隔离 + 推理加速 | 3.80（需 GPU） |
| E. 记忆 OS（MemOS / Letta） | 记忆投毒防御 + 检索加速 | 4.43 |

## 4. 权衡对比

详见[提案第 6 节](../proposals/0001-base-project-selection.md#6-对比矩阵)。

关键结论：

- **A 在"契合度 + 可行性 + 工程规范空间"三项上同时领先**，且无硬件依赖。
- **B 的上限最高**（系统功底锻炼最强），但**强依赖 KVM**，属条件性可行。
- **E 与 A 同谱系**，是 A 的主要备选，且二者不互斥（记忆管理器是内核组件）。
- **D 因需 GPU 且代码库庞大，可行性不足**，本轮排除。

## 5. 决策

### 5.1 决策结论（2026-09-14，已接受）

**决定采用：以「低资源受限环境下的能力感知智能体运行时」为项目主线，
以自研 Harness 与安全层为核心增量，复用成熟开源组件作为积木。**

即采纳[提案 0003](../proposals/0003-lowspec-coding-agent.md) 的产品定义；
完整需求见 [`docs/requirements/srs.md`](../requirements/srs.md)。

**产品一句话**：让能力有限的模型，在资源与网络受限的环境中，也能被安全地用于完成力所能及的工作。

**本项目要回答的核心问题（两条论点）**：

1. **Harness 必须与模型能力协同设计**——不能把为大模型设计的 Harness 直接套到小模型上
   （工具集、提示结构、验证强度、重试预算都应按能力档位调整）。
2. **安全层必须"能力边界感知"**——目标不是让模型不犯错，而是
   ① 不让错误造成不可逆的伤害（执行侧权限与沙箱）；
   ② 超出能力边界时主动停下（输出侧拒答与转人工）。

**自研增量（约 30%）**：

| # | 模块 | 定位 |
| --- | --- | --- |
| 1 | 本地 + 云端统一模型层与模型能力探测 | 基础 |
| 2 | **能力自适应 Harness**（工具裁剪 + 提示分级） | **核心论点** |
| 3 | **能力边界感知的安全层**（权限 + 沙箱 + 审计 + 拒答） | 安全主线 |
| 4 | 上下文效率引擎（仓库索引 + 压缩 + 懒加载） | 效率主线 |
| 5 | 领域包（Domain Pack）机制 | 扩展性 |

**决策理由**：

1. **产品形态完整**——安装、配置、模型管理、交互、权限确认、审计、评估、发布齐备，
   软件工程全链路都能体现。
2. **安全从"附加"变为"内在需求"**——在本地执行 AI 生成的代码天然构成「致命三要素」
   （私有数据 + 不可信内容 + 对外通信），安全是准入门槛而非装饰。
3. **效率从"优化指标"变为"可用性前提"**——4B 模型 + 8 GB 内存下，不做上下文与工具工程产品不可用。
4. **可完成性可控**——无 GPU、无 KVM、无付费依赖；自研范围限定为 5 个可独立验证的模块；
   Must / Should / Won't 边界明确。

## 6. 后果

### 正面

- 研究方向明确、可量化，且不依赖未确认的硬件能力。
- 安全与性能两条主线可并行推进，且都属于**内核级**问题，有系统研究价值。
- 增量可拆分为多个单迭代可交付单元（权限模型 → 沙箱 → 审计 → 调度 → 缓存）。

### 负面

- 需要对上游代码做**较多重构**才能达到"规范"标准，前期投入较大。
- AIOS 上游工程质量与文档完善度**尚未核验**【待验证】，存在选型后返工的风险。
- 与主流 agent 框架（LangGraph 等）生态距离较远，可参考的实现较少，
  需要更多自主设计。

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 上游质量不及预期（R-1） | 高 | 决策前完成**源码核验**（时间盒半天）；不通过则转向备选 E 或 C |
| 硬件约束与预期不符（C-6） | 中 | 本方案无特殊硬件依赖；仅有基准测试规模受影响 |
| 范围失控（R-4） | 高 | 需求分层 Must/Should/Could，Must 优先；单周迭代 + 3 天卡点规则 |
| 与课程要求变化冲突（C-10） | 中 | 架构可裁剪；交付物形态（运行时 + 文档 + 基准）与常见验收形式兼容 |

## 7. 验证方式

- **核验门槛（决策转正条件）**：完成对 `agiresearch/AIOS` 源码与活跃度的核验，
  结论归档到 `docs/research/`；确认存在可增量改造的内核模块。
- **M1 里程碑**：需求规格、架构设计、威胁模型完成，且安全与性能两条主线
  各有至少 1 条 Must 级需求具备可测量的验收标准。
- **M3 里程碑**：安全主线在预定义对抗场景集上达到预期拦截率；
  性能主线在固定基准下达到预期改进幅度。若届时无法达成，
  触发**重新评估**并新增 ADR（可能需要缩减范围或更换方向）。
