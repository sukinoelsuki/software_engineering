## 1. 背景与问题

[ADR-0023](0023-ci-downgrade-to-manual-trigger.md) 已经停掉全部自动跑测，
并把四道可信闸门搬进了脚本。但**停掉之后**才拿到平台的权威用量数据，
它推翻了两处原有的判断：

### 1.1 构建桶的额度与"基数"终于确定（谜团解开）

| 项 | 实测值 | 含义 |
| --- | --- | --- |
| `ci_in_sec`（构建） | total = free = **576000 s** | **160 核时/月**，按顶级组织结算 |
| `dev_in_sec`（开发） | total **63360000 s**、free 5760000 s | 总量 **17600**／免费 **1600** 核时/月 |
| 本项目构建用量（09-24 前） | **325589 s = 90.44 核时** | 占构建免费额度 **56.7%**，余 69.34 |

⇒ [ADR-0014](0014-benchmark-automation.md) §2.3 那个"配额 ≈17600"的来源确认了：
**它是开发桶的总量**。当年"310 核时/月 ≈ 1.8%"是**拿构建消耗除以开发总额度**——
一次跨桶比较。按构建桶免费额度算，是 **194%**。
**绝对量算对了，桶用错了。**

### 1.2 真正的超支点在**开发**桶，而这正是新方法的落脚点

| 桶 | 已用 | 免费额度 | 状态 |
| --- | --- | --- | --- |
| 构建 | 90.66 核时 | 160 | 未超额（56.7%） |
| **开发** | **2512.7 核时** | 1600 | ⚠️ **已超额 912.7 核时（157%）** |

而 ADR-0023 的新方法（"环境内一键跑测"）**跑的就是开发环境** ⇒
它是往一个**已经在计费的桶**里搬东西。**只盯构建桶削，不足以达成"大幅削减用量"。**

### 1.3 成本模型：开发桶的成本主要不是"跑测"，而是"环境活着"

```text
开发桶成本 = runner.cpus × 环境存活小时数      （8 核环境 ⇒ 8 核时/小时）
构建桶成本 = runner.cpus × 流水线时长          （单核门禁 ⇒ 1 核时/小时）
```

用本项目本月开发用量反推：`1077.5 ÷ 8 = 134.7 小时`
（24 天内平均 5.6 h/天）——**开机一小时就是 8 核时，与在不在跑测无关**。

⇒ **一根定时夜轮 = 6.1~7.3 核时；而环境空转一天（8 h）= 64 核时 ≈ 9 个夜轮。**
⇒ "削减跑测"是**次要项**，"削减环境存活时间"才是**主要项**。这是本 ADR 要解决的核心。

## 2. 决策

### 2.1 确立成本模型为**设计的首要约束**（而不是事后记账）

| 量 | 定义 | 谁负责可核对 |
| --- | --- | --- |
| 构建桶消耗 | Σ(门禁 `cpus` × 时长) | 平台 API（`cnb charge`） |
| **开发桶消耗** | Σ(**环境 `cpus` × 存活时长**) | 同上 |

**由此推出的三条硬纪律**：

**D-C1｜环境生命周期优先。** 任何需要开发环境的动作（跑测、人工复核、实验）
都必须**先想好"什么时候关"**；不做事就把环境关掉。
判据：**不允许"开着环境等"**——等待期间按 8 核时/小时计费。

**D-C2｜核数与档位匹配（不许"一律 8 核"）。**

| 用途 | 需要的核数 | 依据 |
| --- | --- | --- |
| 只跑 **S/M** 档 | **4 核**（8 GiB） | 实测峰值 S 2.67 / M 4.84 GiB |
| 跑到 **L** 档 | **8 核**（16 GiB） | L 峰值 **8.69 GiB**，4 核只有 8 GiB ⇒ OOM |
| 门禁（lint/typecheck/test/security） | **1 核** | 见 ADR-0023 §2.2 |

⚠️ **"4 核跑 S/M"目前是推论，不是实测**：4 核下单轮耗时与是否 OOM 都**没有数据**
（待验证项 `W-2`）。在它被实测之前，**不得**把它当成已成立的省法。

**D-C3｜预算与记账。** 每次跑测/长时环境：① 行动前写明预计核时；
② 结束后在 devlog 记实际核时（跑测取 `index.json` 的 `core_hours`）；
③ **月末**用 `cnb charge` 做一次组织级核对，把数字写进 devlog。

### 2.2 「人工拉起 + 环境内自动化」的流程（**谁在什么时候做什么**）

```text
① 决定（所有者 / 领导）
     └─ 需要一个新数据点吗？预计核时 = cpus × 预计时长 → 记入 devlog 待办
② 拉起（在 test/<slug> 分支上借环境；环境从与 develop 一致的提交起）
     └─ ⚠️ 环境 = 计费时钟开始（8 核时/小时）
③ 准备 + 跑测（环境内，一次性跑完）
     └─ make bench（四道闸门在脚本里；闸门全过才发布到 bench/data）
④ 校验 + 发布
     └─ 四道闸门 + schema 校验 → bench/data（唯一持久化出口）
⑤ 关闭（**这一步是流程的一部分，不是收尾**）
     └─ 发布成功即关闭环境；关不掉/忘了关 = 直接的资金损失
⑥ 记账（同一会话内）
     └─ devlog：原因 / 轮次标签 / 实际核时 / 是否入库
⑦ 月度核对（每月一次）
     └─ `cnb charge get-quota` + `get-volume` + `get-repos-volume` → 写进 devlog
```

**关键设计点（与 ADR-0023 的分工）**：

| 维度 | ADR-0023（怎么停 / 闸门搬去哪） | 本 ADR（停完之后怎么跑） |
| --- | --- | --- |
| 触发 | 从 `crontab` 改为人工 | 人工的**准入判据**：有明确问题 + 有预算 |
| 闸门 | 四道，落在 `scripts/bench/` | **不变**（本 ADR 不动测量口径） |
| 成本 | 只算"跑测那一段" | **算"环境活着"的全部时长** |
| 数据出口 | `bench/data`（唯一） | **不变** |

### 2.3 旧 CI 的处置：**保留为归档证据，不删除、不再运行**

所有者的明确要求：**代码、配置、分支都保留，只是不再运行，作为成果证明**。

| 对象 | 处置 | 位置 |
| --- | --- | --- |
| 代码（`src/agent_sec_perf/bench/`、`scripts/bench/`） | **保留并继续使用**（闸门就在里面） | 仓库 |
| **退役的流水线配置** | **原文照录归档**（不可执行、只作证据） | [`../engineering/archived-ci-benchmark-pipelines.md`](../engineering/archived-ci-benchmark-pipelines.md) |
| `bench/nightly` 分支 | **保留，不再推送**（不再被任何流水线读取） | 远端（D 类禁止删） |
| `bench/data` 分支 | **保留，继续作为唯一数据出口** | 远端 |
| 5 条可比序列 + 678 个文件 | **保留**（成果本身） | `bench/data` |
| 四道可信闸门 | **保留，迁移到脚本** | `scripts/bench/gates.py` |

**理由（为什么归档而不是删除）**：
① 它是**课程交付/答辩**意义上的"过程与成果证明"；
② 删除会让 [ADR-0014](0014-benchmark-automation.md) 与 devlog 的引用**指向不存在的对象**；
③ 归档文本让"当年怎么做的"**可被第三方复核**，而 git 历史需要额外操作才能读懂。

## 3. 备选方案与取舍

| 方案 | 为何不选 |
| --- | --- |
| 继续按 ADR-0023 只削构建桶 | 构建桶已降到 ≈1.5~2 核时/月，**再削也省不出多少**；真正的账在开发桶（已超 912.7 核时） |
| 把跑测搬回 CI，但降到最低频（如每月 1 次） | 跑测必须 8 核 16 GiB ⇒ 一轮 ≈6.8 核时；且 CI 桶只剩 69.34 核时余量，**还要留给新项目**。降频是"少花"，但不解决"结构性占用" |
| 停掉开发环境，全部在本地机器跑测 | 本地是 Windows + VMware 的笔记本，**与 CI 的 CPU 型号不同** ⇒ 会产生**第三条不可比的序列**（`signature` 含 CPU 型号）；且 L 档 8.69 GiB 在本地易受干扰 |
| 把跑测环境 `cpus` 固定降到 4 | **L 档会 OOM**（8.69 > 8 GiB）⇒ 不能一律降；只能"按档位选核数"（D-C2） |
| 不做记账，靠月末看账单 | 月末才知道 ⇒ **发现即已超支**；记账的目的是**事中**可停 |

**采纳**：**成本模型优先（D-C1~C3）+ 人工拉起的 7 步流程 + 旧 CI 归档保留**。

## 4. 后果

### 正面

- 成本从"事后发现"变成"**设计时就约束**"：环境生命周期成为一等公民；
- "构建桶免费额度 160 / 已用 90.44 / 余 69.34"成为**可引用、可复核**的事实
  （原先只有文档推测）；
- 旧 CI 有了**单一、可复读的归档位置**，答辩时不必"从 git 历史里翻"；
- 与 ADR-0023 组合后，**"停"与"跑"两侧都有明确纪律**，不再有"停完了然后呢"的空档。

### 负面后果与已知限制（**必须逐条读**）

1. ⚠️ **开发桶已经在超额计费**（2512.7 / 1600），而本 ADR 的新方法**仍要用开发环境**
   ⇒ 本 ADR **不能**把组织账单降到 0；它只能**把我们的增量压到最小**。
   要回到免费额度内，需要**全组织**（含 `aimForJob` 954、`My_tinykv` 400）一起降。
2. ⚠️ **D-C2 的"4 核跑 S/M"是推论**（`W-2` 未验证）⇒ 在实测前**不得**按它写预算。
3. ⚠️ **"环境存活时长是主要成本"是反推**（`1077.5 ÷ 8`），**未逐会话核对**（`W-1`）；
   若实际有相当部分来自其它开发活动（例如高核数的临时任务），则该结论要修正。
4. **人工流程天然会漏**：⑦ 月度核对与 ⑤ 及时关闭都是**流程纪律**，
   **不可由 CI 强制**（CI 已不跑测，看不到这些动作）⇒ 按威胁模型口径记**部分缓解**，
   **不得**表述为机制。
5. **降频 ⇒ 数据更稀**（同 ADR-0023 §4 第 1 条）：本 ADR 进一步强化了"按需触发"，
   可比序列的增长会更慢；趋势判断能力随之变弱。
6. **归档文本有"漂移风险"**：归档文件是**原文照录**，不代表当前规则；
   若日后有人照着归档文件"恢复"流水线，会**立刻重新产生构建桶消耗**
   ⇒ 归档文件必须带**不可执行**的显式标注（已写）。

| Q3 | 归档可读且**不可执行** | 打开 [`archived-ci-benchmark-pipelines.md`](../engineering/archived-ci-benchmark-pipelines.md) | 顶部有"不可执行/不再启用"标注；内容为原文照录；且**不在** `.cnb.yml` 里 |
| Q4 | 跑测成本可记账 | `make bench` 后读 `index.json` 的 `core_hours` | devlog 里有"预计 vs 实际"两条数字 |
| Q5 | 四道闸门仍生效 | `make bench`（`BENCH_DRY_RUN=1` 亦可） | 逐道 `[gate ①..④][OK]`（ADR-0023 的 `V4`/`V5` 继续适用） |

`W-3`（开发桶超额的计费口径）、`W-4`（credits 归属）、`W-5`（深跑的失败点）、
`W-6`（`compute-matrix` 可复用成果——**令牌不可读，需所有者提供**）。
