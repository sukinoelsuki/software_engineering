## 1. 背景与问题

项目所有者提出本项目技术追求的准确表述：

> 在**受限环境**发挥**最好性能**得到结果。而环境是**不断变化**的
> （笔记本与 PC 之间硬件差异极大），因此技术上应增加一个重点：
> **动态探知硬件条件，据此生成合适的动态 Harness**——
> 这是"在基础安全调教之外的**剩余价值利用**"。

同时明确当前交付定位：

- 这是**实验性质的软件工程**：在**小范围内得到一定验证**即为最大的技术成功；工程能力上按软件工程步骤把 demo 跑通即可；
- 当前应用场景聚焦**笔记本电脑与个人 PC**；**移动端暂不适配**（成本高、收益低）；
- 当前要求是"**够跑、能跑出合适结果**"。

**需要决策的是**："动态适配"要落到什么粒度、在什么时机发生、以什么为验收？
若不界定，它会自然膨胀为一个无边界的研究项目——这正是 SRS 已识别的 **R-2（范围膨胀）**。

## 2. 决策驱动因素

| 因素 | 说明 | 类型 |
| --- | --- | --- |
| 单人、2~3 个月、必须推出 demo | 适配机制必须**可测试、可解释、可演示** | 硬约束 |
| 硬件差异极大（项目所有者已指出） | 内存 8~64 GiB、核数 4~24；**这是机会而非负担** | 硬约束 |
| 探测本身不可信 | 同一"核数"在容器里有**六个答案**，其中 `lscpu` 是错的 | 硬约束 |
| 已有"档位裁剪"需求 | `REQ-HARNESS-03/04` 已要求按能力档位裁剪工具与提示 | 既有约束 |
| 复现性 | 结论必须能解释"**为什么选这套配置**" | 硬约束 |
| 移动端冻结 | 适配不做进移动端 | 范围约束 |
| 不做持续优化 | 否则实验不可控、结论不可复现 | 偏好（本 ADR 定为硬约束） |

## 3. 候选方案

### 方案 A：运行中持续优化

- 简述：会话进行中持续监测资源，动态调整上下文长度、线程数、工具集。
- 优点：理论上性能最优、最"智能"。
- 缺点：**不可复现**（每次运行的配置不同）；**不可解释**（无法回答"为什么这次慢"）；
  调试成本极高；对 demo 无收益。

### 方案 B：启动时探测 + 固定档位预设（**采纳**）

- 简述：会话启动时探测一次硬件预算（并允许手动覆盖），据此从**固定 3 档**中选一套预设配置；
  运行中不再调整。整个过程留下"探测值 → 决策 → 生效配置"的记录。
- 优点：**可复现**（同一探测结果→同一配置）、**可解释**、实现成本可控、
  天然产生可归档的实验数据（降级曲线）；与既有 `REQ-HARNESS-03/04` 的档位机制直接衔接。
- 缺点：无法应对运行中的资源变化（如后台程序争抢内存）；
  档位粒度粗，可能有"介于两档之间"的配置浪费。

### 方案 C：只做静态配置 + 文档说明

- 简述：手动配置，文档告诉用户"什么硬件用什么参数"。
- 优点：零实现成本。
- 缺点：**放弃本项目的核心主张**——"能力感知/自适应"是立论（SRS §4.1），
  退化为静态手册后，增量价值所剩无几。

### 方案 D：完整自适应（在线学习 / 自动调参）

- 简述：用探针任务实测模型能力 + 自动搜索最优配置。
- 优点：上限最高。
- 缺点：**远超本期体量**；自动搜索需要大量重复采样，而 CPU 推理成本高（生成约 16 tok/s）；
  且"自动调参"的结论在小样本下不可信。

## 4. 权衡对比

权重：可复现性 5、可解释性 5、对 demo/验收的价值 4、实现与调试成本 3、范围风险控制 5。

| 维度 | 权重 | A 持续优化 | **B 启动探测+档位** | C 静态配置 | D 完整自适应 |
| --- | --- | --- | --- | --- | --- |
| 可复现性 | 5 | 1 | **5** | 5 | 2 |
| 可解释性 | 5 | 1 | **5** | 4 | 2 |
| 对 demo / 验收的价值 | 4 | 3 | **5** | 2 | 4 |
| 实现与调试成本（越低越高分） | 3 | 2 | **4** | 5 | 1 |
| 范围风险控制 | 5 | 2 | **5** | 5 | 1 |
| **加权合计** | | 27 | **86** | 66 | 33 |

## 5. 决策

**决定采用：方案 B —— 启动时探测 + 固定 3 档预设 + 全过程留痕。**

### 5.1 适配的时机与粒度（三条硬性边界）

| 边界 | 规定 |
| --- | --- |
| **时机** | **会话启动时探测一次**；运行中**不调整**。允许用户手动覆盖（覆盖也要留痕） |
| **粒度** | **固定 3 档（S / M / L）**；不做连续调优、不做自动搜索 |
| **留痕** | 必须记录三段：**探测值（含来源）→ 决策依据 → 生效配置**。缺任一段则视为未实现 |

### 5.2 两个正交的轴（关键结构）

项目所有者此前提出过"横向 / 纵向"两种比较方向。引入档位后，二者可以**统一表达**：

| 轴 | 含义 | 回答的问题 |
| --- | --- | --- |
| **纵向：硬件档位**（S/M/L） | 同一模型与 Harness 在不同硬件预算下的配置 | **降级曲线**：性能如何随硬件下降 |
| **横向：同档不同模型** | 同一档位下不同模型的表现 | 同等预算下**选哪个模型** |
| **对照：有/无适配 Harness** | 档位化 Harness vs 裸配置 | **Harness 增益**（本项目核心论点的验证） |

### 5.3 可调参数与决定因素

| 可调参数（llama.cpp / Harness） | 由什么决定 |
| --- | --- |
| 模型规模与量化档（`REQ-MODEL-02`） | **内存预算**（扣除常驻后的可用量） |
| 上下文长度 `-c` | 内存预算 − 模型常驻 − 计算缓冲 |
| 线程数 `-t` / `-tb` | **可调度核数**（`sched_getaffinity`，见笔记） |
| 批量 `-b` / `-ub` | 内存预算 + 核数 |
| 工具集大小与描述详略（`REQ-HARNESS-03`） | **模型能力档位** |
| 提示结构与示例（`REQ-HARNESS-04`） | **模型能力档位** |
| 验证强度与重试预算 | 模型能力档位 + 时延预算 |

> **注意**：**硬件档位**与**模型能力档位**是两个独立的维度。
> 硬件决定"能跑多大、多快"，模型能力决定"该给多少自由度和多少约束"。
> 二者不可互相推导——同一模型在不同硬件上能力档位不变，但配置必须不同。

### 5.4 模型档位矩阵（含新增的大一档模型）

| 档 | 内存预算 | 预置模型 | 说明 |
| --- | --- | --- | --- |
| **S** | ≤ 8 GiB | `Qwen3-4B-Q4_K_M`（2.50 GB） | 对齐目标设备下限；W1 已实测 |
| **M** | 8 ~ 16 GiB | `Qwen3-8B-Q4_K_M`（5.03 GB）**新增** | 笔记本主流配置；对应"稍好硬件条件" |
| **L** | ≥ 24 GiB | 【待定】14B 级 Q4 | 台式/工作站档；**在 16 GiB 开发机上属紧张配置，需实测后再定** |

`AgentCPM-Explore-4B` **不作为档位**，而作为**横向对比对象**（同为 4B，用于回答"同预算选哪个"）。

### 5.5 明确不做（范围边界）

- ❌ 运行中的持续优化 / 自动调参 / 在线学习；
- ❌ 移动端（手机）硬件适配——保留为架构约束与后续可行性验证（SRS `Q-2`）；
- ❌ GPU 适配（本项目为纯 CPU 路径，SRS §6.2 已列为 Won't）；
- ❌ 追求"最优配置"：目标是**"够跑、结果合适"**，不是压榨峰值。

## 6. 后果

### 正面

- 把"动态适配"从愿景变成**可交付、可验证、可解释**的机制：一次探测、三档预设、三段留痕。
- 天然产出**降级曲线**这一有研究价值的实验数据，且数据可比（同一档位配置固定）。
- 与既有需求（`REQ-HARNESS-03/04`、`REQ-MODEL-02/06`）**直接衔接**，不是新增一套并行机制。
- 探测能力可**复用**：ADR-0007 的 `isolation_matrix()` 已建立了"逐维度探测 + 记录来源"的模式，
  硬件探测沿用同一套方法与代码骨架。

### 负面（必须填写）

- **档位粒度粗**：位于档位边界附近的硬件（如 20 GiB）会得不到最优配置；
  且"阈值"本身需要实测校准，不是拍脑袋定的。
- **启动时探测的盲区**：无法应对运行中变化（后台程序争抢、热降频、电量策略），
  因此**性能数据必须标注"探测时环境"**。
- **三档 = 三倍实验量**：纵向对比要在 3 档上各跑一遍，而 CPU 推理成本高（约 16 tok/s），
  实验时间会显著增长。
- **探测的复杂度容易被低估**：核数有六个答案（见笔记），
  内存、磁盘、SIMD 各有陷阱；探测代码本身需要测试与对抗性用例。

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 范围膨胀（R-2）：适配参数越加越多 | **高** | 只允许 §5.3 表中的参数进入适配；新增参数须先写 ADR |
| 档位阈值拍脑袋 | 高 | 阈值必须由实测数据支撑，并登记为【待验证】直到校准完成 |
| 探测值与真实预算不符（不同来源冲突） | 高 | 多源交叉 + 记录来源；以 `sched_getaffinity` / cgroup 配额为准 |
| 适配逻辑本身成为新的故障源 | 中 | 提供"手动指定档位"作为逃生口；探测失败时**降级到最小可用配置**（fail-safe 到能跑） |
| 三档实验量压垮工期 | 中 | 先做 M 档（= 当前开发环境），S/L 档在 M 档跑通后再补 |

## 7. 验证方式

1. **档位生效可验证**：给定模拟/真实的资源预算，探测输出与生效配置符合 §5.4 与 §5.3 的映射；
   同一探测结果**重复运行得到同一配置**（可复现）。
2. **跨环境可验证**：在**容器（8 核 / 16 GiB）**与**本地 VM**上分别运行探测，
   确认探到的预算与实际可用一致；两者结果不同是**预期**的（说明探测在起作用）。
3. **降级曲线可验证**：同一任务在 S/M/L 三档下均可完成，并给出可比的性能数据
   （延迟、token 消耗、成功率），结论必须标注"在哪一档取得"。
4. **留痕完整性可验证**：每次运行都有"探测值 → 决策 → 配置"三段记录；缺段即判失败。
5. **M1 里程碑**：M 档在当前开发环境可完整跑通一次工具调用任务，且配置选择可被解释。
   若届时发现档位机制无法解释实际配置选择，触发重新评估并新增 ADR。
