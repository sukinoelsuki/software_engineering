# 0004. 采用 Python + uv + ruff + mypy 工程基线

- **状态**：已接受
- **日期**：2026-09-14
- **决策者**：Le0n3rd
- **相关**：Issue #4、[`pyproject.toml`](../../pyproject.toml)

---

## 1. 背景与问题

在 base project 尚未冻结的情况下（见 [ADR-0003](0003-select-base-project.md)），
工程初始化阶段是否应该先固定一套语言与工具链？

不固定的后果：`Makefile`、`.cnb.yml`、`pre-commit`、测试目录都无法落地，
CI 门禁无法建立，Phase 0 无法出口。

固定的风险：若最终 base project 是 C++/Rust/Go 主导（如推理引擎类项目），
既有配置需要调整甚至重建。

## 2. 决策驱动因素

| 因素 | 说明 | 类型 |
| --- | --- | --- |
| Phase 0 出口需要可运行的 CI | 没有语言就无法建门禁 | 硬约束 |
| AI/智能体生态语言分布 | 智能体与安全方向生态以 Python 为绝对主导 | 硬约束 |
| 自身能力 | 已具备 Python 工程能力，学习成本低 | 偏好 |
| 性能需求 | 性能热点可能需要 Rust/C++ 扩展 | 硬约束 |
| 可替换性 | 工具链应为**可替换的基线**，不是不可逆决策 | 偏好 |

## 3. 候选方案

### 方案 A：暂不固定语言，Phase 0 只做纯文档

- 优点：完全避免返工。
- 缺点：无法建立 CI 门禁与测试骨架，Phase 0 的出口准则无法满足；
  后续补建 CI 时又要重新组织一次性工作。

### 方案 B：固定 Python 工程基线（uv + ruff + mypy + pytest）

- 优点：契合生态；门禁可立即运行；工程基线可被验证（首日即可 `make check` 全绿）。
- 缺点：若 base project 主语言非 Python，需要调整（但工具链思想与 CI 结构可保留）。

### 方案 C：选定具体 base project 后再建工具链

- 优点：完全对齐最终技术栈。
- 缺点：把 Phase 0 出口绑定在一个尚未完成的决策上，形成**串行阻塞**；
  且选型本身就需要工程基础设施（如基准测试能力）来支撑。

## 4. 权衡对比

| 评估维度 | 权重 | A 纯文档 | B Python 基线 | C 等选型后 |
| --- | --- | --- | --- | --- |
| Phase 0 可出口 | 高 | 1 | 5 | 2 |
| 返工风险（越低越好） | 中 | 5 | 3 | 5 |
| 生态契合度 | 高 | — | 5 | — |
| 门禁可验证性 | 高 | 1 | 5 | 3 |
| 解耦选型决策 | 中 | 5 | 4 | 1 |

## 5. 决策

**决定采用方案 B：Python 工程基线，并显式声明其为"可替换基线"。**

理由：

1. 智能体与 AI 安全方向的**生态以 Python 为主导**（无论 base project 主语言是什么，
   本项目自身的集成层、策略层与测试层几乎必然是 Python）。
2. Phase 0 必须能够出口，而工具链是出口的必要条件，不能与选型决策串行。
3. 工具链是**可逆决策**：若 base project 为 C++/Rust，本项目可保留 Python 作为
   控制面/测试面，性能热点下沉到原生扩展，工具链思想与 CI 结构仍然有效。

## 6. 后果

### 正面

- `make check` 从第一天起就可运行并全绿，门禁有效。
- 提交规范（commitizen）、风格（ruff）、类型（mypy）、测试（pytest）、
  安全（bandit、pip-audit）全部有工具支撑。
- 测试骨架就位，后续开发无需再补基础设施。

### 负面

- 引入了对 Python 工具链的**早期锁定**，若最终方向为纯系统语言（如纯 Rust/C++ 项目），
  部分配置需要替换。
- `uv`、`commitizen` 等工具本身需要学习成本。
- `mypy --strict` 会增加早期开发摩擦（但长期收益更大）。

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| base project 主语言非 Python，配置需重建 | 中 | 保留"控制面 Python + 性能面原生扩展"的可行路径；重建时以本 ADR 为参照，仅替换工具，不改变门禁结构 |
| `mypy --strict` 摩擦过大导致被关闭 | 中 | 允许对特定模块使用较宽松的 override 并记录理由，但**不允许整体关闭** |
| 工具链版本漂移 | 低 | 依赖锁定在 `uv.lock`；CI 使用固定的 `python:3.12` 镜像 |

## 7. 验证方式

- **Phase 0 出口**：`make check` 在新克隆的仓库中可通过（验证基线可复现）。
- **M2 里程碑**：检查是否存在为绕过 `mypy` 或 `ruff` 而添加的成规模 `# type: ignore` /
  `# noqa`；若大量存在，说明基线过严或未适配，需重新评估阈值。
