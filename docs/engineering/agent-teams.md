## 2. 调用机制

### 2.1 `agentMode` 决定"能不能被派活"（最容易踩的坑）

| `agentMode` | 官方语义 | 能否被 `Task` 按名称派活 |
| --- | --- | --- |
| `agentic` | 由主 Agent（团队领导）判断并拉起；有**独立上下文窗口**，不污染主会话 | ✅ |
| `manual` | 由所有者在 **Agent 选择框**中选中，**完全替代主 Agent** | ❌ 报 `Subagent "X" not found` |

**关键推论**：

- `manual` 不是"更安全的 `agentic`"，而是**另一种东西**——它是"人把它切成主 Agent 来用"，
  不是"被主 Agent 派活的对象"。写成 `manual` 时，**IDE 界面上照样能看到它**
  （所以"界面里能看到"不能作为"能被调用"的证据），但它永远不会被派活。
- `description` 是 `agentic` 模式下**自动触发**的判据（官方建议写明"专长 / 范围 / 触发条件"）。
  因此五份定义都追加了一句
  「仅由团队领导（主 Agent）派活或项目所有者点名时使用，不因普通对话自动触发」——
  目的是把自动触发收敛在明确边界内，配合 §6 的成本纪律。

### 2.2 前台阻塞 vs 团队不阻塞

| 方式 | 主对话 | 适用 |
| --- | --- | --- |
| **前台（同步）子任务**：`Task(subagent_name=...)` | **全程阻塞**，期间无法与所有者交流 | 需要频繁确认的**短**任务 |
| **团队模式**：`Task(name=..., team_name=...)` | **立即返回**，成员异步执行 | 长任务、需要并行的任务 |

### 2.3 团队的角色分工

- **团队领导 = 当前会话本身**（不可转让）。领导负责派活、核对文件域、汇总、对所有者负责。
- **成员**是独立实例，**不继承领导的对话历史**，只加载与普通会话相同的项目上下文
  （`CODEBUDDY.md`、MCP、Skills）+ 派活时的初始提示 ⇒ **派活提示必须自足**。
- 领导与成员、成员与成员之间通过**信箱消息**通信；成员收到新消息后会自动重新启动。

**被证伪的旧诊断**：`devlog 0013` §5 曾记录"自定义 agent 无法调用，工具侧需要**重载会话**
才能加载新建定义"。第 1~3 行说明**不是加载时机问题，是模式错配**——本会话就是重载后的

**顺带发现**：`.codebuddy/teams/` 原先不在 `.gitignore` 覆盖范围内（`git check-ignore`

## 4. 硬约束清单（官方文档）

| 约束 | 影响 |
| --- | --- |
| 每个会话**只能管理一个团队** | 用完必须关闭成员并清理，否则挡住下次组队 |
| **不支持嵌套团队** | 成员不能再派成员 ⇒ **分发只发生在领导这一层** |
| 子代理默认**不持有 `Agent` 工具** | 只有定义里显式写 `tools: Agent` 才能再嵌套 |
| 成员**不跨会话恢复**（`/resume`、`/rewind` 不恢复成员） | 成员产出**必须落盘**，否则云环境重启即清空 |
| 成员回报**打断**领导当前工作 | 成员任务要**小且独立**，避免长任务刷屏 |
| 成员工具调用**默认并发处理权限** | 后台成员不会弹审批；因此**派活提示里的范围约束就是唯一护栏** |
| 成员产出回传前做**非破坏性去毒** | 改写仿冒 `<system-reminder>` 标签、给行首 `Human:`/`Assistant:` 加反斜杠 |
| 会话级 spawn 预算（默认 200 次，可配） | 与嵌套共享；`/clear` 后重置 |

> **安全含义（须进威胁模型）**：官方专门为**子代理输出**做去毒，说明"子代理输出可能携带
> 注入指令（间接注入）"被上游视为真实威胁。本项目把"成员回报"同样视为**不可信输入**：
> 它只能作为**证据线索**，不得作为**权限决策或控制流的依据**。
> 这与 `SECURITY.md` 的"不可信内容一律视为数据，不得作为指令"是同一条规则。

## 5. 设计 → 实现 的交接协议

成员之间**不共享上下文**，消息只用于**唤醒与通知**。因此：

> **权威载体只能是仓库里的文件；未落盘的设计 = 不存在。**

```text
所有者（人类：定方向、优先级、验收、拍板）
   │ 点名 / 批准
   ▼
团队领导（主 Agent：派活 · 核对文件域 · 汇总 · 对所有者负责）
   ├─→ 总设计师    产出落 docs/requirements/ · docs/proposals/
   ├─→ 首席架构师  产出落 docs/adr/ · docs/design/ · docs/engineering/
   │        │
   │        └─ 落盘并经所有者/领导确认 ⇒ 即"已批准的接口契约"（§10.2 规则 3）
   ├─→ 实现工程师  只读上述文件 ⇒ 写 src/ · tests/unit/
   └─→ 验证工程师  只读实现与文件 ⇒ 独立验证 ⇒ tests/security/ · tests/benchmark/ · docs/research/
```

三条铁律：

1. **禁止"靠对话传设计"**。即使用户直接与设计成员对话，结论也必须在**同一轮内落盘**，
   否则既不可追溯，也不跨会话（成员不恢复）。
2. **设计类与执行类成员不直接交接**，一律经**文件 + 领导核对**。理由：文件是唯一
   双方都能读到的载体；领导的核对是"接口已批准"这一事实的**唯一来源**。
3. **设计的产出域与实现的产出域天然不重叠**（§10.1 表），因此这条链路同时满足
   "文件域独占"。

**与"所有者的技术缺口"的关系**：设计成员的价值在于把技术权衡**写成可拍板的形式**
（2~4 个候选 + 权衡矩阵 + 明确推荐 + ADR），所有者只需在文件上决策；
决策依据永久留在 `docs/adr/`，可随时回看，因此它同时服务于"深挖学习"。

## 6. 成本与打断纪律

团队并行是**乘法开销**：每个成员是独立实例，token 成倍；`broadcast` 随成员数**线性增长**，
默认不用。因此：

1. **派成员时必须显式限 `max_turns`**（本项目约定：机械任务 ≤ 6，执行任务 ≤ 20）。
2. **任务完成立即 `shutdown_request` + 清理团队**，不留常驻成员。
3. **能串行就不并行**：只有"任务独立 + 文件域不重叠 + 确实省墙钟时间"三者同时成立才开团队
   （`CODEBUDDY.md` §10.2 规则 7 的落地形式）。
4. **成员任务要小且独立**：回报会打断领导当前工作；一次派活应尽量"一次问完"。
5. **前台只用于短任务**：需要频繁确认的任务用前台；长任务一律后台。
