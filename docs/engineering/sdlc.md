# 软件生命周期与迭代流程

> 本项目周期约 2~3 个月（2026-09 ~ 2026-12），单人独立开发。
> 本文定义**阶段划分、里程碑、迭代节奏与工件清单**，是所有进度判断的唯一依据。

---

## 1. 阶段划分

```text
Phase 0  工程初始化          ██████████  ← 当前
Phase 1  需求与设计
Phase 2  核心实现（多迭代）
Phase 3  加固与优化（安全 / 性能）
Phase 4  验证与交付
```

| 阶段 | 目标 | 出口准则（Exit Criteria） |
| --- | --- | --- |
| **Phase 0** 工程初始化 | 建立可长期运行工程基线 | 仓库骨架、流程规范、Agent 准则、CI 门禁、base project 冻结（**M0 出口的可判定判据见 §3.1**） |
| **Phase 1** 需求与设计 | 把"想做什么"变成"可验证的规格" | SRS 成稿；架构设计成稿；**威胁模型成稿**；模块接口定义；测试计划成稿 |
| **Phase 2** 核心实现 | 交付可运行的最小完整系统 | 端到端主流程可跑通；单元+集成测试覆盖关键路径；CI 稳定 |
| **Phase 3** 加固与优化 | 让系统"安全且快"有量化证据 | 对抗性测试集全部通过；性能基准达标并归档；无已知高危问题 |
| **Phase 4** 验证与交付 | 形成完整的工程证据链 | 系统测试报告、性能报告、安全评估报告、发布版本、完整文档、演示材料 |

> **阶段不是瀑布**：Phase 2 中允许回到 Phase 1 修正设计，但**必须同步更新设计文档**。
> 判断标准是"文档是否仍然描述现状"，而不是"是否走完了流程"。

---

## 2. 迭代节奏

采用**单周迭代（Sprint）**，因为单人项目的最大风险是节奏漂移。

| 时点 | 活动 | 产出 |
| --- | --- | --- |
| 周一 | **计划**：从 backlog 挑选本迭代任务 | 迭代目标 + 任务清单（Issue 形式） |
| 周二~周四 | **执行**：小步提交，走 PR 流程 | 代码 + 测试 + 文档 |
| 周五 | **收尾**：自评审、补齐文档、更新 CHANGELOG | 合并到 `develop`；迭代小结 |
| 周五 | **回顾**：本次迭代什么做对了/做错了 | 不超过 10 行的回顾记录（附在 Issue 或 `docs/` 中） |

**迭代目标必须可验证**。反例："完成安全模块"。正例："实现能力模型并在 6 个越权场景下拒绝率 100%"。

### 时间盒（Timebox）原则

任何任务超过 **3 天**没有实质进展，必须：

1. 拆分为更小的任务；或
2. 降级为 `exp/*` 探索任务，设定硬性时间盒；或
3. 明确记录卡点（Blocked）与原因。

**禁止**"闷头做两周然后发现方向错了"。

## 4. 需求工程

### 需求来源

1. **上游差距分析**：对 base project 做安全与性能评估，识别可改进点；
2. **威胁建模**：由 STRIDE / OWASP Agentic AI Top 10 推导出的安全需求；
3. **性能基线**：由基准测试暴露的瓶颈；
4. **工程质量**：可测试性、可观测性、可维护性需求。

### 需求写法

每条需求必须包含：

```text
REQ-<模块>-<序号>：<需求陈述>
- 类型：功能 / 安全 / 性能 / 质量
- 优先级：Must / Should / Could（MoSCoW）
- 验收标准：可测量、可测试的条件
- 验证方式：单元 / 集成 / 安全 / 基准 / 人工评审
- 关联：Issue #N、威胁 T-N、设计 D-N
```

**没有验收标准的需求不是需求，是愿望。**

### 需求变更

需求变更**允许且必然发生**，但必须留痕：更新 `docs/requirements/`，并在 `CHANGELOG.md`
的 `[Unreleased]` 中记录；影响架构的变更需新增 ADR。

## 5. 设计与威胁建模

- **架构设计**：`docs/design/` 下的架构文档（C4 视角或分层描述 + 关键时序图）。
- **接口契约**：模块间接口必须先定义（类型、错误语义、并发假设），再实现。
- **威胁模型**：`docs/design/threat-model/`，**与设计同步产出**，不是事后补。
  要求见 [`SECURITY.md`](../../SECURITY.md) 第 4 节。

**设计评审由谁做？** 单人项目中，设计评审 = 三件事：

1. 以**攻击者视角**重新审视设计（每个信任边界都问"这里怎么被绕过"）；
2. 以**运维视角**审视（出错怎么定位？怎么回滚？怎么观测？）；
3. **AI 辅助评审**（要求 AI 专门挑刺，而不是求认同）。

## 8. 与"非目标"的关系

本项目的**非目标**（见 [`README.md`](../../README.md)）与目标同等重要：

- 不追求刷榜式指标；优先保证工程质量。
- 不做与主线无关的功能；超出范围的想法进入 backlog 并显式记录，而非顺手实现。

**范围蔓延是单人项目最主要的失败模式。**
