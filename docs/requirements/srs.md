## 1. 产品愿景

> **让能力有限的模型，在资源与网络受限的环境中，也能被安全地用于完成力所能及的工作。**

三个关键词：

| 关键词 | 含义 |
| --- | --- |
| **能力有限** | 不是回避小模型的不足，而是**承认并适配**它——用系统（Harness）来界定和补偿模型的能力边界 |
| **受限环境** | 无网络 / 弱网络、无 GPU、内存小、设备老旧，甚至只有一部手机 |
| **安全地** | 不是让模型不犯错，而是让系统**在超出能力边界时明确停下**，并在执行侧防止越权与泄漏 |

**产品本质**：一个**能力感知的智能体运行时（Capability-Aware Agent Runtime）**——
它在同一套框架下同时支持**本地端侧小模型**与**线上 API 模型**，
并根据当前模型的实际能力**自动调整自身的 Harness 配置**（工具集、提示策略、验证强度、安全约束）。

## 2. 问题背景与空缺

### 2.1 现状观察

| 观察 | 说明 |
| --- | --- |
| **模型部署能力已成熟** | Ollama / llama.cpp 让端侧模型部署变得简单，CPU 也能跑 |
| **但部署与"能力"之间是断开的** | Ollama 只提供模型服务与简单对话框，**不具备 agent 能力**；通常作为 API 供外部 IDE/工具调用，自身不做集成 |
| **主流 agent 工具假设强模型** | Cursor / Cline / Claude Code / OpenHands 等默认上下文充足、推理快、工具调用可靠，**不针对低资源设备设计** |
| **小模型单独使用体验差** | 幻觉较重、工具调用不稳定、长上下文能力弱，直接调用 API 几乎不可用 |
| **受限环境缺少可用方案** | 无网/弱网、只有手机的场景下，现有云端 agent 全部失效，本地又只有"能聊天但不能干活"的工具 |

### 2.2 空缺

> **"部署端侧模型"与"把模型用起来（agent 化）"之间的集成层是缺失的**，
> 而这一层恰恰是决定弱模型能否产生实际价值的关键。

现有项目在这条线上各占一端：

| 类型 | 代表 | 覆盖 | 缺口 |
| --- | --- | --- | --- |
| 模型运行时 | Ollama、llama.cpp、LocalAI | ✅ 部署与推理 | ❌ 无 agent 能力、无执行安全 |
| 云端 agent | CodeBuddy、Cursor、Claude Code | ✅ agent 能力 | ❌ 依赖网络与强模型 |
| 开源编码 agent | Aider、Cline、Goose、OpenHands | ✅ agent 能力 | ❌ 假设强模型；对低资源无针对性设计 |
| 本地聊天界面 | Open WebUI、LibreChat | ✅ 交互界面 | ❌ 无工具执行与安全边界 |

## 3. 目标用户与典型场景

> ⚠️ **本节识别出本项目最大的范围风险：以下两类用户的需求差异很大。**
> 见第 12 节开放问题 Q-1 —— **必须先确定主线用户**。

### 3.1 用户群体 A：受限环境下的工作者（开发者 / 专业人员）

| 项 | 内容 |
| --- | --- |
| 画像 | 需要在无网或弱网环境下处理技术工作的人；设备性能有限（4B 级模型可用） |
| 典型场景 | 内网/离线环境的代码修改与审查；现场（工地、机房、野外）的技术手册问答与故障排查；应急情况下的文档与脚本处理 |
| 核心诉求 | **能干活**：改代码、查资料、生成脚本、做检查，而不是只能聊天 |
| 关键约束 | 不能联网；不能接受代码/数据外泄；设备资源有限 |
| 成功判据 | 在离线状态下完成原本需要联网才能做的任务 |

### 3.2 用户群体 B：数字能力受限人群（老年人、低数字素养用户）

| 项 | 内容 |
| --- | --- |
| 画像 | 不熟悉智能设备操作，子女不在身边；可能只有一部手机 |
| 典型场景 | 手机操作指导、信息查询、文本理解与代办（如读懂一条短信/通知）、生活事务辅助 |
| 核心诉求 | **门槛低、说人话、出错别出事** |
| 关键约束 | 交互必须极简；**错误代价可能很高**（涉及医疗、用药、钱财、法律时） |
| 成功判据 | 用户能独立完成原本需要他人协助的事项，且**没有因错误建议受到伤害** |

### 3.3 两类用户的差异（为什么不能混为一谈）

| 维度 | 群体 A（开发者） | 群体 B（普通/弱势用户） |
| --- | --- | --- |
| 主要风险 | 代码/数据外泄、危险命令执行、注入攻击 | 错误建议造成实际伤害、隐私泄露、被欺骗 |
| 安全层重点 | **执行隔离**（沙箱、权限、审计） | **输出把关 + 能力边界拒答** |
| 效率层重点 | 上下文管理、工具裁剪 | 交互时延、极简流程、本地可用性 |
| 验证方式 | 任务成功率、token 消耗、延迟 | 任务可理解性、拒答正确率 |

**统一它们的，不是用户，而是技术内核**：两者都需要
「**能力感知的 Harness**」+「**能力边界感知的安全层**」。
因此产品策略是：**核心与领域无关，用"领域包（Domain Pack）"承载不同场景。**

## 4. 核心设计论点（本项目的灵魂）

> 这一节是整个项目的立论。所有功能与安全需求都应能追溯到它。

### 4.1 论点一：Harness 必须与模型能力协同设计

**主张**：不能把为大模型设计的 Harness 直接套到小模型上（"小马拉大车"）。
模型能力不同，Harness 的**工具集、提示结构、验证强度、重试预算、自由度**都应当不同。

**依据**（来自 2026 年 Harness 工程的公开实践）：

| 证据 | 说明 |
| --- | --- |
| 工具裁剪 | Vercel 从 v0 砍掉 80% 工具后效果**变好**；Claude Code 用懒加载实现约 95% 上下文缩减 → 工具越多，弱模型越乱 |
| 上下文退化 | 关键信息落在上下文中间时性能下降 30%+（"Lost in the Middle"）；大窗口也会降低指令遵循 |
| 效率研究（ACON） | 优先保留推理痕迹而非原始工具输出，可减少 26%~54% token 消耗且保持 95%+ 准确率 |
| 错误放大 | 10 步流程每步 99% 成功，端到端仅约 90.4% → 弱模型必须压缩步数、增加验证 |

**推论（可验证的假设）**：

> **H1**：对给定小模型 M，存在一个**能力档位适配的 Harness 配置 H\*(M)**，
> 使得在同等资源预算下，H\*(M) 的任务成功率显著高于直接把大模型的 Harness 套用于 M。

这个假设可以设计实验来验证，其结论本身就是项目的重要产出。

### 4.2 论点二：安全层必须"能力边界感知"

**主张**：小模型必然犯错。安全设计的目标**不是让模型不犯错**，而是：

1. **不让错误造成不可逆的伤害**（执行侧：权限、沙箱、审计）；
2. **在超出能力边界时主动停下**（输出侧：拒答、转人工、明确说明不确定性）。

**对"有总比没有好"的精确化**：

| 场景类型 | 判定 | 系统行为 |
| --- | --- | --- |
| 低代价错误 | 闲聊、信息检索、文案润色、格式转换 | **允许尽力回答**，"有总比没有好"成立 ✅ |
| 高代价错误 | 用药剂量、医疗诊断、法律意见、电气接线、金融操作 | **必须主动拒答或强制转人工**，不得"尽力尝试" ⚠️ |
| 不可逆操作 | 删除文件、覆盖配置、发起支付、对外发送数据 | **必须显式人工确认 + 可回滚** |

**这一分层是面向群体 B 的安全护栏的核心设计**，也是本项目与"直接套一个开源护栏"的区别所在。

### 4.3 论点三：模型路由（本地 / 云端）既是产品能力，也是评估手段

- **产品能力**：有网且允许时用云端强模型保证成功率；无网时自动降级到本地模型，**功能不中断**。
- **评估手段**：云端强模型的结果可作为**上限基线**，用来量化"本地小模型 + 适配 Harness"距离
  目标还有多远 —— 这为项目提供了天然的对照实验设计。

## 5. 产品定位与差异化

### 5.1 定位

> 一个**同时支持本地端侧小模型与线上 API 模型**、**在资源与网络受限环境下可用**、
> **以安全执行为前提**、**可根据模型能力自动调整 Harness** 的智能体运行时与客户端。

### 5.2 差异化

| 维度 | 现有项目 | 本项目 |
| --- | --- | --- |
| 模型来源 | 只管本地 **或** 只管云端 | **统一抽象，可路由、可降级** |
| 与模型能力的关系 | 一套 Harness 通吃 | **Harness 按能力档位适配** |
| 安全 | 多为"人工确认"或不做 | **能力边界感知的权限 + 沙箱 + 审计** |
| 目标环境 | 开发机 / 服务器 | **低资源设备，并向移动端延伸** |
| 任务边界 | 默认"什么都能做" | **显式声明能力边界，越界则停** |

### 5.3 对标说明（重要）

对标 [CodeBuddy](https://www.codebuddy.ai/) / Cursor 这类综合智能体的**工程形态**
（工具集设计、权限确认、会话与上下文管理、可观测性），

**但不对标它们的任务成功率与质量** —— 它们使用最强模型，
把它们的指标当作本项目标准会造成必然挫败。本项目的评价标准是：
**在给定的小模型与受限资源下，相对"直接对话"的基线提升了多少。**

## 6. 产品形态与范围边界

### 6.1 形态

| 阶段 | 形态 | 说明 |
| --- | --- | --- |
| **本期（Must）** | **命令行客户端（CLI）** | 交互式 + 非交互式；可脚本化、可进 CI |
| 本期（Should） | TUI 或轻量 Web 界面 | 提升可用性 |
| **架构原则** | **可移植性** | 面向桌面与移动端共同约束设计（纯 CPU 路径、低内存、无 x86 专有依赖） |
| 后续（非本期） | 移动端 App | 见 Q-2 |

### 6.2 范围边界

| 级别 | 内容 |
| --- | --- |
| **Must** | 模型管理（本地+云端统一）· 代理循环 · 能力自适应 Harness · 权限与沙箱 · 审计 · 上下文效率 · CLI · 测试与文档 |
| **Should** | 任务路由与降级 · 领域包机制 · 注入检测与输出护栏 · TUI · 工具懒加载 · 对抗回归 · 追踪接入 |
| **Won't（本期明确不做）** | IDE 插件 · 自研代码编辑器/GUI 富客户端 · 模型训练与微调 · 多智能体协作 · KVM/microVM 沙箱 · 云端服务与账号体系 · 团队协作功能 · 移动端 App 交付 |

> **Won't 列表是硬边界**，任何"顺手加一下"一律进入 backlog 并显式记录。

### 6.3 硬件适配的目标范围（2026-09-15 明确）

| 项 | 规定 |
| --- | --- |
| **本期适配目标** | **笔记本电脑与个人 PC**（异构但可枚举：内存 8~64 GiB、核数 4~24） |
| **移动端** | **不做适配交付**；但通过 **S 档（2B 模型）** 做**代表性验证**——即以可测数据回答"移动端 agent 能力边界"，见 [ADR-0011](../adr/0011-tier-composition-revision.md) |
| **加速器** | 纯 CPU 路径；GPU 适配列入 Won't |
| **适配时机** | 会话启动时探测一次 + 固定 3 档预设；**不做运行中持续优化、不做自动调参** |

**档位构成（三档全部可在当前云开发环境验证）**：

| 档 | 对应场景 | 内存预算 | 模型 |
| --- | --- | --- | --- |
| **S** | 移动端（代表性验证） | ≤ 4 GiB | `MiniCPM5-2B-Q4_K_M` |
| **M** | 目标设备下限 / 通用基线 | 8 GiB | `Qwen3-4B-Q4_K_M` |
| **L** | 笔记本 / 个人 PC | 16 GiB | `Qwen3-8B-Q4_K_M` |

> 14B 级（≥ 24 GiB）**已移出档位矩阵**（本环境无法验证）。
> 依据：[ADR-0011](../adr/0011-tier-composition-revision.md)。

> 依据：[ADR-0010](../adr/0010-dynamic-hardware-adaptation.md)。
> 该决策把项目所有者的"动态适配"愿景收敛为**可交付、可验证、可解释**的形态，
> 以避免范围膨胀（`R-2`）。

## 8. 非功能性需求

| 类别 | 要求 |
| --- | --- |
| **资源占用** | 在 8 GB 内存设备上可运行 4B 级（4-bit）模型并完成一轮工具调用任务 |
| **平台** | Linux x86_64/arm64、Windows；架构上不排斥移动端 |
| **性能** | 首 token 延迟与单轮任务总时长须有可复现基线；上下文 token 消耗相对基线下降 ≥ 30% |
| **安全** | 默认拒绝、最小权限、fail-secure；所有特权操作可审计；无密钥泄漏 |
| **可用性** | 无网络时核心功能不中断（能力内任务）；中文优先；错误提示可理解 |
| **可维护性** | 模块边界清晰、接口有类型标注、`mypy --strict` 通过；文档与代码同步 |
| **可移植性** | 不依赖 x86 专有指令、不依赖 GPU、不依赖 KVM |
| **隐私** | 默认全部本地处理；任何出站请求必须显式授权并记录 |

## 11. 与上游/竞品的关系

- **复用而非重写**：推理（llama.cpp）、模型分发（HF Hub）、代码解析（tree-sitter）、
  工具协议（MCP）、内容防护（LLM Guard）、CLI/TUI（Typer/Textual）。
  沙箱**不复用第三方隔离工具**——原因见 [ADR-0006](../adr/0006-sandbox-execution-degradation.md)：
  L1 档仅用标准库，L2 档（bwrap/firejail）作为**可选后端**且必须通过能力探针。
- **自研范围（本项目的"自己的东西"）**：
  1. 本地 + 云端统一模型层与能力探测
  2. **能力自适应 Harness**（工具裁剪 + 提示分级）—— 核心论点
  3. **能力边界感知的安全层**（权限 + 沙箱 + 审计 + 拒答）
  4. 上下文效率引擎（索引 + 压缩 + 懒加载）
  5. 领域包机制
- **不做上游 PR 优先**：以集成为主；若产生通用改进可另行考虑回馈。

## 13. 需求变更与维护规则

1. 本文件是需求的**唯一权威来源**；Issue、讨论与代码中的需求描述不得与之冲突。
2. 变更流程：提出（Issue）→ 评估影响（是否影响架构/安全/工期）→ 更新本文档 + 版本号 →
   记录到 `CHANGELOG.md` → 若影响架构则新增 ADR。
3. **需求不得静默删除**：失效需求标记为"已废弃"并说明原因与替代。
4. 每条需求必须可追溯到：**验收标准 + 验证方式**；不可验证的表述不得进入本文件。
5. 每个迭代结束时复查本文件，确认与实现保持一致。

## 14. 术语表

| 术语 | 含义 |
| --- | --- |
| Harness | 包裹模型的软件基础设施：编排循环、工具、上下文管理、记忆、状态、错误处理、安全护栏。公式：`Agent = Model + Harness` |
| 能力档位 | 对**模型能力**的粗略分级，用于选择工具集与提示结构。**与硬件档位是两个独立的轴** |
| **硬件档位（S/M/L）** | 对**可用硬件预算**（内存、核数）的分级，用于选择模型规模、量化档、上下文长度与并行度。**不可由模型能力推导，反之亦然** |
| **剩余价值利用** | 在基础安全调教之外，通过动态适配把给定硬件的性能"榨"出来——本项目对"动态 Harness"的定位 |
| 能力自适应 Harness | 根据模型能力档位自动调整工具集、提示结构、验证强度与重试预算的 Harness |
| 能力边界拒答 | 系统识别任务超出当前模型能力或存在高代价错误风险时，主动拒绝或转人工 |
| 领域包（Domain Pack） | 可插拔的领域配置：提示、工具集、示例、安全策略与输出规范 |
| 致命三要素（Lethal Trifecta） | 私有数据访问 + 处理不可信内容 + 对外通信能力，三者同时具备即构成高危机组合 |
| 受限环境 | 无网/弱网、无 GPU、内存小、设备老旧，甚至仅有手机的环境 |
