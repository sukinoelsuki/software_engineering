# 需求规格目录

本目录存放**需求规格（SRS）**、用例与验收标准。Phase 1 的主要产出之一。

---

## 需求编号规则

```text
REQ-<模块>-<序号>
```

模块前缀**必须**取自下表，且与 `srs.md` §7 的功能需求分组一一对应
（依据：`srs.md` §7 实际分组，2026-09-18 核对）：

| 前缀 | 职责 |
| --- | --- |
| `MODEL` | 本地/云端模型的发现、校验、加载，以及能力探测与路由降级 |
| `HARNESS` | 代理编排循环、工具集与提示分级、上下文与状态、错误处理、领域包 |
| `SEC` | 权限授权、沙箱执行、注入防护、审计、输出护栏与能力边界拒答 |
| `PERF` | 性能基线、上下文效率、硬件探测与档位适配、基准自动化与测量纪律 |
| `TOOL` | 内置工具、MCP 接入、工具描述与来源校验 |
| `UX` | CLI/TUI 交互、权限确认交互、安装流程与中文优先的可理解性 |
| `OBS` | 结构化日志、审计查看、可选追踪接入 |
| `PLAT` | 平台支持与可移植性、移动端可行性（架构约束） |
| `OPS` | CI 门禁、测试分层与覆盖率、文档、可复现构建与版本发布 |

> 新增前缀前必须先在 `srs.md` §7 建立对应分组；**不得**在本文档单独发明前缀。
>
> 历史说明（2026-09-18）：旧版本文档曾列出 `KERNEL`（内核/运行时）示例，
> 但它**从未在 `srs.md` 中被使用**，且与实际的 `HARNESS` 分组语义重叠。此处**删除**该前缀——
> 编号规范是**规范**而非历史记录，保留一个无定义、未使用的词只会让新需求"无据可依"；
> 若将来确需内核/运行时层，应先经需求变更在 `srs.md` §7 建立分组，再回到本表登记。

## 需求条目模板

```markdown
### REQ-<模块>-<序号>：<一句话需求>

- **类型**：功能 / 安全 / 性能 / 质量
- **优先级**：Must / Should / Could（MoSCoW）
- **来源**：<上游差距分析 / 威胁 T-N / 性能基线 / 工程质量>
- **描述**：
  <需求陈述。避免"支持 XX"这类无法验证的表述。>
- **验收标准**：
  - [ ] <可测量、可测试的条件 1>
  - [ ] <可测量、可测试的条件 2>
- **验证方式**：单元测试 / 集成测试 / 安全测试 / 性能基准 / 人工评审
- **关联**：Issue #N、威胁 T-N、设计 D-N
```

---

## 硬性要求

1. **每条需求必须有验收标准**。没有验收标准的需求不是需求，是愿望。
2. **每条需求必须有验证方式**，且落在上述五类之一。
3. 安全需求必须能追溯到威胁模型中的具体威胁条目。
4. 性能需求必须给出**可测量的指标**（P50/P95/P99、吞吐、内存）与测量条件，
   而不是"要快"。
5. 需求变更允许且必然发生，但必须更新本文档并在 `CHANGELOG.md` 中记录；
   影响架构的变更需新增 ADR。

## 用例（Use Case）

关键场景需补充用例描述：**参与者 → 前置条件 → 主流程 → 异常流程 → 后置条件**。
对安全相关场景，必须显式写出**滥用场景（Misuse Case）**，
即"攻击者会怎么做"。
