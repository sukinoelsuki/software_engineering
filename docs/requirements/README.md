# 需求规格目录

本目录存放**需求规格（SRS）**、用例与验收标准。Phase 1 的主要产出之一。

---

## 需求编号规则

```text
REQ-<模块>-<序号>
```

模块示例：`SEC`（安全）、`PERF`（性能）、`KERNEL`（内核/运行时）、
`TOOL`（工具与供应链）、`OBS`（可观测性）、`OPS`（工程与运维）。

---

## 需求条目模板

```markdown
### REQ-<模块>-<序号>：<一句话需求>

- **类型**：功能 / 安全 / 性能 / 质量
- **优先级**：Must / Should / Could（MoSCoW）
- **来源**：<上游差距分析 / 威胁 T-N / 性能基线 / 工程质量>
- **描述**：
  <需求陈述。避免"支持 XX"这类无法验证的表述。>
- **验收标准**：
  - [ ] <可测量、可测试的条件 1>
  - [ ] <可测量、可测试的条件 2>
- **验证方式**：单元测试 / 集成测试 / 安全测试 / 性能基准 / 人工评审
- **关联**：Issue #N、威胁 T-N、设计 D-N
```

---

## 硬性要求

1. **每条需求必须有验收标准**。没有验收标准的需求不是需求，是愿望。
2. **每条需求必须有验证方式**，且落在上述五类之一。
3. 安全需求必须能追溯到威胁模型中的具体威胁条目。
4. 性能需求必须给出**可测量的指标**（P50/P95/P99、吞吐、内存）与测量条件，
   而不是"要快"。
5. 需求变更允许且必然发生，但必须更新本文档并在 `CHANGELOG.md` 中记录；
   影响架构的变更需新增 ADR。

---

## 用例（Use Case）

关键场景需补充用例描述：**参与者 → 前置条件 → 主流程 → 异常流程 → 后置条件**。
对安全相关场景，必须显式写出**滥用场景（Misuse Case）**，
即"攻击者会怎么做"。
