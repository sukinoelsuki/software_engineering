# 0001. 隔离与沙箱：为什么"退出码 0"不等于隔离生效

- 面向：我（初学者视角）
- 关联：[ADR-0006](../adr/0006-sandbox-isolation-strategy.md)、
  [devlog 0007 §4.6/§4.7](../devlog/0007-2026-09-15-开发环境验证与沙箱方案修正.md)
- 事实来源：2026-09-15 本项目在 CNB 开发环境内的实测（命令与输出见 devlog 0007）

---

## 1. 一句话结论

**沙箱的价值在于"边界真的存在"，而"命令跑成功了"完全不能证明边界存在。**
判断沙箱是否生效，必须去**观察隔离的客观痕迹**（例如命名空间编号），
而不是看命令有没有报错、退出码是不是 0。

---

## 2. 直觉模型：门禁的两个层次

想象一栋楼：

- **门禁系统**（隔离机制）：刷卡才能进，权限之外的门打不开。
- **前台对讲机**（命令执行）：你在门口喊一声"帮我拿个快递"，里面有人应了。

现在的问题是：**"里面有人应了"能不能证明"门禁装好了"？**

不能。因为**什么门禁都没有的大楼，里面照样有人应你**。
你听到"有人应答"，只能证明楼里有人，**不能证明门禁存在**——甚至门禁坏了、被拆了，
应答一样正常。

这正是我们踩的坑：`firejail` 的沙箱**根本没建起来**，但它照样执行了我们的命令，
还打印了 `sandbox-ok`、退出码 0。**"命令跑通了"这句话，对"沙箱是否生效"这个问题零信息量。**

正确的问法是：**我怎么证明门禁真的装好了？**
答案只能是去检查**门禁系统本身的状态**（锁是否上锁、刷卡机是否在工作），
而不是去喊一嗓子看有没有人应答。

---

## 3. 原理：Linux 的"隔离"到底靠什么

### 3.1 命名空间（namespace）：把"全局资源"变成"每个进程一份"

Linux 内核里有若干类"全局资源"：进程号、挂载表、网络接口、主机名、用户/权限映射……
**命名空间**做的事情，就是让某个进程看到的是**这些资源的一份独立副本**：

| 命名空间 | 隔离了什么 | 没有它会发生什么 |
| --- | --- | --- |
| `mnt` | 挂载点（能看到哪些目录） | 沙箱里能直接看到并改写宿主机的整个文件系统 |
| `pid` | 进程号 | 沙箱里能看见并 `kill` 宿主机上所有进程 |
| `net` | 网络接口、路由、端口 | 沙箱进程可以直接访问局域网/外网 |
| `user` | 用户与权限映射 | 非 root 用户无法在自己的沙箱里"假装成 root" |
| `ipc` / `uts` / `cgroup` | 共享内存、主机名、资源组 | 跨沙箱干扰与信息泄露 |

每个命名空间在 `/proc/<pid>/ns/` 下有一个 **inode 编号**。
**同一个命名空间 → 编号相同；不同的命名空间 → 编号不同。**

> 这就是我们用来"抓假阳性"的那个客观痕迹：
> 如果沙箱内的 `mnt` 编号和宿主机**一模一样**，说明它根本没建新命名空间。

### 3.2 为什么"建命名空间"需要特权

创建新的命名空间是一个**降低隔离难度的动作**，但它本身**扩大**了调用者的能力
（比如进入新的 `user` 命名空间后，进程在新命名空间内可以拥有完整的 root 能力）。

所以内核设了门槛：

- 创建新的 `user` 命名空间：历史上对非特权用户开放，但需要 `kernel.unprivileged_userns_clone` 允许；
- 创建 `mnt` / `pid` / `net` 等其它命名空间：需要 **`CAP_SYS_ADMIN`** 能力
  （或者先进入一个新的 `user` 命名空间，在其中获得完整能力）。

`bubblewrap`、`firejail`、`nsjail` **全都依赖"能创建命名空间"这个前提**。
前提不成立，它们就都无处发力。

### 3.3 容器套容器：为什么"里面"建不出来

我们的开发环境**本身就是一个容器**。容器运行时为了防止逃逸，会：

1. **砍掉能力**：不给 `CAP_SYS_ADMIN`，而且写进 **bounding set**（此后无法再获得）；
2. **上 seccomp 过滤器**：直接把 `unshare` / `clone(CLONE_NEW*)` 这类系统调用拒掉。

这两条都是**在容器外设定的**——容器内的进程无论做什么都没法解除。
实测结果：`unshare(CLONE_NEWUSER)` 与 `unshare(CLONE_NEWNS)` 都返回 `EPERM`。

> 顺带一个易错点：`/proc/sys/user/max_user_namespaces` 显示一个极大的数字，
> **看起来像是允许的**。但那个值只是"上限"，真正的拦截发生在 seccomp 与能力检查上。
> **不要用一个看似相关的开关去推断结论，要直接测你想做的那个动作。**

### 3.4 那为什么 `docker run` 又能用？

关键要分清"**谁在建命名空间**"：

- 在容器**内**执行 `unshare` → 是**我们自己**在建 → 被 seccomp/能力拦住 → 失败；
- 执行 `docker run` → 请求发给**运行在容器之外**的 Docker 守护进程 →
  **由守护进程在宿主侧**建好新容器 → 成功。

所以我们起的是**兄弟容器**（同一个守护进程下的另一个容器），
而不是"容器里再套一个容器"。**边界是"借来的"，不是自己具备的**——
这一点直接影响架构结论：如果目标环境没有 Docker，我们就失去了这条隔离路径。

## 4. 我们项目里的真实例子

### 4.1 原方案：bwrap 直接失败

```text
$ bwrap --bind / / --tmpfs /tmp --proc /proc --dev /dev /bin/echo sandbox-ok
bwrap: No permissions to create new namespace, likely because the kernel
does not allow non-privileged user namespaces.
```

失败很"诚实"：**报错、退出码非 0**。这种失败虽然不理想，但**不会被误判**。

### 4.2 备选方案：firejail 静默直通（最危险的一种失败）

```text
$ firejail --quiet --noprofile /bin/sh -c 'echo sandbox-ok'
sandbox-ok            # ← 退出码 0，看起来成功了
```

去掉 `--quiet` 之后真相才出来：

```text
Warning: an existing sandbox was detected. /bin/sh will run without any
additional sandboxing features
```

**它检测到"自己已经在沙箱里"，于是放弃全部加固，直接把命令跑掉了。**

客观验证（对比命名空间编号）：

| namespace | 宿主机 | firejail 内 | 结论 |
| --- | --- | --- | --- |
| user | 4026543963 | 4026543963 | 相同 → 未隔离 |
| mnt | 4026546742 | 4026546742 | 相同 → 未隔离 |
| net | 4026548046 | 4026548046 | 相同 → 未隔离 |

再加一条：`firejail --net=none` 之后，容器内的 `eth0` **依然存在**。

**这就是"门禁坏了但前台照样应答"的真实版本。**
更糟的是：原验证清单的判定规则写的是"**任一沙箱可用** → 沙箱方案可行"，
而 firejail 的表现恰好是"输出成功字样、退出码 0"——
**按表面判定会得出"沙箱可用"的错误结论，进而让整个安全设计建立在不存在的前提上。**

### 4.3 现在的方案：以容器为边界

改为用一次性容器执行不可信命令，并逐项验证加固参数：

```bash
docker run --rm --network none --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --cap-drop=ALL --security-opt=no-new-privileges \
  --pids-limit=64 --memory=256m -u 65534:65534 alpine:latest sh -c '...'
```

| 验证点 | 观察到的结果 |
| --- | --- |
| 降权运行 | `uid=65534`（非 root） |
| 根文件系统只读 | `touch /x` → `Read-only file system` |
| 临时区可写 | `/tmp` 可写（受 `size`/`noexec` 限制） |
| 网络隔离 | 外网不可达 |
| 能力清空 | `--cap-drop=ALL` |

**每一项都是"去观察一个客观状态"，而不是"看命令是否成功"。**

### 4.4 一个额外认识：一次性环境改变了风险的形状

在"开发环境即执行环境"的前提下，执行不可信命令可能造成的损害有两类：

| 风险 | 在"一次性、可重建"的环境里是否降低 |
| --- | --- |
| 环境被改坏、被污染 | **降低**——销毁重建即可 |
| **凭据与源码外泄**（`.git`、平台 token、代码） | **没有降低**——执行命令的机器上就有这些东西 |

所以沙箱的**第一优先目标**应该定义为"阻止不可信命令读取/外传凭据与源码"。
这也解释了为什么"隔离不可用时降级为直接执行"是不可接受的：
一旦降级，泄露风险原样存在。

## 5. 术语表

| 术语 | 含义 |
| --- | --- |
| namespace（命名空间） | 内核机制，让进程看到某类全局资源的独立副本 |
| `CAP_SYS_ADMIN` | 权限极大的 Linux 能力，创建多数命名空间需要它 |
| bounding set | 进程能力集的**上限**；被移除的能力之后无法再获得 |
| seccomp | 内核机制，按过滤器**拒绝系统调用**；容器常用它限制逃逸 |
| unprivileged user namespace | 允许非特权用户创建的 `user` 命名空间（可被平台关闭） |
| fail-secure | 失败时**拒绝执行**，而不是"降级放行" |
| Landlock | Linux 5.13+ 的 LSM，可在**不需要命名空间/特权**的情况下限制文件访问 |

## 6. 我原来的误解 / 容易踩的坑

| 误解 | 事实 |
| --- | --- |
| "命令执行成功 ⇒ 沙箱生效" | 完全无关。要观察隔离的客观痕迹（命名空间编号、能力集、挂载视图） |
| "报错才算失败" | **静默降级**（警告 + 继续执行）比报错危险得多，因为它会被误判为成功 |
| "看开关数值就能判断能不能用" | `max_user_namespaces` 很大，但 `unshare` 仍被 seccomp 拒绝。**要测那个动作本身** |
| "容器里能 `docker run`，说明能嵌套虚拟化" | 是**兄弟容器**，边界由容器外的守护进程建立，"借来的能力" |
| "Landlock 是备选" | 它需要内核 ≥ 5.13；我们的平台是 5.4，所以也不可用 |
| 只测"能不能起一个进程" | 要测的是**边界**：能否写根目录、能否联网、能否拿能力、能否 `fork` 炸弹 |

1. 我说"沙箱生效了"，需要拿出哪三类客观证据？（提示：命名空间 / 能力 / 文件系统与网络视图）
