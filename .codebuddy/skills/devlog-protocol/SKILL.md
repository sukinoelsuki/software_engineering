# 开发日志与活待办流程

> **本 Skill 只写顺序与停下条件，不复述任何规范。** 写法要求见
> [`ADR-0017`](../../../docs/adr/0017-project-level-agent-skills.md) §5.1「三条硬性写作要求」。
> 引用一律写**章节名**；**若指针失效，以权威源为准，并就地修本 Skill**。

## 触发条件

- **每笔提交后**（追加一条变更记录）；
- **开工 / 重拾语境**时（新会话、中断后恢复）；
- **一个议题讲完、准备收篇**时；
- 需要知道"**下一步做什么**"时。

## 流程要点（只写顺序；每步的停下条件在最右列）

| # | 顺序动作 | 停下条件 |
| --- | --- | --- |
| 1 | 找到**当前（最新）篇** —— 依据 [`docs/devlog/README.md`](../../../docs/devlog/README.md) 的「索引」表（状态列） | 索引与文件名不一致（最新篇不对）⇒ 停下先修索引，再写记录 |
| 2 | 每笔提交后在当前篇追加一条记录，内容含**三要素**：提交哈希 / 变更内容 / 验证方式 —— 出处 `README` 的「更新时机」节、「单篇结构模板」节的 §3 | 缺任一要素 ⇒ 不算一条合格记录 |
| 3 | **活待办 = 最新一篇的 §7**；不另建 todo / backlog 文件 —— 出处 `README` 的「活待办」节 | 想新建待办文件 ⇒ 停下，改在 §7 追加 |
| 4 | 完成一项 ⇒ 从当前篇 §7 **删除**，并在 §3 记**内容总结** —— 出处 `README` 的「§3 与 §7 的写法要求」节 | §3 写成 `☑ 做了 A` 式流水账 ⇒ 改写为连贯叙述（该节明令禁止打勾清单） |
| 5 | **议题讲完即收篇**：补「学到了什么」与「下一步」，未完成项**抄进新篇 §7**，并登记进 `README` 索引；旧篇由此成为**封闭记录** —— 出处 `README` 的「收篇与承接」节 | 议题没讲完而篇幅偏长 ⇒ 按**子议题**拆分，不要为卡行数把连贯议题硬切两半 |
| 6 | **重拾语境**：走 `README` 的「重拾语境（新会话 / 中断后的固定动作）」四步（索引 → 最新篇全文 → 顺 §7 读引用 → 从 §7 第一项动手） | 凭记忆开工 ⇒ 停下，先走这四步 |
| 7 | 日志**当时写** —— 出处 `README` 的「更新时机」节末的原则 | 事后大规模补写 ⇒ 停下（会失真，失去日志的价值） |
| 8 | 哈希引用只引用**产生它的那笔提交之前**的提交；本篇自身哈希由**下次回填** —— 出处 `README` 的「哈希引用规则」 | 要引用一个**尚不存在**的哈希 ⇒ 停下，留给下次回填（不得 `--amend` 已推送提交） |

## 权威源

- [`docs/devlog/README.md`](../../../docs/devlog/README.md) —— 分篇约定、活待办、重拾语境、更新时机、哈希引用规则、单篇结构模板、索引。
- [`CODEBUDDY.md`](../../../CODEBUDDY.md) §2（维护开发日志与活待办的义务）、§9（Phase 0 当前待办）。

## 不写什么（硬性）

- 日志的**模板正文**与各节标题定义（属 `docs/devlog/README.md`）；
- **具体待办清单**（属最新一篇的 §7——本 Skill 只在 `README` 的索引上判断"哪篇是最新"）；
- 协作机制与角色分工（属 [`docs/engineering/agent-teams.md`](../../../docs/engineering/agent-teams.md) 与 `CODEBUDDY.md` §10）；
- 学习笔记的写作要求（属 `docs/notes/README.md` 与 `ADR-0009`）。
